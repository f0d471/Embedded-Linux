## 二、学透的定义

一个知识点算"学透"，要同时有三件东西，缺一件都不算：

    1  教程    Knowledge/ 里有一篇讲得完、能自足的教程（主线章或专题章），
               命令与代码完整给出，配图，配自检
    2  实验    Knowledge/labs/ 里有对应实验与 check.sh，判据能注错见红
    3  工程    对应的技术在本仓 Project/ 里落地成一层、一个后端或一个测试项，
               Project/check.sh 覆盖到它

"读过""抄过一份能跑的代码"都不算。数字一律本机或板上实跑，不抄现成数字。

### 5.2 两条边界

**不把 OpenCV 搬上板。** 三条理由：一是说不出所以然的调用不算能力；二是本板
rootfs 没有 OpenCV，装上它要先交叉编译一整套；三是五条规则本身都是标准算法。
它的正确位置是判据的金标准：

    1  WSL 里用 OpenCV 对固定输入算一遍，结果存成 fixture
    2  纯 C 实现在 x86 上算一遍
    3  同一个纯 C 实现交叉编译后在板上算一遍
    4  三份结果逐项比对，不一致就是纯 C 实现错了

**不用 Qt。** Qt 的 linuxfb 后端会独占 `/dev/fb0`，与本仓 display 层抢同一个
设备；本仓的 ui/page 用注册链表自己画，形状已经落地。

### 5.3 定性

**质检是第二个业务，不是第二个终点。** 它与监看共用采集、解码、显示、录像
这条流水线，只在解码后的 RGB 上多挂一个消费者。这个定性决定了 Project 的
架构（第六节），也决定了新增只有 `inspect` 与 `record` 两层。

### 5.4 平台约束决定的技术选型

i.MX6ULL 没有 GPU、没有 VPU、没有 IPU，只有 CSI 与 PXP。三条硬结论：

    H.264 实时编码封死   x264 软编在 A7 单核上只有个位数帧率，CPU 打满
    推流走 MJPEG         UVC 摄像头芯片内部自带 JPEG 编码器，板子零编解码转发
    本地显示才解码       libjpeg-turbo 解 MJPEG，PXP 转 RGB / 缩放，再写 fb0

PXP 是这颗 SoC 唯一的图像硬件加速。性能预期（640x480 约 15～25 fps 量级）
全部未实测，上板第一次跑出真数就回来替换本段；spec 不写 1080p。

## 六、Project 的目标形态

### 6.1 一台设备，两个业务

    监看业务    摄像头 -> 显示 / 推流 / 录像 / OSD
    质检业务    触发 -> 采图 -> 规则检测 -> 落库 -> 联动 / 告警 / OTA

两个业务共用一条流水线：

    采集线程 -> 帧队列 -> 解码线程 -> RGB 队列
      |
      +-> 消费者甲  显示线程 -> fb0 -> HDMI
      |
      +-> 消费者乙  检测线程 -> inspect -> record
                                |
                                +-> 设备联动 / 告警

检测线程与显示线程互不阻塞。

### 6.3 扩展规则（可判据化）

    1  加一层只动两处：Makefile 的 SUBDIRS、main.c 的 g_layers 表
    2  每个 provider 挂注册链表；换后端时上层代码 diff 为空（刀 10c 的判据）
    3  层间只走自己目录下的头文件接口，不跨层直接调底层实现
    4  业务不写进层：调度在 business，页面在 page，规则在 inspect
    5  可配置的不写死：分辨率、帧率、阈值、规则组合从配置文件来
    6  每层配 unittest，整机配 Project/check.sh，判据都要能注错见红

## 十二、三条反面判据（L2 素材）

写教程 07 与整合时当反面判据用：

    1  逐行解析配置文件时遇空行凭空生成一个空名字配置项
       （sscanf 匹配 0 项仍把计数加一），条目里多出 name=""
    2  配置项数组有固定上限，解析循环却不做边界检查，超出上限的那一行越界写
    3  pthread_cond_wait 之后用 if 而不是 while 重查条件，虚假唤醒会返回错误；
       POSIX 明确允许虚假唤醒

这三条都是"看着能跑、判据一碰就错"的典型写法。
