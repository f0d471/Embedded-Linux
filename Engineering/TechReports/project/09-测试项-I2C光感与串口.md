# 09 测试项：I2C 光感与串口

## 一、动机

第 08 章交付的四层里，主页的测试项按钮会执行配置里写的命令，但配置里
还没有什么值得执行的命令。路线图给第 08/09 章的 L4 产出是"无新层，
板载 AP3216 光感和调试串口做成 business 的测试项"——本仓的安排是
学完两章的应用编程后，把成果
做成两个独立小工具放进 `items/`，由配置文件点名执行。一个"测试项"
由此有了完整的定义链：配置文件里一行 `command`，按钮按下，fork 出去，
退出码回到日志。

## 二、为什么是这几步

```
S1  ap3216_read: i2c-dev 直读 AP3216C, 总线自动探测
S2  serial_loop: termios raw 模式 + 帧校验和回显自检
S3  WSL 判据(错误路径 + 伪终端对端)
S4  板上验证: 真传感器连读、双串口探针
```

S1 与 S2 是两章教程的直接落地：I2C 章讲 `/dev/i2c-N` 上的
`ioctl(I2C_SLAVE)` 与 write/read 序列，串口章讲 `termios` 的 raw 配置。
S3 决定了两个程序的可测边界：WSL 没有 I2C 总线也没有第二根串口线，
本机能判的是错误路径与伪终端对端；真器件与真 UART 的行为只能上板，
这条边界不是偷懒，是"判据必须能判对错"在硬件上的自然止步。S4 在
上传全部产物后一次完成，连读多帧观察读数活性。

## 三、每一步做了什么

### 3.1 ap3216_read：i2c-dev 直读

```
open /dev/i2c-N (O_RDWR)
ioctl(I2C_SLAVE, 0x1e)
write [0x00, 0x03]        打开 ALS+PS+IR 三路
usleep 200ms              等一轮转换
逐寄存器读 0x0A..0x0F      ALS/IR/PS 各两字节
```

寄存器访问是一次 write 一次 read：write 把寄存器号发过去，紧跟的 read
从那个寄存器搬数据，这是 i2c-dev 的基本用法。换算按数据手册
`lux = als × 0.35`。总线号不写死：自动探测逐个 `open + I2C_SLAVE +
读配置寄存器`，谁应答用谁——板上 AP3216C 在 i2c-0，没有设备树节点
（`/sys/bus/i2c/devices/` 里没有 `0-001e`），出厂系统不认识它，
i2c-dev 用户态直读是唯一通路。`--loop COUNT INTERVAL_MS` 连读，
观察读数活性。

### 3.2 serial_loop：termios 与帧校验

```
open O_RDWR|O_NOCTTY|O_NONBLOCK
tcgetattr -> cfmakeraw -> cfsetispeed/ospeed(B115200) -> CLOCAL|CREAD
VMIN=0 VTIME=10           read 最多等 1 秒
tcsetattr(TCSANOW) 后摘掉 O_NONBLOCK
循环: 发 "PING <seq4hex> <sum2hex>\n" -> 原样等回显 -> 逐帧核对
```

校验和覆盖帧的前 10 字节（除校验和及其前导空格外的全部字节）的异或，
收方重算比对。`--probe` 模式只 open + tcgetattr/tcsetattr + close，
不发数据：板上调试串口 ttymxc0 是控制台，往它上面发测试帧会污染
唯一的上板链路，探针模式验证"设备在、termios 调得动"就够了。

### 3.3 WSL 判据

`check_gui.sh` 的 [22] 组：无 I2C 总线的机器上 `ap3216_read --bus 99`
以退出码 1 干净报错；串口回显用 `unittest/serial_pty.py` 开一对
伪终端，从端路径交给 `serial_loop` 当串口设备，python 端收到什么原样
回什么——等价于一根 TX-RX 短接的跳线，5 帧全对退出码 0。注错把
`frame_build` 的校验和起点从第 0 字节改成第 1 字节，回显核对立即变红。

## 四、遇到的问题

### 4.1 探测循环里的 fd 还没挂上去

**第一现场**（板上首跑，2026-10-04 实测，strace 节选）：

```
openat(AT_FDCWD, "/dev/i2c-0", O_RDWR|O_LARGEFILE) = 3
ioctl(3, _IOC(_IOC_NONE, 0x7, 0x3, 0), 0x1e) = 0
write(-1, "\0", 1)                      = -1 EBADF (Bad file descriptor)
ap3216: no sensor at 0x1e on /dev/i2c-*
```

**解读** 打开 i2c-0 成功（fd 3）、`I2C_SLAVE` 绑定成功，随后寄存器读
却写到了 fd -1：`read_reg`/`write_reg` 只认全局 `g_fd`，而 `open_sensor`
的循环把 `g_fd = fd` 写在探测成功之后——探测本身就是第一次寄存器访问，
那一刻 `g_fd` 还是初值 -1。板上 python 直读同一地址同一寄存器
（`write reg: 1 / read val: 00`）证明器件与总线都好。

**定位** strace 三个系统调用把现场钉死：fd 3 开着、ioctl 成功、write
拿的是 -1。WSL 上的判据（"没有 I2C 总线时报错退出"）从未走到探测内部——
open 就失败了，所以这条 x86 判据一直绿着，绿的原因是错的。

**根因与修法** 候选 fd 在探测前挂上 `g_fd`，探测失败先 `g_fd = -1` 再
close。修后板上读出真实数据。原判据为什么没覆盖到：错误路径判据只验
"总的开不了"，探测内部路径需要真实总线才有输入，这是本仓第一次由
上板验证抓住的代码缺陷——判据体系"本机判据 + 板上验证"两层设计的
直接兑现。

### 4.2 ALS 读数在高低位之间跳动

**第一现场**（板上连读六帧，2026-10-04 实测）：

```
ap3216 bus=0 addr=0x1e als=0   ir=27 ps=19 lux=0.0
ap3216 bus=0 addr=0x1e als=0   ir=24 ps=20 lux=0.0
ap3216 bus=0 addr=0x1e als=0   ir=25 ps=5  lux=0.0
ap3216 bus=0 addr=0x1e als=256 ir=24 ps=0  lux=89.6
ap3216 bus=0 addr=0x1e als=1   ir=19 ps=0  lux=0.3
ap3216 bus=0 addr=0x1e als=257 ir=24 ps=0  lux=89.9
```

**解读** ir 稳定在 19..27，als 在 0/1 与 256/257 之间整档跳动。256
恰好是高字节一档（0x0100），两个候选解释：环境光恰在计数边界附近
振荡，或 ALS 低/高两个寄存器分两次事务读取、读的不是同一次转换的
快照（撕裂读），低字节来自上一轮、高字节来自下一轮。200ms 的转换
等待按数据手册够用，撕裂读的可能性更大。

**定位** PS 与 IR 的波动是正常的采样噪声；als 的波动与 256 的整档
边界吻合，指向高位寄存器。

**根因与修法** 未修，如实记录。修法是把两字节合并成一次
`I2C_RDWR` 字事务或读前锁存，属于下一轮。判据设计不依赖 als 的
绝对值：连读活性（读数随采样变化）已是本章判据，遮光后读数下降
需要人工遮传感器，留第六节。

## 五、结果

测量方法：ARM 静态产物经串口上传（SHA-256 对账），板上经调试串口执行；
WSL 判据跑 `check_gui.sh` 的 [22] 组。

| 测量项 | 结果（2026-10-04 实测） |
|---|---|
| AP3216C 探测 | i2c-0 @ 0x1e，无设备树节点，用户态直读 |
| 传感器连读 | 六帧读数随采样变化（3.1/4.2 节原始输出） |
| 串口探针 | ttymxc2 与 ttymxc5 均打开、termios 配置成功、baud=115200 |
| WSL serial 回显 | 伪终端对端 5/5 帧全对，退出码 0 |
| WSL ap3216 错误路径 | `--bus 99` 退出码 1，报"no sensor" |
| 4.1 缺陷 | 板上抓到、修复、复测通过 |

判据计数：`check.sh` 总判据在本章与第 08 章合并统计（第 08 章第五节
的 124 PASS 含 [22]/[23] 组的 items 判据 6 条与分层边界 4 条）。

已知误差与不确定：遮光判据（遮住传感器，als 应显著下降）需要人工
在板边操作，本轮未执行；ALS 撕裂读嫌疑未用示波器或总线分析仪排除；
板上另有 ttymxc5，两路串口的对通（一路发一路收）需要第二根 USB 转
串口线，缺件未测。

## 六、还欠什么

三笔。其一，人工遮光判据：接手者执行
`ap3216_read --bus 0 --loop 6 300`，第二次起用手遮住板上光感区域，
记录 als 下降幅度，补进本章第五节。其二，ALS 撕裂读按 4.2 的修法
改成单次字事务后复测，若读数稳定即按"遇到的问题"追加修法。其三，
AP3216 的内核字符驱动（设备树节点 + platform_driver + 中断 + poll）
是驱动开发阶段的活，做的时候本程序的寄存器序列就是驱动 write 路径
的现成参考。
