# 06 netinput：第二个输入源走网络

## 一、动机

input 层（第 05 章）交付后，注册链表上挂着 evdev 和 replay 两个 provider，但
两者都读本机数据源。路线给第 06 章的 L4 产出是
"input 层加一个网络输入源"（netinput）：
在另一台机器上把指针动作发过来，设备的屏幕跟着动。它的工程价值不在演示——
注册链表当初的卖点是"换一个输入源不改上层"，第二个真实的、与本地设备性质
完全不同的源挂上去还能工作，这条设计才算被验证过。

常见做法是把已经聚合好的 `InputEvent` 结构体整个塞进 socket。
本仓的帧聚合在 manager（`parse_raw`），provider 只出原始记录；采用那种做法
意味着把聚合逻辑再实现一遍或者倒挂接口。定稿选择让网络只搬运原始记录，
聚合仍走同一条路：网上来的一串记录与本地 evdev 读到的一串记录在
`parse_raw` 眼里没有区别。

## 二、为什么是这几步

```
N1  定义线上格式与合法性规则
N2  把 provider 的 fd 契约从单个扩成一组
N3  实现 netinput provider（监听、收客户端、攒记录、校验）
N4  写发送端 netinput_send，吃 replay 同格式的文本
N5  判据与板上回环验证
```

N1 决定一切。TCP 是字节流，没有消息边界；一条记录多长、从哪个字节重新对齐、
什么样的字节流算"不是本协议的客户端"，必须先写死再写代码。N2 在 N3 之前：
netinput 任意时刻要 poll 的 fd 是"监听 socket 加零或一个客户端 socket"，
第 05 章定的 `get_fd()` 单 fd 契约装不下它，先改契约再写实现，否则 provider
接口会出现"为某一个后端开的口子"。N4 在 N5 之前：判据要逐行对账应用事件，
发送端必须能产出与 `input_replay.txt` 完全相同的事件序列——它直接吃同一种
文本，同一份 fixture 于是既驱动本地回放判据又驱动网络判据，两条路径的输出
可比较。缺 N1，边界处理全靠猜；缺 N2，netinput 只能独占 poll 循环；缺 N4，
网络判据只能跟"肉眼看着像"比较。

## 三、每一步做了什么

### 3.1 线上格式

```
offset  size  field
0       2     magic  = 0x6e49, 线上字节 49 6e
2       2     type   (EV_SYN / EV_KEY / EV_REL / EV_ABS)
4       2     code
6       2     pad    (对齐用, 收端不检查)
8       4     value
12      4     sec
16      4     usec
```

20 字节定长小端记录，内容与 evdev 的 `struct input_event` 同构。收端靠字节数
重新对齐：攒满 20 字节校验一次，magic、type 范围（`EV_MAX`）、code 范围
（`KEY_MAX`）、usec 范围四项任一不过，整条连接丢弃、服务继续等下一个客户端。
`_Static_assert(sizeof == 20)` 把"字段一动格式就变"钉在编译期。x86 与 ARM
都是小端，记录原样收发；协议注释里写明大端机器接入前要先改这里，由阅读者
而不是编译器兜底。

### 3.2 fd 契约从单个扩成一组

`struct input_provider` 的 `get_fd()` 换成 `get_fds(int *fds, int max)`：
把本轮 poll 要监听的 fd 填进数组、返回个数。evdev 和 replay 返回自己的
单个 fd，netinput 返回监听 socket 加当前客户端（若有）。manager 每轮 poll
前重新调用一次，个数随连接建立与断开自然变化，poll 循环本身不知道
"netinput" 这个词。

`read_raw()` 的返回语义相应补全一条：客户端断开（EOF、复位、协议错误）时
关掉这条连接、返回 `ERR_BUSY`。第 05 章里 `ERR_NOTFOUND` 是"输入源到头了"
（回放 EOF，消费者该收场），服务型后端永远不返回它，两种"没有数据"在
manager 层语义不同。

### 3.3 半条记录与断开的边界

`netinput_read_raw()` 的读循环区分三种返回：

```
got > 0                     攒进 g_rec, 攒满 20 字节走校验
read == EAGAIN              这批字节读完了, 半条记录留在 g_rec 等下一轮
EOF / 复位 / 其他错误        关闭这条连接, 等下一个客户端
```

半条记录跨 poll 周期存活是设计使然：内核什么时候把 TCP 段递上来不由应用
决定，一帧 20 字节可能分两次到达。校验失败与断开都是连接级事件，影响面
限于一根线；监听 socket 不受影响，下一个客户端照常 accept。

### 3.4 发送端与判据

`unittest/netinput_send.c` 把 `input_replay.txt` 同格式的文本行
（`sec usec type code value`）逐行变成 20 字节记录发过去，`--bad` 把第一条
记录的 magic 改坏、`--partial` 只发半条就断开，分别喂注错判据。判据在
`check_font_input.sh` 的 [15] 组：同一份 fixture 先走本地回放再走 TCP，
两路输出逐行对账；坏客户端走后好客户端必须照常送达；无客户端时
`--once` 等满 5 秒干净超时。板上验证走 loopback，不经网线。

## 四、遇到的问题

### 4.1 发送端结构体多了一个占位字段

**第一现场**（2026-10-04 实跑，`make test`）：

```
unittest/netinput_send.c:38:1: error: static assertion failed:
    "wire record is 20 bytes"
```

**解读** 发送端自己声明的记录结构体是 24 字节：写的时候在 sec 前多挂了一个
"占位"字段。`_Static_assert` 同时写在收发两端，发送端刚写错就被编译器拦下，
一条 24 字节的记录进 20 字节的收端会从此错开 4 字节。

**定位** 收发两端各写一份结构体是刻意的：netinput 是协议两端，谁也不该
include 谁的内部头。契约的对齐靠静态断言加上 TechReports 的格式表，这次
断言第一次生效。

**根因与修法** 删掉占位字段。原判据为什么没覆盖到：这类错误发生在编译期，
运行判据根本没机会看到；它证明的是静态断言本身在岗。

### 4.2 EAGAIN 被当成断开，好客户端被中途踢掉

**第一现场**（判据 [15r] 前置组间歇性失败，2026-10-04 实跑）：

```
FAIL  坏客户端走后好客户端照常送达: got [write: Connection reset by peer]
      want [sent 21 records]
```

连跑三次，两次通过一次失败。

**解读** `read()` 返回 `EAGAIN` 只说明这一批可读数据耗尽；当时的实现把它与
EOF、复位一起归进"断开"分支，把客户端连同攒了一半的记录一起丢掉。21 条
记录 420 字节在 loopback 上通常一个 TCP 段到达、一次读完，判据碰不到
这个分支；段被内核拆开递送时，第二次 `read` 撞上 `EAGAIN`，连接被误杀，
发送端剩下的写入吃到 RST。

**定位** 三种返回的语义在 3.3 节定稿时就已经分清，第一版代码少写了
`EAGAIN` 分支。间歇性失败本身就指向"依赖内核分段时机"的路径——它不是
竞态，是内核行为没有进入实现的假设清单。

**根因与修法** `EAGAIN` 单独返回 `ERR_BUSY`，连接与半条缓冲原样保留；
EOF 与错误才走断开分支。修后连跑三遍全绿。原判据为什么没覆盖到：
"发送 21 条记录"的判据在单段到达时永远走不到坏分支，能抓住它的是
连续多次运行，一次通过算不上证据。

### 4.3 判据把原始记录数写成了应用事件数

**第一现场**（判据 [15] 首跑）：

```
FAIL  发送端发满 21 条原始记录: got [sent 21 records] want [sent 5 records]
```

**解读** 发送端逐行搬运原始记录，`input_replay.txt` 有 21 条合法记录，
归并成 5 个应用事件。判据初稿把 5（应用事件粒度）写在了发送端对账上
（原始记录粒度）。两级粒度在同一个 fixture 里共存，是本章判据的立意所在：
网络路径与回放路径最终比的是那 5 行应用事件，发送端对账比的是 21 条搬运。

**定位** `netinput_send` 的输出就是搬运条数，逐行对账判据（[13] 的
`EXPECTED_INPUT` 复用）才是语义判据。两者各自成立。

**根因与修法** 发送端对账改为 `sent 21 records`，标签写成"21 条原始记录"。
原判据为什么没覆盖到：这条本身就是新写的判据，错在期望值，不在被测代码。

## 五、结果

测量方法：`wsl bash Project/check.sh`；ARM 静态产物与 fixture 经串口上传
（整文件 SHA-256 对账）；板上验证经调试串口完成。

| 测量项 | 改动前 | 本轮后 |
|---|---|---|
| `Project/check.sh` 总判据 | 73 PASS（05 章后） | 83 PASS / 0 FAIL（netinput 占 10 条） |
| [15] 组连续稳定性 | 首版间歇红（4.2） | 修后连跑三遍全绿 |
| input 层 provider 数 | 2（evdev、replay） | 3（+netinput） |

本机（2026-10-04 实跑）：同一份 `input_replay.txt`，回放路径与 TCP 路径的
应用事件输出逐行相同（第 05 章第五节的五行）；发送端发满 21 条原始记录；
坏客户端（magic 损坏）被丢弃后，好客户端的 21 条照常送达；无客户端时
`--once` 等满整个 5 秒窗口退出码 0。

板上（2026-10-04 实测，loopback）：`INPUT_BACKEND=netinput` 下服务端
`source name=netinput path=tcp:0.0.0.0:23232` 打开正常，无客户端时
`--once` 等满超时退出码 0；后台服务端加板上 `netinput_send` 回环发送，
`--wait 6000 --count 5` 收满 5 帧退出，输出为：

```
pointer x=522 y=305 dx=10 dy=5 buttons=1
pointer x=0 y=0 dx=-1000 dy=-1000 buttons=1
key code=30 value=1
pointer x=0 y=0 dx=0 dy=0 buttons=0
pointer x=1023 y=0 dx=0 dy=0 buttons=1
```

事件序列与 x86 逐行同构；坐标不同是因为显示几何不同：板上 fb0 是
1024x600，第 1 帧 x=512+10=522、y=300+5=305，第 5 帧绝对量程顶格
4095 缩放为 1023。换算规则（钳位、量程、`int64_t` 中间值）与假屏上验证的
是同一套代码。

已知误差与不确定：板上 loopback 验证了协议与 provider 全链路，两台真机
经网线的场景未测（板上当时只有 `lo` 一个 IPv4 地址）；多客户端并发不在
本章范围。

## 六、还欠什么

两笔。其一，双客户端并发推流属于视觉终端路线刀 5 的判据
（"两个客户端同时拉，互不影响帧率"），netinput 当前一次只服务一个客户端，
届时要么扩展要么另起。其二，板上多网口/网线连通后的跨机发送未验，
等网络环境具备时复跑同一条回环判据即可。
