# 07 多线程：读取线程、环形队列与三本账

## 一、动机

第 05 章把 input 层的读取模型定成"调用线程里同步 poll"，当时的理由写在
TechReports 05 的 4.1 节：参考项目的读取线程带着三个并发缺陷（队满静默丢、
条件等待不重查、退出无协议），第 07 章之前项目没有线程，输入语义和并发
缺陷绑死在一起两件事都验不清。第 07 章的教材内容是 pthread，路线图给本章
的 L4 产出是"input 层的环形缓冲与线程"——当初推迟的正是这一章的活。

现在欠的债到了还的时候：消费者（未来的 GUI 主循环）处理一帧的时间不可控，
同步模型下它慢了，provider 的解析和 poll 全部跟着卡；采集节奏应当由专职
线程维持，慢的代价是队列里最旧的事件被挤掉，且挤掉了几个要有账可查。

## 二、为什么是这几步

```
T1  队列与互斥锁：丢最旧策略，received/delivered/dropped 三本账
T2  消费者等待：cond 绑定 CLOCK_MONOTONIC，期限语义不变
T3  读取线程：poll/解析搬进后台，EOF 与错误的收场协议
T4  错误穿透：provider 的致命错误经队列传给消费者
T5  压力判据与 tsan
```

T1 先行：队列的"队满怎么办"是这个设计里唯一的行为决策，三本账是它的
观测面，判据全部建立在账目闭合上。T2 在 T3 之前：消费者的 `timeout_ms`
语义（-1 永久、0 不等、正数最长等待毫秒）是第 05 章写进头文件的契约，
线程化不许改变它——`pthread_cond_timedwait` 的绝对期限必须和
`monotonic_ms()` 同一个时钟，否则"最多等 1000ms"会被两个时钟的差悄悄
拖长。T3 把现有 poll 循环原样搬进线程，加的只有退出检查与收场广播。
T4 处理搬进线程后出现的新问题：provider 的错误在线程里结束，消费者
如果只看到"队列空"，畸形回放被拒绝的判据（第 05 章 [14]，退出码 2）
就失去依据。T5 收口：400 帧压力对账三本账，tsan 盯数据竞争，注错拆锁
见红。缺 T1，丢帧不可观测；缺 T2，超时判据的数字不再可信；缺 T4，
线程化悄悄吞掉一类错误。

## 三、每一步做了什么

### 3.1 队列与丢帧策略

```
g_queue[32]      环形槽位, g_head 写位, g_tail 读位, g_count 在队数
g_received       推入队列的应用事件累计
g_delivered      交给消费者的累计
g_dropped        队满时被挤掉的最旧事件累计
```

队满时挤掉最旧的一条：指针事件的价值随时间衰减，消费者要的是"现在的
位置"而不是"三帧前的位置"。新事件一定入队、消费端永不阻塞推送，
`received = delivered + dropped` 在同一次 init/exit 内恒成立，这个等式
就是 [16] 组判据的全部根基。账目由 `input_get_stats()` 对外只读。

### 3.2 cond 的时钟与等待

```
pthread_condattr_setclock(&attr, CLOCK_MONOTONIC)
pthread_cond_init(&g_not_empty, &attr)
```

消费者的期限由 `monotonic_ms() + timeout_ms` 算出，`cond_timedwait` 收的
绝对期限也必须用同一个时钟的刻度。cond 默认绑实时时钟，NTP 校时或手动
改时间会把"等 1000ms"变成长短不一的任意值；绑定语句三行，写在 init。
等待循环重查条件（队列空、未关闭、未超时才继续等），虚假唤醒与 EINTR
不产出任何东西。

### 3.3 读取线程与收场协议

线程主体是第 05 章那个 poll 循环原样搬入，两处新增：

```
poll 超时 200ms          每轮醒来查一次 g_quit, 退出请求最多等一个周期
退出/EOF/错误收场        加锁置 g_closed(与 g_error), broadcast, 线程结束
```

`input_exit()` 置 `g_quit`、broadcast、`pthread_join`，然后才关 provider——
join 在 close 之前，线程不会踩着已关闭的 fd。`g_error` 记 provider 的
致命错误（如畸形回放的 `ERR_IO`），消费者在队列排空后把它原样返回；
回放 EOF 置 `g_closed` 不置错误，消费者拿到 `ERR_NOTFOUND`。两类收场
在消费端的返回码不同，第 05 章 [14] 的两条失败路径判据在线程化后逐字
未改仍然成立。

### 3.4 压力判据

[16] 组用 awk 生成 400 帧回放（每帧两条原始记录），消费者每取一帧睡
5ms：生产端瞬间灌满 32 槽，之后每一帧都造成一次挤旧。四条判据：
采集数等于 400；送达数与 `pointer` 行数一致（账目不虚报）；
`received - delivered - dropped == 0`；dropped 大于 0。[17] 组在
`-fsanitize=thread` 下重跑同一场景，注错把 `pthread_mutex_lock(&g_lock)`
整体替换为 `(void)0;`，拆锁后 tsan 报出 7 处数据竞争。

## 四、遇到的问题

### 4.1 timeout=0 的同步假设被线程化打破

**第一现场**（线程化后首跑判据 [13]，2026-10-04 实跑）：五帧回放判据
偶发只读到 0 条事件。

**解读** 第 05 章的同步模型里，`timeout_ms=0` 意味着"poll 一次不等待"，
而回放文件是普通文件、永远可读，第一次 poll 必然拿到数据。线程化后
"现有数据"取决于读取线程此刻推到哪儿了，消费者第一枪打出时队列可能是空的，
`ERR_BUSY` 直接把 `input_test` 送出循环。

**定位** 被打破的是"数据必然已在"这条隐含假设，它从来不在接口契约里，
只活在同步实现的时序里。

**根因与修法** 判据侧补 `--wait 1000`：每次取事件最多等 1 秒，语义从
"碰运气看一眼"回到"等数据或等 EOF"。产品代码不改——`timeout=0` 的
契约本来就是"只检查现有数据"。原判据为什么没覆盖到：同步时代这条判据
测不到线程化会引入的时序，它是线程化的伴生判据。

### 4.2 provider 的错误死在线程里

**第一现场**（[14] "畸形回放被拒绝"判据在线程化后失败）：`input_test`
退出码 0，判据要 2。

**解读** 畸形行让 `replay_read_raw` 返回 `ERR_IO`，第 05 章的同步模型里
这个错误码从 `input_get_event` 直接交到消费者手里。线程化后 `ERR_IO` 在
线程里结束循环，消费者只看到队列永远空、`g_closed` 置位，拿到的是
`ERR_NOTFOUND`——"读坏了"与"读完了"被合并，退出码从 2 变 0。

**定位** 队列是单向通道，错误状态是第二类消息，需要一个专门的信箱。

**根因与修法** 线程收场时按 EOF 与错误分写 `g_closed` 与 `g_error`，
消费者在队列排空后先查 `g_error`。原判据为什么没覆盖到：第 05 章的
判据写在错误码契约上，线程化改变的是错误码的传递路径，判据正好抓到
这条路径上的断点。

### 4.3 pthread 的链接选项经不起命令行覆盖

**第一现场**（ARM 静态构建计划评审时发现，无运行输出）：Makefile 若把
`-pthread` 写进 `LDFLAGS :=`，命令行 `make LDFLAGS=-static`（板上产物
必需，TechReports 03 记过 glibc 版本冲突）会把整个变量替换掉。

**解读** `LDFLAGS :=` 是普通赋值，命令行变量优先级高于它；`override
LDFLAGS += -pthread` 在命令行赋值之后追加，两种取值下都保得住。本机
glibc 2.4x 已把 pthread 并进 libc，缺 `-pthread` 不一定立刻断链接，
ARM 静态产物同理；把希望寄托在"恰好不断链"上，下次换工具链就会还回来。

**根因与修法** `override LDFLAGS += -pthread`，注释写明与 `-static`
命令行的关系。原判据为什么没覆盖到：判据体系没有"构建变量被命令行
覆盖后仍成立"的条目，这条记进 Makefile 判据的候选。

## 五、结果

测量方法：`wsl bash Project/check.sh`。

| 测量项 | 改动前 | 本轮后 |
|---|---|---|
| `Project/check.sh` 总判据 | 83 PASS（06 章后） | 90 PASS / 0 FAIL（多线程占 7 条） |
| 压力场景（400 帧，消费 5ms/帧） | 未测 | received=400，delivered=33，dropped=367 |
| tsan（同场景） | 未跑 | 无报告；拆锁后报 7 处竞争 |
| [13]/[14] 既有判据 | 全绿 | 逐字未改，全绿 |

压力账目（2026-10-04 实跑）：

```
stats received=400 delivered=33 dropped=367
```

生产端瞬间灌满 32 槽后开始挤旧，消费者以 5ms/帧的速度在约 2 秒内取完
队列里存活的帧；`400 = 33 + 367` 闭合，`pointer` 行数与 delivered 相等。
tsan 对照：正常构建无竞争报告；拆掉 `pthread_mutex_lock` 后同一场景
报出 7 处 `WARNING: ThreadSanitizer`，涉及队列下标与计数器的并发访问。

已知误差与不确定：队列深度 32 是编译期常数，没有进配置层——它属于
线程参数，等有真实负载证据再决定要不要让它可调。
