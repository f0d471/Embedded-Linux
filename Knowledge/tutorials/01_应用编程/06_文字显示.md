## 0 这一章解决什么问题

**“显示文字”是两条数据流在像素处会合：一条从 UTF-8 字节解到
字符身份，一条从字体轮廓算出覆盖率；display 层拿覆盖率和颜色，才生成
framebuffer 的最终像素。**

整条链拆成七步：

| 顺序 | 所在层 | 输入 → 输出 | 负责什么 | 本篇 |
|---|---|---|---|---|
| 1 | 用户态编码层 | `41 e4 b8 ad` → `U+0041 U+4E2D` | 验证并解码 UTF-8，回答"字符是谁" | 第 1 节 |
| 2 | 用户态字体层 | 码点 + 8x16/HZK16/TTF → glyph | charmap 选择"字体中哪个字形" | 第 2~5 节 |
| 3 | 用户态字体层 | glyph 轮廓 → `FT_Bitmap` | 光栅化出灰度覆盖率与度量 | 第 6~7 节 |
| 4 | 用户态显示层 | 覆盖率 + 前景/背景 RGB → 像素色 | alpha 混合、裁剪、格式转换 | 第 8 节 |
| 5 | 用户态显示层 | 像素色 → framebuffer | 描点（不进内核） | 第 8 节 |
| 6 | 硬件 LCDIF | 持续扫描 framebuffer | 输出显示信号 | 第 05 篇 |
| 7 | HDMI 屏 | 显示信号 → 画面 | 呈现文字 | 第 05 篇 |

三条边界始终守住：

1. **编码边界**：`char *` 是字节流不是码点数组；先验证并解码 UTF-8。
2. **字体边界**：字体库产出覆盖图和排版度量，不知道 framebuffer 是 565 还是 8888。
3. **显示边界**：display 层管行宽、位段、裁剪和背景色；font 层不再打开 `/dev/fb0`。

教材示例为单文件演示把三层揉在一个 .c 里；本章照它看清原理，第 9 节对账
Project 里已经立好的边界。

## 1 字节怎么还原成字符

### 1.1 第一性原理：身份和形状必须分开

打开同一个 TXT 换宋体、黑体、斜体，字节一个没变，屏幕形状变了。这证明两件事：

> **字符（character）**：文字系统里的抽象单位，如 A、"中"。
> **字形（glyph）**：某款字体把某字符画成的具体形状。
> **字符集/码点**：给每个字符分配的编号；Unicode 写成 U+XXXX，"中"是 U+4E2D。
> **字符编码**：把码点变成可保存字节的规则，如 UTF-8、UTF-16。

| 问题 | 处理链 |
|---|---|
| "它是谁" | "中" → U+4E2D → UTF-8 字节 `e4 b8 ad` |
| "它长什么样" | U+4E2D → 宋体的 glyph → FreeType 光栅化 → 灰度点阵 |

**编码回答"它是谁"，字体回答"它长什么样"。** 编码不含笔画，字体也不能替文件
决定那三个字节解成什么字符。

### 1.2 ASCII 到 Unicode：先统一身份证号

ASCII 用 7 bit 编 128 个编号（`'A'=0x41`），第 8 位恒 0，所以每个字符恰好
一字节，但 128 个位置装不下中文。视频 4_6-1 的记事本实验：
`"a中"` 存成 ANSI 是 `41 d6 d0` 三字节；ANSI 指的是"当前系统代码页"
——同一串 `d6 d0` 在简体中文 CP936 里是"中"，换 Big5 或 ISO-8859-1 就是别的
字符。**数值和字符一对多，这就是乱码的根源。**

Unicode 第一步先建全球共享的身份证表：`A=U+0041`（ASCII 原样保留）、
`中=U+4E2D`、`🙂=U+1F642`，解决了"一对多"。但码点是抽象整数，文件仍是一排
字节，还需要第二步：**编码实现**。直接写 `41 4e 2d` 不行，读的人不知道后面
两个字节是一个字符还是两个（视频 8:00 的"识文断字"问题）。

视频 4_6-3 的现场补一刀：**源码文件的保存编码会偷偷控制程序行为**。同一份
`printf` 长度的代码，按 GB2312 保存则 `"中"` 是 2 字节 `d6 d0`，按 UTF-8 保存
是 3 字节 `e4 b8 ad`；GCC 可用 `-finput-charset=GB2312 -fexec-charset=UTF-8`
在编译期转换。要记住的结论是**入口明确接收 UTF-8，不让源码文件
编码充当运行时协议**。

### 1.3 UTF-8：每个首字节自己报告长度

```text
码点范围            字节模板
U+0000..U+007F       0xxxxxxx
U+0080..U+07FF       110xxxxx 10xxxxxx
U+0800..U+FFFF       1110xxxx 10xxxxxx 10xxxxxx
U+10000..U+10FFFF    11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

"中" U+4E2D：`e4 b8 ad` = `11100100 10111000 10101101`，去前缀拼接得
`0100 1110 0010 1101` = 0x4E2D。首字节 `1110` 自报"本字符共 3 字节"，后续
字节必须以 `10` 开头，所以损坏之后解码器能重新找边界（视频说"丢一个字节
不影响其他字符"要加条件：错误附近可能产生一两个替换符，**后面的合法首字节能
重新同步**）。

一个合格解码器必须拒绝：`c0 af`（过长编码）、`ed a0 80`（surrogate）、
`f4 90 80 80`（超 U+10FFFF）、孤立的 `80..bf`（无首字节的后续字节）。
只查"后续字节以 10 开头"不够。UTF-16 补一句（[fundamentals/11] 第二节）：
编码单元 2 字节，非 BMP 码点用 surrogate 对共 4 字节；BOM 管端序不管内容。

### 1.4 [做 L2] 写 UTF-8 解码器，让坏输入只伤局部

实验 `Knowledge/labs/06_text/utf8.c`。约定：成功返回消耗字节数并写出码点；
失败返回 -1，**调用者只跳过当前 1 字节再尝试同步**。

```bash
cd ~/t06 && gcc -Wall -Wextra -Werror -O2 -o utf8 \
  /mnt/e/Workspace/Embedded-linux/Knowledge/labs/06_text/utf8.c
./utf8 'A中🙂'
./utf8 --hex c0 af 41
```

本机实测（2026-10-16）：

```text
bytes=8
U+0041 at=0 len=1
U+4E2D at=1 len=3
U+1F642 at=4 len=4
summary codepoints=3 errors=0

ERROR at=0 byte=C0
ERROR at=1 byte=AF
U+0041 at=2 len=1

```

对账：`1+3+4=8`；后一项 at = 前一项 at+len；`c0 af` 被拒绝为两个坏字节，

越界读。

### 1.5 [判] 第 1 节

    [ ] 一句话区分字符、码点、编码、glyph
    [ ] A中🙂 解出 U+0041/U+4E2D/U+1F642,长度 1/3/4
    [ ] 拒绝 C0 AF 过长编码;丢"中"的中间字节后 A 仍恢复
    [ ] UTF-16 编码单元 2 字节,非 BMP 码点要 4 字节
    [ ] 接口文档不写"ANSI",写 UTF-8 或明确代码页

## 2 ASCII 字符怎么变成 8x16 点阵

### 2.1 第一性原理：字符编号只是数组下标

8x16 点阵把每个字符画在 8 列 16 行的格子里：

```text
一个字符   8 × 16 = 128 个开关,每位 1 bit 亮/灭
总大小     128 bit = 16 字节;256 个编号全预留 = 4096 字节
```

Linux 内核就带这套字库（`fontdata_8x16[FONTDATAMAX]`）。ASCII 码不告诉屏幕
怎么画 A，它只给出 65；字库作者约定第 65 项放 A 的点阵：

```c
dots = &fontdata_8x16[(unsigned char)'A' * 16];
```

这是最简单的 `字符身份 → glyph` 映射；FreeType 的 charmap 做同一类事，
只是不再保证"码点乘固定大小"。

### 2.2 一行一个字节，一位一个像素

A 的 16 字节 `00 00 10 38 6c c6 c6 fe c6 c6 c6 c6 00 00 00 00`，按 MSB-first
展开（0x10 = `...#....`，0xfe = `#######.`）成 16 行 8 列。点阵左上角放
(x, y) 时：

```text
屏幕横坐标 = x + (7 - b)      bit 号从右往左减,屏幕列从左往右加
屏幕纵坐标 = y + i
```

公式是把两条方向接起来，不用背。**每字节 MSB-first 是点阵自己的协议**
（[fundamentals/11] 第三节），和 CPU 端序是两份协议。

### 2.3 [做 L2] 不看屏幕，先在终端和 PGM 里验点阵

A 接近左右对称，位序反转后仍像 A、点数不变，所以实验保留不对称的 F 当
对照（实验 `Knowledge/labs/06_text/bitmap8.c`，`--pgm` 写最简单的 P5 PGM）：

```bash
gcc -Wall -Wextra -Werror -O2 -o bitmap8 Knowledge/labs/06_text/bitmap8.c
./bitmap8 A --pgm A.pgm
./bitmap8 F
./bitmap8 F --lsb-first        # 注错版:bit0 画在左边
```

本机实测（2026-10-16）：

```text
glyph=A order=MSB lit=39 bbox=0,2..6,11     A.pgm 像素体 128 字节
glyph=F order=MSB lit=34 bbox=0,2..6,11
glyph=F order=LSB lit=34 bbox=1,2..7,11
```

三笔对账：A 的 16 字节 popcount 合计 39 = 画出的前景像素数；8x16 格子里真正
有墨迹的外框只有 x=0..6, y=2..11；**F 镜像前后都是 34 个点**——点数判据抓不住
位序反转，外框和逐行图才红。

### 2.4 从点阵到显示：font 层不绑死 fb0

教材 `lcd_put_ascii` 对每点直接调 `lcd_put_pixel`——理解原理的最短路径。
落项目时分两层：

| 层 | 输入 | 负责 | 输出 |
|---|---|---|---|
| font 层 | 字库 bit | bit=1 → coverage 255；bit=0 → coverage 0 | 覆盖率、前景色、坐标 |
| display 层 | 覆盖率、RGB888、坐标 | 裁剪、line_length 定位、位段打包 | 565/8888 像素 |

bit=0 一律画黑的话文字带 8x16 黑矩形擦掉背景；UI 要透明背景：coverage=0
什么都不写。

### 2.5 [判] 第 2 节

    [ ] A 表项偏移 = 65*16;A 点阵 39 个前景像素,bbox 0,2..6,11
    [ ] F 镜像前后都是 34 点,第三行左右位置不同(位序注错的活证据)
    [ ] PGM 头后恰好 128 字节
    [ ] font 层不用 xres*bpp/8 算行宽,不自己 open /dev/fb0

## 3 中文怎么在 HZK16 里找到 32 字节

### 3.1 第一性原理：格子变大，查表规则也变了

16x16 汉字点阵每字 `16*16 bit = 32 字节`（每行 2 字节）。HZK16 用 GB2312
编码索引：两个字节都在 `0xA1..0xFE`，各 94 个取值，形成 94×94 区位表。区码
位码都从 0xA1 起是为了避开 ASCII 区（视频 4_6-3 的解释：从 0/1 起会和 ASCII
重合）：

```text
area   = first  - 0xA1        where = second - 0xA1
index  = area * 94 + where
offset = index * 32
```

"中" `D6 D0`：area=53, where=47, index=5029, **offset=160928**。四个数一条
对账链，错 1 就跳到另一个汉字。

### 3.2 源码编码会偷偷控制结果（视频 4_6-3 的核心现场）

教材写 `unsigned char str[] = "中";` 然后拿 `str[0] str[1]` 套区位公式。
源文件按 UTF-8 保存时数组实际是 `e4 b8 ad`，拿 `e4 b8` 套 GB2312 公式：
两个值碰巧也在 A1..FE 范围内，**程序不报错，安静地查出另一个合法 glyph**，
`ad` 还残在后面。板上现场（视频 14:04）：屏幕打出来的"不是中字"，`file` 看
不出格式，notepad++ 打开才发现源码是 UTF-8；加
`-fexec-charset=GB2312`（或转存编码）后才显示"中"。

教训是**编码混用经常不崩溃，只是稳定地显示错字**。项目
做法：入口明确 UTF-8 → 解成码点 → 需要 HZK16 时显式映射到 GB2312；FreeType
则直接用 Unicode charmap。另注：`-fexec-charset` 管窄字符串，宽字符串
`L"..."` 对应 `-fwide-exec-charset`（PDF 示例只写了前者，不完整）。

### 3.3 [做 L2] 按区位公式取"中"，再故意喂 UTF-8 前两字节

```bash
HZK="$Q/04_嵌入式Linux应用开发基础知识/source/09_show_chinese/HZK16"
gcc -Wall -Wextra -Werror -O2 -o hzk16 Knowledge/labs/06_text/hzk16.c
./hzk16 "$HZK" d6 d0
./hzk16 "$HZK" e4 b8
```

本机实测（2026-10-16）：

```text
bytes=D6D0 index=5029 offset=160928 file_size=267616 lit=52 bbox=1,0..14,15 fnv1a=0b4ee7e7
bytes=E4B8 index=6321 offset=202272 file_size=267616 lit=77 ...      ← 另一个 glyph
```

- index/offset 与手算逐项相等；**资料 HZK16 实际 267616 字节 ≠ 理论
  94×94×32=282752**——读任何区位前先查 `offset+32 <= file_size`，不能只信
  理论表格。
- FNV-1a 摘要验证 32 字节原样；错误输入的摘要必然不同。**这就是"喂错编码
  不崩溃只是显示错字"的机械化判法。**

### 3.4 两层循环为什么是 16 x 2 x 8

```text
for y = 0..15           16 行
    for byte = 0..1     每行 2 字节
        for bit = 7..0  MSB-first
screen_x = origin_x + byte*8 + (7-bit)
screen_y = origin_y + y
```

总次数 16×2×8=256 恰好覆盖 16x16。与 ASCII 相比只是每行多一个字节；
位序、透明背景、裁剪全是同一套。

### 3.5 HZK16 为什么没有成为项目最终接口

优点：小、确定、无依赖，适合启动画面和教学。限制：字符范围受 GB2312 限制、
字号固定 16x16 放大有锯齿、只有 0/1 没有抗锯齿、没有 bearing/advance 排版
度量、统一 UTF-8 入口还要做 Unicode→GB2312 映射。它是文字栈的第二级台阶；
Project 保留 bitmap provider 做内置救援字体，再挂 FreeType provider，
上层接口不变（第 9 节）。

### 3.6 [判] 第 3 节

    [ ] D6D0 → area=53 where=47 index=5029 offset=160928
    [ ] 读前检查 offset+32 ≤ 真实文件大小 267616
    [ ] "中" 32 字节 FNV-1a = 0b4ee7e7,前景 52 像素
    [ ] E4B8 当 GB2312 能读出"合法" glyph,摘要与"中"不同
    [ ] 项目入口写明 UTF-8,源码文件编码不当运行时协议

## 4 FreeType 从哪里来

### 4.1 第一性原理：库有"构建时的一生"和"运行时的一生"

为什么点阵不够、要用 FreeType（视频 4_6-5 开头）：点阵字号固定，8x16 放大
靠缩放，模糊、锯齿。**矢量字体**存轮廓控制点+曲线+度量，不存某个字号的最终
像素；关键点相对位置不随缩放变，字就不变形。显示分三步（关键点→曲线连接→
填充），FreeType 把这三步全包了：**给定码点和字号，还你一张位图**。

库本身有两生（完整模型在
[fundamentals/12](../../fundamentals/12_第三方库的交叉构建与部署.md)）：

```text
WSL 跑 configure/make        build = x86_64
arm-linux-gnueabihf-gcc 编库  host  = ARM Linux
板子加载执行                 ARM EABI5 + 板端 ABI
```

本章这一次的决定：不把头文件/库复制进公共工具链目录；`--prefix=/usr`（目标机
逻辑路径）配 `DESTDIR=$STAGE`（本机假根）；第一轮关掉 zlib/png/bzip2 等可选
依赖；真机探针用 `.a` 静态链接切断板端 glibc 变量。

### 4.2 `wchar_t` 能用，但不拿它当外部协议

PDF 用 `L"中gif"` 让每个 `wchar_t` 直接存 Unicode 值（Linux/GCC 下实测
`sizeof(wchar_t)=4`，打印 `0x4e2d 0x67 0x69 0x66`）。它适合受控源码里快速
调 `FT_Load_Char`，但：C 标准不保证 32 位（Windows 常见 16 位）；它的外部
字节表示属平台 ABI，不适合写文件/发网络/做稳定接口。本章实验用
`uint32_t codepoint` 存码点并自己验证 UTF-8；FreeType 本身接受 `FT_ULong`，
不要求先变 wchar_t。

### 4.3 [做 L1] 隔离交叉构建 FreeType 2.10.2

完整命令与 staging 模型见
[fundamentals/12 第五节](../../fundamentals/12_第三方库的交叉构建与部署.md#五实测交叉构建-freetype-2102)。
关键实测（2026-09-16）：

```text
checking build system type... x86_64-pc-linux-gnu
checking host system type... arm-unknown-linux-gnueabihf
checking whether we are cross compiling... yes
libfreetype.so.6.17.2: ELF 32-bit LSB shared object, ARM, EABI5
```

`cross compiling... yes` 与 `Machine: ARM` 是两条独立证据。GCC 15 对 2020 年
的 FreeType 报两组 `-Wdangling-pointer` 警告，构建仍成功。第三方旧源码不纳入
本仓的 `-Werror` 纪律。

用 staging 编真机程序：

```bash
arm-linux-gnueabihf-gcc -static -Wall -Wextra -Werror -O2 \
    -I"$STAGE/usr/include/freetype2" -o fbtext-arm fbtext.c \
    -L"$STAGE/usr/lib" -lfreetype -lm
```

`-I` 发生在预处理、`-L` 在链接、`-l` 是库、`LD_LIBRARY_PATH` 在运行。四个
时刻四件事。产物 `readelf -d` **没有动态段**，板上不需要另找 libfreetype.so.6。

### 4.4 [判] 第 4 节

    [ ] configure: build=x86_64 / host=arm / cross compiling=yes
    [ ] 安装只进 $STAGE;libfreetype 的 readelf Machine 是 ARM
    [ ] fbtext-arm 是 ARM EABI5 静态链接,readelf -d 无动态段
    [ ] 说得出 -I/-L/-l/LD_LIBRARY_PATH 各发生在哪个时刻

## 5 一个矢量字怎么变成灰度覆盖图

### 5.1 五个对象和一条最短调用链

> **FT_Library** 库实例；**FT_Face** 打开的一张字体（TTC 可多 face）；
> **charmap** 码点→glyph index 映射表；**glyph** 字体内部字形对象；
> **FT_GlyphSlot** face 自带的工作槽，每次 `FT_Load_*` 覆盖上一次结果。

```c
FT_Init_FreeType(&library);
FT_New_Face(library, font_path, 0, &face);
FT_Select_Charmap(face, FT_ENCODING_UNICODE);
FT_Set_Pixel_Sizes(face, 0, pixel_height);
FT_Load_Char(face, codepoint, FT_LOAD_RENDER | FT_LOAD_TARGET_NORMAL);
/* 结果在 face->glyph */
```

`FT_Load_Char` 内部合并三步：码点 --charmap→ glyph index --加载轮廓→
slot --render→ bitmap。但**不要跳过 `FT_Get_Char_Index`**：返回 0 通常表示
字体没这个码点，`FT_Load_Char` 会继续给你 `.notdef` 方框，只看 API 成功会把
缺字误判成正常。资源按申请反序释放（`FT_Done_Face` → `FT_Done_FreeType`）。
教材演示省略了错误处理与释放，项目不能照省。

### 5.2 `FT_Bitmap`：width 不是 pitch，字节也不是颜色

```text
width       有效像素列数
rows        行数
pitch       行跨距(字节),可大于 width,可为负
buffer      第一行地址
pixel_mode  FT_PIXEL_MODE_GRAY(本机值 2);num_grays 256
```

访问第 y 行**不能写死 `buffer + y*width`**：

```c
row = pitch >= 0 ? buffer + y*pitch
                 : buffer + (rows-1-y)*(-pitch);
```

灰度值 a 是**覆盖率**：a=0 完全在轮廓外不改背景；a=255 完全在内写前景色；
中间是边缘。教材把 a 直接传给把参数当 0xRRGGBB 的 `lcd_put_pixel`——结果只有
蓝通道变化，那是"把覆盖率当颜色"的演示，不是通用文字绘制。正确做法每个通道
独立混合：

```text
out = (foreground * a + background * (255-a) + 127) / 255
```

`+127` 整数四舍五入。白字黑底：a=128 → 128（中灰边缘）。红底白字的边缘
R/G/B 三通道必须分别混，不能指望 framebuffer 理解 alpha。真机 fbtext 的
顺序：读旧像素 → 按 fb bitfield 解到 8bit → 三通道分别混合 → 按运行时
bitfield 压回——所以插拔 HDMI 改 bpp 也不用重编。

### 5.3 [做 L2] 在 WSL 里量单字，不先依赖屏幕

实验 `Knowledge/labs/06_text/ftprobe.c`（本机 FreeType 2.14.2 + 资料宋体，
2026-10-16 复跑一致）：

```bash
gcc -Wall -Wextra -Werror -O2 $(pkg-config --cflags freetype2) -o ftprobe \
    Knowledge/labs/06_text/ftprobe.c $(pkg-config --libs freetype2)
./ftprobe "$Q/.../10_freetype/02_freetype_show_font/simsun.ttc" 48 'Ag中' line.pgm
```

```text
freetype=2.14.2 family=SimSun glyphs=3 pixel_size=48
glyph cp=U+0041 gid=36   bitmap=24x33 pitch=24 left=0 top=34  bottom=1   advance=24.000px nonzero=241 mid=145 full=96
glyph cp=U+0067 gid=74   bitmap=21x28 pitch=21 left=2 top=22  bottom=-6  advance=24.000px nonzero=279 mid=218 full=61
glyph cp=U+4E2D gid=1025 bitmap=37x45 pitch=37 left=6 top=40  bottom=-5  advance=48.000px nonzero=368 mid=270 full=98
line bbox=0,-6..91,40 width=91 height=46 advance=96.000px missing=0 nonzero=888 mid=633
pgm=line.pgm size=95x50 baseline_row=42
```

单字四条：

- **请求字号 48，A 的 bitmap 只有 24x33**——字号管整体度量，不等于每字墨迹盒
  （坑 10）。
- **g 的 bottom=-6**：6 行落在基线下；把所有 bitmap 顶对齐基线就乱。
- "中" advance 48px，A/g 各 24px，定宽步进会在英文后留大洞。
- 三字 633 个 `0<a<255` 边缘像素；只画 a==255 轮廓会明显变瘦起锯齿。
  （`pkg-config --cflags/--libs` 给出本机 FreeType 路径与 `-lfreetype`，
  不手抄 /usr/include。）

### 5.4 `slot` 为什么不能存起来下次再画

`face->glyph` 是工作槽不是缓存：Load 'A' 后 slot 是 A，Load 'g' 就被覆盖。

```text
立即消费 slot->bitmap                 可以
复制 bitmap 数据和度量到自有缓存       可以(记得 pitch/生命周期)
只保存 slot->bitmap.buffer 指针       不可以,下次 Load/Done 后失效
FT_Get_Glyph 复制 glyph 对象          可以,最后 FT_Done_Glyph
```

本章两遍排版（7.4）的第二遍重新 `FT_Load_Char`，不存第一遍的 slot 指针。

### 5.5 [判] 第 5 节

    [ ] FT_Get_Char_Index 返回 0 计缺字,不把 .notdef 当成功
    [ ] A/g/中 的 width、rows、pitch 分别打印;行地址用 pitch 且处理 pitch<0
    [ ] 灰度按 alpha 与背景混合,不直接当 0xRRGGBB
    [ ] 三 glyph 共 888 非零覆盖像素,其中 633 半覆盖
    [ ] 48px 的"中"advance 48px,A/g 24px,不写固定步长
    [ ] 每次 Load 后立即消费 slot,或复制所有权明确的数据

## 6 多个字怎么沿一条基线排开

### 6.1 第一性原理：排版需要一条线，不是很多左上角

点阵字体每格同尺寸，左上角排齐即可；矢量字体 A/g/中 宽度、上伸、下伸各不同，
必须有共同参照：

| 度量 | 含义 |
|---|---|
| baseline 基线 | 一行 glyph 共用的水平参考线；g/p/q/y 的下伸部可越到线下 |
| pen/origin | 当前 glyph 的书写原点，在基线上，**不是 bitmap 左上角** |
| bitmap_top | bitmap 顶边相对基线的高度 |
| advance | 画完当前 glyph 后 pen 移到下一个的距离（26.6 定点，[fundamentals/11]） |

两个坐标系（视频 4_6-6）：FreeType 用"y 向上"的笛卡尔坐标，LCD 用"y 向下"；
给定 LCD 基线 baseline_y，转换只需两行：

```text
lcd_bitmap_left = pen_x + bitmap_left
lcd_bitmap_top  = baseline_y - bitmap_top
next_pen_x     = pen_x + advance.x        (26.6 原样累加,落像素时才取整)
```

每字 advance 先取整再累加，一行几百字会累计误差。

### 6.2 两遍排版：先量，再反推 pen

需求"整行墨迹外框左上角落在 (target_x, target_y)"——第一字 pen 不等于这个点，
分两遍：

```text
第一遍  pen=(0,0) 逐字 Load 取 bbox 合并成 line_bbox,pen += advance
反推    pen_x_26_6 = (target_x - xmin) * 64
        baseline_y = target_y + ymax          (LCD y 向下)
第二遍  从这个 pen/baseline 重新 Load 并画
```

为什么第一遍不存 bitmap 指针——5.4 的槽覆盖。重新 load 最简单；要性能再做
自有 buffer 的 glyph cache。

### 6.3 用实测数字把外框和步进分开

`Ag中` 的行摘要（5.3 节同一组数据）：

```text
line bbox=0,-6..91,40 width=91 height=46 advance=96.000px
pgm=line.pgm size=95x50 baseline_row=42
```

逐项对账：24+24+48=96=advance_px；墨迹宽 91≠96（差在 bearing/留白）；
高 46 = 40-(-6)（g 的下伸进入 ymin）；PGM 四边各留 2 像素：91+4=95、46+4=50；
baseline_row = 2+40 = 42。**五个独立数字逐个咬合**，比"图片看着挺齐"更能抓住
坐标错一行、漏下伸部这类问题。

### 6.4 本章边界：FreeType 不是完整文本塑形器

`FT_Load_Char` 按码点逐个取 glyph，够讲中/英基本绘制；真实文字还有 kerning
（`FT_Get_Kerning` 可做基础字偶距）、shaping（阿拉伯连写等要 HarfBuzz）、
fallback（缺字去下一款字体）、line break。所以 font 层接口**不把"一个 UTF-8
字符必对应一个 glyph"写死进 ABI**，未来接 shaping 时 display 层一行不改。
视频 4_6-5 末尾的旋转演示（`FT_Set_Transform` 传矩阵+pen，`-lm` 链数学库）
属同类扩展，判据应比 0/90/180 度的 bbox 摘要而非截图（延伸 B）。

### 6.5 [判] 第 6 节

    [ ] pen 在基线上,不是 bitmap 左上角;lcd_bitmap_top = baseline_y - bitmap_top
    [ ] advance 相加 96px 与 bbox 宽 91px 分开用
    [ ] g 的 bottom=-6 进整行 ymin,下伸部不裁
    [ ] PGM 95x50 与 bbox 91x46+四边 2px 逐项相等
    [ ] pen 用 26.6 累加;第一遍量第二遍重新 load

## 7 上板：把覆盖图真正写进 framebuffer（2026-09-16/23 归档）

`Knowledge/labs/06_text/fbtext.c` 是真机探针（非 Project 最终 font 层），比
教材示例多做五件事：自己验 UTF-8、按 bitmap.pitch 取行、用 bitmap_left/top
沿基线排字、运行时读 line_length 与 RGB bitfield 不写死 565/8888、读旧像素
按覆盖率混合再写回。用法：

```text
fbtext FB FONT UTF8_TEXT X BASELINE_Y PIXELS 0xRRGGBB [--clear]
```

板上基线：fb0 1024x600x32 line_length=4096 rgba 8/16,8/8,8/0；GUI=mxapp2。
ARM 静态程序经 staging 链接（`ELF 32-bit ARM EABI5, statically linked`，
3142968 字节，sha256 d818688f…），上传 56 块中真实丢字节重传 1 块、
sha256 OK、耗时 236.8 秒；板上已有 msyh.ttc 无需传 10 MiB 字体
（sha256 d6a1a92b…）。

停 GUI 后画白色 `Ag`（基线 40,120，字号 72，--clear）：

```text
fb=1024x600 bpp=32 line_length=4096 rgb=16/8,8/8,0/8
glyphs=2 missing=0 covered=2162 mid=609 written=2162 clipped=0
advance26_6=6208 advance_px=97.000
```

六条结构判据全过：glyphs=2、missing=0、mid>0、clipped=0、written=covered、
advance>0。missing>0 时先换字体/字符，别把 .notdef 方框当通过。串口命令不能
带中文，用八进制转义生成 `A中g`（黄色 0xffd040，基线 40,160）：

```text
glyphs=3 missing=0 covered=3650 mid=917 written=3650 clipped=0
advance26_6=10816 advance_px=169.000
```

**回读对账**（独立程序 `rawcheck.c` 不调 FreeType 不开 fb0，按命令行 bitfield
解下载文件——不是"让被测程序证明自己"）：

```text
32bpp 白 Ag: dd bytes=2457600=4096*600;下载 sha256 OK
             rawcheck: nonblack=2162 bbox=40,66..130,138 colors=217
中文 A中g:   nonblack=3650 bbox=40,100..202,178 colors=220
```

三个独立量咬合：2162 nonblack = 2162 written = 2162 covered；bbox 下边 y=138
证明 g 的下伸真在基线 120 之下；217 色 = 黑+216 级实际灰度，抗锯齿没塌成
开关。把 fb 临时切 16bpp 再跑同一程序（不重编）：

```text
fbset: 1024x600x16 rgba 5/11,6/5,5/0 line_length=2048
fbtext: covered=2162 written=2162 mid=609 clipped=0
rawcheck: nonblack=2141 colors=88      ← 少的 21 个是极低覆盖率被 565 量化为 0
```

**注错见红（本章最关键的反例）**：`-DBUG_NO_ALPHA` 把所有非零覆盖率强改 255：

```text
                    正确版              BUG_NO_ALPHA
covered/written     2162 / 2162         2162 / 2162
bbox                40,66..130,138      40,66..130,138
显存非黑像素         2162                2162
显存颜色种类         217                 2            ← 只有这里红
```

**几何正确不等于光栅化正确。** "画了多少点"和 bbox 全会放过 alpha 错误，
只有颜色种类判据见红。另两个注错（`BUG_WIDTH_AS_PITCH` 在本字体样本
pitch==width 可能不红；`BUG_FIXED_565` 在 16bpp 恰好不红）——**注错不红不是
代码正确，是输入没激发错误**，记录并换合成样本复测。实验结束已恢复 32bpp 并
重启 mxapp2。

## 延伸 A：码点不等于用户眼中的一个字

`é` 可以是 U+00E9 一个码点，也可以是 `e + ◌́`（U+0065 U+0301）两个码点；
家庭 emoji 是多个 emoji+ZWJ。**字素簇**（用户认为的一个字符）需要 Unicode
分段/塑形层，不能拿 strlen 或码点数代替，UTF-8 解码只产出码点。

## 延伸 B：旋转为什么同时需要矩阵和 pen

`FT_Set_Transform(face, &matrix, &pen)`：matrix 改轮廓方向/缩放（旋转 45 度），
pen 改 26.6 平移。旋转后 bbox 会变，不能用未旋转的 width/rows 做裁剪；
sin/cos 来自 libm（视频里链接报 undefined reference 后补 `-lm` 的现场）。
主线不依赖旋转；做的话判据比 0/90/180 度的 bbox 和像素摘要，不只截图。

## 顺带一提：和 NEMU 的字模对照（跳过不影响）

NEMU/VGA 和本板 LCDIF 一样不认识文字；monitor 里能显示字符也是上层拿字模
自己画像素。区别只在最后写像素的接口：NEMU 写模拟显存/SDL，本章 display 层写
mmap 的 /dev/fb0；共同上层是 编码→glyph→bitmap→blend。font 层不依赖 fb0，
同一套排版代码才能在 WSL 假屏、NEMU 风格内存屏和真板之间复用。
