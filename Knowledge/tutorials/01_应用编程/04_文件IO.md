## 0 这一章解决什么问题

### 0.1 先看结果：两个"成功但没做完"的返回值

本机实测（2026-10-16，管道）：

```text
read(要 100) 实际返回 5
write(要 1048576) 实际返回 4096
```

两个都算成功，退出码 0，但都没搬完。本章第一条就是：**返回值是"实际做成了
多少"，不是"你要了多少"**。后面 fd、缓冲、mmap 全是这条的推论。

### 0.2 这一章为什么存在

一句话：**`read`/`write` 的返回值是"实际做成了多少"，和"你要的多少"是
两回事；`fd` 是下标，内核不给指针；标准 IO 与系统调用 IO 唯一的实质差别
是一块用户态缓冲。**

这三句话撑起整章。Linux 里"一切皆文件"，普通文件、串口、显存、网络 socket
都从同一组接口进出，所以这一章的每个细节都会在后面每一章再遇到：
framebuffer 是 `open`+`ioctl`+`mmap`，串口是 `termios`+`read`，日志落文件是
`dup2`+`O_APPEND`。

从 `printf` 到磁盘之间的四层（原书 4.1 图的文字版）：

| 顺序 | 层 | 发生什么 | 本篇 |
|---|---|---|---|
| 1 | 你的程序 | 调用 `printf` 或 `fopen/fwrite` / `open/write` | 第 1~3 节 |
| 2 | C 库 | 标准 IO 先写用户态缓冲（4096 字节），攒满才调 `write` | 第 3 节 |
| 3 | 内核 VFS | fd → struct file → inode → 分派读写函数 | 第 1 节、[基础 06] |
| 4 | 硬件路径 | 普通文件走文件系统+块设备；设备节点直达驱动 | 第 03 章起 |

### 0.3 为什么会有两套函数

`open/read/write` 和 `fopen/fread/fwrite` 干同一件事，但它们是**两个标准**
（视频 4_4-1 的来历推导）：

| 接口层 | 标准来源 | 可移植范围 | 与下一层的关系 |
|---|---|---|---|
| `fopen / fread / fwrite` | C 标准库 | Windows/Linux 重新编译即可 | 内部调用下面那套，额外多一块用户态 buffer |
| `open / read / write` | POSIX | Linux 及各家 UNIX | 贴近内核和设备接口 |

两条结论，全章反复用：

1. **上面那套是拿下面那套实现的。** `fwrite` 内部最终调 `write`，
   它多出来的东西只有一个：用户态缓冲（第 3 节）。
2. **越往上越可移植，越往下越贴硬件。** 碰 `/dev` 下的设备一律用下面那套，
   上面那套为了可移植把 `ioctl` 整个砍掉了（3.5 节）。

## 1 一个 fd 到底是什么

### 1.1 第一性原理：内核不肯给你指针，只好给你下标

内核里描述"一次打开"用的是 `struct file`，它有地址。为什么不把地址给你？
**用户态拿到内核内存的地址，等于拿到了改内核的能力。** 特权级边界是硬件
强制的（你在 ysyx 里做过 U 态访问内核地址会异常）。指针不能给，就在每个
进程里放一张数组，把指针填进数组，只把**下标**给你——下标越界内核查得出
来，指针给出去就没法验证了。

三张表的关系（`fd = open("data.txt")` 得到 3 之后）：

![图 3　fd 背后的三张表：进程 fd 数组、struct file、inode](fig/04-fd三张表.svg)

读法：fd 3 和 fd 5 是 `dup` 出来的一对，指向**同一个** struct file，所以
共用一个 f_pos；fd 4 是第二次 `open`，有自己独立的 struct file。一句话
记住中间那张表为什么必须存在：

> `f_pos`（读到哪了）属于"这一次打开"，不属于"这个文件"。

完整的三张表逐行精读、以及它与 ysyx `nanos-lite/fs.c` 的对照，在
[fundamentals/08](../../fundamentals/08_文件描述符与VFS.md)。

### 1.2 0、1、2 是谁放进去的

程序一启动，fd 表前三格已填好：

    fd 0   stdin    标准输入
    fd 1   stdout   标准输出
    fd 2   stderr   标准错误

**这三格是 shell 填的。** shell fork 出子进程，子进程继承 shell
的整张 fd 表，三格里装的是终端。`./prog > out.txt` 的 `>` 就是在 execve
之前把子进程 1 号那一格改指向 `out.txt`。`open` 返回的第一个 fd 一定是 3：
内核分配 fd 的规则是**"当前未使用的最小编号"**。

推论：这张表每进程一份，**fd 编号只在它自己的进程里有意义**。同时跑两个
程序各开不同的文件，两边拿到的都是 3（2026-09-14 实测）：

```text
    pid=2598 fd=3 file=f1.txt
    pid=2599 fd=3 file=f2.txt
```

所以"fd 等于 3 的那个文件"这句话不完整，必须说"**某进程里** fd 等于 3 的
那个文件"。`/proc/<pid>/fd/` 这个路径本身就写着这件事：先有 pid，才有 fd。

### 1.3 [做 L1] 把三张表从 /proc 里看出来

实验程序 `Knowledge/labs/00_basics/02_fd_and_vfs/fdshow.c`（fundamentals
08 篇配套）：open 同一个文件两次，再 dup 一次，打印各 fd 的位置。

```bash
cd ~/fio04                                   # 在 WSL 原生目录做
printf 'ABCDEFGH' > data.txt
gcc -w /mnt/e/Workspace/Embedded-linux/Knowledge/labs/00_basics/02_fd_and_vfs/fdshow.c -o fdshow
./fdshow
```

本机实测（2026-10-16）：

```text
open 返回的编号: fd1=3 fd2=4 fd3=5

[读之前] 三个 fd 的位置：
  fd 3  (open 1    )  pos:	0
  fd 4  (open 2    )  pos:	0
  fd 5  (dup fd1   )  pos:	0

从 fd1 读了 1 个字节（读到 'A'）

[读之后] 三个 fd 的位置：
  fd 3  (open 1    )  pos:	1
  fd 4  (open 2    )  pos:	0
  fd 5  (dup fd1   )  pos:	1
```

fd1 读了一个字节后，**fd5 的位置跟着变成 1**：dup 出来的 fd 与源 fd 共用
同一个 struct file；fd4 纹丝不动，第二次 open 有自己的一份。
再从内核那头看一遍（另开终端）：

```bash
ls -l /proc/<pid>/fd          # 第 1 张表: 编号 -> 文件
cat  /proc/<pid>/fdinfo/3     # 这个 fd 背后的 pos 和 flags
```

2026-09-14 实测：三个编号指向同一个文件，fdinfo 里的 pos 却是 1 / 0 / 1。
**内核自己把"中间那张表存在"这件事报了出来。**

### 1.4 open 两次、dup 一次、fork，差别在哪一层

| 操作 | fd 表 | struct file | f_pos |
|---|---|---|---|
| `open` 两次 | 增加两格 | 各建一份 | 各算各的 |
| `dup / dup2` | 增加一格 | 新旧 fd 指向同一份 | 共享 |
| `fork` | 子进程复制整张表 | 父子表项仍指向同一份 | 跨进程共享 |

第三条解释一个日常现象：`(./a; ./b) > log` 里两个程序共用 struct file，
写位置接着走；`./a > log; ./b > log` 是两次独立重定向，第二次把第一次清掉。
`close(fd)` 关的是 fd 表里那一格；struct file 上有引用计数，减到 0 才真关。

### 1.5 [做 L2] 用 dup2 把 printf 骗进文件

`printf` 认的是**数字 1**。改不了它的实现，就改 1 号槽指向谁：

```c
int save = dup(1);                 /* 先存一份原 stdout,事后好恢复 */
int fd = open(argv[1], O_RDWR | O_CREAT | O_TRUNC, 0644);
dup2(fd, 1);                       /* 1 号槽改指这个文件(旧的先被关掉) */
printf("hello, world\n");          /* 现在它落进文件 */
fflush(stdout);                    /* 把 C 库缓冲推进内核(原因见第 3 节) */
dup2(save, 1);                     /* 恢复 */
```

实验程序 `Knowledge/labs/04_file_io/dup2_printf.c`。本机实测（2026-10-16）：
out.txt 里是 `hello, world`，13 字节。

- `dup2(oldfd, newfd)`：让 newfd 指向 oldfd 指的 struct file；
  newfd 本来开着会**先被关掉**。`dup` 是内核挑最小空编号，`dup2` 由你指定，
  想覆盖 0/1/2 就必须用 `dup2`。
- **一个坑，跑之前先想**：把最后 `return 0` 改成 `_exit(0)`（下划线那个，
  不走 C 库收尾），文件会变 0 字节。`printf` 的内容还压在 C 库缓冲里，
  `_exit` 不冲缓冲。所以代码里有 `fflush`。为什么，见第 3 节。
- 这族还有 `dup3(oldfd, newfd, flags)`，flags 只有 0 或 `O_CLOEXEC`
  （exec 后自动关），讲进程时才有意义。

### 1.6 内核那一侧：open 进去之后发生了什么

用户态怎么进内核（svc 指令、调用号放 r7、sys_call_table 查表）在
[fundamentals/07](../../fundamentals/07_系统调用与用户内核态.md) 已用反汇编
逼出来，不重复。这里补两件。

**OABI 和 EABI 差在哪**：调用号怎么传给内核，变过一次——

    OABI(老)   调用号编进指令本身: swi #5
               内核收到异常后回用户空间把那条指令读出来,抠出低 24 位
    EABI(新)   调用号放寄存器:     mov r7, #5  然后 svc #0
               内核直接读 r7

改的理由：OABI 每次都要多一次访存去取指令，还要处理那块内存被换出的情况；
EABI 把号放进寄存器，异常一进来它就在现场。工具链前缀里的 `eabi` 就是它，
**内核和应用必须同一套**，混了每个系统调用都调错函数。

**sys_open 的三步**（`SYSCALL_DEFINE3` 的 3 是参数个数）：

    1. get_unused_fd_flags()   在 fd 表里找个空格,返回下标——只管第 1 张表
    2. do_filp_open()          真去打开文件,得到 struct file——只管第 2、3 张表
    3. fd_install(fd, file)    把指针填进第 fd 格——两边这才挂上钩

**这三步的分法本身就是答案**：dup 干的就是跳过第 2 步，直接拿现成的
struct file 做第 1 步和第 3 步。read 反着走同一条路：拿 fd 查出 struct
file，取 f_pos，读完挪 f_pos。

### 1.7 [更正] 视频说的 sys_open，实测发出去的是 openat

**视频这条链上有一环名字对不上。** 应用写的是 `open`，glibc 发给内核的不是
open 的号。本机实测（2026-10-16）：

```bash
strace -f -e trace=open,openat -o to.txt ./dup2_printf z.txt
grep -c "open(" to.txt; grep -c "openat(" to.txt
```

```text
open=0
openat=3
```

一个 `open(` 都没有，全是 `openat(`。ARM 侧 2026-09-14 反汇编也验过：
glibc 装进 r7 的号是 **322（openat）** 不是 5（open）——

```text
#define __NR_open   (__NR_SYSCALL_BASE + 5)
#define __NR_openat (__NR_SYSCALL_BASE + 322)
```

为什么改用 openat：它能表达 open 表达不了的东西："相对于某个已打开的目录
fd 解析路径"；`open(path)` 只是 `openat(AT_FDCWD, path)` 的特例，内核让两套
共用后面的路径解析。**视频没有讲错，它讲的那版内核之后又改了。**
实际影响：strace 抓文件打开要 `grep openat`；在内核里下断点别背教程函数名，
以板子的 4.9.88 源码为准。

### 1.8 [判] 第 1 节的判据

    [ ] 说得出 fd 为什么是下标不是指针（指针给出去没法验证）

    [ ] /proc/<pid>/fdinfo 里 dup 出来的 fd 与源 fd 的 pos 相同

## 2 read / write 的真相

### 2.1 第一性原理：返回值是"实际做成了多少"

```c
ssize_t read (int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);
```

返回值是**这次实际搬了几个字节**，可以小于 count，而且**小于不是错误**。
count 是你的愿望，能不能满足取决于对面：

    read  少读:  文件读到末尾 / 管道里暂时只有几个字节 / 信号打断
    write 少写:  管道或 socket 缓冲满 / 磁盘满 / 信号打断

实验 `Knowledge/labs/04_file_io/pipe_rw.c`，本机实测（2026-10-16）：

```text
read(要 100) 实际返回 5
write(要 1048576) 实际返回 4096
```

（管道容量本身实测 65536 字节，见 `pcap` 探针，教程 3.2 的缓冲计数也是它；
非阻塞大写入实际走多少受内核分页策略影响，**别把某个具体数背下来**，
要背的是"小于 count 不是错误"。）

所以正确写法只有两种：要么检查返回值等于你要的量、不等当错误；
要么循环直到搬完。对普通文件前者够用（除非磁盘满总是全写）；
对面是管道、socket、串口时必须用后者。第 08 章网络正面撞上。

读的一侧还有个细节：

```c
len = read(fd, buf, sizeof(buf) - 1);   /* 为什么 -1 */
buf[len] = '\0';                        /* 因为这里要放结束符 */
```

`read` 不补 `'\0'`，它只搬字节。少这个 `-1`，`buf[len]` 就写出一格。

### 2.2 [做 L2] O_APPEND 和 lseek+write 不是一回事

两个进程同时追加一个日志。写法 A `open(O_APPEND)` 后循环 write；
写法 B 每次 `lseek(fd, 0, SEEK_END)` 再 write。实验程序是
`Knowledge/labs/00_basics/02_fd_and_vfs/append.c`：

```bash
N=2000
./app a.txt append $N & ./app a.txt append $N & wait
stat -c %s a.txt                     # 期望 2 * 2000 * 17 = 68000
```

本机实测（2026-09-14，各 5 轮）：

```text
append 版:  68000  68000  68000  68000  68000     每次一字不差
seek   版:  46325  38964  34085  49062  45305     每次不同,每次都少
```

板上复跑同构（2026-09-14，tmpfs 与 eMMC 各 5 轮）：append 全部 68000，
lseek 版 67898~67983 不等。原因在 [fundamentals/08](../../fundamentals/08_文件描述符与VFS.md)
3.3 节：`O_APPEND` 让内核把"定位到末尾"和"写"放进同一把锁，是**一个**原子
操作；`lseek`+`write` 是**两个**系统调用，中间那一瞬别人插进来，你手里那个
"末尾"就过期了。Project 的日志文件用 `O_APPEND`，理由就是这条实测。

### 2.3 [做 L1] lseek 到中间写：覆盖，不是插入；空洞：两个"大小"

实验 `Knowledge/labs/04_file_io/wp.c`（`lseek` 到偏移 3 写 "123"）：

```text
写前   abcdefghijklmnopqrst    21 字节
写后   abc123ghijklmnopqrst    21 字节      (2026-10-20)
```

**覆盖，不是插入**，长度一个字节没变。文本编辑器在文件中间插一个字符必须
整个文件重写，因为底下没有任何系统调用能"插入"。

既然只能覆盖，"跳过中间写到很远"当然不会把中间填上，这就是空洞。
实验 `Knowledge/labs/04_file_io/hole.c`（写 4 字节，lseek 到 1 MiB，再写
4 字节），**在 WSL 原生目录跑**：

```text
ls -l  逻辑大小 = 1048580
du -h  实占     = 8.0K
stat            = 1048580 字节, 16 个 512B 块
空洞里读出来     全 0                     (2026-10-16, ext4)
```

没写过的区域叫**空洞**：文件系统没给它分配块，读它得到 0。
`/mnt/e`（NTFS）上跑同一程序，du 会显示 1.1M，空洞被老老实实写成了 0
（2026-09-14 实测），**这是文件系统能力差异，WSL 没有 bug**。板上 eMMC
ext4 已验：逻辑同为 1048580，实际分配 4096 字节（2026-09-14）。

### 2.4 [做 L3] 自己写一个 copy

实验程序 `Knowledge/labs/04_file_io/mycopy.c`（完整参考答案）。
要求五条：参数检查、失败用 `perror`、**处理少读少写**（2.1）、目标用
`O_WRONLY|O_CREAT|O_TRUNC` + mode 0644、两个都 close。判据：

```bash
head -c 8388608 /dev/urandom > big.bin
./mycopy big.bin copy.bin && cmp big.bin copy.bin && echo SAME
./mycopy /etc/hostname hx.txt && cat hx.txt
: > empty.bin && ./mycopy empty.bin e2.bin && ls -l e2.bin
```

本机实测（2026-10-16）：`SAME`；hostname 内容照拷；空文件拷出 0 字节。
**判据的关键是 `cmp` 不是"看起来对"**：拷贝程序最典型的 bug 是最后不满一个
缓冲区的那段丢了，文本文件肉眼看不出，`cmp` 一比就出。

### 2.5 mode 和 umask：0777 传下去不会原样落地

`open` 带 `O_CREAT` 的第三个参数是**请求**权限，落地的是 `mode & ~umask`。
实验 `Knowledge/labs/04_file_io/mode.c`，本机实测（2026-10-16，umask 0022）：

```text
新建 0777      -> 755        0777 & ~022
已存在写 0600  -> 755        没变
已存在写 0777  -> 755        仍没变
```

**文件已存在时 mode 根本不看**，连报错都不报。视频 4_4-3 在这里试了三次才
承认。这条有安全含义：你用 `open(path, O_WRONLY|O_CREAT, 0600)` 存私密数据，
若 path 已被别人以 0666 建好，数据就落进人人可读的文件。要真的保证，
用 `O_EXCL`（已存在就失败）。四种常见开法：

| 组合 | 语义 |
|---|---|
| `O_RDONLY` | 只读，文件必须已存在 |
| `O_WRONLY\|O_CREAT\|O_TRUNC` | 不存在就建，存在就清空。**建新文件用这个** |
| `O_WRONLY\|O_CREAT\|O_APPEND` | 不存在就建，存在接着末尾写。**日志用这个** |
| `O_WRONLY\|O_CREAT\|O_EXCL` | **必须不存在**，已存在就失败。用来抢锁 |

### 2.6 [做 L1] 让 open 失败，看清 errno

实验 `Knowledge/labs/04_file_io/o.c`，本机实测（2026-10-16）：

```text
打开不存在的文件        fd= -1 errno= 2 No such file or directory
用 O_RDWR 打开一个目录   fd= -1 errno=21 Is a directory
用 O_RDONLY 打开一个目录 fd=  3 errno=21 Is a directory   ← 注意这行
O_CREAT|O_EXCL 打已存在  fd= -1 errno=17 File exists
用 O_WRONLY 打 444 文件  fd= -1 errno=13 Permission denied
```

**第三行是坑 4 的活证据**：open 明明成功了（fd=3），errno 却是 21，那是
上一次失败留的残值。**errno 只在函数确实失败之后才有意义，成功的调用不会
把它清零。永远是先判返回值，再看 errno。**

最后一行是视频 4_4-2 结尾的现场：权限在 `open` 那一刻检查，不是 read/write
那一刻。open 成功后当场 `chmod 000` 甚至 `unlink`，已有的 fd 照样能读写完
整文件（2026-09-14 实测：unlink 后 read 仍得 ABCD）。这是三张表的直接推论：
fd → struct file → inode，**这条链上没有文件名**。它同时解释：删掉一个正被
写的大日志文件，`df` 的空间不变回来，inode 上还挂着打开的引用。

报错三种写法选一种：`printf("%d", errno)`（要查表，不推荐）、
`strerror(errno)`（自己拼上下文，写库用）、`perror("open")`（最省事，固定打
到 stderr）。

### 2.7 [做 L3] 综合实验：处理一个 CSV 表格

PDF 那个空标题 4.3 的全部内容就是视频 4_4-6。这是本章唯一的"真实任务"：
`open/read/write` 只占十几行，剩下全是数据处理。视频结尾说得对：
**"open、read 本身并不重要，重要的是你处理数据的逻辑。"** 但恰恰是这些
"不重要"的地方藏着三个坑。

输入用资料仓 `05_process_excel/score.csv`（93 字节，**只拷 csv，不要拷
process_excel.c，那是答案**）。参考答案在
`Knowledge/labs/04_file_io/csvproc.c`。任务规格：

    ./csvproc <输入.csv> <输出.csv>
    - 逐行读/逐行处理/逐行写,不许一次读进整个文件
    - 表头行原样输出;数据行补上总分与评价(>=270 A+, >=240 A, 其余 B)
    - 输出行尾统一 CRLF,保留文件开头的 BOM

先搭框架再填函数（先定接口，你才有机会发现"读一行"的返回值不够用）：

```c
while (1) {
    len = read_line(fd_in, line, sizeof(line));   /* 读一行 */
    if (len < 0) break;      /* <0 才停 */
    if (len == 0) continue;  /* 0 是空行,继续 */
    process_line(line, result);
    write(fd_out, result, strlen(result));
    write(fd_out, "\r\n", 2);
}
```

**坑 1：行尾是一个字节还是两个，只能看，不能猜。**
视频里用十六进制工具翻出行尾是 `0D 0A`（Excel 存的 CRLF）；资料仓这份实测
（2026-10-16，`hexdump -C score.csv`）**只有 `0a`**，进 git 仓库时被转成了
Unix 行尾。结论是**行尾不能假设**，两个都要判：
`if (c == '\n' || c == '\r')`。只判 `\n` 的话 CRLF 文件每行末尾多一个 `\r`，
它是"回到行首"，printf 打出来看不出异常，你只会觉得"怎么少了几行"。
**看不见的字节只有 hexdump 能告诉你。**

**坑 2：第一行开头那三个字节。** 认表头写 `line[0] == ','` 不成立——

```text
00000000  ef bb bf 2c ...      BOM 在逗号前面
```

`ef bb bf` 是 UTF-8 的 BOM，Excel 存 UTF-8 时加的，cat 看不见、wc -c 算进
长度。判断要认这三个字节，且**必须转 unsigned char**：

```c
if ((unsigned char)line[0] == 0xEF && (unsigned char)line[1] == 0xBB
    && (unsigned char)line[2] == 0xBF)
```

`char` 有没有符号是平台实现定义的：x86 上 `char c = 0xEF` 是 -17，
`c == 0xEF` 恒为假；ARM 上默认无符号，判得出来（板上 7.6 节实测）。
**一个平台写对了不等于另一个平台对。** `file score.csv` 会直接告诉你
`UTF-8 (with BOM)`。

**坑 3：`sscanf("%s")` 会把整行吞掉。** 拆 `张三,90,91,92,,`，第一反应
`sscanf(line, "%s,%d,...")` 里 `%s` 的停止条件是**空白字符**，逗号不是，
它一路吞到行尾，后面三个 `%d` 全落空（本机实测 name 得到整个数据行）。
换成 `%[^,]`："读到逗号为止"：

```c
sscanf(line, "%99[^,],%d,%d,%d,", name, &s0, &s1, &s2);
```

**"读一行"的返回值怎么设计**——三种情况塞进一个 int：

```text
> 0   读到了这一行的字节数
  0   空行(连着的换行),不是错误,继续读
< 0   文件读完(且手里没有半行)或出错
```

关键在中间那种：把"读到 0"也当结束的话，文件里有一个空行就会提前停掉，
后面数据全丢。所以循环里必须 `<0 break` 和 `==0 continue` 两条，不能合成
`<=0 break`。另一种边界：最后一行没有换行就到了 EOF，手里攥着半行，
要先交出去，下一次调用再报 EOF。

**这两个分支，score.csv 一条都测不出来**（它行尾干净、没有空行）。自己造
两个输入把路径逼出来：

```bash
perl -pe 's/\n/\r\n/' score.csv > crlf.csv      # 行尾换 CRLF(别用 sed:它按行处理)
printf '\xEF\xBB\xBF,a,b,c,d,e\n\xE7\x94\xB2,1,2,3,,' > nonl.csv   # 末行无换行
```

本机判据实测（2026-10-16）：

```text
./csvproc score.csv out.csv   -> 110 字节;行尾 0d 0a;BOM 保留;273/A+/243/A/213/B
./csvproc crlf.csv o1.csv     -> 4 行
./csvproc nonl.csv  o2.csv    -> 2 行
```

**别拿资料仓的 result.csv 当金标准**：它 106 字节，与正确输出差的 4 字节
正是 4 个 `\r`，仓库那份预期输出也被转过行尾。**预期文件要先确认没被
转换过才能当判据。**

注错见红（本机实测，2026-09-14 注，基线 110）：

```text
行尾只写 \n          106 字节   少 4 = 4 行各少一个 \r
用 %s 不用 %[^,]     208 字节   数据行整行塞进 name,三个 %d 落空
不认 BOM             每次不一样  表头被当数据行,sscanf 失败,
                                scores[] 是栈上残值——"红的形状每次不同"
                                说明踩到未初始化变量(补 sscanf != 4 判定即红)
```

**两个"注错不红"**（都出在输入上，2026-09-14 实测）：把 read_line 改成 EOF
直接丢半行，score.csv 仍 110 全绿，nonl.csv 从 2 行掉到 1 行才红；把主循环
改 `<=0 break`，score.csv 仍 4 行全绿，crlf.csv 掉到 1 行才红。**判据的
输入必须覆盖它声称覆盖的边界**；写判据先问"哪种输入会让它失败"，答不上来
这条判据多半是摆设。

### 2.8 [判] 第 2 节的判据

## 3 标准 IO 那层 buffer

### 3.1 第一性原理：进一次内核很贵，所以先攒着

`printf` 不是系统调用，`write` 才是，中间隔着 C 库一块 4096 字节的缓冲：
printf 把文本复制进缓冲就返回；攒满 4096，C 库才 `write(1, buf, 4096)` 进
一次内核。一次系统调用要保存现场、切特权级、走 VFS、再恢复，攒着发一次
比发几百次便宜得多。

### 3.2 [做 L1] 用 strace 把这件事数出来

实验 `Knowledge/labs/04_file_io/buf.c`（循环 printf 1000 行，共 8890 字节）。

```bash
gcc -Wall buf.c -o buf
strace -f -e trace=write -o tf.txt ./buf > out.txt      # 输出到文件
strace -f -e trace=write -o tp.txt ./buf | cat > /dev/null
script -q -c "strace -f -e trace=write -o tt.txt ./buf" /dev/null   # 假终端
grep -cE '(^|[0-9]+ +)write\(' tf.txt    # 数次数
```

- `-e trace=write` 只跟 write；`-f` 跟 fork 出的子进程，**加了 -f 行首多一个
  pid**，数行数的正则必须是 `(^|[0-9]+ +)write\(`，写 `^write(` 会数成 0。
- `script -q -c "命令" /dev/null`：给命令造一个假终端测"输出到终端"。

本机实测（2026-10-16）：

| stdout 接到哪 | 缓冲方式 | write 次数 |
|---|---|---:|
| 文件 | 全缓冲 | **3** |
| 管道 | 全缓冲 | **3** |
| 终端 | 行缓冲 | **1000** |

3 能对账：三次 write 长度 4096 + 4096 + 698 = 8890 = 输出总字节。
行缓冲那 1000 次，每次正好一行。**这是本章最硬的判据：计数型，还能和总
字节数对账。**

### 3.3 三种缓冲方式，谁决定用哪种

```text
无缓冲  _IONBF  每次调用立刻 write            stderr 恒定是这个
行缓冲  _IOLBF  遇 \n 或攒满才 write           stdout 接终端时
全缓冲  _IOFBF  攒满才 write                   stdout 接文件/管道时
```

**谁接在后面是 C 库在 main 之前自己探测的**：对 stdout 调一次 `isatty(1)`。
所以同一个程序，`./prog` 和 `./prog > log` 的输出时机完全不同，重定向到
文件后日志"延迟"就是这个。想自己定用 `setvbuf(stdout, NULL, _IONBF, 0)`，
必须在这个流任何 IO 之前调。

### 3.4 [做 L1] 崩溃时，缓冲里的数据会丢

实验 `Knowledge/labs/04_file_io/crash_stdio.c`：printf 一行、fprintf(stderr)
一行、然后 abort。本机实测（2026-10-16，`> c_out.txt 2> c_err.txt`）：

```text
退出码 = 134            134 = 128 + 6 (SIGABRT)
c_out.txt = 0 字节      printf 那一行没了
c_err.txt = to stderr   stderr 那一行在
```

stdout 接文件是全缓冲，那行还压在用户态缓冲里，进程被信号打死这块内存就
没了；stderr 恒定无缓冲，fprintf 当场变成 write。**这就是日志要走 stderr
的原因**：掉电、段错误、看门狗复位三种情况下 stdout 的最后几 KB 全拿不回。
Project 的日志走 stderr 是这条实测，不是习惯。

三层"落盘"别混：`fflush(fp)` 只把 C 库缓冲交给内核；`fsync(fd)` 让内核把
脏页真写磁盘；`O_SYNC` 打开时就要求每次 write 等落盘，最慢。FILE* 想真落盘
两个都要调，先 `fflush` 再 `fsync(fileno(fp))`。

### 3.5 为什么访问驱动不能用标准 IO

三条理由，全是上面的推论：**时机不可控**（写一帧图像要"现在就写"，全缓冲
变成"攒够 4096"）；**没有 ioctl**（分辨率/波特率全靠 `ioctl`，FILE* 接口
里根本没有，`fileno(fp)` 抠 fd 不如一开始就用 fd）；**缓冲会切碎数据**
（驱动的 write 常有语义边界，一次 write 一帧/一条命令，攒 4096 会粘包或
切包）。规矩：**碰 /dev 下的东西一律 open/read/write/ioctl/close。**
第 05 章的 framebuffer、第 11 章的串口全按这条来。

### 3.6 [判] 第 3 节的判据

    [ ] printf 1000 行:输出到文件 write 3 次、终端 1000 次、管道 3 次
    [ ] 三次 write 长度 4096+4096+698=8890,与输出总字节对上账
    [ ] abort 后 stdout 0 字节、stderr 那行在,退出码 134
    [ ] 说得出 fflush 和 fsync 各管到哪一层
    [ ] 说得出设备不能用标准 IO 的三条理由

    注错见红:printf 循环前加 setvbuf(stdout, NULL, _IONBF, 0),
    输出到文件的 write 次数从 3 变 1000——"3"完全来自那层缓冲。

## 4 mmap

### 4.1 第一性原理：把那次拷贝去掉

read 一次，数据走两段：磁盘→页缓存，页缓存→你的 buf（内核替你做的一次
memcpy）。mmap 的想法：**页缓存本来就是内存，让指针直接指过去。**

```c
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
```

| 参数 | 给什么 | 管什么 |
|---|---|---|
| addr | 一般 NULL | 映射到哪；NULL 让内核挑 |
| length | 文件大小（fstat 查） | 映射多长 |
| prot | PROT_READ / PROT_WRITE | 这段内存能读能写 |
| flags | MAP_SHARED / MAP_PRIVATE | 写进去算不算数（[fundamentals/09](../../fundamentals/09_虚拟内存与mmap.md)） |
| fd / offset | 已 open 的 fd / 0 | 映射谁；offset 必须页对齐 |

返回指针，当普通内存用；失败返回 `MAP_FAILED`（不是 NULL）。**调用返回时
一个字节都还没读**，真正的读发生在第一次访问触发缺页时（fundamentals/09
的主题）。原书这一章没讲 mmap，但第 05 章 framebuffer 上来就要用。

### 4.2 [做 L2] 数一数系统调用，也数时间

实验 `Knowledge/labs/04_file_io/cp_rw.c`（`-DUSE_MMAP` 编出 mmap 版）。
8 MiB 文件各拷一遍（2026-10-16）：

```text
cp_rw    read+write 共 4098 次   (2048 满读 + 1 次读到 0 + 2048 写 + 1 次加载器读 ELF)
cp_mmap  2 次                    (1 次加载器 + 拷贝本身 1 次 write)
cmp 两者一致
```

系统调用差 2000 倍。**时间呢？** 本机实测三轮：9/9、9/8、10/8 ms，
**看不出稳定差别**。这个规模下真正的开销是搬 8 MiB 数据本身，系统调用
省下的零点几毫秒淹没在搬运噪声里。**"次数少 2000 倍"和"快 2000 倍"是
两回事**：报次数容易，报时间要真去测，两个数不会自动互相印证。
mmap 真正赢的场景是随机访问大文件：read 要 lseek+read 两趟换一小块，
mmap 就是一次解引用。

### 4.3 三个边界

**空文件不能映射**：length 0 返回 MAP_FAILED，errno EINVAL（cp_mmap 没处理
这一支，拷空文件直接报错，资料仓原版同样）。**映射按页取整，文件不按**：
5000 字节的文件映射到 8192，超出部分读 0、写不进文件。**摸出末尾所在页之外
是 SIGBUS**（实验 `Knowledge/labs/00_basics/03_vm_and_mmap/sigbus.c`，
板上 2026-09-14 实测）：

| 访问 | 位置 | 结果 |
|---|---|---|
| p[0] | 文件内 | 'a' |
| p[100] / p[4095] | 第一页内、文件外 | 0，不报错 |
| p[5000] | 第二页，整页在文件外 | Bus error，退出 135 |

135 = 128+7（SIGBUS），**见到 SIGBUS 先怀疑映射长度**，它和 SIGSEGV 是
两种毛病。

### 4.4 [判] 第 4 节的判据

    [ ] cp_rw 4098 次 / cp_mmap 2 次,cmp 都一致,说得出 4098 怎么凑的
    [ ] 计时说得出"次数差 2000 倍,时间看不出稳定差别"
    [ ] 空文件 mmap 返回 MAP_FAILED(EINVAL);越末尾页是 SIGBUS(135)

    注错见红是一条"故意不红":把 cp_mmap 的 MAP_SHARED 改成 MAP_PRIVATE,
    拷贝结果不变、判据全绿——只读映射时两者确实没差别。判据覆盖不到哪里,
    自己要知道;验那个差别得另写"往映射区写、别的进程读"的程序
    (labs/00_basics/03_vm_and_mmap/shared_private.c,板上已验)。

## 5 落进 Project：日志能落到文件了

板子上只有一根串口，日志刷过去就没了。本章给 Project 加一个函数
（`Project/common.c`，声明在 `include/common.h`）：

```c
int log_redirect(const char *path, int *os_errno);
```

设了环境变量 `LOG_FILE`，main 就调它，之后所有日志落进那个文件；没设照旧
打到终端。四个设计决定，每一个都来自本章：

1. **只改 stderr 的去向，不给每层加日志参数**（`dup2(fd, STDERR_FILENO)`，
   六层日志代码一行不改）。选它而不是"每层都知道日志文件"，理由和 1.5 的
   dup2 一样：printf/LOG 认的是数字 2，改 2 号槽指向谁就够了。
2. **`O_APPEND` 不是 `O_TRUNC`**（2.2 的原子性实测）。多进程写日志时
   lseek+write 会互相覆盖。
3. **日志走 stderr 不走 stdout**（3.4 的崩溃实测，掉电时 stdout 缓冲全丢）。
   判据有守门人：把 `fprintf(stderr` 改成 `stdout` 判据必须红（`[6r2]`）。
4. **项目错误码和 errno 分开传**：`ERR_IO` 回答"哪类操作失败"，`int
   *os_errno` 带出"这次系统调用为什么失败"。dup2 失败后先存 errno 再
   close(fd)（close 也可能改 errno）：先保存失败现场，再做清理。

## 8 已知的坑

    坑 1  不要在 /mnt/e 下做稀疏文件和 mmap 实验:NTFS 没有稀疏,
          du 会显示 1.1M,结论整个反过来。在 WSL 原生目录(~)做。          (2.3)

    坑 2  strace -f 之后行首多了 pid,数系统调用的正则要写
          grep -cE '(^|[0-9]+ +)write\('。写 ^write( 会数成 0,
          差点得出"终端下 printf 一次系统调用都不发"的结论。             (3.2)

    坑 3  LOG_FILE=x strace ./prog 把变量给了 strace。要给被跟踪的程序设
          变量,写成 strace ... env LOG_FILE=x ./prog。                  (5.1)

    坑 4  errno 只在失败之后才有意义,成功调用不清零。
          本篇 2.6 第三行就是活证据:open 成功 fd=3,errno 还是上一次
          失败的 21。先判返回值,再看 errno。                            (2.6)

    坑 5  mmap 失败返回 MAP_FAILED((void*)-1)不是 NULL,
          写 if (p == NULL) 永远判不出来。                               (4.3)

    坑 6  strace 里 grep 'open(' 什么都抓不到——实际发的是 openat。
          要么 grep openat,要么 -e trace=%file。写判据时这一条会静默
          把计数变成 0。                                                (1.7)

    坑 7  line[0] == 0xEF 在 x86 上恒为假(char 有符号,0xEF 是 -17),
          在 ARM 上却是对的(默认无符号)。两边都已实测。凡拿 char 和
          大于 0x7F 的常量比较,一律先转 unsigned char。                 (2.7)

    坑 8  tar 解包失败时,已经解出来的文件还留在那里。上传报 MISMATCH
          就停,不要接着解包"试试看";判据要比对退出码和完整输出。
          (2026-09-14 真实事故:包尾损坏,其余实验全对,只有包里最后的
          sigbus 一上来就段错误,被"退出 135"那条判据拦住。)             (6)

## 9 这一章交出了什么

现在能独立做到：

- 用 fd 与三张表解释 open 两次、dup、fork 之后"共享到哪一层"
- 正确处理短读短写：返回值小于 count 不是错误，循环到搬完或分情况判断
- 用 lseek 覆盖写、看懂空洞的两个"大小"，并说得出 ext4 与 NTFS 的差别
- 用 dup2 把 printf 重定向进文件，用 O_APPEND 保证多进程追加不互相覆盖
- 说得出标准 IO 三种缓冲各在什么条件下生效，以及崩溃时哪些日志会丢
- 用 mmap 建立映射，解释 SIGBUS 与 MAP_SHARED/PRIVATE 的差别
- 用 strace 数系统调用，看出 open 实际发的是 openat

还不能做：

- 自己写 VFS、文件系统或驱动（第 2 阶段）
- socket 的阻塞、粘包与并发（第 08 篇）
- 内核 writeback、IO 调度的细节（不展开）

这一章在整机里的位置：它是后面所有设备访问的手脚。05 篇用它开 `/dev/fb0`，
07 篇用它读 `/dev/input/eventX`，08 篇 socket、10 篇 I2C、11 篇串口同一套；
Project 的日志落文件、录像写盘也走这里。
