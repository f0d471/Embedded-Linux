# Knowledge：知识库

仓库的重心。三部分各管一件事：

| 目录 | 收录范围 | 维护方式 |
|---|---|---|
| [tutorials/](tutorials/) | 教程主线。`01_应用编程/` 00～11 篇，`02_驱动开发/` 待写 | 一章一篇；每完成一篇，在 Engineering/Todo/学习与项目路线.md 勾状态 |
| [fundamentals/](fundamentals/) | 前置知识与速查清单：一个名词一篇讲透，成堆的选项、标志位、函数表在这里集中保存 | 用到才加；索引与体例见 fundamentals/README.md |
| [labs/](labs/) | 实验源码与判据脚本 | 按教程章号建目录，check.sh 自动核对 |

三者的关系：教程回答"这件事为什么存在、怎么一步步做出来"；fundamentals 回答
"这个名词到底是什么""这个选项有哪些"；labs 回答"做没做对"，由机器判定。

本目录的全部内容都是自己的陈述：讲的是事物本身，依据是本机或板上的实测、
Linux 内核源码、man 手册、芯片数据手册与标准文档。不写"某某资料里说"。

## 一、写给谁

读者的起点按最低处算：会用终端敲命令，写过一点 C，但没碰过交叉编译、内核、
设备文件。读者的目标是自己能从零重新推出每一章的结论，而不是记住结论。

由此定下全库的总原则：**一次只加一块积木，每一块都从上一块自然推出来。**
读者读到任何一句，都应该能说出"这句话是从前面哪句推过来的"；如果说不出，
就是写跳了。

## 二、讲解的写法（tutorials 与 fundamentals 共用）

### 2.1 推进方式：问题链

每一节从一个问题开始，这个问题必须是上一节的结论自然引出来的。写法上就是
在节首用一两句话把这条线接上：

    上一节：hello_arm 在电脑上运行，报 Exec format error。
    这一节的问题：是谁拒绝了它？凭什么判断它"格式不对"？

一节只回答一个问题。回答完，在节末写"这一节搭好的积木"：一两句话说清现在
多知道了什么，以及它马上会引出的下一个问题。

不允许的写法：节首直接甩一张总表、一串名词或一条结论，再回头解释。总表和
总结放在讲透之后。

### 2.2 一块新积木的五步

一个新概念（或一个新机制）第一次出现时，按这五步讲，不省略：

    1. 现象    先让读者看见它：一条命令、一段输出、一个报错。
    2. 身份    它真实是什么：一个文件、一段内核代码、一个寄存器、一条约定。
               按真实构造描述，比喻至多一句作辅助。
    3. 必要性  没有它会怎样。从"如果没有"推出"所以必须有"，读者才会觉得
               这个东西是被逼出来的，而不是凭空规定的。
    4. 机制    它怎么工作，一步一步写，中间步骤不省。
    5. 回扣    回到第 1 步的现象，用刚讲的机制把它完整解释一遍。

### 2.3 不跳步

- 推导里每一步都写出来，包括看起来显然的那一步。"显然""不难看出""记住即可"
  "后面会讲"不能出现在论证里。
- 一个结论依赖的前提，必须在它之前讲过；没讲过的，就地讲。
- 数字要算给读者看：115200 波特为什么是每秒 11520 字节，写出 10 位一字符那一步。
- 引用前文时写清是哪一节的什么结论，不只写"如前所述"。

### 2.4 就地讲透，深入再跳

教程里出现一个前置名词（ELF、系统调用、sysroot……），先在正文里用几段话讲到
"读者能顺着往下读"的程度：它是什么、在本章起什么作用。想彻底弄懂的，再给一个
fundamentals 链接。不能只留一个链接让读者去别处补课再回来。

### 2.5 命令与输出

每条命令按四步写：

    要回答的问题    这条命令是为了看清什么
    命令本身        完整给出；每个参数第一次出现时用注释说明它在管什么
    真实输出        本机或板上实跑的原样输出，标注日期与环境
    逐行读          输出里看哪一行、哪一列，它说明了什么，和前面哪个数对得上

命令和代码一律完整给出，不留"自己想"的空白。能跑的实验代码放 labs/ 对应章目录，
正文里贴出并逐行讲。代码块后面的讲解要覆盖到读者可能卡住的每一处：声明、
循环的三段、赋值方向、标点的作用，第一次出现时都讲。

### 2.6 文字量

不吝啬文字。描述、分析、解释都写出来，宁可多一句让读者确认"我理解对了"，
也不要少一句让读者停下来猜。但不注水：每句话要么在描述现象，要么在推理，
要么在解释原因；同一件事不换个说法重复说。

### 2.7 常见误解

容易想错的地方就地澄清，写成"容易以为 X；实测是 Y；原因是 Z"。不写成
"某处说 X"。

### 2.8 语言

- 真实描述优先于比喻。
- 先讲行为，再给术语："输入是什么、执行后能观察到什么、失败时怎样"在前，
  名字和内部原理在后。
- 不用 emoji；不用破折号串句子；成稿后按去 AI 味的规则过一遍语言。

## 三、教程的章结构（tutorials/）

    章首元信息    实验目录与实测环境（日期、系统、编译器版本），不写别的
    读前须知      需要的底子（每条一句"为什么需要"）；不会也能读，正文会就地讲
    在整机里的位置  上接哪篇、下接哪篇、补的是整机的哪个零件
    不学它会怎样  一个具体现象或报错，读者在后续章节会亲眼遇到
    0 起点        本章从一个什么现象出发、最后要能解释什么。不提前给答案表
    1～N 正文     问题链，一节一个问题，节末"这一节搭好的积木"
    回看          把整章的问题链从头串一遍：每一步的问题、答案、证据在哪一节
    自检          每题都能用命令验证，标出对应小节
    已知的坑      现象、原因、在哪一节
    交出了什么    现在能做到的、还做不到的、下一章

00 篇是例外：它讲"这台机器是什么、我们要造什么、各章补整机的哪一块"，不写代码，
不套上面的结构。

## 四、实验、判据与数字

1. **判据跟着实验走。** 每个实验配 `[判]` 块，列出可以逐条打勾的检查项；
   每条都要能"注错见红"：故意改坏一处，判据必须失败。
2. **数字必须实跑。** 输出、体积、耗时、退出码一律来自本机或板上真跑，
   标注日期。板子不在线时沿用已归档的板上实测，不重跑、不编造、不改数字。
3. 实验强度分四级：

       L1 复现   跑通并观察现象，建立事实基础
       L2 改造   给定目标改现有代码，必须改出预期的可观测变化
       L3 从零写 自己写一段完整的程序
       L4 入项目 把这一层能力落进 Project/，加出一整层代码

## 五、配图

图最大的价值是画清边界：哪一步在内核里、哪一步在用户态、哪一步在编译期。

- 两个单元以内的线性关系可以画 ASCII（不用中文字符撑边框，换字体会错位）。
- 超过两排不同单元、带分支或分层的图一律做 SVG，放所在目录的 `fig/`，命名
  `<篇号>-<名称>.svg`，正文用相对链接引用。
- SVG 规范：白底，无渐变、无阴影、无装饰圆角；实线是会执行的通路，虚线是被拒绝
  或未接入的通路；颜色只承载一种语义且图内有图例；框内写代码里的真实名字；
  最小字号 9px；提交前用 Edge 无头渲染一次，确认无重叠、无裁切。
- 讲解型的图按推导顺序拆开：每张只比上一张多一个元素，跟着正文一步一步出现。

## 六、fundamentals

一套章节，文件名 `NN_中文名.md`，编号按教程用到的顺序排。它干两件事：

1. **讲透名词**：教程里出现、不属于本章主线、以后还会反复出现的通用名词，
   在这里有一篇从头讲到尾，写法同第二节。
2. **速查清单**：同一层次的罗列性内容（GCC 选项、make 语法与函数、open 标志、
   ioctl 请求码、信号表……）集中保存在每篇的"速查清单"一节，每条标注是否实测。

体例与索引的唯一出处是 [fundamentals/README.md](fundamentals/README.md)。
每篇配 `labs/00_basics/NN_xxx/check.sh`（清单型篇目视内容免），判据注错见红。

## 七、labs

目录按教程章号组织：`00_basics/`（fundamentals 配套）、`01_hello/`、`02_gcc/`、
`03_makefile/`、`04_file_io/`……与 tutorials 一一对应。

- 实验源码入库，编译产物一律不入（.gitignore 白名单），由 check.sh 或教程命令重建。
- 每个 check.sh 从源码重建一切再逐条核对，末尾打印 `N PASS / N FAIL / N SKIP`。
- 判据基线登记在根 README 进度节；判据变化的 commit 同步更新基线。
