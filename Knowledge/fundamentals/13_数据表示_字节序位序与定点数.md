## 0 先动手看一眼

一个程序把四层"同一串比特、不同规格"各打印一遍（本机实测，2026-10-21，
下同）：

```text
native bytes: 78 56 34 12
2d 4e as LE=0x4e2d as BE=0x2d4e
0x62 MSB-first: .##...#.
0x62 LSB-first: .#...##.
-1  bytes: ff ff ff ff
-33 bytes: df ff ff ff

26.6: one_pixel=64 ten_and_half=672 raw_672_floor=10 raw_672_round=11

```

同一排字节 `2d 4e`，按小端读是"中"，按大端读是另一个数；同一个 `0x62`，
两种位序画出来互为镜像；同一个 `0xd6`，按符号读是 -42、按无符号读是 214；
同一个 1536，按 26.6 读是 24 像素，按普通整数读大 64 倍。**裸数据不会自述
含义，全看拿哪份规格来解释。**本篇把这四份规格逐一拆开。

## 1 先把三个"序"拆开

> **地址顺序**：内存地址从小到大，或文件偏移从小到大。
> **字节序（endianness）**：一个多字节数拆开后，各字节按权重放进地址顺序
> 的办法。
> **位序（bit order）**：一个字节里的各 bit 对应空间位置或线上时间位置的
> 办法。

再加一个经常混进来的概念：

> **字符顺序**：文本里字符出现的先后。`A中` 永远先是 A 再是中，不会因为
> CPU 是小端就变成 `中A`。

用 UTF-16LE 保存 `A中`，四个内容字节是：

```text
字符顺序            A                     中
编码单元          U+0041                U+4E2D
小端拆字节         41 00                 2d 4e
文件偏移        0     1               2     3
```

小端只在每个 16 位编码单元**内部**交换权重，并没有把字符队伍倒过来。
UTF-8 更简单：它的最小组成单位本来就是字节，规范把字节顺序写死了，"中"
永远是 `e4 b8 ad`，所以不存在 UTF-8LE 和 UTF-8BE。

**这一节搭好的积木**：三个"序"层次不同、各管一段；字符顺序永远不受端序
影响。接下来逐层实验。

## 2 字节序：内存里只有字节

### 2.1 权重实验：同两个字节，解释出两个数

内存从低地址到高地址摆着两个字节 `2d 4e`。先想再跑：

1. 如果低地址字节权重是 2⁰（乘 1），结果是什么？
2. 如果低地址字节权重是 2⁸（乘 256），呢？
3. 这两个字节是不是自带"小端标签"？

第三问答案是否定的：内存里只有 `2d 4e`，解释规则在程序或文件格式手里。
`repr.c` 把权重明确写出来：

```c
little = p[0] | (p[1] << 8);   /* 低地址字节乘 2^0：小端 */
big    = (p[0] << 8) | p[1];   /* 低地址字节乘 2^8：大端 */
```

本机实测：

```text
2d 4e as LE=0x4e2d as BE=0x2d4e
```

小端读出 0x4e2d，正是"中"的 Unicode 码点；大端读出 0x2d4e，另一个数。
**同一排字节没有唯一答案，除非格式先告诉你端序。**处理外部字节流时就该
这样写（或用格式库的读取函数），不要把任意地址强转成 `uint16_t *`：那
会再引入未对齐访问、别名规则和宿主端序三个变量。

`0x12345678` 这个 uint32 落在本机内存里是 `78 56 34 12`（第 0 节首行）：
最低权重的 0x78 放在最低地址，x86-64 是**小端**。落盘用 xxd 实看：

```bash
xxd -p mem.bin
```

```text
78563412
```

### 2.2 编码文件里的字节序：iconv 实转

拿真正的转换工具验证第 1 节的推理（`iconv` 做编码转换，`xxd -p` 看十六
进制）：

```bash
printf 'A中' | iconv -f UTF-8 -t UTF-16LE | xxd -p
printf 'A中' | iconv -f UTF-8 -t UTF-16BE | xxd -p
printf 'A中' | iconv -f UTF-8 -t UTF-16   | xxd -p | cut -c1-4
printf '中'  | xxd -p
```

本机实测：

```text
41002d4e        UTF-16LE：A=41 00，中=2d 4e
00414e2d        UTF-16BE：A=00 41，中=4e 2d
fffe            UTF-16 默认带 BOM：小端声明
e4b8ad          UTF-8 的"中"只有一种排法
```

`A中` 两个字符的先后在四种输出里都没变（A 的字节总在前）；变的只是每个
16 位单元**内部**两字节的权重方向。UTF-16 的 BOM（`ff fe` / `fe ff`）就是
文件开头的端序声明；UTF-8 的 `ef bb bf` 只是"我是 UTF-8"的文件标记。

### 2.3 两个编译器：都小端，char 却不一样

板子是 ARM。用预定义宏直接问两个编译器（`-dM -E` 列出全部内置宏）：

```bash
arm-linux-gnueabihf-gcc -dM -E - </dev/null | grep -E "__BYTE_ORDER__|__CHAR_UNSIGNED__"
gcc -dM -E - </dev/null | grep -E "__BYTE_ORDER__|__CHAR_UNSIGNED__"
```

本机实测：

```text
#define __CHAR_UNSIGNED__ 1                        （ARM 这行有）
#define __BYTE_ORDER__ __ORDER_LITTLE_ENDIAN__     （ARM）
#define __BYTE_ORDER__ __ORDER_LITTLE_ENDIAN__     （x86-64，无 CHAR_UNSIGNED 行）
```

两个结论：**ARM 也是小端**（所以本仓的显存、文件格式在两边读法一致）；
但 **ARM 的 char 默认无符号、x86-64 的 char 默认有符号**：同一个
`char c = 0xd6`，在板子上是 214、在电脑上是 -42。跨平台代码要么别拿
char 存数（用 `int8_t`/`uint8_t` 明示），要么编译时加 `-fsigned-char`
钉死。这也是第 2.4 节补码实验把类型写得这么较真的原因。

**这一节搭好的积木**：端序只管多字节数的权重排放，文件与协议各自声明；
x86 与 ARM 都小端，char 符号性却不同。接下来的问题：一个字节**内部**
的 8 个 bit 有没有顺序。

### 2.4 注错见红

`-DBUG_ENDIAN` 把小端读取的两项权重对调：

```text
小端公式两项权重写反，U+4E2D 实得 [0x2d4e]
```

判据是"已知字节必须还原成已知码点"，一反就红。

### 2.5 [判] 第 2 节

    [ ] 0x12345678 的内存字节是 78 56 34 12；xxd 实看 mem.bin 一致
    [ ] 2d 4e 按小端是 0x4e2d、按大端是 0x2d4e
    [ ] iconv 实转：UTF-16LE 是 41002d4e、BE 是 00414e2d、BOM 是 fffe
    [ ] UTF-8 的中只有 e4b8ad 一种排法
    [ ] x86 与 ARM 预定义宏都是小端；__CHAR_UNSIGNED__ 只在 ARM 出现
    [ ] 注错见红：权重写反，码点判据变红

## 3 位序：点阵字模的约定

### 3.1 一个字节内部，没有"更低地址的 bit"

取字节 0x62：

```text
bit 编号     7 6 5 4 3 2 1 0
bit 值       0 1 1 0 0 0 1 0
```

这 8 个 bit 一起住在同一个字节地址里。"内存是小端"只讨论**多个字节**，
推不出把 bit 7 画在左边还是 bit 0 画在左边：那是字库规格单独约定的事。
HZK16 和内核 8x16 控制台字库都约定 **MSB-first**：bit 7 对应最左像素，
0x62 画成 `.##...#.`；循环若写成 `byte & (1 << x)` 就从 bit 0 起步，
画出镜像的 `.#...##.`。

### 3.2 亲手画一个 A：逐位展开

`repr.c` 里存着内核 8x16 字库 'A' 的前 12 行，逐字节按 MSB-first 展开，
标尺是 bit 编号：

```text
bit: 76543210
0x00 ........
0x00 ........
0x10 ...#....
0x38 ..###...
0x6c .##.##..
0xc6 ##...##.
0xc6 ##...##.
0xfe #######.
0xc6 ##...##.
0xc6 ##...##.
0xc6 ##...##.
0xc6 ##...##.
```

从上往下就是大写 A 的上半部：尖顶、展开的两臂、中间的横杠（0xfe 那行）、
两条竖腿。**同一批 0/1，按 MSB-first 一摆就成了字形。**验一行账：0x6c =
0110 1100，bit 5、4、2、1 为 1，对应左数第 2、3、6、7 格，即 `.##.##..`，
与输出一致。

### 3.3 为什么判据不能只画 A

大写 A 接近左右对称：把每行 bit 反过来，肉眼仍觉得它是 A；亮点总数更是
完全不变（0x62 两种画法都是 3 个亮点）。所以点阵判据要用不对称的样本
（06 篇的点阵实验用 `F` 抓方向）：

```text
正确 MSB-first      错误 LSB-first（镜像）
#######.            .#######
.##...#.            .#...##.
```

**输入没打到错误的敏感方向，程序错了判据也绿。**测试样本本身就是判据
设计的一部分。

**这一节搭好的积木**：字节内部无地址，位序由字库规格约定（HZK16 与内核
字库都是 MSB-first）；对称样本抓不住镜像，判据要用不对称字形。接下来的
问题：同一字节按"有没有符号"读，怎么差出 214 和 -42。

### 3.4 [判] 第 3 节

    [ ] 0x62 MSB-first 是 .##...#.，LSB-first 是 .#...##.
    [ ] 字库 'A' 逐位展开成 A 形；0x6c 行是 .##.##..
    [ ] 注错见红：恒从 bit 0 起步，0x62 判据变红（实得镜像图案）

## 4 补码：负数在内存里长什么样

### 4.1 -1 与 -33 的四个字节

把 -1 和 -33 两个 int32 按内存字节打出来：

```text
-1  bytes: ff ff ff ff
-33 bytes: df ff ff ff
```

这就是**补码**（two's complement）：负数用"取反加一"编码，-1 是全 1；
-33 = -1 - 32，只在最低字节少了 0x20（ff - 20 = df），高三位字节仍是 ff。
好处是硬件加法器不用区分加减：`a + (-b)` 和 `a - b` 是同一套电路。解读
规则随之确定：最高位是符号位，其余位按无符号读出来再减 2³¹（对 int32）。

### 4.2 同一个 0xd6，两种身份

```text
(int8_t)0xd6=-42 (uint8_t)0xd6=214
```

同一个字节 0xd6（二进制 1101 0110，最高位 1）：按 int8 读是负数，
256 - 214 = -42；按 uint8 读就是 214。**数据没有变，类型决定解释**：
这正是全篇的主题在"符号"维度上的再现。

### 4.3 两个容易踩的运算

```text
-33>>6=-1  u8:255+1=0
```

- **负数右移是算术右移**（高位补符号位 1）：-33 >> 6 得 -1 而不是 0。
  这恰好和第 5 节的 26.6 向下取整对上：负的定点数右移 6 位就是向负无穷
  取整。
- **uint8 的 255+1 绕回 0**：8 位装不下 256，高位截掉。教程 02 篇批 2
  实测过同一个现象（`b + 4'd1` 截断），那边是 Verilog，这边是 C 的
  无符号整数，规则同源：**模 256**。

**这一节搭好的积木**：负数按补码存放（-1 全 1）；符号性由类型决定；
负数右移即向下取整，无符号加法模 2ⁿ 绕回。接下来的问题回到 06 篇：
1536 凭什么打印成 24 像素。

### 4.4 [判] 第 4 节

    [ ] -1 的四个字节 ff ff ff ff；-33 是 df ff ff ff
    [ ] (int8_t)0xd6 是 -42，(uint8_t)0xd6 是 214
    [ ] -33>>6 得 -1（算术右移）；uint8 的 255+1 绕回 0

## 5 定点数：1536 为什么是 24 像素

### 5.1 定点数是被什么逼出来的

排版会遇到半像素：某个字的步进可能是 24.5 像素，旋转后的坐标很少恰好
落在整数上。只存整数，每个字后面丢一点，一整行累计明显漂移；用浮点，
字体库还要照顾没有快速浮点的老机器，而且多数几何操作只需要固定的小数
精度。FreeType 的选择是 **26.6 定点数**：

> **26.6 定点数**：一个有符号整数，低 6 位解释为小数，其余位是整数部分。
> 二进制点约定放在低 6 位之前，数值与像素之间相差 2⁶ = 64 倍。

```text
实际像素        26.6 保存的整数
1.0             64
10.0            640
10.5            672
24.0            1536
```

FreeType 的 `FT_Pos`/`FT_F26Dot6`、字段 `advance.x`、传给
`FT_Set_Transform` 的 `pen.x` 都是这种尺度。06 篇实测宋体 48 像素时
字母 A 的 `advance.x=1536`，一步正好 24 像素。

### 5.2 还原与取整

把 672 变回像素有两种需求：向下取整 10.5 → 10，四舍五入 10.5 → 11。

```c
floor = value >> 6;            /* 非负数：右移 6 位 */
round = (value + 32) >> 6;     /* 先加半个 0.5（32/64）再移 */
```

本机实测：

```text
26.6: one_pixel=64 ten_and_half=672 raw_672_floor=10 raw_672_round=11
26.6 negative: raw_-33_floor=-1 raw_-33_round=-1
26.6 advance: 1536>>6=24 6144>>6=96
```

负数要停一下。C 的整数除法向 0 截断，`-33 / 64 == 0`；几何里的 floor 是
向负无穷，`floor(-33/64) == -1`。`repr.c` 的负数分支
`-(((-value) + 63) >> 6)` 就是先按正数向上凑再翻回来。贴着左边界排字时，
这一个像素决定外框漏不漏最左一列。第 4.3 节的 `-33>>6=-1` 从硬件行为一侧
印证了同一件事：负数算术右移天然就是向负无穷取整。

真实尺度验两笔：06 篇量到的单字步进 `advance.x=1536`，`1536 >> 6 = 24`
像素；一整行所有字符的 advance 加起来 6144，`6144 >> 6 = 96` 像素，
对上行宽。

### 5.3 注错见红

两支注错各打一种手滑。`-DBUG_FIXED_100` 把 26.6 当成百分制：
672 四舍五入从 11 变成 7（`(672+50)/100`）。`-DBUG_TRUNC_DIV` 把负数取整
写成 C 除法：-33 向下取整从 -1 变成 0。两个判据都会当场变红：

```text
注错见红：把 26.6 错当百分制，672 四舍五入变成 [7]
注错见红：负数向下取整错写成 C 除法，-33 变成 [0]
```

**这一节搭好的积木**：26.6 = 整数 + 约定二进制点在低 6 位前，换算乘除 64；
负数取整必须避开 C 除法的向 0 截断。回答了开头第三问。

### 5.4 [判] 第 5 节

    [ ] 1 像素存成 64；10.5 像素存成 672
    [ ] 672 向下取整 10、四舍五入 11；-33 向下取整 -1 不是 0
    [ ] 真实 advance：1536>>6=24；一行 6144>>6=96
    [ ] 注错见红：错当百分制得 7；错用 C 除法得 0

## 速查清单

每条标依据。本机实测 2026-10-21（WSL，gcc 15.2.0 与交叉 gcc 15.2.0）。

**同一串位，四种规则**：

| 原始值 | 问题 | 规则 | 解释结果 |
|---|---|---|---|
| `0x4E2D` | 字节权重怎么排 | 小端 | 内存顺序 `2d 4e` |
| `0x4E2D` | 字节权重怎么排 | 大端 | 内存顺序 `4e 2d` |
| `0x62` | 哪个 bit 对应最左像素 | MSB-first | `.##...#.` |
| `0x62` | 哪个 bit 对应最左像素 | LSB-first | `.#...##.`（镜像） |
| `0xd6` | 有没有符号 | int8 / uint8 | -42 / 214 |
| 整数 1536 | 二进制点在哪 | 26.6 | 24 像素；按普通整数大 64 倍 |

**字节序与编码**（iconv 实测）：

| 编码 | 单位 | LE/BE | 实测（A中） |
|---|---|---|---|
| UTF-8 | 字节序列，前缀标长度 | 无 | `41 e4 b8 ad` |
| UTF-16LE | 16 位单元 | 有 | `41 00 2d 4e` |
| UTF-16BE | 16 位单元 | 有 | `00 41 4e 2d` |
| UTF-16（带 BOM） | 同上 | BOM 声明 | `ff fe` 开头 |

**补码**（第 4 节实测）：

| 表达式 | 结果 | 原因 |
|---|---|---|
| -1（int32） | `ff ff ff ff` | 取反加一的全 1 形态 |
| -33（int32） | `df ff ff ff` | -1 再减 0x20 |
| (int8_t)0xd6 | -42 | 最高位 1，按有符号读 |
| (uint8_t)0xd6 | 214 | 按无符号读 |
| -33 >> 6 | -1 | 算术右移 = 向负无穷取整 |
| (uint8_t)255 + 1 | 0 | 模 256 绕回 |

**定点数**：

| 格式 | 小数位 | 1 像素的原始值 | 换算 |
|---|---|---|---|
| 26.6 | 6 | 64 | `raw >> 6`（负数另行向下取整） |
| 16.16 | 16 | 65536 | `raw / 65536` |
| 8.8 / 24.8 | 8 | 256 | `raw / 256` |

**HZK16 与内核 8x16 字库**：一汉字 16x16 点 32 字节；行从上到下每行 2 字节
（8x16 每行 1 字节）；**每字节 MSB 对应最左像素**；HZK16 按区位码定位。

| 字符顺序会被端序打乱吗 | 不会；端序只管单元内部 | 1、2.2，iconv 四连 |
| 为什么没有 UTF-8LE | UTF-8 的单位就是字节，顺序写死 | 1、2.2，e4b8ad |
| 板子和电脑端序一样吗 | ARM、x86 都小端；但 char 符号性不同 | 2.3，预定义宏 |
| 字节内的 bit 有顺序吗 | 地址到不了 bit 内部；字库约定 MSB-first | 3.1、3.2，A 字模展开 |
| 镜像错误为什么测不出 | 对称样本两种位序都像样；要用 F 这类不对称字形 | 3.3 |
| 负数在内存里什么样 | 补码：-1 全 1；类型决定 0xd6 是 -42 还是 214 | 4.1、4.2 |
| 1536 为什么是 24 | 26.6 定点数，低 6 位是小数，右移 6 位 | 5.2，1536>>6 |
| 负坐标取整为什么不能随手除 | C 除法向 0，几何要向负无穷 | 5.2，-33 得 -1 |

---

## 带走

开头三个问题的答案：

1. **裸数据不自述含义。** 同一串位按字节序、位序、符号性、定点规则四种
   规格能解出四个答案（0x62/0xd6/1536 各有分身）；规格在文件格式、协议
   和类型里，不在数据里。
2. **字节序管多字节权重，位序管字节内比特，两者独立。** x86 与 ARM 都是
   小端，char 符号性却相反；UTF-8 无端序可言，UTF-16 靠 BOM 声明；字符
   先后永不受影响。判据要选不对称样本，否则镜像抓不住。
3. **26.6 是"整数 + 约定二进制点"。** 乘除 64 换算；负坐标取整要向负无穷
   （-33/64 = -1），C 的向 0 除法和它不是一回事；负数算术右移天然就是
   向下取整，补码让这套移位直通硬件。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `ff fe` / `fe ff` 文件头 | UTF-16 BOM，声明端序 |
| 码点 0x4e2d 变 0x2d4e | 字节权重放反了 |
| 点阵字能认但整字镜像 | 位序用反；换不对称字形测 |
| FreeType 坐标大了 64 倍 | 忘了 26.6 |
| 贴左边界差 1 像素 | 向下取整写成了 C 除法 |
| 同一字节时正时负 | char/int8 符号性；跨平台用固定宽度类型 |
| 网络字段读出怪数 | 先查协议端序，再查 ntohs/ntohl |
