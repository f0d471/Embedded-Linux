### 0.2 三处命令行，不是同一台机器

```text
你的 Windows 电脑
├─ 窗口 A：WSL Ubuntu（x86-64）
│    读 hello.c → 运行编译器 → 在 E 盘生成 ELF 文件
│
└─ 窗口 B：Windows PowerShell
     运行 serial-board.ps1 → 经 USB / COM8 发送文件或命令
                                      │
                                      ▼
开发板：Buildroot Linux（ARM）
     板上 shell 接收命令 → 板上内核加载程序 → 板上 CPU 执行
                                      │
                                      └─ 串口把文字输出送回窗口 B
```

| 本文标记 | 你打开什么 | 路径示例 |
|---|---|---|
| **A：WSL** | 一个 PowerShell 窗口进入 Ubuntu 后保持该窗口 | `/mnt/e/Workspace/embedded-linux` |
| **B：PowerShell** | 另一个 PowerShell 窗口，保持 Windows 环境 | `E:\Workspace\embedded-linux` |
| **板上执行** | B 中用脚本 `-Command '…'` 发送 | `/tmp/lesson01-20260906` |

A 的 `/mnt/e/Workspace` 与 B 的 `E:\Workspace` 指向同一份电脑文件。板上 `/tmp` 属于开发板，不在电脑的 E 盘里。经首次实测，它是 tmpfs，重启后需要重新上传实验文件。

不要复制命令提示符中的 `PS ...>`、`$` 或 `[root@100ask:~]#`；只复制代码块中的命令。

## 1. 建立能相信的操作环境

**先自己想：**怎样确认命令是在电脑上跑还是在板上跑？仅仅看到 Linux 提示符够不够？

### 第 1 步：确认当前串口号

**动机。** USB 插进去只说明物理连接。先确认 Windows 识别到串口，才能选对通信入口。

**在哪里、怎么写：B，Windows PowerShell。**

```powershell
Get-PnpDevice -PresentOnly -Class Ports
```

**命令组成。** `Get-PnpDevice` 查询即插即用设备；`-PresentOnly` 只列当前连接的设备，排除已拔走的历史记录；`-Class Ports` 限制为端口类别。`Ports` 是类别名，不是随便起的名字。

**看什么确认。** 找状态为 `OK` 的 `USB-Enhanced-SERIAL CH9102 (COM8)`。COM3、COM4 在首次会话中是蓝牙串口。COM8 是电脑分配的编号，换插孔后可能变化；若当前是其他编号，后面每条脚本调用加 `-Port COM实际数字`，把“实际数字”换成查到的数字。

**不符合时。** 没有对应设备，核对是否接的是板载 USB 转串口接口；未知设备或非 OK 状态先检查驱动和线缆。查询报“拒绝访问”时，可在 Windows 设备管理器“端口（COM 和 LPT）”查看。仅凭设备枚举还不能证明板上 Linux 已启动。

**对应原文。** [主线 §2.11][main]“第一步，串口连上板子”：先确定 PC 使用哪个串口。

### 第 2 步：需要时先登录板上 Linux

**动机。** 辅助脚本发送 Linux shell 命令，不会填写登录名。板子停在 `login:` 时，把 `uname` 发过去只会被当作用户名。

**在哪里、怎么做：Windows 串口终端。** 如果板子自首次演示后没有重启，可先做第 3、4 步；若脚本提示未找到 root shell，再回来。本步使用已安装的 MobaXterm 或 PuTTY，创建 Serial / 串口会话：

| 设置                        | 填什么            | 控制什么                        |
| ------------------------- | -------------- | --------------------------- |
| Serial port / Serial line | COM8，或第 1 步的编号 | 打开哪个 Windows 串口             |
| Speed / Baud rate         | 115200         | 传输速率，两端必须一致                 |
| Data bits                 | 8              | 每帧有效数据位数                    |
| Parity                    | None           | 不附加奇偶校验位                    |
| Stop bits                 | 1              | 每帧一个停止位                     |
| Flow control              | None           | 不等待未连接的 RTS/CTS 握手，也不使用软件流控 |

连接后等启动完成，按一次回车。看到 `100ask login:` 时输入 `root` 并回车；若出现 `Password:`，空密码直接回车。`root` 是登录名，不是 Linux 命令。

**看什么确认。** 出现类似 `[root@100ask:~]#` 的提示符，才表示进入 shell。乱码优先核对波特率；完全无输出同时检查供电、串口编号、接口、流控，不能全部归因于流控。

**下一步前。** 断开终端的串口连接，让出 COM8；不要输入 `exit` 退出板上登录。同一串口通常只能由一个程序占用。

**对应原文。** [主线 §2.11][main]串口参数表和 root 登录；PDF 第 96–99 页。此时只证明通信通了，未验证交叉编译。

### 第 3 步：窗口 B 进入脚本所在目录

**动机。** 后面的 `.\` 表示当前目录，先定位正确才能找到脚本。

**在哪里、怎么写：B，Windows PowerShell。**

```powershell
cd E:\Workspace\embedded-linux\labs\01_toolchain
```

**命令组成。** PowerShell 的 `cd` 是切换当前位置的命令别名；后面的绝对路径是目标文件夹。没有额外参数，不会移动或复制文件。

**看什么确认。** 提示符应变成 `PS E:\Workspace\embedded-linux\labs\01_toolchain>`。若路径不存在，核对 E 盘和目录拼写。

**对应原文。** [主线 §0.4][main]的实验目录；这是文件定位准备，不是编译。

### 第 4 步：让板子报告自己是谁

**动机。** 确认串口连接到能执行命令的 ARM Linux 板，而不只是 USB 串口芯片存在。

**在哪里、怎么写：B 输入，板上执行引号中的内容。**

```powershell
.\serial-board.ps1 -Command 'uname -m'
```

**命令组成。** `.\serial-board.ps1` 是当前目录中的 PowerShell 脚本；`-Command` 是脚本定义的参数，接要发送的 Linux 命令；外层单引号让 PowerShell 原样传递内部文字。板上 `uname` 查询系统信息，`-m` 只显示机器架构。脚本默认 COM8、115200 / 8N1 / 无流控。

**看什么确认。** 应有 `armv7l`。命令回显、`__DONE_一串字符__:0`、板上提示符是脚本通信信息，不是 hello 的输出；`:0` 表示本次命令返回 0。

**不符合时。** `Expected an idle root shell` 要回第 2 步登录，或让板子回到空闲提示符；端口打开失败先关闭占用 COM8 的软件。Windows 若提示脚本执行受策略阻止，属于本机策略问题，不是开发板故障。

**对应原文。** [主线 §2.11][main]的“串口能登录，uname 有输出”判据，连接 §2.1 的目标平台概念。

### 第 5 步：窗口 A 进入编译用的 Ubuntu

**动机。** 本仓的 Linux 编译器安装在 WSL Ubuntu 中，需要进入那个环境。

**在哪里、怎么写：另开一个 PowerShell 窗口，作为 A。**

```powershell
wsl -d Ubuntu
```

**命令组成。** `wsl` 是 Windows 启动 WSL 的工具；`-d` 选择发行版；`Ubuntu` 是已安装的发行版名称。这条命令不连接开发板。

**看什么确认。** 提示符由 `PS ...>` 变成 Ubuntu shell 提示符，通常含用户名、主机名和 `$`。此后 A 的命令都是 Bash / Linux 命令。

**对应原文。** [主线 §0.4][main]：电脑上的 WSL Ubuntu 承担编译。

### 第 6 步：确认电脑端 Linux 架构

**动机。** 将电脑与板子的架构并排看，建立两种编译器的使用前提。

**在哪里、怎么写：A，WSL。**

```bash
uname -m
```

**命令组成。** `uname` 查询系统信息，`-m` 只显示架构，与第 4 步相同；这次没有串口脚本，由 WSL 直接执行。

**看什么确认。** 本机应输出 `x86_64`，板上是 `armv7l`。记下两个结果；这次“同一命令、不同结果”来自执行位置不同。

**对应原文。** [主线 §1][main]“x86-64 Ubuntu / ARM Cortex-A7”脉络图，以及 §2.1 的目标指令集。

### 第 7 步：在 A 中找到同一份源码

**动机。** 两种编译器要读取同一个 `hello.c`，控制实验变量。

**在哪里、怎么写：A，WSL。**

```bash
cd /mnt/e/Workspace/embedded-linux/labs/01_toolchain
```

**命令组成。** Bash 的 `cd` 切换当前目录；`/mnt/e` 是 WSL 访问 Windows E 盘的位置。它与第 3 步指向同一文件夹。

**看什么确认。** 不报错，提示符路径改变；下一步成功读取 `hello.c` 是进一步确认。

**对应原文。** [主线 §0.4、§2.5][main]的工作目录和同一源码实验。

### 第 8 步：运行前先预测源码会打印什么

**动机。** 不先看代码，最后看到 Hello 就无法判断是不是预期逻辑。

**在哪里、怎么写：A，WSL。**

```bash
cat hello.c
```

**命令组成。** `cat` 读取并显示文件；`hello.c` 是输入文件，无其他参数，不修改源码。

**看什么确认。** 当前文件的 `main(int argc, char **argv)` 在 `argc >= 2` 时打印 `Hello, %s!\n` 并使用 `argv[1]`，否则打印 `Hello, world!\n`，最后 `return 0`。若你已改过文件，以当前代码重新预测。

程序名也占一个参数：带一个名字时 `argc = 2`，`argv[0]` 是调用路径，`argv[1]` 是名字；`%s` 是字符串占位符，`\n` 是换行，`return 0` 表示成功结束。

**对应原文。** [主线 §2.5][main]的 hello 和 `argc / argv`。笔记示例大小写、标点与当前文件不同，本实验以当前文件的 `Hello, learner!` 为准。

### 第 9 步：为三个产物准备输出目录

**动机。** 保留多个版本，避免第二次编译覆盖第一次产物。

**在哪里、怎么写：A，WSL。**

```bash
mkdir -p board-first-run
```

**命令组成。** `mkdir` 创建目录；`-p` 在需要时创建父目录，目标目录已存在时也不因此报错；`board-first-run` 是当前目录下的子目录。

**看什么确认。** 正常没有输出。后续编译不报输出目录不存在，是进一步确认。目录存在不表示其中的旧程序已更新。

**对应原文。** [主线 §2.5][main]保留不同目标平台产物的操作准备。

## 2. 在电脑上编出能解释的三个文件

**先自己想：**编译器名称加上 ARM 前缀，是让编译器搬到板上运行，还是在电脑上生成给 ARM 用的代码？

### 第 10 步：生成电脑自己能运行的版本

**动机。** 先得到本机对照，确认源码正常行为，后面才能判断板上失败属于平台问题还是逻辑问题。

**在哪里、怎么写：A，WSL。**

```bash
gcc -Wall -Wextra -O0 -g hello.c -o board-first-run/hello_x86
```

**命令怎样拼。** 先选工具，再写编译选项，给输入源码，最后用 `-o` 指定产物：

| 组成部分                           | 本条命令中负责什么                      |
| ------------------------------ | ------------------------------ |
| `gcc`                          | 本机 C 编译器，在这套 WSL 中默认目标为 x86-64 |
| `-Wall`                        | 开启一组常用警告，不表示启用所有警告             |
| `-Wextra`                      | 再增加一组警告，帮助发现可疑写法               |
| `-O0`                          | 大写 O 加数字 0，关闭优化，便于学习时观察        |
| `-g`                           | 把调试信息写入产物，方便之后调试；不自动启动调试器      |
| `hello.c`                      | 输入源文件                          |
| `-o board-first-run/hello_x86` | 指定输出路径；`-o` 后紧跟文件名，大小写敏感       |

**看什么确认。** 正常编译通常没有输出。出现 error 就停下修正，不要运行旧文件；warning 也应读清楚。下一步检查格式并实际运行，才进一步确认产物。

**对应原文。** [主线 §2.5][main]“同一份源码，两个目标平台”，以及 §3.2 的预处理、编译、汇编、链接。这里没有 `-E / -S / -c` 停止选项，GCC 会完成到链接，生成可执行文件。

### 第 11 步：让文件说明自己给谁用

**动机。** `hello_x86` 只是名字，改名不会改变机器码，需要检查文件内容。

**在哪里、怎么写：A，WSL。**

```bash
file board-first-run/hello_x86
```

**命令组成。** `file` 根据内容识别格式；后面是待检查文件路径，无额外参数。

**看什么确认。** 首次实测包含 `ELF 64-bit`、`x86-64`、`dynamically linked` 和 `interpreter /lib64/ld-linux-x86-64.so.2`。先抓住“Linux ELF、64 位、x86-64、动态链接”四点，不必背 BuildID。

**对应原文。** [主线 §2.5][main]的 `file` 输出；§2.8 解释 `pie executable`。没有 `.exe` 后缀也可以是 Linux 可执行文件。

### 第 12 步：在电脑端验证预测的输出

**动机。** 验证“源码 → 本机可执行文件 → 正常输出”已通。

**在哪里、怎么写：A，WSL。**

```bash
./board-first-run/hello_x86 learner
```

**命令组成。** 工具就是刚生成的程序；`./` 表示从当前目录定位，后面是文件相对路径，`learner` 是传给程序的名字参数。它不是 GCC 参数，编译已结束。

**看什么确认。** 未改源码时输出 `Hello, learner!`，首次实测与此一致：`argv[1]` 被代入 `%s`。输出不对，回看第 8 步及实际编译的源文件。

**对应原文。** [主线 §2.5][main]的本机运行和参数传递；这是正常行为对照组。

### 第 13 步：换目标编译器，生成 ARM 动态版

**动机。** 电脑版不适合直接交给 ARM 板。保持源码不变，换用生成 ARM Linux 程序的工具链。

**在哪里、怎么写：A，WSL。**

```bash
arm-linux-gnueabihf-gcc -Wall -Wextra -O0 -g hello.c -o board-first-run/hello_arm_dynamic
```

**命令组成。** 工具换成 `arm-linux-gnueabihf-gcc`：`arm` 指目标架构家族，`linux` 指目标操作系统，`gnueabi` 指这套 GNU / EABI 约定，`hf` 指硬浮点调用约定。具体默认 ARM 子架构取决于工具链配置，不能仅凭名称判断。编译器自身仍在电脑上运行。

`-Wall / -Wextra` 开警告，`-O0` 关闭优化，`-g` 加调试信息，`hello.c` 仍是相同输入；`-o` 后换成 `board-first-run/hello_arm_dynamic`，保留 x86 文件。这套工具链未指定 `-static` 时默认使用动态链接的 C 库。

**看什么确认。** 命令无 error；若 `command not found`，是 WSL 找不到交叉编译器或你不在正确环境，不能继续假设 ARM 文件已更新。

**对应原文。** [主线 §2.1、§2.2、§2.5][main]：选择机器码和 ABI。ARM 前缀不是传文件的命令。

### 第 14 步：检查 ARM 版文件头

**动机。** 用文件中的证据验证“换编译器改变了目标架构”。

**在哪里、怎么写：A，WSL。**

```bash
arm-linux-gnueabihf-readelf -h board-first-run/hello_arm_dynamic
```

**命令组成。** `arm-linux-gnueabihf-readelf` 读取 ELF 元信息，不执行 ARM 文件；`-h` 在这个工具里表示 ELF header，不是帮助；最后是输入文件。

**看什么确认。** 找 `Class: ELF32`、`Machine: ARM`；默认 PIE 产物还会显示 `Type: DYN`。与第 11 步的 64 位、x86-64 对比。DYN 在这里不表示“只能当动态库，不能运行”。

**对应原文。** [主线 §2.6][main]：`Machine` 对应 ELF 的 `e_machine`，ARM 值为 40；§2.8 解释 PIE 的 DYN 类型。结构细节见 [基础：ELF 与程序加载][elf]“ELF header 的关键字段”。

### 第 15 步：查 ARM 动态版的库版本要求

**动机。** ARM 架构只是第一道条件。先查程序启动时需要的动态库符号版本，稍后与板上报错对照。

**在哪里、怎么写：A，WSL。**

```bash
arm-linux-gnueabihf-readelf -V board-first-run/hello_arm_dynamic
```

**命令组成。** 工具仍是 `readelf`，改用大写 `-V` 读取版本信息；最后是 ARM 动态版路径。小写 `-v` 与它不是同一选项。

**看什么确认。** 找 `Version needs section`；首次实测有 `File: libc.so.6`、`Name: GLIBC_2.4` 和 `Name: GLIBC_2.34`。这是所需符号版本，不是要求安装一个名叫“GLIBC_2.34”的单独程序，也不能因此断定需要 2.34 的就是 printf。

**对应原文。** [主线 §3.6][main]：printf 可以只需较旧符号版本，但启动代码等其他符号可能要求 `GLIBC_2.34`。编译时的库要与目标根文件系统兼容。

### 第 16 步：再准备静态版作为解决办法

**动机。** 首次实测知道板上 glibc 较旧。保留动态版，再生成静态版，比较两种链接方式。

**在哪里、怎么写：A，WSL。**

```bash
arm-linux-gnueabihf-gcc -Wall -Wextra -O0 -static -no-pie hello.c -o board-first-run/hello_arm_static
```

**命令组成。** ARM GCC 负责目标平台；`-Wall / -Wextra` 开警告，`-O0` 关闭优化；`-static` 选择静态链接，把本例需要的 libc 等库代码链接进产物；`-no-pie` 明确生成非 PIE 可执行文件。这里没有 `-g`，不请求调试信息。`hello.c` 不变，`-o` 后使用新的静态版文件名。

`-static` 管链接方式，`-no-pie` 管 PIE 形式，二者都不是“设置 ARM”。静态链接不等于无条件复制 libc 的全部函数，也不意味着跨任意 CPU 和内核运行。

**看什么确认。** 编译无 error；若缺静态库而报链接错误，先处理，不能拿旧文件当新产物。

**对应原文。** [主线 §3.7][main]“−static 的代价”及 §2.8 的 EXEC / DYN。参数定义见 [GCC 官方链接选项](https://gcc.gnu.org/onlinedocs/gcc/Link-Options.html)。

### 第 17 步：确认静态链接生效

**动机。** 需要证明准备上传的文件具有预期链接方式，不能只相信敲过的命令。

**在哪里、怎么写：A，WSL。**

```bash
file board-first-run/hello_arm_static
```

**命令组成。** `file` 检查格式，输入换成静态版，无额外选项。

**看什么确认。** 首次实测包含 `ELF 32-bit`、`ARM`、`statically linked`。`ARM` 验证架构，`statically linked` 验证链接方式，二者各管一件事。

**对应原文。** [主线 §3.7][main]静态版的文件结构变化。检查通过后继续上传。

### 第 18 步：观察静态链接的体积代价

**动机。** 静态版更容易在本板跑通，但嵌入式存储有限，需要看到代价。

**在哪里、怎么写：A，WSL。**

```bash
ls -lh board-first-run/hello_arm_dynamic board-first-run/hello_arm_static
```

**命令组成。** `ls` 列文件；`-l` 用长格式显示权限、大小等；`-h` 将大小用 K、M 等单位显示；`-lh` 是两选项合写。后面显式列两个文件，避免通配符把压缩包也算进来。

**看什么确认。** 首次编译动态版约 69K，静态版约 476K，后者明显更大。这里两个构建的 `-g` 也不同，是实际产物大小对比，不是只改变一个参数的严格体积实验，不能把精确差值全部归于静态链接。

**对应原文。** [主线 §3.7][main]：静态链接减少本例运行时库依赖，同时增大文件。进一步定量研究应固定其他选项再比较。

## 3. 通过串口把静态版送上板，先完成一次成功运行

**先自己想：**COM8 原本传的是串口字节，怎样传一个二进制文件？“上传成功”和“程序能运行”为什么需要分别验证？

### 第 19 步：压缩静态版，减少串口传输量

**动机。** 串口比常见网络传文件慢；先压缩，能少发送一些字节。压缩只服务传输，不改变程序的目标架构。

**在哪里、怎么写：A，WSL。**

```bash
gzip -c board-first-run/hello_arm_static > board-first-run/hello_arm_static.gz
```

**命令组成。** `gzip` 默认做压缩；`-c` 把压缩结果写到标准输出，保留原文件；输入是静态版；`>` 是 Bash 的输出重定向，把结果保存到右侧 `.gz` 文件。`>` 不是 gzip 参数，目标文件已存在时会被覆盖，本步正是要更新旧压缩包。

**看什么确认。** 正常没有终端输出，因为输出进入了文件。首次压缩包约 226K。不能只凭 `.gz` 后缀判断内容有效；上传校验和板上解压会进一步验证。

**对应原文。** [主线 §2.11][main]“把编译产物送到板子”的操作支撑。gzip 不属于交叉编译，也没有把 x86 转成 ARM。

### 第 20 步：从 Windows 把压缩包上传到板上

**动机。** 文件还在电脑 E 盘上，板子不能凭空访问它。现在跨过两台机器的文件系统边界。

**在哪里、怎么写：切回 B，仍在第 3 步的 PowerShell 目录。**

```powershell
.\serial-board.ps1 -Upload .\board-first-run\hello_arm_static.gz -Destination /tmp/lesson01-20260906/hello_arm_static.gz
```

**命令组成。** `.\serial-board.ps1` 是本仓辅助脚本；`-Upload` 指定电脑上的输入文件，`.\board-first-run\...` 是 Windows 相对路径；`-Destination` 指定板上输出文件的绝对路径。脚本会创建需要的板上父目录。本脚本只接受 `/tmp/` 下的上传路径。

脚本的实际工作是：本地二进制转成 Base64 文本 → 经串口分批发送 → 板上 `base64 -d` 还原文件 → 用 `sha256sum` 比较板上文件与本地文件。Base64 是编码，不是压缩；前一步 gzip 才是压缩。你不需要手工粘贴编码文本。

**看什么确认。** 等待返回提示符，并找到 `/tmp/lesson01-20260906/hello_arm_static.gz: OK`。这是 SHA256 内容校验通过，不是程序运行成功。传输期间可能一段时间没有输出，不要把其他命令插进上传过程。报校验失败就重新传，先不要解压执行。

**对应原文。** [主线 §2.11][main]的文件交付环节。原文 NFS、U 盘、adb 和本步串口上传解决同一问题：让板子拿到产物；本脚本是这次环境的补充方案。

### 第 21 步：从板子的视角检查收到的文件

**动机。** 再次分清“电脑有文件”与“板子有文件”，避免以后在错误机器上找程序。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'ls -lh /tmp/lesson01-20260906/hello_arm_static.gz'
```

**命令组成。** 脚本的 `-Command` 发送单引号中的 Linux 命令；板上 `ls` 列文件，`-l` 显示详情，`-h` 显示易读大小，最后是板上绝对路径。外层 PowerShell 不会尝试在 Windows 中打开 `/tmp`。

**看什么确认。** 有文件详情，大小非 0；首次约 226K。若 `No such file or directory`，先核对第 20 步目标路径以及上传之后是否重启过板子。文件存在与内容正确是两层证据，内容正确仍靠上一条哈希校验。

**对应原文。** [主线 §2.11][main]中“PC 目录”和“板上目录”的区别。本方案是复制，不像 NFS 那样自动看到电脑的后续修改。

### 第 22 步：在板上还原可执行文件

**动机。** `.gz` 是传输用压缩包，Linux 不能把它直接当成本例的 ELF 程序执行。先解压成真正的程序。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'gzip -dc /tmp/lesson01-20260906/hello_arm_static.gz > /tmp/lesson01-20260906/hello_arm_static'
```

**命令组成。** 外层仍用脚本 `-Command`；板上 `gzip` 的 `-d` 表示解压，`-c` 表示写到标准输出，`-dc` 是合写；输入为 `.gz` 文件；`>` 由板上 shell 解释，将解压结果保存到没有 `.gz` 的程序路径。单引号确保这次重定向发生在板上。

**看什么确认。** 没有 gzip 错误，脚本完成标记为 `:0`。如果出现 `not in gzip format` 或 `unexpected end of file`，回查压缩和上传，不要继续执行。目标文件存在时本步会更新它。

**对应原文。** [主线 §2.11][main]上传阶段的收尾；联系 [基础 ELF][elf]：加载器期待 ELF 格式，压缩包不是 ELF。

### 第 23 步：给还原后的文件执行权限

**动机。** 文件通过重定向创建，不能假设带执行权限。要允许 Linux 把它作为程序启动。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'chmod +x /tmp/lesson01-20260906/hello_arm_static'
```

**命令组成。** 脚本发送 `chmod` 命令；`chmod` 修改权限，`+x` 添加执行权限，最后是板上文件。省略用户类别时，具体受 umask 规则影响；本步只需要保证当前登录用户可执行。

**看什么确认。** 正常无业务输出，完成标记为 `:0`；第 24 步查看权限。若文件不存在，回第 22 步；若是只读文件系统，先核对是否确实使用了本板可写的 `/tmp`。

**对应原文。** [主线 §2.11][main]运行前准备。执行权限解决的是“是否允许尝试执行”，不会改变文件里的 ARM 指令或 libc 要求。

### 第 24 步：确认权限和解压后的体积

**动机。** 把“解压”和“加执行权限”的结果落实为可见证据。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'ls -lh /tmp/lesson01-20260906/hello_arm_static'
```

**命令组成。** 脚本发送板上 `ls`；`-l` 看权限等详情，`-h` 看易读大小，输入换成解压后的无 `.gz` 文件。

**看什么确认。** 权限字符串中应有当前用户适用的 `x`，首组三个权限是文件所有者的权限；大小应与电脑静态版同量级，首次约 476K。不要要求所有机器的权限字符串完全一样。检查对象若仍是 226K 的 `.gz`，说明路径看错了。

**对应原文。** [主线 §2.11][main]上板运行前确认；体积联系 §3.7 的静态链接代价。

### 第 25 步：在 ARM 板上运行，并立即读取程序退出码

**动机。** 第一次完整验证“电脑编译 → 串口复制 → 板子加载 → 程序 main 产生预期行为”。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command '/tmp/lesson01-20260906/hello_arm_static learner; echo $?'
```

**命令组成。** `-Command` 后第一个命令是程序的板上绝对路径；`learner` 传给 `argv[1]`；`;` 让板上 shell 在程序结束后执行下一条命令，不论前一条成功或失败；`echo` 显示后面的值；Bash 的 `$?` 是紧接在它之前的程序退出码。外层用单引号，防止 PowerShell 把 `$?` 当作自己的状态变量提前展开。

**看什么确认。** 首次实测程序输出 `Hello, learner!`，退出码为 `0`。按本条命令运行时，应看到 Hello 行后跟一行 `0`。必须同时满足“文本正确”和“退出码正确”。

**这里为什么不能分两次脚本调用。** 辅助脚本会自动追加 `printf` 打印完成标记，下一次调用还会探测提示符。若另起一次调用再执行 `echo $?`，读到的可能已经是辅助命令的状态。程序和 `echo $?` 必须放在同一个 `-Command` 内。

加了 `echo $?` 后，末尾的 `__DONE_...__:0` 对应的是最后一条 echo 的状态；**程序退出码要看 echo 单独打印的数字**。不能用脚本的 `:0` 判断前面的程序一定成功。

**对应原文。** [主线 §2.11][main]“板上 ARM hello 打印预期输出”判据；§2.5 的 `argc / argv`、退出码；[基础 ELF][elf]“从 execve 到 main”：本次加载成功后进入了你的代码。

## 4. 故意运行两个失败版本，找到失败发生在哪一层

**先自己想：**同样是启动失败，CPU 架构不对与 libc 版本不对，会在同一个阶段被发现吗？先预测它们有没有机会进入 main。

### 第 26 步：先检查板上的 C 库

**动机。** 第 15 步查到程序需要什么，现在检查板子提供什么，把报错解释建立在两边证据上。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'ls -l /lib/libc.so.6 /lib/ld-linux-armhf.so.3'
```

**命令组成。** 脚本发送板上 `ls`；`-l` 显示详情，便于看到符号链接的箭头；后面两个绝对路径分别是 C 库与 ARM hard-float 动态链接器。不使用 `-L`，因为本步正要看链接指向的文件名。

**看什么确认。** 首次实测为 `libc.so.6 -> libc-2.30.so`、`ld-linux-armhf.so.3 -> ld-2.30.so`。这是本镜像的库版本线索；后面实际出现的版本错误是兼容性失败的直接证据。若换了系统且链接命名不同，不应仅按文件名猜版本。

**对应原文。** [主线 §3.6][main]：动态链接程序会使用板上的动态链接器和 libc；§2.3 的 sysroot 说明编译环境的库与目标系统的关系。

### 第 27 步：上传 ARM 动态版

**动机。** 静态版跑通后，再测试第 13 步的动态版，观察同为 ARM 文件是否必然能运行。

**在哪里、怎么写：B，Windows PowerShell。**

```powershell
.\serial-board.ps1 -Upload .\board-first-run\hello_arm_dynamic -Destination /tmp/lesson01-20260906/hello_arm_dynamic
```

**命令组成。** `-Upload` 后是电脑动态版文件的 Windows 相对路径；`-Destination` 后是板上绝对路径。这次直接传较小的原文件，没有 gzip 包，也就不需要解压。脚本仍做 Base64 传输和 SHA256 校验。

**看什么确认。** 找 `/tmp/lesson01-20260906/hello_arm_dynamic: OK`，等待命令结束。它确认文件完整，不能推导出库兼容。

**对应原文。** [主线 §2.11][main]的上板对照实验，准备验证 §3.6 的运行时库依赖。

### 第 28 步：给动态版执行权限

**动机。** 排除权限不足，否则会先被 `Permission denied` 挡住，看不到本实验要研究的版本错误。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'chmod +x /tmp/lesson01-20260906/hello_arm_dynamic'
```

**命令组成。** `-Command` 发送板上命令；`chmod` 修改权限，`+x` 添加执行权限；路径指向动态版。规则与第 23 步相同，不会改变链接方式。

**看什么确认。** 无 chmod 错误，完成标记 `:0`。若文件不存在，回第 27 步，而不是修改编译参数。

**对应原文。** [主线 §2.11][main]的运行准备；控制权限这个干扰因素后再观察库问题。

### 第 29 步：观察 ARM 动态版为什么进不了 main

**动机。** 用一次真实失败验证“指令集相同不等于运行环境兼容”。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command '/tmp/lesson01-20260906/hello_arm_dynamic learner; echo $?'
```

**命令组成。** 程序路径换成动态版；`learner` 仍是名字参数；`;` 保证失败后也会执行 `echo`；`$?` 立即读取程序退出码。外层单引号防止 PowerShell 展开 `$?`。不要把分号换成 `&&`，否则失败后就不会打印退出码。

**看什么确认。** 首次实测报错的关键内容是：

```text
/lib/libc.so.6: version `GLIBC_2.34' not found
```

程序退出码是 `1`，没有 `Hello, learner!`。按本条写法应看到报错后 echo 打印 `1`；脚本完成标记仍可能为 `:0`，因为 echo 自身成功，不能误判。

**现象怎么解释。** 第 14 步已确认 ARM 架构；第 15 步确认依赖 `GLIBC_2.34`；第 26 步板上是 2.30。这里动态链接器启动了，但检查依赖版本失败，你的 main 尚未运行。`chmod +x`、改文件名、改打印字符串都不能补齐缺失的库符号版本。

如果动态版成功，先核对板上系统、工具链和实际上传文件是否变化。成功可能表示环境已经兼容，不能为了复现旧报错而硬判失败。

**对应原文。** [主线 §3.6][main]“编译时 libc 与板子 rootfs 的 libc 必须兼容”，以及 §2.11 末尾的动态链接注错实验。正式工程可选择匹配目标 sysroot 的工具链；本节使用静态版先跑通，不改板上系统库。

### 第 30 步：上传电脑使用的 x86 版

**动机。** 再制造一个更早阶段的失败：让 ARM 板尝试加载 x86 文件，与动态库错误对照。

**在哪里、怎么写：B，Windows PowerShell。**

```powershell
.\serial-board.ps1 -Upload .\board-first-run\hello_x86 -Destination /tmp/lesson01-20260906/hello_x86
```

**命令组成。** `-Upload` 指电脑 x86 版；`-Destination` 指板上 x86 版路径；脚本只复制内容，不因目标是 ARM 板而转换机器码。

**看什么确认。** `/tmp/lesson01-20260906/hello_x86: OK` 表示内容校验通过。这个 OK 恰好保证后面研究的是“完整的错误架构程序”，而不是传坏的文件。

**对应原文。** [主线 §2.5、§2.11][main]的镜像实验：x86 机器运行 ARM 失败；ARM 板运行 x86 也失败。

### 第 31 步：排除 x86 版的权限问题

**动机。** 同样先允许尝试执行，才能观察内核对文件格式的判断。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'chmod +x /tmp/lesson01-20260906/hello_x86'
```

**命令组成。** `-Command` 发送 Linux 命令；`chmod +x` 添加执行权限；最后路径换成 x86 文件。

**看什么确认。** 无错误，完成标记 `:0`。加权限成功不表示架构通过检查，只是完成执行前的一项准备。

**对应原文。** [主线 §2.11][main]运行准备；下一步才检验 §2.6、§2.7 的 ELF 加载。

### 第 32 步：观察内核拒绝错误架构

**动机。** 验证 CPU 尚未执行你的 main，内核就可以根据文件格式与架构信息拒绝启动。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command '/tmp/lesson01-20260906/hello_x86 learner; echo $?'
```

**命令组成。** 板上程序路径换成 x86 版；`learner` 是参数；`; echo $?` 无论前一程序成败，都立即打印其退出码；外层单引号原样传递 Bash 语法。

**看什么确认。** 首次实测关键输出为 `cannot execute binary file: Exec format error`，程序退出码 `126`。按本条写法应看到报错后独立的一行 `126`。这次既没有 Hello，也不是 `GLIBC_2.34 not found`。

**现象怎么解释。** 第 11 步证明文件是 x86-64 / ELF64，第 4 步证明板子是 ARM。内核在 ELF 加载检查阶段拒绝不适合本平台的产物；这个运行结果支持原文所讲的架构检查机制，但不是对某一条内核 C 语句的现场跟踪。

**对应原文。** [主线 §2.5、§2.6、§2.7][main]，以及视频 4_1-1 约 12:25 的板上 x86 失败演示。这里不是“CPU 试跑了几条 x86 指令才发现不认识”。

### 到这里，把三个结果放回同一条启动路径

```text
板上 shell 请求执行文件
          │
          ▼
内核检查 ELF 格式、目标架构等
          ├─ x86 版：加载失败 → Exec format error → 未进入 main
          │
          ▼
ARM 动态版：启动动态链接器，检查库和符号版本
          ├─ 板上缺 GLIBC_2.34 → 启动失败 → 未进入 main
          │
ARM 静态版：本例不需要上述板上动态 libc
          │
          ▼
程序启动代码 → main → printf → Hello, learner! → return 0
```

| 首次实测版本 | 程序退出码 | 直接观察到什么 | 能得出的结论 |
|---|---|---|---|
| x86 | 126 | Exec format error | 本板不能直接加载这个 x86 产物 |
| ARM 动态 | 1 | GLIBC_2.34 not found | 目标架构匹配仍不足以保证运行 |
| ARM 静态 | 0 | Hello, learner! | 这个程序在当前板上已完成加载和执行 |

静态版成功不证明它适用于所有 ARM 板；CPU 特性、ABI、内核能力仍要满足要求。本实验也没有验证完整 GCC 四步、Makefile 或驱动开发，后续仍按主线继续。

## 5. L2：由你修改程序，证明整条流程真正掌握了

**先自己想，不急着看参考答案。** 让程序在收到名字时打印 `Hello from ARM, 名字!` 并返回 0；没有名字时打印用法提示并返回 1。需要改的是哪个 if 分支、哪条 printf、哪条 return？名字来自 argv 的哪一项？

### 第 33 步：打开源码，自己完成修改

**动机。** 前面跑的是已有代码。现在要观察“你的改动”确实在板子上生效，排除只会重复运行现成文件。

**在哪里、怎么写：B，Windows PowerShell，保持实验目录。**

```powershell
notepad .\hello.c
```

**命令组成。** `notepad` 打开 Windows 记事本；`.\hello.c` 是当前目录的源码路径；没有额外选项。也可用你平时的代码编辑器打开同一个文件，编辑器选择不影响交叉编译。

**现在要做。** 修改现有 main 的分支、输出和返回值，然后保存。不要另存成 `hello.c.txt`。保留 `#include <stdio.h>`，它为 printf 等提供声明。

<details>
<summary>自己尝试之后，再展开参考实现</summary>

```c
#include <stdio.h>

int main(int argc, char **argv)
{
    if (argc < 2) {
        printf("Usage: %s NAME\n", argv[0]);
        return 1;
    }

    printf("Hello from ARM, %s!\n", argv[1]);
    return 0;
}
```

`argc < 2` 表示只有程序名，没有名字参数；此时 `argv[0]` 用于提示怎样调用，返回 1 表示本程序约定的失败状态。通过参数检查后才读取 `argv[1]`；打印名字后返回 0。1 的含义由本程序约定，不能认为所有程序的退出码 1 都代表“缺名字”。

</details>

**看什么确认。** 保存后编辑器中出现新字符串，并且无名字分支有 `return 1`。此时只修改了电脑上的源码，板上旧程序还不会变化。

**对应原文。** [主线 §2.5][main]的参数与返回值，以及 §0.3 对 L2“改出可观测变化”的定义。

### 第 34 步：从编译环境确认保存到了正确文件

**动机。** 编辑器显示新内容不代表 GCC 会读到它；先从 WSL 读取实际输入路径。

**在哪里、怎么写：A，WSL，仍在实验目录。**

```bash
cat hello.c
```

**命令组成。** `cat` 显示当前目录下的 `hello.c`；不加参数，不修改文件。

**看什么确认。** WSL 输出应包含刚保存的新字符串和无名字返回 1 的分支。若仍旧内容，检查编辑器保存路径、保存状态和 A 的当前目录，不要继续编译错误文件。

**对应原文。** [主线 §2.5][main]的输入源码；§0.4 强调运行现象不符时先查当前实际环境。

### 第 35 步：把修改后的源码重新编成 ARM 静态版

**动机。** 改源码不会自动改二进制。必须重新运行编译器，才能把新逻辑变成机器码。

**在哪里、怎么写：A，WSL。**

```bash
arm-linux-gnueabihf-gcc -Wall -Wextra -O0 -static -no-pie hello.c -o board-first-run/hello_arm_static
```

**命令组成。** ARM GCC 指定目标平台；`-Wall / -Wextra` 检查可疑写法，`-O0` 关闭优化，`-static` 静态链接，`-no-pie` 生成非 PIE 可执行文件；输入是修改后的 `hello.c`，`-o` 更新原来的静态产物路径。

**看什么确认。** 无编译错误才继续。若编译失败，即使旧产物还存在也不能上传。最终的新文本和退出码是验证本次编译使用了新代码的判据。

**对应原文。** [主线 §2.5、§3.7][main]；这一步手工完成构建，后面 §4 的 Makefile 会自动管理何时重编。

### 第 36 步：更新压缩包，避免上传旧版本

**动机。** 第 35 步更新的是 ELF，旧 `.gz` 不会随之更新。跳过本步会继续把旧程序送上板。

**在哪里、怎么写：A，WSL。**

```bash
gzip -c board-first-run/hello_arm_static > board-first-run/hello_arm_static.gz
```

**命令组成。** `gzip` 压缩新 ELF，`-c` 输出压缩数据且保留原文件；Bash 的 `>` 用新结果覆盖右侧旧压缩包。

**看什么确认。** 无 gzip 错误，等待返回提示符。后面“上传哈希通过但仍打印旧文本”时，本步是重点排查对象：哈希相同只能证明上传内容相同，不证明选择了最新输入。

**对应原文。** [主线 §2.11][main]的重复交付环节；这是本方案增加的操作，不是新的 GCC 阶段。

### 第 37 步：把更新后的压缩包再次传上板

**动机。** 电脑上的产物更新，不会自动同步板上文件。本方案是复制，不是 NFS 共享目录。

**在哪里、怎么写：B，Windows PowerShell。**

```powershell
.\serial-board.ps1 -Upload .\board-first-run\hello_arm_static.gz -Destination /tmp/lesson01-20260906/hello_arm_static.gz
```

**命令组成。** 脚本 `-Upload` 读取电脑的新 `.gz`；`-Destination` 指定同一个板上临时文件路径；本次上传会更新该路径的内容，并再次核对 SHA256。

**看什么确认。** 等待对应文件的 `OK` 和返回提示符，再解压。若板子已重启，先按第 2 步重新登录，脚本会重新创建上传目录。

**对应原文。** [主线 §2.11][main]“改一次代码要拷一次”的代价，以及 NFS 可减少手工复制的动机。

### 第 38 步：更新板上真正要执行的 ELF

**动机。** 板上收到新 `.gz`，原来的无后缀程序仍可能是旧的，还要解压覆盖它。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'gzip -dc /tmp/lesson01-20260906/hello_arm_static.gz > /tmp/lesson01-20260906/hello_arm_static'
```

**命令组成。** 脚本发送 `gzip`；`-d` 解压，`-c` 写标准输出；板上 shell 的 `>` 将结果写入实际运行路径，覆盖旧内容。外层单引号保持重定向在板上发生。

**看什么确认。** 无解压错误，完成标记 `:0`。不要对仍在运行的同名程序做覆盖；本节 hello 会迅速退出，等待它结束后再更新。

**对应原文。** [主线 §2.11][main]“板子运行的是交付的文件”，而不是电脑上的源文件。

### 第 39 步：明确设置本次产物的执行权限

**动机。** 让流程同时适用于首次创建和重新上传，避免依赖上一次遗留的权限。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command 'chmod +x /tmp/lesson01-20260906/hello_arm_static'
```

**命令组成。** `-Command` 发送板上命令；`chmod +x` 添加执行权限；文件路径指向刚解压的静态版。

**看什么确认。** 命令无错误，完成标记 `:0`。已有执行权限时重复设置不会修改程序代码。

**对应原文。** [主线 §2.11][main]运行准备；权限仍不替代后面的行为验证。

### 第 40 步：检验有名字时的新行为

**动机。** 用特有的新文本证明板子执行的是你刚改的代码，而不是原来的 Hello。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command '/tmp/lesson01-20260906/hello_arm_static learner; echo $?'
```

**命令组成。** 程序路径指向更新后的板上文件，`learner` 作为 `argv[1]`；`;` 串接 `echo`，`$?` 立即读程序退出码；PowerShell 单引号防止提前展开。

**看什么确认。** 如果按上面的目标修改，应看到 `Hello from ARM, learner!` 和单独一行 `0`。这是你本次练习的预期，助手没有代改源码或声称已测过该版本。

**不符合时。** 仍是 `Hello, learner!` 就依次排查：编辑器保存 → 第 34 步源码路径 → 编译成功 → 重压缩 → 上传新包 → 板上解压 → 执行路径。不要直接认定“串口缓存了旧程序”。

**对应原文。** [主线 §0.3][main]的 L2 可观测变化；§2.11 上板闭环；§2.5 的参数传递。

### 第 41 步：检验无名字时确实走失败分支

**动机。** 仅修改打印字符串还不够，要证明参数条件和退出状态也按要求工作。

**在哪里、怎么写：B 输入，板上执行。**

```powershell
.\serial-board.ps1 -Command '/tmp/lesson01-20260906/hello_arm_static; echo $?'
```

**命令组成。** 与第 40 步相比，故意去掉 `learner`；程序只收到自身调用路径，通常 `argc = 1`。`; echo $?` 保证失败后立即打印返回值；仍使用外层单引号。

**看什么确认。** 应出现你的用法提示，并打印退出码 `1`。不能崩溃，也不应继续打印成功欢迎语。脚本自己的完成标记可能为 0，仍只看 echo 显示的程序退出码。

**对应原文。** [主线 §2.5][main]的 `argc / argv` 与退出码，及 §0.3 的“实验必须有判据”。这里验证的是你写的程序如何报告失败，与动态链接器报错虽然都可能返回 1，发生阶段和含义不同。

## 6. 学完怎么验收，出错先查哪里

先用自己的话回答，再勾选：

- [ ] 我能指出 A、B 和板上 shell 各在哪里运行，哪个目录属于哪台机器。
- [ ] 我能说明 ARM GCC 在电脑运行，但输出是给 ARM 板使用的。
- [ ] 我能从文件内容而非文件名判断目标架构，并找到 ELF 的 Machine 字段。
- [ ] 我能分别解释文件传输校验、执行权限、架构检查、动态库版本检查解决什么问题。
- [ ] 我亲手观察到三个版本的结果，或者根据实际环境变化解释为何与旧实测不同。
- [ ] 我修改了源码，板上出现新文本；有名字返回 0，无名字返回 1。
- [ ] 我知道通过本辅助脚本读取程序退出码时，必须在同一次调用里立即读取。

**注错见红。** 可以先只修改源码、暂时不重新编译上传，运行第 40 步：它应仍显示旧行为，新文本判据必须失败。然后补齐第 35–40 步，判据才通过。这个实验能证明你的验收确实能发现“板子还在跑旧程序”。不要把助手演示完成等同于你已掌握。

| 现象 | 先查哪一步 | 它说明什么，不能说明什么 |
|---|---|---|
| 端口打不开、被占用 | 1–4 | Windows 串口连接问题，尚未涉及 ELF |
| Expected an idle root shell | 2、4 | 尚未登录或板上不是空闲提示符 |
| 找不到 gcc / ARM GCC | 5、10、13 | 编译环境或工具定位问题 |
| 上传 SHA256 失败 | 20 / 27 / 30 / 37 | 文件交付未验证，先不要解释程序行为 |
| Permission denied | 23、28、31、39 | 先查执行权限和路径；不是架构错误的同义词 |
| Exec format error | 11、14、32 | 本对照实验中架构不匹配；一般排障还要考虑文件损坏等 |
| GLIBC_2.34 not found | 15、26、29 | 动态加载时找不到所需符号版本 |
| No such file or directory | 21、22 | 先查路径和重启；若 ELF 确实存在，还可能是解释器路径缺失，见主线 §3.6 |
| 仍显示旧文本 | 34–40 | 检查保存、编译、压缩、上传、解压、运行是否使用同一版 |

本节只完成第一章的交叉编译上板闭环，并提前借用 §3.6、§3.7 解释本板的库兼容问题。下一步回到主线 §3.1、§3.2，拆开 GCC 的四个步骤，再进入 Makefile。
