### 2.1 第一性原理：编译器只是在选"给谁生成机器码"

一句话：**编译器不是一个通用的翻译机，它是一台专门给某一个平台生产机器码的机器。**

这句话推出这一节的全部内容。既然产物是给某个平台的，
那么"某个平台"这件事就必须在编译时说清楚，而它至少包含三件独立的事：

    1. 指令集    生成 ARM 机器码还是 x86-64 机器码
    2. 调用约定  参数放哪个寄存器、结构体怎么对齐、栈帧怎么排
    3. 配套的头文件和库在哪   编译时 include 的 stdio.h、链接时用的 libc.so

这三件事互相独立：指令集相同、调用约定不同的两个产物不能互相调用；
前两者都相同、配套库版本不同的产物拷过去会启动失败。

它们被塞进了一个名字里：

    arm  -  linux  -  gnueabi  hf  -  gcc
     |        |         |      |
     |        |         |      +--- hard float: 浮点参数走 VFP 寄存器 s0/s1/d0
     |        |         |           soft/softfp: 浮点参数拆成整数走 r0-r3
     |        |         +---------- ABI: 参数怎么传、结构体怎么对齐、栈帧怎么排
     |        |                     gnu 表示配 glibc，eabi 是 ARM 的标准嵌入式 ABI
     |        +-------------------- 目标 OS: 决定用哪套 syscall 约定、链接什么 C 库
     +----------------------------- 架构 ISA: 生成 ARMv7-A 还是 x86-64 机器码

    arm - buildroot - linux - gnueabihf - gcc      板子 BSP 里那个
           ^^^^^^^^^
           厂商/构建者标识，apt 那个省略了这一段

这个名字叫 target triplet，实际常常是四段。

三件事分别落在 ELF 文件的不同位置：

    +--------------------------------------------------------+
    |  hello (ELF)                                           |
    |                                                        |
    |  ELF header   e_machine = EM_ARM        <--- ISA 决定  |
    |  .text        ARM 机器码                <--- ISA 决定   |
    |               参数放 r0-r3 / s0-s7      <--- ABI 决定   |
    |  .interp      /lib/ld-linux-armhf.so.3  <--- sysroot   |
    |  .dynamic     NEEDED libc.so.6          <--- sysroot   |
    +--------------------------------------------------------+

[基础] 这一节会用到三个通用概念，不熟就先跳过去：

    ABI 和 sysroot 到底是什么   ->  [00_基础/03_ABI与sysroot](../00_基础/03_ABI与sysroot.md)
    r0 / s0 这些寄存器名        ->  [00_基础/02_ARM寄存器与调用约定](../00_基础/02_ARM寄存器与调用约定.md)

### 2.2 hf 这一位是硬约束，不是性能选项

同一个函数 `float f(float a, float b)`，两种 ABI 的调用现场完全不同：

    hf (hard float)                    soft / softfp
    -----------------------            -----------------------------------
    a -> s0                            a -> r0   (float 的 32 位原样塞进整数寄存器)
    b -> s1                            b -> r1
    返回值 <- s0                       返回值 <- r0
    直接发 vadd.f32                    调 __aeabi_fadd，或搬进 VFP 再算
    调用方按 hf 把参数放进 s0 ------> 被调方按 soft 去 r0 取
                                       取到的是垃圾

所以链接器不让这两种 `.o` 链到一起，直接报错：

    xxx.o uses VFP register arguments, yyy.o does not

（s0、r0 是什么，以及三种浮点 ABI 编出来的汇编长什么样，
见 [00_基础/02](../00_基础/02_ARM寄存器与调用约定.md) 第三、四节，那边有实测的汇编对照。）

IMX6ULL 的 Cortex-A7 带 VFPv4 和 NEON，所以用 hf。

### 2.3 两种 sysroot 布局

sysroot 是"目标系统的根目录"：编译时用的 `stdio.h`、链接时用的 `libc.so`，
必须是给 ARM 的那一份，不能是你 Ubuntu x86 上那一份。

    Debian/Ubuntu multiarch 布局              buildroot / BSP 的独立 sysroot
    ------------------------------------      --------------------------------
    /usr/include/            架构无关头        <sysroot>/usr/include/
    /usr/arm-linux-gnueabihf/include/  ARM 头  <sysroot>/usr/lib/
    /usr/arm-linux-gnueabihf/lib/      ARM 库
    /usr/include/x86_64-linux-gnu/     x86 头   -print-sysroot 返回那个目录
    -print-sysroot 返回 /                       整套目标根文件系统自成一棵树

    优点: 一台机器上可以并存多个架构        优点: 和板子 rootfs 一一对应，
          的库，apt 直接装                        版本完全可控
    风险: /usr/include 也在 ARM 编译器的     用法: 第 2 阶段编内核模块必须用它
          搜索路径里

第 2 阶段编驱动时会换成板子 BSP 里的 `arm-buildroot-linux-gnueabihf-gcc`，
那时 `-print-sysroot` 会返回一个很长的真实路径。

### 2.4 [做 L1] 让工具链自报家门

**先自己想，别急着往下看：**

    问题 1  怎么让编译器自报家门，说出它给哪个平台编、默认什么浮点 ABI？
            线索：几乎所有编译器都有一个"啰嗦模式"开关，一个字母。
    问题 2  怎么知道它去哪些目录找头文件？
            线索：头文件是预处理阶段的事，gcc 里让它只做预处理的选项是 -E。
                  再配上问题 1 那个开关，它会把内部动作全打出来。
                  可是 -E 要一个输入文件，能不能不建文件？
                  提示：很多 Unix 工具用 - 表示"从标准输入读"。
    问题 3  怎么问它某个具体的库文件在哪？
            线索：man gcc 里搜 print-file-name。gcc 有一批 -print-xxx 选项。

自己拼过之后再对答案：

    # 1) 它给谁编？ISA 和默认 ABI
    arm-linux-gnueabihf-gcc -v 2>&1 | grep -E 'Target:|--with-(arch|fpu|float)'
    #                       ^^  ^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    #                       |   |      -E 用扩展正则，| 是"或"，(a|b) 是分组
    #                       |   这些信息走 stderr，2>&1 把它并到 stdout 才能进管道
    #                       -v verbose。单独跑 -v 会刷屏，所以拿 grep 挑重点

    # 2) 头文件去哪找？
    echo 'int main(){}' | arm-linux-gnueabihf-gcc -E -v - 2>&1 \
        | sed -n '/search starts here/,/End of search/p'
    #     ^^^^^^^^^^^^^^^^^^ 造一个最小的合法 C 程序，从管道喂进去，不落文件
    #                                                 -E 只做预处理就停
    #                                                    -v 打印内部动作
    #                                                       -  从标准输入读源码
    #          sed -n '/起/,/止/p'   -n 默认不打印，只打印 p 指定的
    #                                /a/,/b/ 是行范围：从匹配 a 的行到匹配 b 的行

    # 3) 和本机 gcc 对比，看两套路径有没有一条重合
    echo 'int main(){}' | gcc -E -v - 2>&1 \
        | sed -n '/search starts here/,/End of search/p'

    # 4) sysroot 和实际的库在哪？
    arm-linux-gnueabihf-gcc -print-sysroot
    arm-linux-gnueabihf-gcc -print-file-name=libc.so
    #                       ^^^^^^^^^^^^^^^^ 问它"如果我要链接这个库，你会用哪个文件"
    ls /usr/arm-linux-gnueabihf/
    file -L /usr/arm-linux-gnueabihf/lib/libc.so.6
    #    ^^ 跟随符号链接看真身，不加 -L 只会告诉你"这是个 symbolic link"

第 2 条那个技巧视频 4_2-2 的 21:02 处演示过，视频里的说法是
"难道我们想去确定这些路径时，都要去编写 `.c` 文件吗？不需要的"。

**本机实测**，第 1 条从一长串 configure 参数里挑出来的关键几项：

    Target: arm-linux-gnueabihf
    --with-arch=armv7-a+fp          ISA：ARMv7-A 带浮点单元
    --with-float=hard               ABI：hf，对应 2.2 那张寄存器图
    --with-mode=thumb               默认生成 Thumb-2 指令，16/32 位混合，代码更小
    --with-sysroot=/                对应 2.3 讲的 multiarch 布局
    --enable-default-pie            对应 2.8 讲的 e_type 为什么是 DYN
    --includedir=/usr/arm-linux-gnueabihf/include

一条 `-v` 就把本章后面要讲的四件事全预告了。

**本机实测**，第 2 条的输出：

    #include <...> search starts here:
     /usr/lib/gcc-cross/arm-linux-gnueabihf/15/include
     /usr/lib/gcc-cross/arm-linux-gnueabihf/15/../../../../arm-linux-gnueabihf/include
     /usr/include
    End of search list.

第 4 条的 `-print-sysroot` 输出是一个光秃秃的 `/`。这跟"sysroot 是目标系统的
根目录"的说法看起来矛盾，其实就是 2.3 那两种布局的区别。

**[判]** 逐条对着输出回答，答不上来就是没看懂：

    [ ] Target: 那一行完整是什么，四段各管什么
    [ ] --with-float= 的值是 hard 还是 soft，为什么这台机器上是这个值
    [ ] ARM 编译器的头文件搜索路径里，哪几条是它专属的
        （特征：路径里带 arm-linux-gnueabihf 或 gcc-cross）
    [ ] 本机 gcc 的搜索路径里有 x86_64-linux-gnu，ARM 的没有
    [ ] /usr/arm-linux-gnueabihf/lib/libc.so.6 存在，并且 file 一下它是 ARM 的

    注错见红：把第 2 条命令里的 arm-linux-gnueabihf-gcc 换成 gcc 再跑，
    两次输出必须不同。如果一样，说明命令敲错了或者装了个假的。

### 2.5 内核在哪一步拒绝了 ARM 程序

**[做 L1] 同一份源码，两个目标平台**

先自己想：

    问题 1  同一个 .c，怎么分别编出 x86 版和 ARM 版？
    问题 2  编出来之后，怎么一眼看出哪个是哪个？
            线索：有个命令专门用来"猜这个文件是什么"，名字就三个字母。
    问题 3  在 x86 机器上运行 ARM 版会怎样？先预测，再跑，看你猜没猜中。

`hello.c` 自己敲一份，别去资料仓拷：

    #include <stdio.h>
    int main(int argc, char **argv)
    {
        printf("hello, %s\n", argc > 1 ? argv[1] : "world");
        return 0;
    }

    /* 收 argv 是为了后面能传参数进来看效果，
       argc > 1 ? argv[1] : "world" 是三目运算符：有参数就用参数，没有就用 world */

然后：

    gcc                     -o hello_x86 hello.c
    arm-linux-gnueabihf-gcc -o hello_arm hello.c
    #                       ^^ 指定输出文件名。不加 -o 的话产物一律叫 a.out，
    #                          两次编译会互相覆盖

    file hello_x86 hello_arm
    #    file 读文件开头的特征字节来判断类型，不看扩展名。
    #    它认识几千种格式，ELF 只是其中一种。

    ./hello_x86 weidongshan
    ./hello_arm weidongshan          # 这一句会失败，失败方式才是重点
    echo $?                          # $? 是上一条命令的退出码，记住这个数

**本机实测：**

    hello_x86: ELF 64-bit LSB pie executable, x86-64, ... dynamically linked,
               interpreter /lib64/ld-linux-x86-64.so.2
    hello_arm: ELF 32-bit LSB pie executable, ARM, EABI5 ... dynamically linked,
               interpreter /lib/ld-linux-armhf.so.3

    bash: ./hello_arm: cannot execute binary file: Exec format error

视频 4_1-1 的 12:25 处在**板子上**做了这件事的镜像版本：
把 x86 编的 hello 拷到 ARM 板上跑，报的是同一句话。
两个方向报同一个错，说明拦下它的东西两边都有。它是什么，下面两节回答。

[基础] 下面要拆 ELF 文件头。ELF 是什么、section 和 segment 有什么区别、
`.bss` 为什么不占文件空间，见
[00_基础/01_ELF与程序加载](../00_基础/01_ELF与程序加载.md)。
跟 ysyx 的对照：你 `objcopy -O binary` 扔掉的就是这些东西。

### 2.6 那两个被检查的字节

内核检查的是 ELF header 里的 `e_machine` 字段，它在文件开头第 18、19 字节。

    xxd -l 20 hello_arm
    xxd -l 20 hello_x86

**本机实测**（最左边是文件偏移）：

    hello_arm
    00000000: 7f45 4c46 0101 0100 0000 0000 0000 0000  .ELF............
    00000010: 0300 2800                                ..(.

    hello_x86
    00000000: 7f45 4c46 0201 0100 0000 0000 0000 0000  .ELF............
    00000010: 0300 3e00                                ..>.

拆开读：

    偏移   字节          含义
    ----   -----------   ----------------------------------------------------
    0x00   7f 45 4c 46   magic，也就是 '\x7f' 'E' 'L' 'F'。全世界的 ELF 都一样
    0x04   01 / 02       EI_CLASS   01 = 32 位，02 = 64 位
                         hello_arm 是 01，hello_x86 是 02
    0x05   01            EI_DATA    01 = 小端
    0x06   01            EI_VERSION
    0x10   03 00         e_type     0x0003 = ET_DYN，为什么不是 EXEC 见 2.8
    0x12   28 00         e_machine  小端 0x0028 = 40 = EM_ARM      <== 就是它
           3e 00                    小端 0x003e = 62 = EM_X86_64

    对一下 readelf 说的和字节是否一致：
        readelf -h hello_arm | grep -E 'Class|Machine|Type:'

### 2.7 完整的拒绝路径

    ./hello_arm
        |
        v
    bash: fork() + execve("./hello_arm", argv, envp)
        |
        |  用户态到此为止，下面全在内核里
        v
    do_execveat_common()
        |
        v
    bprm_execve()   读文件开头 256 字节到 bprm->buf
        |
        v
    search_binary_handler()   轮流问每个已注册的 binfmt handler：这个你能加载吗
        |
        +--> binfmt_script   头两字节是 #! 吗？   不是        -> -ENOEXEC
        |
        +--> binfmt_elf      头四字节是 \x7fELF 吗？  是
        |       |
        |       v
        |    load_elf_binary()
        |       |
        |       v
        |    elf_check_arch(&elf_ex)
        |       文件里 e_machine == EM_ARM (40)
        |       本机能跑的是 EM_X86_64 (62)
        |       不等                                          -> -ENOEXEC
        |
        +--> binfmt_misc     匹配上任何一条注册规则吗？
        |       这台机器没注册 EM_ARM 的规则                  -> -ENOEXEC
        |
        v
    所有 handler 都拒绝，execve 返回 -ENOEXEC
        |
        v
    bash 把 ENOEXEC 翻译成人话：
        cannot execute binary file: Exec format error

**拦下它的不是 CPU，是内核里一段普通的 if 判断。** CPU 根本没机会看到那些
ARM 指令。这句话是 2.5 那两个方向报同一个错的原因：两边都是 Linux，
两边都跑同一段 `elf_check_arch`。

### 2.8 顺便：为什么 e_type 是 DYN 不是 EXEC

书上常说"可执行文件是 ET_EXEC，共享库是 ET_DYN"，但上面实测出来的可执行文件
是 ET_DYN。因为现代 gcc 默认开 PIE（position independent executable）：
程序编成位置无关的，内核每次加载时随机选一个基址，这叫 ASLR，防溢出攻击用的。
2.4 里 `-v` 打出来的 `--enable-default-pie` 就是它。

    传统 ET_EXEC                      PIE / ET_DYN
    --------------------------        ---------------------------------
    链接时就定死加载地址              加载地址运行时才定，每次都不同
    file 说 "executable"              file 说 "pie executable"

    想看传统形态：
        gcc -no-pie -o hello_nopie hello.c
        readelf -h hello_nopie | grep Type:        -> EXEC

嵌入式上这一位有实际影响：PIE 需要动态链接器参与重定位，
纯静态且 `-no-pie` 的程序才是真正的"拷过去就能跑"。3.7 会看到 `-static` 的产物类型。

### 2.9 binfmt_misc：为什么 WSL 里能直接敲 notepad.exe

2.7 流程图里 `binfmt_misc` 那一支不是摆设。它允许往内核注册一条规则：

    看到文件头是这几个字节 -> 别自己加载，交给我指定的解释器去跑

你这台机器上就有活的例子：

    ls /proc/sys/fs/binfmt_misc/
    cat /proc/sys/fs/binfmt_misc/WSLInterop

**本机实测：**

    $ ls /proc/sys/fs/binfmt_misc/
    WSLInterop  python3.14  register  status

    $ cat /proc/sys/fs/binfmt_misc/WSLInterop
    enabled
    interpreter /init
    flags: P
    offset 0
    magic 4d5a           <-- 'M' 'Z'，Windows PE 文件的头两个字节

    +--------------------+     +-------------------+     +------------------+
    | 你敲 notepad.exe   | --> | 内核看头 2 字节   | --> | 匹配 WSLInterop  |
    +--------------------+     |   是 4d5a 即 MZ   |     | 交给 /init 去跑  |
                               +-------------------+     +------------------+
                                                                |
                                                                v
                                                          转给 Windows 侧执行

同一个机制，把 magic 换成 ELF 头里 `e_machine` 等于 `EM_ARM` 的那几个字节，
解释器换成 `qemu-arm-static`，ARM 程序就能在 x86 上直接跑起来。
Docker 在 x86 机器上拉 arm64 镜像跑，靠的就是这个。

本仓故意没装 `qemu-user-static`，因为装了之后 `./hello_arm` 会真的打印
`hello, weidongshan`，2.10 那条"必须报 Exec format error"的判据就失效了。
等你把这一节吃透，可以自己装上再跑一遍看现象反转，那本身就是最好的验证。

### 2.10 [判] 第 2 节的判据

    [ ] file 的两行输出里，架构字段不同（x86-64 与 ARM），位宽也不同（64 与 32）
    [ ] xxd 看到偏移 0x12 处两个字节，一个是 28 00，一个是 3e 00
    [ ] readelf -h 的 Machine 字段和上面两个字节对得上
    [ ] 运行 hello_arm 报的是 Exec format error，不是 Permission denied
        （后者说明是权限问题，chmod +x 就好，跟架构无关）
    [ ] 说得出 e_type 为什么是 DYN，以及 -no-pie 编出来会变成什么
    [ ] /proc/sys/fs/binfmt_misc/WSLInterop 的 magic 是 4d5a，说得出它是什么

**注错见红。这条务必动手，而且要做两次，对照着看。**

第一次，改动态版：

    cp hello_arm hello_fake
    printf '>' | dd of=hello_fake bs=1 seek=18 conv=notrunc
    #        ^  '>' 的 ASCII 码是 0x3e，正好是 EM_X86_64 的低字节
    #                  bs=1 一次一字节  seek=18 跳到第 18 字节
    #                  conv=notrunc 只覆盖这一字节，不把后面截掉
    xxd -s 16 -l 4 hello_fake            # 确认变成了 0300 3e00
    ./hello_fake; echo "exit=$?"

你把 `e_machine` 从 40 改成了 62，内核那道 if 就骗过去了。**本机实测**的结果
不是段错误，而是：

    bash: ./hello_fake: cannot execute: required file not found
    exit=127

找不到文件？文件明明就在眼前。找不到的是 `.interp` 里写的那个
`/lib/ld-linux-armhf.so.3`，你的 x86 机器上根本没有 ARM 的动态链接器。
也就是说你确实骗过了 arch 检查，内核往下走了一步，卡在了下一关。

第二次，改静态版。它没有 `.interp`，没有下一关：

    arm-linux-gnueabihf-gcc -static -o hello_sta hello.c
    cp hello_sta hello_sta_fake
    printf '>' | dd of=hello_sta_fake bs=1 seek=18 conv=notrunc
    ./hello_sta_fake; echo "exit=$?"

**本机实测：**

    Segmentation fault
    exit=139                            139 = 128 + 11，11 号信号是 SIGSEGV

这一次 CPU 真的开始执行那段 ARM 机器码了。x86 的解码器拿 ARM 字节当 x86
指令啃，几条之内必然踩坏内存。

两次对照，把 2.7 的流程图和 3.6 的加载时序一起验活了：

    e_machine     动态版                        静态版
    -----------   ---------------------------   ---------------------------
    原样 (40)     Exec format error   exit=126  Exec format error   exit=126
                  内核 elf_check_arch 拦下      同左
    改成 62       required file not found       Segmentation fault  exit=139
                  exit=127                      没有 .interp 这一关，内核
                  过了 arch 检查，卡在找 ld.so  直接跳到 ARM 代码入口

    126 是内核不认这个格式；127 是内核认了，但配套的解释器找不到；
    139 是内核放行之后 CPU 自己崩的。三个退出码正好对应流程图上三个位置。

### 2.11 [做 L1] 上板：串口 + NFS，把 hello 跑到板子上

板子已经到货，这一节可以真做了。视频 4_1-1 的 6:20 到 15:25 演示的就是这段，
下面是把它压缩成清单，并且改成 WSL 环境的版本。

**先自己想：**

    问题 1  板子上没有编译器，程序在 PC 上编好，怎么送到板子上去？
            想三种办法，比较它们改一次代码要花几秒。
    问题 2  NFS 是把谁挂到谁身上？挂完之后 PC 上改一个文件，
            板子上看到的是新的还是旧的？
    问题 3  串口那几个参数（波特率、数据位、流控）里，哪一个填错会导致
            "屏幕上什么都不显示"，哪一个会导致"显示乱码"？

**第一步，串口连上板子。**

    参数        值              填错了会怎样
    ----------  --------------  ------------------------------------------
    波特率      115200          填错 -> 满屏乱码（时钟对不上，采样点错位）
    数据位      8
    停止位      1
    校验        无
    流控        无（None）      **没关掉 -> 一个字都不显示，而且你敲什么都没反应**

流控这一条视频里特别强调了两遍（4_1-1 的 7:29 处）：
"这个高级选项一定要设置，把流控给去掉，设置为 None"。
它的机理是硬件流控要靠 RTS/CTS 两根线握手，板子那边没接这两根线，
PC 这边就一直以为对方没准备好，一个字节都不发。

Windows 上用 MobaXterm 或者 PuTTY，COM 口号在设备管理器的"端口"里看。
接上之后回车，输入 `root` 登录。

**第二步，PC 侧把交叉编译产物放进一个目录，导出成 NFS。**

WSL2 里跑 NFS 服务端要装 `nfs-kernel-server`，而且 WSL2 的网络是 NAT 的，
板子直接访问不到。有两条路：

    路 A（推荐）  在 Windows 侧或者路由器同网段的另一台机器上做 NFS 服务端
    路 B          WSL2 配端口转发 + 防火墙放行，麻烦但能通

先不折腾。**第一次上板用最笨但一定成功的办法：U 盘或者 SD 卡拷过去**，
或者用板子的 USB OTG 走 adb push（PDF 99-101 页第 4 章讲了这个）。
把 NFS 留到你要频繁改代码的那一章（第 03 章 Framebuffer，改一次看一次屏幕）。

NFS 挂载命令长这样，四个参数各管一件事：

    mount -t nfs -o nolock,vers=3 192.168.1.137:/home/book/nfs_rootfs /mnt
    #     ^^^^^^                                                      ^^^^
    #     |                                                           挂到板子的哪个目录
    #     -t nfs  设备类型是网络文件系统
    #          ^^^^^^^^^^^^^^^^^^
    #          nolock  不使用文件锁。**漏了这个会卡死**
    #          vers=3  用 NFSv3。服务端是 v4 而客户端默认 v3 时也要显式指定
    #                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    #                            服务端 IP : 服务端导出的目录

视频 4_1-1 的 10:25 处现场踩了这个坑：第一次不加 `nolock` 敲下回车，
"它并没有任何反应""我现在都没办法退出了，只能够重启了"。
挂载卡死之后连 Ctrl-C 都没用，因为进程卡在内核态等锁。

挂载成功之后，PC 上那个目录和板子上的 `/mnt` 是同一份东西：
PC 上重新编译一次，板子上直接 `./hello` 就是新的，不用再拷。

**第三步，在板子上复现 Exec format error。**

这是 2.5 那个实验的镜像版：

    # 在板子上：
    ./hello_x86
    #  预期：-sh: ./hello_x86: cannot execute binary file: Exec format error

    #  预期：hello, weidongshan

**[判] 上板判据**

    [ ] 串口能登录，敲 uname -a 有输出（说明串口参数全对）
    [ ] 板子上跑 hello_x86 报 Exec format error
    [ ] 板子上跑 hello_arm 打印 hello, weidongshan

## 3 第二段：GCC 的四个步骤与"去哪找"

### 3.0 看哪里

    视频    4_2-1（17 分）、4_2-2（23 分），过滤表见 0.2
    PDF     143-153 页。145 页往后那一大段选项清单是从书里截的，当手册用

### 3.1 第一性原理：四个步骤是被历史逼出来的

视频 4_2-1 的 1:00 到 5:20 那五分钟是这一集最有价值的部分，
它没有从"预处理、编译、汇编、链接"讲起，而是反过来推：

    最早    程序员像电工，操作一堆开关和电线
              |
              | 太累
              v
    改进    在纸带上打孔，一条纸带对应一条机器码
              |
              | 还是要记住每条机器码的每一位
              v
    改进    用英文助记符代替机器码           <-- 这就是汇编
              |                                  助记符 -> 机器码 = 汇编
              | 汇编指令还是太多太琐碎
              v
    改进    高级语言 C / C++                 <-- 高级语言 -> 汇编 = 编译
              |
              | 多个文件各自编出机器码，要组装成一个程序
              v
            组装                             <-- 多个 .o -> 一个 app = 链接
              |
              | 源码里的 #include 和 #define 要先处理掉
              v
            预处理                            <-- .c + .h -> .i = 预处理

**所以四个步骤不是设计出来的，是每一层抽象各自留下的一道翻译。**
记住这条推导链，比记住四个名词有用得多：
以后看到任何一个新工具链（Rust、Go、Verilog 综合器），
第一个问题都是"它把哪几层抽象各自翻译到哪里"。

反过来的那一步也有名字：机器码变回汇编叫**反汇编**，调试时会用到。

    源码 hello.c
      |  预处理 cpp        把 #include 展开、#define 替换、#ifdef 裁剪
      v
    hello.i               还是 C，只是没有任何预处理指令了
      |  编译 cc1         C -> 汇编
      v
    hello.s               汇编助记符
      |  汇编 as          汇编 -> 机器码
      v
    hello.o               机器码，但地址还没定，外部符号还是空的
      |  链接 ld          多个 .o + 库 + 启动代码 -> 一个完整程序
      v
    hello                 可执行文件

### 3.2 [做 L1] 亲手拆开四步，并看见 gcc 内部的三个程序

**先自己想：**

    问题 1  gcc 一条命令就编完了，怎么让它停在中间某一步？
            线索：三个选项，各对应一个停点。想想产物的扩展名是什么。
    问题 2  怎么看见 gcc 内部到底调了哪几个程序？
            线索：还是 2.4 那个"啰嗦模式"开关。
    问题 3  语法错误是在哪一步被发现的？先猜，再验。
            线索：预处理只做文本替换，它需要理解 C 语法吗？

答案：

    gcc -E hello.c -o hello.i    # 只预处理。-E 的 E 是 Expand/prEprocess
    gcc -S hello.i -o hello.s    # 只编译到汇编。大写 S
    gcc -c hello.s -o hello.o    # 只汇编。小写 c
    gcc    hello.o -o hello      # 不加参数就是链接

    gcc -v -o hello hello.c 2>&1 | grep -E 'cc1|/as |collect2'
    #   ^^ 把内部调用的每一条命令都打出来

**本机实测**，`-v` 里出现的内部程序（路径已简化）：

    /usr/libexec/gcc/x86_64-linux-gnu/15/cc1          预处理 + 编译，一个程序干两件事
    as                                                 汇编
    /usr/libexec/gcc/x86_64-linux-gnu/15/collect2      链接的外壳，它再去调 ld

ARM 那边同样三个，路径不同：

    /usr/libexec/gcc-cross/arm-linux-gnueabihf/15/cc1
    /usr/lib/gcc-cross/arm-linux-gnueabihf/15/../../../../arm-linux-gnueabihf/bin/as
    /usr/libexec/gcc-cross/arm-linux-gnueabihf/15/collect2

**注意 `cc1` 一个程序干了预处理和编译两件事。** 视频 4_2-1 的 7:21 处就是
在这里卡了一下："显然这一步又做了预处理和编译这两个工作"。
四个逻辑步骤，三个实际程序。

**本机实测**，四步产物的规模（`hello.c` 就是 2.5 那个，加上 `#include <stdio.h>`）：

    hello.c      2 行
    hello.i    840 行        <-- stdio.h 整个被展开进来了
    hello.s     45 行        <-- 变回很短，因为 840 行里绝大部分是声明，不产生代码
    hello.o   1480 字节
    hello    15952 字节

**2 行变 840 行再变 45 行**，这三个数把预处理在干什么讲清楚了：
它把头文件的全部内容原样贴进来，而头文件里绝大部分是函数声明和类型定义，
不产生任何机器码。

`hello.i` 里值得看两处：

    head -20 hello.i        # 开头是一堆 # 1 "xxx.h" 的行标记，
                            # 告诉编译器"下面这些行来自哪个文件的第几行"，
                            # 报错时的文件名行号就是从这来的
    grep -n 'int main' hello.i    # main 在最后面，前面全是展开进来的声明

问题 3 的答案：**预处理不检查语法。** 视频 4_2-1 的 16:54 处现场验了这个：
往 `.c` 里故意插一个语法错误，`gcc -E` 一声不吭，`gcc -S` 才报错。
道理是预处理只做文本替换，它不需要理解 C 语法。

自己验一遍：

    cp hello.c hello_bad.c
    echo 'this is not c' >> hello_bad.c
    gcc -E hello_bad.c -o /dev/null; echo "预处理 exit=$?"
    gcc -S hello_bad.c -o /dev/null; echo "编译   exit=$?"

**顺便一个中文的坑。** "编译"这个词在中文里指三个不同的范围，
视频 4_2-1 的 16:17 处专门提了这件事：

    窄义   .i -> .s 那一步
    中义   预处理 + 编译 + 汇编（也就是 gcc -c 干的事）
    宽义   四步全部（也就是 gcc 一条命令干的事）

读文档时要看上下文。本笔记里凡是需要精确区分的地方都写全称。

### 3.3 一次编多个文件，和分开编再链接

视频 4_2-2 的 0:00 到 6:20 讲的是这件事，它是第 4 节 Makefile 存在的全部理由。

一条命令编两个文件：

    gcc -o test main.c sub.c

它内部做的是：

    main.c --预处理--编译--汇编--> /tmp/xxxx.o  \
                                                 +--链接--> test
    sub.c  --预处理--编译--汇编--> /tmp/yyyy.o  /

中间那两个 `.o` 在 `/tmp` 下，用完就删。**代价是每次都要全部重做一遍。**
视频里把它推到极端：一千个文件，改一个，另外 999 个也要重新处理。

分开编：

    gcc -c -o main.o main.c        # -c 编译不链接，产物留下来
    gcc -c -o sub.o  sub.c
    gcc -o test main.o sub.o       # 只链接

改了 `main.c` 之后只需要重跑第一条和第三条。

**问题是：谁来判断"只需要重跑第一条和第三条"？**
手工判断，文件一多就判断不过来。这就是 make 存在的理由，第 4 节接着讲。

### 3.4 四个"去哪找"

视频 4_1-2 和 4_2-2 反复讲的是同一件事的四个实例。
把它们放在一张表里，这一段就压缩完了：

    找什么                 谁去找        默认去哪找                 怎么加自己的
    ---------------------  ------------  -------------------------  ------------------
    头文件 <stdio.h>       预处理器      工具链的 include 目录      -I<目录>
    头文件 "myhead.h"      预处理器      先当前目录，再同上         -I<目录>
    库文件 libsub.so       链接器        工具链的 lib 目录          -L<目录> 加 -l<名>
    动态库（运行时再找）   ld.so         /lib、/usr/lib 等          LD_LIBRARY_PATH

**最后一行是最容易漏的一条：链接时找得到，不代表运行时找得到。**
这两件事由两个不同的程序、在两个不同的时刻、按两套不同的规则去找。

`-l` 的名字规则：`-lsub` 找的是 `libsub.so` 或者 `libsub.a`，
前面的 `lib` 和后面的后缀都省略掉。

两个最常见的报错，各对应表里的一行：

    fatal error: xxx.h: No such file or directory      头文件没找到  -> 加 -I
    undefined reference to `xxx'                        符号没找到    -> 加 .o 或 -l
    error while loading shared libraries: libxxx.so     运行时没找到  -> LD_LIBRARY_PATH

视频 4_1-2 的 4:32 处把前两个称为"你会经常发现的两个问题"。

### 3.5 [做 L2] 现场做一个静态库和一个动态库

**先自己想：**

    问题 1  静态库和动态库，哪个在链接的时候被复制进可执行文件，
            哪个在运行的时候才加载？
    问题 2  一个只有两个文件的小程序，做成静态库和动态库，
            最终可执行文件的体积会差多少？先猜一个数量级，再跑。
    问题 3  动态库版本编好之后直接跑，会成功还是失败？为什么？

自己敲两个文件：

    /* sub.c */
    #include <stdio.h>
    void sub_func(void) { printf("sub\n"); }

    /* main.c */
    void sub_func(void);
    int main(void) { sub_func(); return 0; }

    注意 main.c 里用的是"声明"而不是 #include。这是 4_1-2 讲的
    .h 声明 / .c 定义分工的最小演示：编译 main.c 时编译器只需要知道
    sub_func 长什么样，不需要知道它在哪。"在哪"是链接器的事。

然后：

    # 先各自编成 .o
    gcc -c -o main.o main.c
    gcc -c -o sub.o  sub.c

    # 静态库：本质就是一堆 .o 打包成一个文件
    ar rcs libsub.a sub.o
    #  ^^ archive。r 插入或替换，c 不存在就创建且不警告，s 建符号索引
    gcc -o test_static main.o libsub.a

    # 动态库：需要位置无关代码
    gcc -shared -fPIC -o libsub.so sub.c
    #   ^^^^^^^ 产物是共享库不是可执行文件
    #           ^^^^^ position independent code，
    #                 因为动态库被加载到什么地址运行时才知道
    gcc -o test_shared main.o -L. -lsub
    #                          ^^^ 去当前目录找库
    #                              ^^^^^ 找 libsub.so 或 libsub.a

**本机实测：**

    1352  main.o
    1480  sub.o
    1626  libsub.a          静态库 = sub.o 加上一点索引开销
    15536 libsub.so         动态库大得多，它自带一套完整的 ELF 结构

    16016 test_static       静态链接
    15944 test_shared       动态链接

    两个可执行文件只差 72 字节。

第 2 问的答案多半和你猜的不一样。**这个例子里静态和动态几乎一样大**，
因为 `sub.c` 本身只有一行代码，复制进去也没多少。
视频 4_2-2 的 13:58 处也说了同一件事："小了若干个字节而已，这很正常"。

体积差异要在库很大的时候才显现。3.7 节 `-static` 那个实验里，
把整个 libc 静态链进来，差的就是 7 倍了。

第 3 问，**本机实测：**

    $ ./test_shared
    ./test_shared: error while loading shared libraries: libsub.so:
    cannot open shared object file: No such file or directory

    $ LD_LIBRARY_PATH=. ./test_shared
    sub

链接的时候你用 `-L.` 告诉了链接器库在当前目录，
但那个信息**没有被写进可执行文件**。运行的时候 `ld.so` 按自己的规则去找，
当前目录不在它的搜索列表里。这就是 3.4 表格最后一行说的那件事。

顺便看一眼"符号没找到"长什么样：

    $ gcc -o t main.c
    /usr/bin/ld: /tmp/ccXXXXXX.o: in function `main':
    main.c:(.text+0x9): undefined reference to `sub_func'
    collect2: error: ld returned 1 exit status

    注意报错的是 ld，不是 cc1。编译 main.c 完全没问题——
    它只需要那句声明。是链接这一步找不到实现。

**[判] 第 3.5 节的判据**

    [ ] ar 出来的 libsub.a，用 ar -t libsub.a 能列出里面有 sub.o
    [ ] nm test_static | grep sub_func 显示 T（有实现）
        nm test_shared | grep sub_func 显示 U（未定义，运行时才填）
    [ ] ./test_shared 直接跑失败，加 LD_LIBRARY_PATH=. 之后成功
    [ ] readelf -d test_shared | grep NEEDED 能看到 libsub.so

    注错见红：把 libsub.so 删掉，test_static 照样能跑，test_shared 跑不了。
    这一条最直观地说明了"静态链接把库搬进了自己的文件里"。

### 3.6 printf 到底是谁在干活

`gcc -o hello hello.c` 编出来的 hello 里，没有 printf 的代码。

[基础] 这一节全程在讲符号和链接。符号表的 U/T/W 各是什么、PLT 和 GOT 为什么
存在，见 [00_基础/04_静态库动态库与符号](../00_基础/04_静态库动态库与符号.md)。
那边有本机实测的 PLT 反汇编，三条指令就把跳板讲完了。

**[做 L1] 把 printf 的去向查出来**

先自己想：

    问题 1  怎么看一个可执行文件里都有哪些符号，哪些是"我需要但我没有"的？
            线索：binutils 里有个两字母的工具，name 的缩写。
    问题 2  .interp 段里存的是一个字符串。怎么把某个 section 的内容当字符串打出来？
            线索：readelf 有个 -p 选项，p 是 printable 的意思。
    问题 3  怎么知道这个程序依赖哪些动态库？
            线索：两条路，一条是读 .dynamic 段，一条是有个三字母命令直接列。

答案：

    nm hello_arm | grep -i printf
    #  ^^ 列符号表。输出三列：地址、类型字母、符号名
    #                 类型字母大小写敏感：大写=全局，小写=文件内可见
    #                 U 表示 undefined，这一列会是空白（还没有地址）

    readelf -p .interp hello_arm
    readelf -p .interp hello_x86

    readelf -d hello_arm | grep NEEDED
    #       ^^ -d 读 .dynamic 段，动态链接的所有信息都在这儿

    ldd hello_x86
    #   ^^^ 递归列出所有依赖库及其加载地址
    #   注意：ldd 对 ARM 文件用不了，它是靠真的跑一遍来列的。
    #         交叉编译的产物只能用 readelf -d 看。

**本机实测：**

    $ nm hello_arm | grep -i printf
             U printf@GLIBC_2.4         <-- U 是 Undefined，这个文件里没有它

    $ readelf -p .interp hello_arm
      [     0]  /lib/ld-linux-armhf.so.3

    $ readelf -p .interp hello_x86
      [     0]  /lib64/ld-linux-x86-64.so.2

**从 execve 到 main，中间还插了一个程序：**

    内核                         ld.so (用户态)             hello (用户态)
    -----------------------      ----------------------     -------------------
    load_elf_binary()
      发现 PT_INTERP 段
      读出里面那个字符串
      /lib/ld-linux-armhf.so.3
      把 ld.so 也 mmap 进来
      跳到 ld.so 入口 --------->  _start
                                   读 hello 的 .dynamic 段
                                   看到 NEEDED libc.so.6
                                   mmap libc.so.6 进地址空间
                                   重定位：把 GOT 表里的
                                   printf 表项填成 libc 里
                                   printf 的真实地址
                                   跳到 hello 的入口 ------>  _start
                                                              __libc_start_main
                                                              main()

所以 `.interp` 段里那个路径不是注释，是内核真的会去读、去加载的一个文件。
**它指定的程序（动态链接器）先于你的 main 运行。**

重定位这一步具体在改什么：

    你的代码           .plt              .got.plt              libc.so.6
    --------------     -----------       ------------------    ----------------
    bl printf ------>  printf@plt -----> [ 一个函数指针 ] ----> printf 的真实代码
                       (跳板)             启动时被 ld.so
                                          填成真实地址

    编译时 gcc 不知道 printf 在哪，就先跳到自家的跳板；
    跳板去查一张表；表在程序启动时由 ld.so 填好。

**这对嵌入式意味着一条硬约束：** 你交叉编译时链接的 libc，
必须和板子 rootfs 里那份 libc 兼容。

    你的 Ubuntu                              板子的 rootfs
    ----------------------------------       ------------------------------
    apt 装的 gcc-arm-linux-gnueabihf         buildroot 构建的
    配的是 Ubuntu 打包的 glibc（较新）       glibc 可能老好几年
              |                                        ^
              | 编出 hello，里面记着                   |
              | printf@GLIBC_2.4                       |
              | 别的符号可能要 GLIBC_2.34              |
              +----------------------------------------+
                       拷过去运行，ld.so 一查：
                       我这儿最高只有 GLIBC_2.28

    ./hello: /lib/libc.so.6: version GLIBC_2.34 not found

这不是你代码的问题，是 sysroot 不匹配。两个解法：

    解法 A（本阶段用这个）  加 -static，把 libc 静态链进去，不依赖板子的库
    解法 B（正式用这个）    用板子 BSP 里的 arm-buildroot-linux-gnueabihf-gcc，
                            它配的就是板子上那份 glibc。第 2 阶段必须换成它

### 3.7 [做 L2] -static 的代价

**先自己想：**

    问题 1  怎么让 gcc 把 libc 整个链进来，不依赖外部 .so？
    问题 2  静态之后，四个观察点（体积、.interp、printf 的符号类型、e_type）
            各会变成什么？先写下预测，再跑。预测错了才有收获。

答案：

    arm-linux-gnueabihf-gcc -static -o hello_arm_static hello.c
    #                       ^^^^^^^ 注意位置：放在 -o 前面。
    #                       放到 -o 后面会被当成输出文件名，这是常见错误

    ls -l hello_arm hello_arm_static
    readelf -p .interp hello_arm_static
    nm hello_arm_static | grep -w printf
    #                          ^^ 全词匹配，不然 fprintf、sprintf 都会被捞出来
    readelf -h hello_arm_static | grep Type:

**本机实测：**

    动态 hello_arm  69,248 字节             静态 hello_arm_static  486,920 字节
    +------------------------+              +----------------------------+
    | ELF header   ET_DYN    |              | ELF header   ET_EXEC       |
    | .interp                |              |   (没有 .interp 段)        |
    |   /lib/ld-linux-       |              |                            |
    |   armhf.so.3           |              |                            |
    | .text                  |              | .text                      |
    |   main                 |              |   main                     |
    |   printf@plt 跳板      |              |   printf 完整实现          |
    | .dynamic               |              |   vfprintf                 |
    |   NEEDED libc.so.6     |              |   malloc / strlen / ...    |
    +------------------------+              +----------------------------+
             |                               自包含，板子上有没有 libc 都能跑
             | 运行时才去板子上找
             v
      /lib/libc.so.6
      版本不对就报 GLIBC_x.xx not found

    $ nm hello_arm_static | grep -w printf
    00010cd5 T printf          <-- 从 U 变成 T，有实际地址了

    $ readelf -p .interp hello_arm_static
    readelf: Warning: Section '.interp' was not dumped because it does not exist

    $ readelf -h hello_arm_static | grep Type:
      Type:  EXEC (Executable file)      <-- 不再是 PIE，没有 ld.so 来做重定位了

代价那一栏别只记"变大了"，记这个量级：**一个 hello world，
为了自带 libc，从 6 万多字节涨到 48 万字节，7.0 倍。**
板子上放几十个这样的程序，rootfs 就撑爆了。
这就是嵌入式上宁可折腾 sysroot 也要用动态链接的原因。

对照 3.5 那个只差 72 字节的实验：静态链接的代价取决于库有多大，
`libsub.a` 只有一行代码，`libc.a` 有整个 C 标准库。

**[判]**

    [ ] 动态版 nm 里 printf 是 U，静态版是 T（或 W）
    [ ] 动态版有 .interp 段，静态版没有
    [ ] 静态版体积是动态版的 5 倍以上
        （本机 486920 / 69248 = 7.0 倍。别背绝对数字，gcc 版本一变就不同）
    [ ] 静态版的 e_type 从 DYN 变成 EXEC，说得出为什么
    [ ] readelf -d hello_arm 能看到 NEEDED libc.so.6，静态版根本没有 .dynamic 段

    注错见红：

        readelf -p .interp hello_arm        2>&1 | grep -c 'ld-linux'
        readelf -p .interp hello_arm_static 2>&1 | grep -c 'does not exist'

    两条都必须是 1。如果第二条是 0，说明 -static 没生效（常见原因：写成了
    -Static，或者放在 -o 后面被当成了输出文件名）。

### 3.8 [做 L2] 绕过 libc，直接跟内核说话

[基础] 用户态怎么请内核干活、`svc` 指令做了什么、缓冲为什么会吃掉你的调试打印，
见 [00_基础/05_系统调用与用户内核态](../00_基础/05_系统调用与用户内核态.md)。
跟 ysyx 的对照：ARM 的 `svc` 就是你实现过的 riscv `ecall`。

视频 4_1-2 的 5:57 处画了三层图：你的 app、库、内核。
下面把那张图的中间一段展开。

`printf` 不是系统调用，`write` 才是：

    printf("hello, %s\n", name)
        |
        |  用户态，全在 libc 内部
        v
    vfprintf()      解析 %s，拼出最终字符串 "hello, world\n"
        |
        v
    stdout 的缓冲区（FILE 结构体里的一块内存）
        |
        |  行缓冲：接到终端时，遇到 \n 才冲刷
        |  全缓冲：重定向到文件时，攒满 4096 字节才冲刷
        |  无缓冲：stderr
        v
    write(1, "hello, world\n", 13)
        |
        |  =========== 用户态 / 内核态 的分界线 ===========
        v
    svc #0          ARM 的系统调用指令（x86-64 上是 syscall）
        |           r7 = 4 (__NR_write), r0 = 1(fd), r1 = buf, r2 = 13(len)
        v
    内核 sys_write()
        |
        v
    tty 驱动 -> 串口 -> 你在 MobaXterm 里看到的那一行

这张图解释了一个嵌入式调试里天天遇到的现象：**程序跑飞了，printf 的内容一个字
都没出来，好像那行代码没执行。** 其实执行了，字符串还躺在缓冲区里，
程序崩了缓冲区就跟着没了。所以调试打印要么加 `\n`，要么 `fflush(stdout)`，
要么直接用 `write`。上板调试时这一条会救你好几次。

**先自己想：**

    问题 1  write 的三个参数分别是什么？去哪查？
            线索：man 2 write。2 是手册第 2 章，专讲系统调用；
                  man 3 是库函数（printf 在这一章）；man 1 是命令。
                  man 2 write 和 man 3 printf 一对比，
                  谁是系统调用谁是库函数一目了然。
    问题 2  第一个参数填 1 是什么意思？2 又是什么？
    问题 3  长度怎么算？直接写死数字和用 strlen 有什么区别？

自己写 `hello_write.c`：不用 printf，用 write 把同样一句话打到屏幕上。
需要 `#include <unistd.h>`。

写完验证：

    arm-linux-gnueabihf-gcc -o hello_write hello_write.c
    arm-linux-gnueabihf-nm hello_write | grep ' U '
    #                                         ^^^^^ 前后各一个空格，
    #                                         精确匹配类型列是 U 的行
    arm-linux-gnueabihf-objdump -d hello_arm_static | grep -B4 'svc' | head -20
    #                           ^^ 反汇编可执行的 section
    #                                              -B4 匹配行的前 4 行也打出来，
    #                                              好看到 svc 之前往 r7 里装了几号

    # x86 版可以用 strace 直接看系统调用
    gcc -o hello_write_x86 hello_write.c
    strace -e trace=write ./hello_write_x86
    #      ^^^^^^^^^^^^^^ 只跟踪 write，不然满屏都是加载动态库的调用

**[判]**

    [ ] 未定义符号列表里没有 printf 了，但仍然有 write
        （write 也在 libc 里，它是对 syscall 的一层薄封装，不是 syscall 本身）
    [ ] 说得清 printf 和 write 的分工：printf 在用户态做格式化和缓冲，
        最终也是调 write
    [ ] 反汇编里找得到 svc 指令。找法：
            arm-linux-gnueabihf-objdump -d hello_arm        | grep -c 'svc'
            arm-linux-gnueabihf-objdump -d hello_arm_static | grep -c 'svc'
        本机实测：动态版 0 条，静态版 15 条。
        动态版是 0 不是 bug，syscall 封装都在 libc.so.6 里，没链进你的文件；
        静态版把 libc 搬进来了，那 15 条就是 write / exit / brk 这些封装的真身。

    注错见红：把 write(1, ...) 的 fd 从 1 改成 2，输出跑到 stderr。
    验证方式 ./hello_write > /dev/null，改之前屏幕上什么都没有，
    改之后字符串照样出现在屏幕上。这条同时也验证了你确实在用 write 而不是 printf。

### 4.1 第一性原理：make 只有一条公理

**make 不理解 C，不理解编译，它只会做一件事：比两个文件的时间戳。**

整个 Makefile 体系都是这一条推出来的。

    规则的形状：

        目标: 依赖1 依赖2 ...
        <TAB>命令

    执行条件只有两个：
        1. 目标文件不存在
        2. 任意一个依赖比目标新

    满足其一，就执行命令。

举例：

    main.c   mtime = 10:00:05          main.o   mtime = 10:00:07
    ---------------------------------------------> 依赖比目标旧，不重编

    main.c   mtime = 10:00:09          main.o   mtime = 10:00:07
    ---------------------------------------------> 依赖比目标新，重编

**比的是 mtime，不是内容哈希。** 直接后果：

    touch main.c        内容一个字没改，依赖它的全部重编
    改完又改回来        内容和原来一样，照样重编

（顺带一提，这也是 ccache 存在的理由：它在 gcc 前面加一层内容哈希缓存，
内容没变就直接吐出上次的 `.o`。你这台机器上已经装了 ccache。）

从这一条公理出发，剩下的一切都是在回答同一个问题：
**"依赖"这张表怎么才能写全、写对、又不用手写。**

    层次一   手写每一条规则                        4.2
      |      问题：一千个文件要写一千条
      v
    层次二   模式规则 %.o : %.c                    4.3
      |      问题：依赖表里少了 .h
      v
    层次三   让编译器自己吐出依赖表               4.6
             这一层不做会出隐蔽 bug

### 4.2 层次一：规则

视频 4_3-2 从 `gcc -o test a.c b.c` 一路推到三条规则，推导过程见 3.3 节。
最终形态：

    test: a.o b.o
    	gcc -o test a.o b.o

    a.o: a.c
    	gcc -c -o a.o a.c

    b.o: b.c
    	gcc -c -o b.o b.c

`make` 不带参数时生成**第一条规则的目标**。它会递归地先满足依赖：
要 `test` 就先要 `a.o`，要 `a.o` 就先看 `a.c` 的时间戳。

**命令前面必须是 TAB，不能是空格。** 这是 Makefile 最著名的坑，
报错是 `missing separator`。编辑器默认可能把 TAB 转成空格，
给 Makefile 单独设一下。

`make xxx` 可以指定生成哪个目标，`make clean` 就是这么工作的。

### 4.3 层次二：模式规则、自动变量、四种赋值

**模式规则**（视频 4_3-3 的 1:19 处）：

    %.o : %.c
    	gcc -c -o $@ $<

    % 是通配符，两边的 % 匹配同一段文字。
    要生成 a.o 时，make 拿 a.o 去套这条规则，% 匹配到 a，依赖就是 a.c。

**三个自动变量**：

    $@   目标
    $<   第一个依赖
    $^   全部依赖，去重

    为什么编译用 $< 而链接用 $^：
        编译     一次只喂一个 .c 给 gcc，所以取第一个依赖
        链接     要把所有 .o 一起喂给 gcc，所以取全部

    这个区别在 4.6 打开自动依赖之后变成硬约束：那时 $^ 里会多出一串 .h，
    喂给 gcc 会出错。

**四种赋值**（视频 4_3-3 的 10:33 到 19:42）：

    :=    即时变量。定义的那一刻就求值，之后右边再变也不影响它
    =     延时变量。用到的时候才求值
    ?=    延时变量，但只在该变量还没被定义过时才生效
    +=    追加。是即时还是延时，取决于前面那个变量是怎么定义的

即时和延时的差别，视频里用这个例子演示的：

    A := $(C)        # 此刻 C 还是空的，所以 A 永远是空
    B  = $(C)        # 用到 B 的时候才去取 C
    C := abc

    all:
    	@echo "A = $(A)"     # A =
    	@echo "B = $(B)"     # B = abc

    注意 make 会先把整个 Makefile 读完再执行规则，所以 C 定义在后面
    对 B 没有影响，对 A 有影响。

自己敲一遍，把 `C := abc` 挪到最前面再跑一次，两次输出对比着看。

**延时变量不能自引用**：`X = $(X) foo` 会让 make 报
`Recursive variable 'X' references itself (eventually)`。
视频 4_3-4 的 8:19 和 4_3-5 的 13:18 各踩了一次。改成 `X := $(X) foo` 即可，
因为即时变量的右边在求值那一刻用的是旧值。

### 4.4 四个函数

视频 4_3-4 讲了四个，加上 4_3-5 用到的一个，本仓的 `project/Makefile` 里全用上了。

    $(wildcard *.c)
        去磁盘上列出匹配的文件。**注意是真的去磁盘找，找不到就不返回。**
        这一条被用在两个完全不同的用途上：
          用途 A  收集源文件      SRCS := $(wildcard *.c)
          用途 B  过滤出真实存在的文件   DEPS := $(wildcard $(DEPS))
                  用途 B 是给 include 用的，见 4.6

    $(patsubst %.c,%.o,$(SRCS))
        模式替换。不匹配的项原样保留。
        简写：$(SRCS:.c=.o)

    $(filter %/,$(LIST))         从列表里挑出符合模式的
    $(filter-out %/,$(LIST))     挑出不符合的
        通用 Makefile 用它区分"这一项是目录还是文件"，见 4.8

    $(foreach d,$(DIRS),$(wildcard $(d)/*.c))
        对列表里每一项做一次展开，结果拼起来。
        project/Makefile 用它收集六个子目录的源文件。

查函数用法就查 GNU make 手册的 Functions 那一章，
视频 4_3-4 全程在演示"忘了就去搜手册"这个动作，这本身也是要学的东西。

### 4.5 假想目标：clean 的那个坑

    clean:
    	rm -f *.o test

平时能用。但如果目录里正好有一个**名字叫 `clean` 的文件**：

    目标 clean 存在
    依赖 一个都没有，没法比时间戳
    -> make 认为目标是最新的
    -> make: 'clean' is up to date.  什么都不做

视频 4_3-3 的 8:03 处现场造了一个 `clean` 文件复现了这个现象。

修法是声明它是假想目标（也叫伪目标）：

    .PHONY: clean
    clean:
    	rm -f *.o test

`.PHONY` 告诉 make："`clean` 不是一个文件名，别去比时间戳，无条件执行。"

自己复现一遍，这一条比看视频印象深：

    touch clean
    make clean          # 预期：什么都不做
    # 加上 .PHONY 那一行再跑
    make clean          # 预期：正常执行

`all` 也要声明，理由相同。

### 4.6 层次三：自动头文件依赖

**这一层是分水岭。视频 4_3-5 整集讲的就是它，是七集里最该逐帧看的一集。**

问题在于：`main.o: main.c` 这条规则里没有 `config.h`。

    Makefile 里写的规则                  实际的 include 关系
    ---------------------                --------------------------
        main.o                               main.o
          |                                    |
          v                                    v
        main.c                               main.c
                                               |
                                               | #include "config.h"
                                               v
                                             config.h      <== make 不知道这条边

你改了 `config.h` 里的一个宏，make 沿着它知道的那条边看：
`main.c` 没变，`main.o` 是最新的，不重编。

视频 4_3-5 的 2:27 处现场演示了这个：改了 `c.h` 里的宏，
`make` 说没事可做，程序输出还是旧值。

**结果是最难查的那类 bug：**

    config.h    struct point { int x, y; }        改成    { int x, y, z; }
    ------------------------------------------------------------------------
    main.o      没重编，还按 8 字节算 sizeof
    display.o   重编了，按 12 字节算
                两边对同一块内存的理解不一样，读出来的坐标全是错的
                编译零警告，跑起来行为诡异

手写依赖是不可能的：视频里说"对我们的内核它有几万个文件，
对于这几万个文件你都要打开确定它的头文件吗"。

**解法：让编译器自己吐出依赖关系。** 四个相关选项，逐级递进：

    gcc -M  c.c              打印完整依赖（含系统头），只打印不编译
    gcc -MM c.c              同上，但跳过系统头
    gcc -MF c.d ...          指定依赖写到哪个文件
    gcc -MD -c -o c.o c.c    边编译边生成 .d
    gcc -MMD -c -o c.o c.c   同上，跳过系统头

    生成的 c.d 内容就是一行普通的 make 规则：
        c.o: c.c common.h config.h

    Makefile 用 include 把所有 .d 读进来，那条虚线就变成实线：

        main.o
          |   \
          v     \
        main.c   config.h

**两种写法，效果一样：**

    教材那套（-MD + wildcard 过滤）           本仓 project/ 用的（-MMD -MP）
    -------------------------------------     ------------------------------
    gcc -Wp,-MD,.$@.d -c -o $@ $<             gcc -MMD -MP -c -o $@ $<

    dep_files := $(foreach f,$(objs),.$(f).d)  -include $(DEPS)
    dep_files := $(wildcard $(dep_files))
    ifneq ($(dep_files),)
      include $(dep_files)
    endif

    wildcard 那步不能省：第一次编译时             -include 对不存在的文件不
    .d 还不存在，include 一个不存在的             报错，所以不用过滤
    文件会让 make 直接报错

    -MD  连系统头一起写进依赖                  -MMD 跳过系统头
                                               （stdio.h 不会变，没必要进表）
                                               -MP  给每个头文件补一条空规则，
                                               这样删掉一个头文件时 make 不会
                                               报 No rule to make target，
                                               而是直接重编

教材那套的价值在于它把每一步都摊开了，值得照着写一遍再换成短的。

**顺便一个视频里踩到的坑**（4_3-5 的 3:54 处）：手工加

    c.o: c.c c.h
    <TAB>

那个 TAB 后面什么都不写，就成了一条**空命令规则**，它会覆盖掉模式规则，
结果是 `c.o` 永远不会被重新生成。删掉那个 TAB 就好了。
这说明 make 里"有命令"和"没有命令"是两回事，空命令也是命令。

**还有一个选项值得现在就加上**（4_3-5 的 14:37 处）：

    CFLAGS := -Werror -Wall

    -Wall     打开常用警告
    -Werror   把警告当错误，编不过去

    视频里的原话：我建议你们编译程序的时候都加上这个选项，
    很多警告都隐藏有错误。

本仓 `project/Makefile` 用的是 `-Wall -Wextra`，没加 `-Werror`。
理由是学习阶段警告太多会挡住进度，但**上板前的最后一次编译建议手工加一次**
`make CFLAGS_EXTRA=-Werror` 看看有没有藏着的问题。

### 4.8 [做 L3] 通用 Makefile：内核那套递归构建

视频 4_3-6 教怎么用，4_3-7 教怎么实现。**这一节要从零复现一遍它。**

**为什么要学它**：本仓的 `project/Makefile` 没有用这套（理由见第 5 节），
但 Linux 内核和 U-Boot 的构建就是这套。第 2 阶段读内核 Makefile 时躲不开。
视频 4_3-7 结尾那句话说得很准："以后我们来分析内核、分析 U-Boot 时，
才需要对 Makefile 有更加深刻的理解。"

**它的设计思想，三条：**

    1. 每个目录一份 Makefile，里面只声明一个变量 obj-y：
           obj-y += main.o
           obj-y += sub.o
           obj-y += a/          <-- 结尾带斜杠的是子目录
       靠结尾那个斜杠区分"这一项是文件还是目录"。

    2. 顶层有一份 Makefile.build，它是递归引擎。
       它被 make -f 反复调用，每次处理一个目录。

    3. 每个目录里的 .o 用 ld -r 合并成一个 built-in.o，
       子目录的 built-in.o 再并进上一层，最后顶层的 built-in.o 链接成程序。

画出来：

        顶层
          main.o  sub.o        a/sub2.o  a/sub3.o
             \      /               \      /
              \    /                 \    /
               \  /              a/built-in.o
                \ |                  /
                 \|                 /
              顶层 built-in.o  <----+
                     |
                     v
                    app

            提示：想想顶层的链接命令要写多长，以及它要怎么知道
            三层深的目录里有哪些 .o。

## 7 已知的坑

    坑 1  串口流控没关掉，屏幕一个字都不显示，而且敲什么都没反应。
          和"波特率填错导致乱码"是两个不同的现象，别混。                    (2.11)

    坑 2  NFS 挂载不加 -o nolock 会卡死，卡死之后 Ctrl-C 无效，只能重启板子。 (2.11)

    坑 3  apt 装的交叉工具链和板子 BSP 的 glibc 版本可能不匹配，动态链接的程序
          拷到板子上会报 GLIBC_2.xx not found。本阶段验证时加 -static 规避，
          第 2 阶段换 BSP 工具链。                                          (3.6)

    坑 4  -static 要放在 -o 前面。放到 -o 后面会被当成输出文件名。           (3.7)

    坑 5  链接时找得到库，不代表运行时找得到。运行时是 ld.so 按另一套规则找。 (3.5)

    坑 6  Makefile 的命令行必须用 TAB 缩进，不能用空格。编辑器默认可能把 TAB
          转成空格，报错是 missing separator。给 Makefile 单独设成 TAB。     (4.2)

    坑 7  一条规则后面跟一个只有 TAB 的空行，它是"空命令规则"，
          会覆盖掉模式规则，导致目标永远不重新生成。                        (4.6)

    坑 8  延时变量不能自引用（X = $(X) foo），会报 Recursive variable。
          改成即时变量 X := $(X) foo。                                      (4.3)

    坑 9  第一次 make 时 .d 文件不存在。用 include 必须先 wildcard 过滤，
          用 -include 则不用管。                                            (4.6)

    坑 10 验证"自动依赖生效了"时，必须先完整 make 一次再 touch 头文件。
          直接 clean 之后 touch 再 make，量到的是"产物不存在所以全编"。      (5.2)

    坑 11 在 /mnt/e/ 下（Windows 文件系统）编译，mtime 精度和 IO 性能都不如
          WSL 原生盘。如果遇到明明改了却不重编的现象，把工程挪到 ~ 下试试。
          project/check.sh 就是把整个工程复制到临时目录再跑的，原因之一就是这个。

    坑 12 wildcard 收集源文件时，如果误留了一个带 main() 的测试文件，
          链接会报 multiple definition of main，报错信息不直观。            (5.2)

    坑 13 装了 qemu-user-static 之后，x86 上直接跑 ARM 程序会成功而不是报错。
          本仓故意没装，为的是保住第 2.10 节那条判据。哪天你发现 ./hello_arm
          居然跑起来了，先去看 /proc/sys/fs/binfmt_misc/ 下多了什么。       (2.9)

    坑 14 视频 4_3-2 起讲的源码在 04_2018Makefile 目录，
          不是视频里口播的那个路径。这是视频剪辑复用旧素材造成的。          (4.0)
