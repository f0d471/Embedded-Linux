## 零、这一章在整个系统里的位置

嵌入式 Linux 开发里，你写的每一行代码最终都要经过同一条路：

    源码 -> 交叉编译器 -> ELF 可执行文件 -> 传到板子 -> 内核 execve 加载 -> 跑起来

这一章讲的就是这条路的前半段。它不是入门礼节，是后面所有章节的地基：
第 2 阶段编内核模块时，工具链选错了直接编不过；项目做到几万行时，
Makefile 写错了每次改一个头文件都要全量重编。

PDF 这三章讲得偏操作手册，给的是命令清单。下面补的是它没讲透的部分。

## 一、解读

### 1.1 交叉编译这个词掩盖了三件独立的事

一个编译器要给某个平台产出可执行文件，需要三样彼此独立的信息：

1. 指令集（ISA）：把 C 翻译成 ARMv7-A 的机器码还是 x86-64 的机器码。
   这决定了 .text 段里的字节。

2. ABI：函数参数放哪个寄存器、结构体怎么对齐、浮点数用什么方式传递、
   栈帧怎么组织。同一个指令集可以有多套互不兼容的 ABI。

3. sysroot：目标系统的头文件和库在哪。编译时用的 stdio.h、链接时用的
   libc.so，必须是目标板子上那一份，不能是你 Ubuntu 上那一份。

工具链的名字把这三件事编码进去了。看这两个名字：

    arm-linux-gnueabihf-gcc                 apt 装的那个
    arm-buildroot-linux-gnueabihf-gcc       板子 BSP 里那个

拆开读（这叫 target triplet，实际常常是四段）：

    arm         架构。IMX6ULL 是 Cortex-A7，ARMv7-A。
    buildroot   厂商/构建者标识。apt 那个省略了这一段。
    linux       目标操作系统。决定用哪套系统调用约定、链接什么 C 库。
    gnueabi     ABI。gnu 表示配 glibc，eabi 是 ARM 的标准嵌入式 ABI。
    hf          hard float。浮点参数通过 VFP 寄存器传递，而不是拆成整数
                走通用寄存器（那叫 softfp 或 soft）。

hf 这一位是硬约束：hf 编出来的 .o 和 soft 编出来的 .o 链接不到一起，
链接器会直接报 ABI 冲突。IMX6ULL 的 Cortex-A7 带 VFPv4 和 NEON，所以用 hf。

亲手验证这三件事：

    arm-linux-gnueabihf-gcc -v 2>&1 | tail -3
    # 看 Target: 和 --with-arch= --with-float= 这些配置项

    echo 'main(){}' | arm-linux-gnueabihf-gcc -E -v - 2>&1 | sed -n '/search starts here/,/End of search/p'
    # 看它到底去哪些目录找头文件，这就是 sysroot

    arm-linux-gnueabihf-gcc -print-sysroot
    arm-linux-gnueabihf-gcc -print-search-dirs

### 1.2 内核到底是在哪一步拒绝 hello_arm 的

在 x86 机器上运行 ARM 版 hello，报 cannot execute binary file: Exec format error。
这个错误的完整路径是：

    shell 调 execve("./hello_arm", ...)
      -> 内核 do_execveat_common()
      -> search_binary_handler() 依次问每个已注册的 binfmt handler：这个文件你能加载吗
      -> binfmt_elf 的 load_elf_binary() 读 ELF header
      -> 检查 e_machine 字段是否等于本机架构（x86-64 上是 EM_X86_64 = 62）
      -> hello_arm 的 e_machine 是 EM_ARM = 40，不匹配，返回 -ENOEXEC
      -> 所有 handler 都说不行，execve 最终返回 ENOEXEC
      -> shell 把 ENOEXEC 翻译成那句人话

关键点：拦下它的不是 CPU，是内核里一段普通的 if 判断。CPU 根本没机会看到
那些 ARM 指令。你可以亲眼看到那个被检查的字节：

    readelf -h hello_arm | grep -E 'Class|Machine|Type|Entry'
    readelf -h hello_x86 | grep -E 'Class|Machine|Type|Entry'
    xxd hello_arm | head -1        # 第 18-19 字节（小端）就是 e_machine

这也解释了 binfmt_misc：往 /proc/sys/fs/binfmt_misc/register 里注册一条规则，
让内核遇到 e_machine 为 EM_ARM 的文件时改用 qemu-arm 去加载，ARM 程序就能在
x86 上跑起来。这就是 Docker 跨架构镜像的原理。

### 1.3 printf 到底是谁在干活

gcc -o hello hello.c 编出来的 hello 里，没有 printf 的代码。验证：

    nm hello_x86 | grep printf        # 显示 U printf，U 表示 Undefined
    objdump -d hello_x86 | grep -B2 -A3 printf   # 看到的是跳到 PLT 桩

真正发生的事：

    可执行文件里有一个 .interp 段，内容是一个路径字符串：
        readelf -p .interp hello_x86      # /lib64/ld-linux-x86-64.so.2
        readelf -p .interp hello_arm      # /lib/ld-linux-armhf.so.3

    内核加载 ELF 时，如果发现有 PT_INTERP 段，它不会直接跳到程序入口，
    而是先把 .interp 指定的那个动态链接器也加载进内存，然后跳到链接器的
    入口。链接器在用户态跑起来，负责：
      - 读 .dynamic 段，找出依赖了哪些 .so（ldd 看的就是这个）
      - 把这些 .so mmap 进地址空间
      - 重定位：把 GOT 表里的 printf 表项填成 libc 里 printf 的真实地址
      - 最后才跳到 main

所以对嵌入式来说有一条硬约束：你交叉编译时链接的 libc，必须和板子
rootfs 里那份 libc 兼容。apt 装的 arm-linux-gnueabihf 用的是 Ubuntu 打包的
glibc（较新），板子的 rootfs 是 buildroot 构建的 glibc（可能较旧）。
用前者编出的动态链接程序拷到板子上，很可能报：

    ./hello: /lib/libc.so.6: version GLIBC_2.34 not found

这不是你代码的问题，是 sysroot 不匹配。两个解法：

    解法 A（本阶段用这个）：加 -static，把 libc 静态链进去，不依赖板子的库。
                            代价是体积从 6KB 涨到 500KB 以上。
    解法 B（正式用这个）：下载板子 BSP，用里面的 arm-buildroot-linux-gnueabihf-gcc。
                          第 2 阶段编驱动时必须用它，那时再装。

对照 PDF 1.2 节问的那几个问题，答案就在这里：交叉编译器的头文件和库
路径就是它自带的 sysroot；-I 指定头文件目录，-L 指定库目录，-labc
链接 libabc.so 或 libabc.a。

### 1.4 静态与动态，在嵌入式上不是随便选

    动态链接    程序小，多个程序共用一份 libc.so，rootfs 总体积小。
                但要求板子上必须有匹配版本的 .so。
                量产工具项目最终要用 freetype、tslib 这些第三方库，
                每个都要交叉编译并把 .so 放到板子上。

    静态链接    程序自包含，拷过去就能跑，不管板子上有什么。
                但每个程序都带一份 libc，几十个程序就是几十份。
                嵌入式里常用于救援工具、bootloader 阶段的程序，
                以及现在这种只是想验证一下的场景。

后面第 6 章交叉编译 freetype 时会真正踩到这个取舍。

### 1.5 Makefile 的三个层次

PDF 3.1 节把 Makefile 从简单到复杂演进了 5 版，那个演进过程本身就是知识。
拆成三个层次看：

层次一，规则模型：

    目标: 依赖
    <TAB>命令

    命令执行的条件只有两个：目标不存在，或任一依赖比目标新。
    make 靠的是文件 mtime，不是内容哈希。这有个直接后果：
    touch 一个内容没变的 .h，依赖它的 .c 也会重编。

层次二，消除重复：

    %.o : %.c
        gcc -c -o $@ $<

    模式规则加自动变量。$@ 是目标，$< 是第一个依赖，$^ 是全部依赖。
    到这一步 Makefile 已经不用为每个文件写一条规则了。

层次三，自动头文件依赖（最关键，也是初学者最容易糊弄过去的一层）：

    问题：main.o: main.c 这条规则里没有 main.h。你改了 main.h，
    make 认为 main.o 是最新的，不重编。结果编出来的程序用的是旧的
    结构体定义，运行时行为诡异。在一个几十个文件的项目里，这类 bug
    极难定位。

    解法：让编译器自己吐出依赖关系。gcc 的 -MD 选项在编译 main.c 时
    会顺便生成一个 .d 文件，内容就是：

        main.o: main.c main.h sub.h stdio.h ...

    然后 Makefile 用 include 把所有 .d 文件包含进来，这些依赖关系就
    自动生效了。PDF 里那两个函数就是干这个的：

        dep_files := $(foreach f, $(objs), .$(f).d)   # 拼出 .d 文件名列表
        dep_files := $(wildcard $(dep_files))         # 过滤掉还不存在的
        ifneq ($(dep_files),)
          include $(dep_files)
        endif

    wildcard 那一步不能省：第一次编译时 .d 文件还不存在，直接 include
    一个不存在的文件会让 make 报错。

    编译命令对应改成：

        gcc -Wp,-MD,.$@.d -c -o $@ $<

这三层缺一不可，尤其第三层。资料仓 05_general_Makefile 里那套通用 Makefile，
以及量产工具项目用的构建系统，本质就是把这三层封装好，再加上多级子目录支持。

### L1 复现：同一份源码，两个目标平台

    cd /mnt/e/Workspace/embedded-linux/labs
    mkdir -p 01_toolchain && cd 01_toolchain
    cp "/mnt/e/Workspace/01_all_series_quickstart-master/01_all_series_quickstart-master/04_嵌入式Linux应用开发基础知识/source/01_hello/hello.c" .

    sudo apt install -y gcc-arm-linux-gnueabihf file binutils-arm-linux-gnueabihf

    gcc                     -o hello_x86 hello.c
    arm-linux-gnueabihf-gcc -o hello_arm hello.c

    file hello_x86 hello_arm
    readelf -h hello_arm | grep -E 'Class|Machine|Entry'
    readelf -p .interp hello_arm
    ldd hello_x86
    ./hello_arm weidongshan          # 预期报 Exec format error

判据：

    [ ] file 的两行输出里，架构字段不同（x86-64 与 ARM）
    [ ] readelf -h 的 Machine 字段，一个是 Advanced Micro Devices X86-64，一个是 ARM
    [ ] .interp 段的内容，两者是不同的动态链接器路径
    [ ] 运行 hello_arm 的报错是 Exec format error，不是 Permission denied
        （如果是后者说明是权限问题，不是架构问题）

记录（做完填）：

    file hello_x86:
    file hello_arm:
    hello_arm 的 e_machine =
    hello_arm 的 .interp =

### L2 改造：把动态变静态，把 printf 换成 write

改造目标一，静态链接：

    arm-linux-gnueabihf-gcc -static -o hello_arm_static hello.c
    ls -l hello_arm hello_arm_static
    readelf -p .interp hello_arm_static     # 预期：找不到 .interp 段
    nm hello_arm_static | grep -w printf    # 预期：printf 有地址了，不再是 U

判据：

    [ ] 静态版体积比动态版大一个数量级以上
    [ ] 静态版没有 .interp 段
    [ ] nm 里 printf 从 U 变成了 T 或 W（有了实际地址）

改造目标二，绕过 libc 直接用系统调用：

    把 hello.c 改成不用 printf，改用 write(1, buf, len) 输出。
    需要 include unistd.h，长度用 strlen 或手工算。然后：

    arm-linux-gnueabihf-gcc -o hello_write hello_write.c
    nm hello_write | grep -E ' U '          # 看还剩哪些未定义符号

判据：

    [ ] 未定义符号列表里没有 printf 了，但仍有 write
    [ ] 能说清 write 和 printf 的区别：printf 在用户态做格式化和缓冲，
        最终也是调 write；write 是对 syscall 的一层薄封装。
        用 objdump -d 找到 write 的实现，看它是不是就几条指令加一个 svc。

### L3 从零写：一个四文件工程加一份手写通用 Makefile

不要看资料仓的 05_general_Makefile，自己写。写完再去对照，看差在哪。

工程要求：

    labs/01_toolchain/mini_proj/
        main.c          调用 add() 和 print_banner()
        math_ops.c      实现 add()
        math_ops.h
        display.c       实现 print_banner()，内部 include config.h
        display.h
        config.h        定义一个宏 BANNER_TEXT

Makefile 要求（这就是后面项目要用的那套，一次写对）：

    1. 源文件列表用 $(wildcard *.c) 自动收集，新增 .c 不改 Makefile
    2. 模式规则 %.o : %.c，不为每个文件写规则
    3. 用 -Wp,-MD 生成 .d 文件并 include，实现头文件自动依赖
    4. 支持 make CROSS=arm-linux-gnueabihf- 切换交叉编译，默认为空即本地编译
    5. make clean 删掉所有 .o、.d 和可执行文件
    6. 编译选项统一走一个变量，方便加 -Wall -O2

判据（这几条必须逐条注错见红）：

    [ ] 判据 1  make 后能跑，输出正确
    [ ] 判据 2  改 config.h 里的 BANNER_TEXT，再 make，display.o 必须重编，
                程序输出必须跟着变。
                注错方式：把 include .d 那几行注释掉，再改 config.h，
                make 应该表现为什么都没做，程序输出不变。见到这个现象
                才算真懂了第三层。
    [ ] 判据 3  新建一个 extra.c 并在 main.c 里调用它的函数，不改 Makefile，
                make 必须成功
    [ ] 判据 4  make clean && make CROSS=arm-linux-gnueabihf- 后，
                file 显示产物是 ARM
    [ ] 判据 5  make clean 后目录里没有任何 .o .d 和可执行文件
                （用 ls -a 检查，.d 是隐藏文件容易漏）

### L4 入项目：搭出 project/ 最小框架

这是本章的最终产出，也是整个项目的第一块地基。

目标：搭出一个能编译、能运行、分层清楚、但每一层都还是空壳的框架。
后面每学完一个层级，就往对应目录里填真实实现，框架本身不用再动。

目录规格：

    project/
        Makefile                顶层，统一收集各子目录源文件
        main.c                  只做三件事：调各层 init、跑主循环、退出时调各层 exit
        include/
            common.h            公共类型、错误码、日志宏
        display/
            disp_manager.c      目前只有 display_init() { return 0; }
            disp_manager.h
        input/
            input_manager.c
            input_manager.h
        font/
            font_manager.c
            font_manager.h
        ui/
        page/
        business/
        build/                  编译产物，不进 git

框架的硬性要求：

    1. main.c 里绝对不出现任何具体硬件操作。它只认各层的 init/exit 接口。
       这一条是整个项目能长大的前提，现在破了后面就回不来了。

    2. 每一层的 .h 只暴露该层对外的接口，不暴露内部结构体细节。
       层与层之间只能通过 .h 里声明的函数通信。

    3. 顶层 Makefile 复用 L3 写的那套，扩展成支持多级子目录。
       新增一个 .c 文件到任何子目录，不需要改 Makefile。

    4. 支持两个构建目标：

           make                                   本地 x86 版，用于逻辑调试
           make CROSS=arm-linux-gnueabihf-        ARM 版，用于上板

       产物分别放 build/x86/ 和 build/arm/，互不覆盖。

    5. 日志宏统一在 common.h 里定义，带文件名行号，可以整体关闭。

判据：

    [ ] make && ./build/x86/product_tool 能跑，每一层打印一行 init OK，
        然后正常退出，退出时每层打印 exit OK，顺序与 init 相反
    [ ] make CROSS=arm-linux-gnueabihf- 出的产物 file 显示 ARM
    [ ] 在 display/ 下新建一个 disp_dummy.c，不改 Makefile，make 成功且
        新文件确实被编译了（检查 build/x86/ 下有对应 .o）
    [ ] 改 include/common.h，所有层的 .o 全部重编
    [ ] 两个构建目标的产物同时存在，互不干扰
    [ ] 把 main.c 里某一层的 init 调用删掉，程序少打印一行，其他层不受影响
        （说明层与层之间没有隐式耦合）

## 四、已知的坑

    坑 1  apt 装的交叉工具链和板子 BSP 的 glibc 版本可能不匹配，动态链接
          的程序拷到板子上会报 GLIBC_2.xx not found。本阶段验证时加 -static
          规避，第 2 阶段换 BSP 工具链。

    坑 2  Makefile 的命令行必须用 TAB 缩进，不能用空格。编辑器默认可能
          把 TAB 转成空格，报错信息是 missing separator。建议在
          .editorconfig 或编辑器里给 Makefile 单独设成 TAB。

    坑 3  第一次 make 时 .d 文件不存在，直接 include 会报错，必须先用
          wildcard 过滤。

    坑 4  在 /mnt/e/ 下（Windows 文件系统）编译，make 依赖的 mtime 精度
          和性能都不如 WSL 原生盘。如果遇到明明改了却不重编的现象，
          把工程挪到 ~ 下试试。

    坑 5  用 wildcard 收集源文件时，如果误留了一个带 main() 的测试文件，
          链接时会报 multiple definition of main，报错信息不直观。
