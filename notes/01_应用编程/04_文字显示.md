## 0 这份笔记怎么用

### 0.1 这一章在做什么

> **屏幕不认识字符，只认识像素。** 显示文字，就是先从字节流还原“这是哪个字符”，
> 再从字体里取出“这个字符长什么样”，最后把字形变成像素覆盖率，交给 display 层写进 framebuffer。

上一章已经能在任意 `(x, y)` 画一个指定颜色的像素。现在输入一个字符串 `A中`，
不能把这几个字节直接写进显存：`0x41` 是一个数字，不是 A 的形状；
`e4 b8 ad` 是“中”的 UTF-8 字节，也不是“中”的点阵。

中间至少隔着四次翻译：

```text
文件/参数里的字节       e4 b8 ad
       | UTF-8 解码
       v
字符的身份             U+4E2D
       | 字体 charmap 查找
       v
字体里的 glyph         宋体的“中”轮廓
       | 光栅化
       v
灰度覆盖图             每格 0..255
       | 颜色混合 + display 层
       v
framebuffer 像素       RGB565 或 XRGB8888
```

教材按历史顺序讲三种办法：

```text
ASCII 8x16       编码值直接当数组下标；固定 8x16；每像素只有亮/灭
HZK16            GB2312 两字节算区位；固定 16x16；每像素只有亮/灭
FreeType + TTF    Unicode 码点查 glyph；任意字号；灰度抗锯齿；按基线排版
```

前两种不是“学完就丢”的旧技术。它们把完整链路压缩到几十行，正适合看清：
**编码负责选哪一项，字体负责那一项里面有哪些点。** FreeType 只是把“查表和造点阵”做得更完整。

**读之前先补两篇基础：**

```text
[基础 11] 数据表示：字节序、位序与定点数
          UTF-16LE/BE、点阵左右方向、FreeType 26.6 坐标       读第 2 节之前

[基础 12] 第三方库的交叉构建与部署
          build/host、prefix/DESTDIR、-I/-L、运行时找库       读第 5 节之前
```

还会继续用到 [基础 03] ABI 与 sysroot、[基础 04] 静态库动态库与符号、
[基础 07] 虚拟内存与 mmap、[基础 10] 显示原理。

**本章路线：**

```text
第 2 节  字节怎么还原成字符：ASCII、Unicode、UTF-8/UTF-16
第 3 节  字符怎么变成固定点阵：8x16 ASCII
```

PDF 和资料源码有六处必须带着问号读：

**1. “UTF-16 每个字符两个字节，所以表不全 Unicode”已经过时。**
现代 UTF-16 的一个**编码单元**是 16 位；BMP 内多数码点用一个编码单元，
U+10000 以上用一对 surrogate，共 4 字节。它能表示到 U+10FFFF。见第 2.4 节。

**2. “ANSI”不是一种固定编码。** Windows 记事本旧菜单里的 ANSI 指当前系统代码页；
简体中文机器通常是 CP936/GBK，不应把 ANSI、GB2312、GBK 三个名字当同义词。见第 2.3 节。

**3. HZK16 示例让源码文件编码决定运行时输入。** `unsigned char str[] = "中"` 只有在执行字符集
恰好是 GB2312/兼容编码时才给出 `d6 d0`。本章实验把两个字节显式写在命令行，
项目接口则统一接 UTF-8，再解码/映射，不把编辑器保存格式当 API。见第 4.2 节。

**4. 三份显示源码又写了一遍错误的行宽公式。** 它们使用
`var.xres * var.bits_per_pixel / 8`；第 03 章已实测行尾可能有 padding，
必须用 `fix.line_length`。本项目 font 层不碰 `/dev/fb0`，只调用 display 层。

**5. FreeType 示例用 `q * bitmap->width + p` 跨行。** 正确跨距是 `bitmap->pitch`，
而且 pitch 可能为负。宽度是有效像素数，不承诺等于每行内存字节数。见第 6.3 节。

**6. bitmap 的一个字节不是 RGB 蓝色。** 默认灰度光栅化时，它表示覆盖率 0..255；
示例直接把它当 `0x000000BB` 写入 framebuffer，只会得到深浅不同的蓝色，
不是任意前景色的抗锯齿。正确做法是 alpha 混合。见第 6.4 节。

## 1 一张脉络图

整条文字显示链可以拆成七步：

| 顺序 | 所在层 | 输入 → 输出 | 负责什么 |
|---|---|---|---|
| 1 | 用户态编码层 | 文件、`argv` 或 socket 中的 `41 e4 b8 ad` → `U+0041 U+4E2D` | 验证并解码 UTF-8，回答“字符是谁” |
| 2 | 用户态字体层 | 码点 + 8×16/HZK16/TTF(TTC) 字体 → glyph id/轮廓 | charmap 选择“这个字体中的哪一个字形” |
| 3 | 用户态字体层 | glyph 轮廓 → `FT_Bitmap` | 光栅化得到灰度覆盖率及 `width/rows/pitch`、`left/top/advance` |
| 4 | 用户态显示层 | 覆盖率 + 前景/背景 RGB → 最终像素色 | alpha 混合、裁剪、格式转换 |
| 5 | 用户态显示层 | 像素色 → 已 `mmap` 的 framebuffer | 描点；映射完成后这一步不再进内核 |
| 6 | 硬件 LCDIF | 持续扫描 framebuffer | 输出显示信号 |
| 7 | HDMI 屏 | 显示信号 → 画面 | 呈现文字 |

三条边界要始终守住：

1. **编码边界**：`char *` 是字节流，不是 Unicode 码点数组；先验证并解码 UTF-8。
2. **字体边界**：字体库产出覆盖图和排版度量，不知道 framebuffer 是 565 还是 8888。
3. **显示边界**：display 层知道行宽、位段、裁剪和背景色；font 层不再打开 `/dev/fb0`。

教材示例为了单文件演示，把三层全部揉在一个 `.c` 里。本章先照它看清原理，
第 9 节再把边界立回来。

## 2 第一段：字节怎么还原成字符

### 2.1 第一性原理：身份和形状必须分开

打开同一个 TXT 文件，换宋体、黑体、斜体，字节一个没变，屏幕形状却变了。
这已经证明两个事实：

> **字符（character）**：文字系统里的抽象单位，例如拉丁字母 A、汉字“中”。
>
> **字形（glyph）**：某款字体把某个字符画成的具体形状。同一个字符可以有很多 glyph 风格。

计算机还缺一座桥：文件里只有数字，怎么指明“我要字符中”？

> **字符集（character set）**：给每个字符分配一个编号的集合。
>
> **码点（code point）**：字符在字符集里的编号。Unicode 写成 `U+XXXX`，例如“中”是 U+4E2D。
>
> **字符编码（encoding）**：把码点变成一串可保存、可传输字节的规则，例如 UTF-8、UTF-16。

把四个概念串起来：

| 问题 | 处理链 |
|---|---|
| “它是谁” | 字符“中” → Unicode 码点 `U+4E2D` → UTF-8 字节 `e4 b8 ad` |
| “它长什么样” | `U+4E2D` → 宋体中的 glyph → FreeType 光栅化 → 灰度点阵 |

**编码回答“它是谁”，字体回答“它长什么样”。** 一个编码不包含笔画，
一个字体也不能替文件决定那三个字节该解成什么字符。

### 2.2 ASCII 到 Unicode：先统一身份证号

ASCII 用 7 bit 表示 128 个编号：

```text
'A' = 0x41 = 65
'0' = 0x30 = 48
'\n'= 0x0a = 10
```

第 8 位为 0，所以 ASCII 文本的每个字符恰好一个字节。问题是 128 个位置装不下中文。

早期扩展方案让 `0x80..0xff` 或双字节的含义随地区变化：简体中文、繁体中文、
西欧各维护一套表。同一串字节不带代码页标签，换一张表就变成另一个字符，这就是乱码的根源。

Unicode 的第一步不是规定文件怎么存，而是先建立一张全球共享的“身份证表”：

```text
A        U+0041
中       U+4E2D
🙂       U+1F642
```

ASCII 的 0..127 被原样保留，所以 U+0041 仍是 A。Unicode 解决了“编号一对多”；
但码点是抽象整数，文件仍是一排字节，还要第二步 UTF-8/UTF-16 来编码。

### 2.3 “ANSI”为什么不能写进接口文档

教材用记事本的“ANSI”菜单演示 GB2312。要把说法收紧：

> **代码页（code page）**：一张“字节值 -> 字符”的地区性映射表。
> Windows 旧界面里的“ANSI”通常表示当前系统的 ANSI code page，不是一个全球固定格式。

简体中文 Windows 常见 CP936，它以 GBK 为主体并兼容 GB2312；“中”的常见双字节是 `d6 d0`。
但把同一字节交给 Big5、Windows-1252 或 ISO-8859-1，结果可能不同。

因此接口不能只写：

```text
input: ANSI string        # 不完整：哪一个代码页？
```

至少要写成：

```text
input: UTF-8 byte string
```

或在遗留接口里明确 `GB2312` / `GBK(CP936)`。本项目从边界开始统一 UTF-8，
只有读取 HZK16 时才把 Unicode/输入字符映射到它要求的 GB2312 区位。

### 2.4 UTF-16LE/BE：一个编码单元两个字节

先读 [基础 11] 第二节。对于 BMP 内的“中” U+4E2D：

```text
UTF-16LE: ff fe | 41 00 | 2d 4e
          BOM     A       中

UTF-16BE: fe ff | 00 41 | 4e 2d
          BOM     A       中
```

> **BOM（byte order mark）**：文件开头可选的 U+FEFF 编码结果，用来提示 UTF-16 的端序；
> 它不是正文字符。UTF-8 的 BOM `ef bb bf` 只标格式，不标端序。

PDF/视频说 UTF-16“每个字符两个字节，不能表示全部 Unicode”。准确说法是：

```text
一个 UTF-16 code unit = 16 bit
U+0000..U+FFFF 中除 surrogate 区外      1 个 code unit = 2 字节
U+10000..U+10FFFF                       2 个 surrogate code unit = 4 字节
```

所以 UTF-16 能覆盖 Unicode 全范围，只是不能假设“字符数 = 字节数/2”。
组合字符、emoji 序列进一步说明“用户眼中的一个字”也不一定等于一个码点，放到延伸 A。

### 2.5 UTF-8：每个首字节自己报告长度

UTF-8 的前缀规则：

```text
码点范围            字节模板
U+0000..U+007F       0xxxxxxx
U+0080..U+07FF       110xxxxx 10xxxxxx
U+0800..U+FFFF       1110xxxx 10xxxxxx 10xxxxxx
U+10000..U+10FFFF    11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

“中” U+4E2D：

```text
e4       b8       ad
11100100 10111000 10101101
    0100   111000   101101   去掉前缀并拼接
    0100 1110 0010 1101    = 0x4e2d
```

首字节 `1110` 表示本字符共 3 字节；后续字节必须以 `10` 开头。
这让解码器在遇到损坏后能重新寻找边界，但视频里“丢一个字节完全不影响其他字符”要加条件：
错误周围可能产生一个或多个 replacement character，**后面的合法首字节能重新同步**，
具体替换个数由解码策略决定。

一个合格解码器还必须拒绝：

```text
c0 af          过长编码：本可用一个字节表示，却故意写成两个
ed a0 80       surrogate U+D800，不是合法 Unicode scalar value
f4 90 80 80    超过 U+10FFFF
单独的 80..bf  没有首字节的 continuation byte
```

只检查“后续字节以 10 开头”不够。

### 2.6 [做 L2] 写 UTF-8 解码器，并让坏输入只伤局部

**先自己想：** 函数输入应该是什么？至少要有“当前指针 + 剩余长度”，
否则遇到截断的三字节序列会越界读。失败时是跳过整个预计长度，还是只跳 1 字节？

本仓 `utf8.c` 的约定：

```text
成功    返回消耗 1..4 字节，写出 uint32_t 码点
失败    返回 -1；调用者记一个错误，只跳过当前 1 字节，再尝试同步
```

构建和正确输入：

```bash

gcc -Wall -Wextra -Werror -O2 -o utf8 utf8.c
./utf8 'A中🙂'
```

实测：

```text
bytes=8
U+0041 at=0 len=1
U+4E2D at=1 len=3
U+1F642 at=4 len=4
summary codepoints=3 errors=0
```

逐行对账：`1 + 3 + 4 = 8`；后一项的 `at` 等于前一项 `at + len`；
三个码点与 Unicode 表逐项一致。

再故意破坏：

```bash

./utf8 --hex e4 ad 41
```

- `--hex`：后续每个参数都当一个十六进制原始字节，能传 shell 不愿直接接收的坏 UTF-8。
- 第一组是过长编码后跟 A；第二组模拟从 `e4 b8 ad 41` 丢掉中间的 `b8`。

自动判据实测：

```text
PASS  过长编码 C0 AF 被拒绝为两个坏字节
PASS  坏字节之后的 A 仍能恢复
PASS  丢掉‘中’的中间字节，只伤两个字节
PASS  丢字节后边界重新同步，A 仍解出
```

## 3 第二段：ASCII 字符怎么变成 8x16 点阵

### 3.0 看哪里

```text
PDF     188-192 页，6.2，图 6.10-6.12
视频    4_6-2 的 0:00-5:37
源码    08_show_ascii/show_ascii.c 的 fontdata_8x16 和 lcd_put_ascii
基础    [基础 11] 第三节（bit 7 到底画左边还是右边）
实验    labs/04_text/bitmap8.c
```

### 3.1 第一性原理：字符编号只是数组下标

8x16 点阵字库把每个字符预先画在一个 8 列、16 行的格子里：

```text
一个字符     8 * 16 = 128 个开关
每个开关     1 bit：亮或灭
总大小       128 bit = 16 字节
```

256 个字节值都预留一格，就是 `256 * 16 = 4096` 字节。教材数组正好定义：

```c
#define FONTDATAMAX 4096
static const unsigned char fontdata_8x16[FONTDATAMAX];
```

ASCII 码没有告诉屏幕怎么画 A；它只给出 65。字库作者事先约定第 65 项放 A 的点阵：

```c
dots = &fontdata_8x16[(unsigned char)'A' * 16];
```

这就是最简单的 `字符身份 -> glyph` 映射。FreeType 的 charmap 和 glyph index
做的是同一类事，只是中间不再保证“码点乘固定大小”这么简单。

### 3.2 一行一个字节，一位一个像素

A 的 16 字节：

```text
00 00 10 38 6c c6 c6 fe c6 c6 c6 c6 00 00 00 00
```

按 MSB-first 展开：

```text
0x00  ........
0x00  ........
0x10  ...#....
0x38  ..###...
0x6c  .##.##..
0xc6  ##...##.
0xc6  ##...##.
0xfe  #######.
0xc6  ##...##.
0xc6  ##...##.
0xc6  ##...##.
0xc6  ##...##.
0x00  ........
0x00  ........
0x00  ........
0x00  ........
```

行号 `i=0..15`，位号 `b=7..0`。点阵左上角放在 `(x, y)` 时：

```text
屏幕横坐标 = x + (7 - b)
屏幕纵坐标 = y + i
```

当 `b=7`，横坐标就是 x；当 `b=0`，横坐标是 x+7。公式不是背出来的，
只是把“bit 号从右往左减、屏幕列从左往右加”接起来。

### 3.3 [做 L2] 不看屏幕，先在终端和 PGM 里验点阵

**先自己想：** 只看一个大写 A，能不能抓住位序反转？A 接近左右对称，
反转后仍像 A；前景像素总数更完全不变。所以实验同时保留 A 和不对称的 F。

```bash
gcc -Wall -Wextra -Werror -O2 -o bitmap8 bitmap8.c
./bitmap8 A --pgm A.pgm
./bitmap8 F
./bitmap8 F --lsb-first
```

- `A` / `F`：选择实验内保留的两个 8x16 glyph。
- `--pgm A.pgm`：把 0/255 灰度写成最简单的 PGM 图片，像素体应为 8x16=128 字节。
- `--lsb-first`：故意把 bit 0 画在左边，作为注错版。

本机实测摘要：

```text
glyph=A order=MSB lit=39 bbox=0,2..6,11
glyph=F order=MSB lit=34 bbox=0,2..6,11
glyph=F order=LSB lit=34 bbox=1,2..7,11
```

三笔对账：

1. A 的 16 个字节 popcount 相加是 39，程序画出的前景像素也是 39。
2. 点阵格是 8x16，但 A 真正有墨迹的外框只有 `x=0..6, y=2..11`。
3. F 位序反转前后都是 34 个点，所以“点数相等”这条判据抓不住；外框和逐行图会红。

`A.pgm` 文件头是 `P5 / 8 16 / 255`，头后像素体实测正好 128 字节。

### 3.4 从点阵到显示：不要把 font 层重新绑死在 fb0

教材的 `lcd_put_ascii()` 对每个点直接调用 `lcd_put_pixel()`，这是理解原理的最短路径。
落到项目时，font 层应该提交“覆盖率/前景色/坐标”，display 层完成最终像素：

| 层 | 输入 | 负责的工作 | 输出 |
|---|---|---|---|
| font 层 | 字库 bit | `bit=1 → coverage 255`；`bit=0 → coverage 0` | 覆盖率、前景色、坐标 |
| display 层 | 覆盖率、RGB888、坐标 | 裁剪 `x/y`，用 `line_length` 定位，把 RGB 转成当前 framebuffer 位段 | RGB565 或 XRGB8888 像素 |

如果 bit=0 时一律画黑色，文字会带一个 8x16 黑矩形，把原背景擦掉。
UI 通常需要透明背景：coverage=0 什么也不写；需要不透明文本框时，先由 display 填背景矩形。

### 3.5 [判] 第 3 节

```text
[ ] A 的表项偏移等于 65*16
[ ] A 的 16 行点阵共 39 个前景像素
[ ] A 的墨迹 bbox 是 0,2..6,11，不等于整个 8x16 格子
[ ] F 的正确/镜像版都有 34 个点，但第三行左右位置不同
[ ] PGM 头后恰好有 128 个像素字节
[ ] font 层不直接用 xres*bpp/8 算行宽，也不自己 open /dev/fb0
```

## 4 第三段：中文怎么在 HZK16 里找到 32 字节

### 4.0 看哪里

```text
PDF     192-197 页，6.3，图 6.13-6.15
视频    4_6-3 字幕缺失，不引用猜测内容
源码    09_show_chinese/show_chinese.c、HZK16、两个 test_charset 文件
基础    [基础 11] 第三节（每字节 MSB-first）
实验    labs/04_text/hzk16.c
```

### 4.1 第一性原理：格子变大，查表规则也变了

16x16 汉字点阵需要：

```text
16 * 16 bit = 256 bit = 32 字节
每行 16 bit = 2 字节
```

ASCII 可以直接用一个字节值乘 16；GB2312 汉字用两个字节，每个都在 `0xA1..0xFE`，
各有 94 个可能值，于是形成 94 行 x 94 列的区位表：

```text
area  = first  - 0xA1       范围 0..93
where = second - 0xA1       范围 0..93
index = area * 94 + where
offset = index * 32
```

“中”的 GB2312 字节是 `D6 D0`：

```text
area   = 0xD6 - 0xA1 = 53
where  = 0xD0 - 0xA1 = 47
index  = 53 * 94 + 47 = 5029
offset = 5029 * 32 = 160928
```

这四个数构成一条完整对账链。只要其中一项错 1，最后会跳到另一个汉字的 32 字节。

### 4.2 源码编码为什么会偷偷控制结果

资料源码写：

```c
unsigned char str[] = "中";
lcd_put_chinese(..., str);
```

如果源文件和执行字符集是 UTF-8，数组实际是：

```text
e4 b8 ad 00
```

函数只拿前两个字节 `e4 b8` 套 GB2312 区位公式。这两个值碰巧也在 A1..FE 范围，
所以程序不会报错，而是**安静地查出另一个合法 glyph**；第三个 `ad` 还残在后面。

教材用 GCC 的字符集选项把窄字符串转换成 GB2312。这能完成演示，但不适合作为项目接口：

```text
编辑器保存格式 -> 编译器参数 -> 可执行文件里的窄字符串 -> HZK16
```

任何一环换了默认值，行为都变。项目应当：

```text
入口明确接收 UTF-8
    -> 解成 Unicode 码点
    -> 若使用 HZK16，显式转换到 GB2312/查映射
    -> 若使用 FreeType，直接用 Unicode charmap
```

另外，GCC 的 `-fexec-charset` 管普通 `"..."` 字符串；宽字符串 `L"..."`
对应的是 `-fwide-exec-charset`。PDF 在 `wchar_t` 示例里只写 `-fexec-charset=UTF-8`，
对宽字符本身并不是那个开关。最稳妥的运行时接口仍是 UTF-8 字节 + 明确解码。

### 4.3 [做 L2] 按区位公式取“中”，再故意喂 UTF-8 前两字节

```bash
Q=/mnt/e/Workspace/01_all_series_quickstart-master
HZK="$Q/04_嵌入式Linux应用开发基础知识/source/09_show_chinese/HZK16"

gcc -Wall -Wextra -Werror -O2 -o hzk16 hzk16.c
./hzk16 "$HZK" d6 d0
./hzk16 "$HZK" e4 b8
```

- 第一个参数：字库文件路径。
- `d6 d0`：两个十六进制原始字节，不依赖当前 shell 或源码编码。
- 第二条故意把“中”的 UTF-8 前两个字节错当 GB2312。

“中”的实测末行：

```text
bytes=D6D0 index=5029 offset=160928 file_size=267616 lit=52 bbox=1,0..14,15 fnv1a=0b4ee7e7
```

逐项读：

- `index=5029` 与手算相等。
- `offset=160928` 正好是 `5029*32`。
- 资料 HZK16 实际 267616 字节，不等于完整 `94*94*32=282752`；
  所以读任何区位前仍要检查 `offset+32 <= file_size`，不能只信理论表格。
- 点阵共 52 个前景像素，墨迹没有占满 16x16，左右边缘至少各留一列。
- FNV-1a 摘要 `0b4ee7e7` 用来判断 32 字节是否原样一致，不代替安全哈希。

错误的 `e4 b8` 也会打印一个合法点阵，但它的 FNV-1a 与 `0b4ee7e7` 不同。
这条注错最重要的结论是：**编码混用经常不崩溃，只是稳定地显示错字。**

### 4.4 两层循环为什么是 16 x 2 x 8

```text
for y = 0..15             16 行
    for byte = 0..1       每行两个字节
        for bit = 7..0    每字节八个像素，MSB-first

screen_x = origin_x + byte*8 + (7-bit)
screen_y = origin_y + y
```

总次数 `16*2*8=256`，正好覆盖 16x16。和 ASCII 相比只是每行多了一个字节；
位序、透明背景、裁剪仍是同一件事。

### 4.5 HZK16 为什么没有成为项目最终接口

HZK16 的优点是小、确定、无需复杂库，适合启动画面、字库受控的设备和教学。
限制同样直接：

```text
字符范围      受 GB2312/字库内容限制
字号          固定 16x16，放大会锯齿
灰度          只有 0/1，没有抗锯齿覆盖率
排版          没有 bearing/advance/kerning 等度量
输入          项目若统一 UTF-8，还要做 Unicode -> GB2312 映射
```

所以它是理解文字栈的第二级台阶，不是 `font_manager` 的唯一实现。
项目可以保留 bitmap provider 做救援字体，再挂 FreeType provider；上层接口不变。

### 4.6 [判] 第 4 节

```text
[ ] D6D0 算出 area=53、where=47、index=5029、offset=160928
[ ] 读之前检查 offset+32 不超过真实文件大小 267616
[ ] “中”的 32 字节 FNV-1a 等于 0b4ee7e7，前景像素 52
[ ] 每字 16*2*8 次检查，坐标不越 16x16
[ ] 把 E4B8 当 GB2312 时程序虽能读，glyph 摘要必须与“中”不同
[ ] 项目入口写明 UTF-8，不让源码文件编码充当运行时协议
```

### 5.1 第一性原理：库有“构建时的一生”和“运行时的一生”

FreeType 不是编译器自带语法。头文件告诉编译器结构体和函数签名，
库文件提供函数机器码；交叉编译时，库里的机器码必须是 ARM。

```text

arm-linux-gnueabihf-gcc 编库   host  = ARM Linux
```

完整模型在 [基础 12]。本节只保留 FreeType 这一次的决定：

1. 不把头文件和库复制进 `/usr/arm-linux-gnueabihf` 等公共工具链目录。
2. `--prefix=/usr` 表示目标机逻辑路径，`DESTDIR=$STAGE` 表示本机临时假根。
3. 第一轮关闭 zlib/libpng/bzip2/Brotli/HarfBuzz，可控地只验证轮廓字体。
4. 真机探针用 `.a` 静态链接，切断板端旧 glibc 和动态依赖变量。

### 5.2 `wchar_t` 能用，但不拿它当外部协议

PDF 用 `L"中gif"` 让每个 `wchar_t` 在 Linux/GCC 下直接保存 Unicode 值，
本机同类环境通常得到：

```text
sizeof(wchar_t) = 4
0x4e2d 0x67 0x69 0x66
```

它适合在受控源码里快速调用 `FT_Load_Char`，但有三条边界：

- C 标准不保证 `wchar_t` 一定 32 位；Windows 常见 16 位，Linux/glibc 常见 32 位。
- `wchar_t` 的外部字节表示属于平台 ABI，不适合直接写文件、发网络或作为稳定插件接口。
- 从运行时 UTF-8 转 `wchar_t` 还受 locale 和转换函数状态影响。

本章实验因此用 `uint32_t codepoint` 保存 Unicode scalar value，并自己验证 UTF-8；
FreeType 接口本身接受 `FT_ULong` charcode，不要求先变成 `wchar_t`。

## 6 第五段：一个矢量字怎么变成灰度覆盖图

### 6.0 看哪里

```text
PDF     200-209 页，6.5；重点图 6.16-6.23
视频    4_6-5 的 0:00-14:55
源码    02_freetype_show_font/freetype_show_font.c
实验    labs/04_text/ftprobe.c
```

### 6.1 第一性原理：固定点阵被“任意字号”逼成轮廓

8x16 的 A 只有 128 个开关。把每个点简单放大 10 倍，会得到 80x160 的方块台阶；
缩小又会丢掉细线。要让同一个字在 12、48、200 像素下都保持结构，
就不能把某个尺寸的最终像素当源数据。

> **矢量字体**：保存轮廓的控制点、曲线和度量，不保存某个固定字号的最终像素。
>
> **光栅化（rasterization）**：把连续的几何轮廓投到离散像素网格，计算每格被轮廓覆盖多少。
>
> **抗锯齿（anti-aliasing）**：边缘像素按覆盖比例显示中间颜色，而不是只有全亮/全灭。

| 阶段 | 内容 |
|---|---|
| TTF/TTC 源数据 | glyph 的几何轮廓与控制点，不是最终像素 |
| 指定字号 | 设为 48 px，并执行缩放、hint 和扫描转换 |
| 灰度覆盖图 | 每个像素得到 `0..255` 的覆盖率，例如一行可能是 `0 37 221 255` |

轮廓仍不是屏幕像素。FreeType 的工作止于“给你位图和度量”；
选前景色、与原背景混合、打包成 RGB565/XRGB8888 是 display/合成层的责任。

### 6.2 五个对象和一条最短调用链

> **FT_Library**：FreeType 库实例，保存模块和全局状态。
>
> **FT_Face**：打开的一张字体 face。一个 TTC 可以含多张 face，`FT_New_Face(..., face_index, ...)` 选择。
>
> **charmap**：从字符码点到字体内部 glyph index 的映射表。
>
> **glyph**：字体内部的字形对象；字符与 glyph 不一定一对一。
>
> **FT_GlyphSlot**：face 自带的一个可复用工作槽，`FT_Load_*` 每次覆盖上一次结果。

最短主线：

```c
FT_Init_FreeType(&library);                 /* 建库实例 */
FT_New_Face(library, font_path, 0, &face); /* 打开第 0 张 face */
FT_Select_Charmap(face, FT_ENCODING_UNICODE);
FT_Set_Pixel_Sizes(face, 0, pixel_height); /* 目标像素高度 */
FT_Load_Char(face, codepoint, FT_LOAD_RENDER | FT_LOAD_TARGET_NORMAL);
/* 结果在 face->glyph，也就是 FT_GlyphSlot */
```

`FT_Load_Char` 内部合并了三步：

```text
codepoint --charmap--> glyph index --加载轮廓--> glyph slot --render--> bitmap
```

但不要因此跳过 `FT_Get_Char_Index`。它返回 0 通常表示字体没有这个码点，
`FT_Load_Char` 可能继续给你 `.notdef` 方框；只看 API 成功会把“缺字”误判成“正常字符”。

资源按申请的反序释放：

```c
FT_Done_Face(face);
FT_Done_FreeType(library);
```

教材演示程序省略了错误处理和释放，本项目不能照省。

### 6.3 `FT_Bitmap`：width 不是 pitch，字节也不是颜色

默认灰度模式中，重要字段：

```text
width       有效像素列数
rows        有效像素行数
pitch       从一行起点到下一行起点的字节跨距，可大于 width，也可能为负
buffer      第一个存储行的地址
pixel_mode  怎样解释 buffer；FT_PIXEL_MODE_GRAY 的值在本机打印为 2
num_grays   灰度级数，常见 256
```

访问第 `y` 行不能写死 `buffer + y*width`：

```c
if (pitch >= 0)
    row = buffer + y * pitch;
else
    row = buffer + (rows - 1 - y) * (-pitch);
```

本次宋体灰度 bitmap 的 pitch 恰好等于 width，但这只能证明这三个 glyph 如此，
不能把偶然相等写成接口契约。`ftprobe` 每个 glyph 都把两者单独打印，就是防止以后偷懒。

灰度值 `a` 表示覆盖率：

```text
a=0      这个像素完全在轮廓外，不改背景
a=255    完全在轮廓内，写前景色
0<a<255  边缘只覆盖一部分，混合前景和原背景
```

教材把 `a` 直接传给 `lcd_put_pixel(i,j,color)`，而后者把参数当 `0xRRGGBB`；
结果只有蓝通道变化。那是“把覆盖率当颜色看”的演示，不是通用文字绘制。

### 6.4 第一性原理：覆盖率怎样变成任意颜色

每个通道独立混合：

```text
out = (foreground * a + background * (255-a) + 127) / 255
```

`+127` 用于整数四舍五入。举例：白字 `fg=255` 画在黑底 `bg=0`：

```text
a=0     out=0       仍是黑
a=128   out=128     中灰边缘
a=255   out=255     白色内部
```

如果背景是红色、前景是白色，边缘的 R/G/B 三个通道必须分别混合；
不能先把覆盖率塞进某个通道，再指望 framebuffer 自动理解 alpha。

真机 `fbtext.c` 的顺序：

```text
读旧 RGB565/XRGB8888
    -> 按 fb_var_screeninfo 的 red/green/blue bitfield 解到 8 bit
    -> 三个通道分别 alpha blend
    -> 再按运行时 bitfield 压回 framebuffer 像素
```

这使它不写死“当前一定是 565”，插拔 HDMI 后 bpp 改变也不重编。

### 6.5 [做 L2] 在 WSL 里量单字，不先依赖屏幕


```text

glyph cp=U+0041 gid=36 bitmap=24x33 pitch=24 mode=2 left=0 top=34 bottom=1 advance26_6=1536 advance_px=24.000 nonzero=241 mid=145 full=96
glyph cp=U+0067 gid=74 bitmap=21x28 pitch=21 mode=2 left=2 top=22 bottom=-6 advance26_6=1536 advance_px=24.000 nonzero=279 mid=218 full=61
```

- “中”的 advance 是 48 像素，A/g 是 24 像素；定宽步进会在英文后留下大洞。
- 三个 `missing=0`，说明字体里都有真实 glyph，不是 `.notdef`。
- 总计 633 个 `0<a<255` 的边缘像素；如果只画 `a==255`，轮廓会明显变瘦和锯齿。

生成图视觉复核：A、g、中的基线关系正确，g 的下伸部落到 A 的底部以下，
“中”没有被 48 像素格裁掉。放大图会看到灰色边缘，这正是 633 个中间覆盖像素。

### 6.6 `slot` 为什么不能存起来下次再画

`face->glyph` 是工作槽，不是 glyph 缓存：

```text
FT_Load_Char(face, 'A', ...)  slot 里是 A
FT_Load_Char(face, 'g', ...)  同一个 slot 被 g 覆盖
```

所以这些做法有区别：

```text
立即消费 slot->bitmap              可以
复制 bitmap 数据和度量到自有缓存     可以，记得 pitch/生命周期
只保存 slot->bitmap.buffer 指针      不可以，下次 Load 或 Done_Face 后失效
FT_Get_Glyph 复制 glyph 对象          可以，最后 FT_Done_Glyph
```

本章两遍排版第二遍会重新 `FT_Load_Char`，不保存第一遍 slot 指针。

```text
[ ] FT_Get_Char_Index 返回 0 时计为缺字，不把 .notdef 当成功
[ ] A/g/中 三个 bitmap 的 width、rows、pitch 分别打印
[ ] 行地址使用 pitch，并处理 pitch<0，不写 y*width
[ ] 灰度值按 alpha 与原背景混合，不直接当 0xRRGGBB
[ ] 本次三个 glyph 共 888 个非零覆盖像素，其中 633 个是半覆盖
[ ] 48px 的“中”advance 是 48px，A/g 是 24px；不写固定步长
[ ] 每次 FT_Load_Char 后立即消费 slot，或复制所有权明确的数据
```

## 7 第六段：多个字怎么沿一条基线排开

### 7.0 看哪里

```text
PDF     209-215 页，6.6，图 6.28-6.35
视频    4_6-6 全集；重点 0:25-6:25、10:37-13:31
源码    04_show_line/show_line.c
基础    [基础 11] 第四节（26.6 定点数）
实验    labs/04_text/ftprobe.c
```

### 7.1 第一性原理：排版需要一条线，不是很多左上角

固定 16x16 点阵可以把每个格子的左上角排齐，因为每格尺寸相同。
矢量字体里 A、g、中有不同宽度、不同上伸和下伸，必须有共同参照。

> **基线（baseline）**：一行字共享的水平参考线；多数拉丁字母主体坐在上面，
> `g/p/q/y` 等下伸部可以越到线下。
>
> **pen/origin**：当前 glyph 的书写原点，通常位于基线上；它不是 bitmap 左上角。

排版时把基线当作共同坐标轴：

| 度量 | 含义 |
|---|---|
| baseline | 一行 glyph 共用的水平参考线 |
| pen A / pen 中 | 各 glyph 在基线上的书写原点，不是 bitmap 左上角 |
| `bitmap_top` | bitmap 顶端相对基线的高度 |
| `advance` | 画完当前 glyph 后，pen 移到下一 glyph 的距离 |
| 下伸部 | `g/p/q/y` 的尾部可以落到 baseline 下方 |

如果 API 参数说“在 `(x,y)` 画一行字”，必须先写清 `(x,y)` 是：

```text
整行墨迹外框左上角？
第一字 pen 的基线原点？
排版框左上角（可能含留白）？
```

教材定义为整行外框左上角；`fbtext` 真机探针为了少一个预扫描，定义为“第一字基线原点”。
项目正式接口可以同时提供 measure + draw，把两种需求分开。

### 7.2 四个度量各管什么

对当前 glyph：

> **bitmap_left（水平 bearing）**：bitmap 左边相对 pen.x 的像素偏移。
>
> **bitmap_top（垂直 bearing）**：bitmap 顶边高于基线的像素数。
>
> **bbox**：真正有墨迹的最小外框，可跨到基线下方。
>
> **advance**：画完当前 glyph 后，下一个 pen 应移动多少；不等于 bitmap width。

在“x 右、y 上”的字体局部坐标里：

```text
glyph_xmin = pen_x + bitmap_left
glyph_xmax = glyph_xmin + bitmap.width
glyph_ymax = bitmap_top
glyph_ymin = bitmap_top - bitmap.rows
next_pen_x = pen_x + advance.x
```

转换到 LCD“y 向下”的坐标，不必把整个屏高搬进来。给定 LCD 基线 `baseline_y`：

```text
lcd_bitmap_left = pen_x + bitmap_left
lcd_bitmap_top  = baseline_y - bitmap_top
```

教材把 FreeType pen 放进全屏笛卡尔坐标，再做 `lcd_y = yres - cartesian_y`，也能得到同一结果；
局部基线公式变量更少，项目里更不容易混入一次多余的 `yres`。

### 7.3 advance 为什么是 26.6，不要过早取整

FreeType 的 `slot->advance.x` 常用 26.6 定点数：[基础 11] 已实测 1 像素=64。

```text
A   1536 / 64 = 24 px
g   1536 / 64 = 24 px
中  3072 / 64 = 48 px
总  6144 / 64 = 96 px
```

pen 应一直保留 26.6 精度，定位实际 bitmap 时才转换到整数像素：

```c
pen_x += slot->advance.x;       /* 原始 26.6 累加 */
pixel_x = floor_26_6(pen_x);    /* 真正落像素网格时再取整 */
```

如果每个字都先把 advance 四舍五入成整数再累加，一行几百字会累计误差。

### 7.4 两遍排版：先量，再反推 pen

需求：“让整行墨迹外框左上角落在 LCD `(target_x,target_y)`。”
第一字 pen 并不一定等于这个点，所以分两遍：

```text
第一遍：假设 pen=(0,0)
        对每个 glyph 取 bbox，平移当前 pen，合并成 line_bbox
        pen += advance

已知 line_bbox=(xmin,ymin,xmax,ymax)，反推真正原点：
        pen_x_26_6 = (target_x - xmin) * 64
        baseline_y = target_y + ymax       （LCD y 向下）

第二遍：从这个 pen/baseline 重新 FT_Load_Char
        按 bitmap_left/top 画 bitmap
        pen += advance
```

为什么不能在第一遍把 `slot->bitmap.buffer` 指针都存下来？上一节说过，slot 会被下一字覆盖。
重新 load 最简单；需要高性能时做拥有自有 buffer 的 glyph cache。

### 7.5 用实测数字把外框和步进分开

`Ag中` 的行摘要：

```text
line bbox=0,-6..91,40 width=91 height=46 advance26_6=6144 advance_px=96.000
pgm=line.pgm size=95x50 baseline_row=42
```

逐项对账：

- 三个 advance 相加 `24+24+48=96`，与 `advance_px=96` 相等。
- 墨迹宽度只有 91，不等于 96；末尾还包含字形的 bearing/留白关系。
- 行最低到 `-6`、最高到 `40`，所以高度 `40-(-6)=46`。
- PGM 四边各留 2 像素，因此 `91+4=95`、`46+4=50`。
- 顶边留 2，基线距 bbox 顶部 40，所以 `baseline_row=2+40=42`。

五个独立数字逐个对上，比“图片看起来挺齐”更能抓住坐标错一行、漏下伸部等问题。

### 7.6 本章边界：FreeType 不是完整文本塑形器

`FT_Load_Char` 按码点逐个取 glyph，足够讲中文/拉丁基本绘制，但真实文字还有：

```text
kerning       AV 这类字偶要调整间距；可用 FT_Get_Kerning 做基础字偶距
shaping       阿拉伯文连写、印度文字重排、emoji ZWJ 等，需要 HarfBuzz 一类塑形器
fallback      当前字体缺字时，要去下一款字体找 glyph
line break    换行、双向文本、断词不是 FreeType 的职责
```

所以 font 层接口不要把“一个 UTF-8 字符必定对应一个 glyph”写死进 ABI。
本章 L4 先支持 UTF-8 基础文本；未来接 shaping 时，display 层完全不用改。

### 7.7 [判] 第 7 节

```text
[ ] 能指出 pen 在基线上，不是 bitmap 左上角
[ ] LCD bitmap_top = baseline_y - bitmap_top
[ ] A/g/中 advance 相加等于 96px，行墨迹 bbox 宽度是 91px；两者不混用
[ ] g 的 bottom=-6 被纳入整行 ymin，未裁掉下伸部
[ ] PGM 宽高 95x50 与 bbox 91x46 + 四边各 2 像素逐项相等
[ ] pen 用 26.6 累加，只在落像素时取整
[ ] 第一遍只算度量，第二遍重新 load；不保存会失效的 slot buffer 指针
```

### 8.5 [判] 不看显示器，回读显存

程序已经清成黑底，因此可见区中非零像素应集中在文字外框。保存可见 framebuffer：



## 11 已知的坑

```text
坑 1   把 Unicode 码点叫“UTF-8 值”
       U+4E2D 是码点；E4 B8 AD 才是 UTF-8 字节。

坑 2   看到中文乱码就盲试编码
       先十六进制看原始字节，再明确当前解码表；不要靠“换到能看”为证据。

坑 3   以为 UTF-16 固定每字符 2 字节
       非 BMP 码点用 surrogate pair 共 4 字节；用户眼中的一个 grapheme 还可能多码点。

坑 4   把 CPU 小端推广到位图 bit 顺序

坑 5   用左右近似对称的 A 验位序
       点数和肉眼都可能假绿；再用 F 或明确逐行摘要。

坑 6   HZK16 只验字节是否在 A1..FE
       UTF-8 的 E4/B8 也会通过范围检查并稳定查错字；还要保证输入编码契约。

坑 7   把第三方库复制进交叉工具链

坑 8   `#include <ft2build.h>` 找不到就移动上游头文件

坑 9   链接成功就以为板上能跑
       还要看 ARM Machine、加载器、glibc 和 NEEDED；本章探针静态链接只是控制变量。

坑 10  `FT_Set_Pixel_Sizes(...,48)` 就断言 bitmap.rows=48
       字号是 face 的整体尺度；本次 A/g/中 rows 分别 33/28/45。

坑 11  用 `width` 跨 bitmap 行
```

## 延伸 A：码点不等于用户眼中的一个字

主线里 `A中🙂` 恰好每个视觉字符都是一个码点，但 Unicode 允许：

```text
é                 U+00E9                     一个码点
e + ◌́            U+0065 U+0301              两个码点，一个视觉字符
👨‍👩‍👧‍👦          多个 emoji + ZWJ           多个码点，一个家庭图形
```

> **grapheme cluster（字素簇）**：用户认为可以作为一个字符移动/删除的一组码点。

UTF-8 解码只产出码点，不负责把它们组成字素簇；FreeType 逐码点取 glyph 也不负责复杂塑形。
编辑器的左右键、退格和 UI 光标将来需要 Unicode 分段/塑形层，不能拿 `strlen` 或码点数代替。

## 延伸 B：旋转为什么同时需要矩阵和 pen

视频 4_6-5 后半使用 `FT_Set_Transform(face, &matrix, &pen)`：

```text
matrix    改变 glyph 轮廓的方向/缩放，例如旋转 45 度
pen       改变 glyph 在 26.6 坐标中的平移位置
```

旋转后的 bbox 也会改变，不能用未旋转时的 width/rows 做裁剪。
三角函数 `sin/cos` 来自 libm，所以示例链接加 `-lm`。主线不依赖旋转；
若做，判据应比较 0/90/180 度的 bbox 和像素摘要，不只截图。

## 顺带一提：和 NEMU 的字模对照

没做过也不影响，跳过即可。

NEMU/VGA 只负责把显存像素送到窗口，和本板 LCDIF 一样不认识文字；
如果 monitor 里能显示字符，也是上层拿字模自己画像素。区别只在最后一个写像素接口：

```text
NEMU       写模拟显存/SDL surface
本章       display 层写 mmap 的 /dev/fb0
共同上层   编码 -> glyph -> bitmap -> blend
```

所以 font 层设计得不依赖 `/dev/fb0`，同一套排版代码才能在 WSL 假屏、NEMU 风格内存屏和真板之间复用。
