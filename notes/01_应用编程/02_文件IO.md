## 1 一张脉络图

这一章讲的是从你的一行 `printf` 到磁盘之间的四层：

```text
    你的程序        printf("hello\n")          fopen / fwrite / fclose
    ------------------------------------------------------------------
    C 库            一块用户空间的 buffer      攒够了才往下走
                    (默认 4096 字节)           <-- 第 4 节
    ------------------------------------------------------------------
                            |  write(1, buf, 4096)      <-- 系统调用边界
                            v                               [基础 05]
    ------------------------------------------------------------------
    内核 VFS        fd -> struct file -> inode  <-- 第 2 节, [基础 06]
                    f_op->write()
    ------------------------------------------------------------------
                            |
              +-------------+-------------+
              |                           |
    普通文件: ext4                  设备节点: 驱动的 write
              |                           |
    页缓存 --> 块设备驱动             直接怼寄存器
              |                           |
             磁盘                        硬件
```

三条贯穿全章的线：

1. **`fd` 是下标不是指针**，第 2 节。搞清楚这一条，`dup` / `dup2` /
   `fork` 之后的行为全都是推论。
2. **`read` / `write` 是"最多"不是"正好"**，第 3 节。
   这一条不知道，写出来的程序在文件小的时候能跑，一上量就丢数据。
3. **C 库那层 buffer 是性能优化，也是麻烦的来源**，第 4 节。
   它是标准 IO 和系统调用 IO 唯一的实质区别。

第 5 节讲 `mmap`，它是绕开上面整条路的另一条路。
第 6 节把这一章的东西落进 `project/`。

## 2 第一段：一个 fd 到底是什么

### 2.0 看哪里

    PDF     170-171 页（4.4.2），那张 task_struct -> files_struct -> file 的图
    源码    01_open/open.c、07_dup/dup.c、07_dup/dup2.c
    基础    [基础 06] notes/00_基础/06_文件描述符与VFS.md

### 2.1 第一性原理：内核不肯给你指针，只好给你下标

内核里描述一个打开的文件用的是 `struct file`，它有地址。
为什么不把这个地址返回给你？

因为**用户态拿到内核内存的地址，等于拿到了改内核的能力**。
你在 NPC 里做过特权级，这条边界是硬件强制的：U 态访问内核地址会异常。
既然指针不能给，那就在每个进程里放一张数组，把指针填进数组，
只把**下标**给你。下标越界内核自己查得出来，指针给出去就没法验证了。

于是：

```text
    fd = open("1.txt", O_RDONLY);   // fd = 3

    进程的 fd 表        struct file             inode
    fd[0] --> ...
    fd[1] --> ...
    fd[2] --> ...
    fd[3] ------------> f_pos   = 0   -------> 大小/权限/数据块在哪
                        f_flags = O_RDONLY
                        f_op    --> ext4 的读写函数表
```

**三张表，不是两张。** 为什么中间那张非有不可、每一层各管什么，
在 [基础 06] 里讲全了，那一篇还从 ysyx 的 `nanos-lite/fs.c` 搭了桥。
这里只用一句话：

> `f_pos`（读到哪了）属于"这一次打开"，不属于"这个文件"。
> 所以它必须待在一个每 `open` 一次就新建一个的结构里。

这一句是本节所有现象的唯一来源。

### 2.2 0、1、2 是谁放进去的

程序一启动，fd 表里前三格已经填好了：

```text
    fd 0   stdin    标准输入
    fd 1   stdout   标准输出
    fd 2   stderr   标准错误
```

**不是 C 库填的，是 shell 填的。** shell `fork` 出子进程之后，
子进程继承了 shell 的整张 fd 表，这三格里装的是终端。
`./prog > out.txt` 里那个 `>`，做的事情就是在 `execve` 之前
把子进程的 1 号那一格改成指向 `out.txt`。

所以 `open` 返回的第一个 fd 一定是 3 —— 内核分配 fd 的规则是
**"当前未被使用的最小编号"**。这条规则第 2.5 节要用到。

### 2.3 [做 L1] 把三张表从 /proc 里看出来

**先自己想：** 同一个文件 `open` 两次，两个 fd 各读一个字节，
读到的是同一个字节还是相邻两个字节？换成 `dup` 呢？
先写下你的预测再往下做 —— 预测错了才有收获。

资料仓 `01_open/open.c` 结尾那个 `while(1) sleep(10)` 就是给这个实验用的：
程序不退出，你才有时间去另一个终端翻 `/proc`。

自己写一个 `fdshow.c`：`open` 同一个文件两次得到 `fd1`、`fd2`，
`dup(fd1)` 得到 `fd3`，各读一个字节打印出来，再用 `lseek(fd, 0, SEEK_CUR)`
把三个位置打出来。

```bash
printf 'ABCDEFGH' > data.txt
gcc -Wall -o fdshow fdshow.c
./fdshow
```

- `printf 'ABCDEFGH'`：造一个内容已知的文件，读出来是第几个字节一眼可见。
- `lseek(fd, 0, SEEK_CUR)`：偏移 0、基准是"当前位置"，
  也就是**什么都不移动，只把当前位置返回**。这是查询 `f_pos` 的标准写法。

**本机实测：**

```text
    pid=31472 fd1=3 fd2=4 fd3=5
    fd1 read 'A'  fd2 read 'A'  fd3 read 'B'
    pos: fd1=2 fd2=1 fd3=2
```

三件事：

- `fd1`、`fd2` 各读到 `'A'` —— 两次 `open` 得到两个 `struct file`，位置各算各的。
- `fd3` 读到 `'B'` —— `dup` 出来的 fd 和 `fd1` 共用一个 `struct file`，
  `fd1` 已经把位置推到 1 了。
- 最后一行是铁证：`fd1` 和 `fd3` 的位置**同时**变成了 2。

再从内核那头看一遍。把程序改成读完一个字节后 `pause()` 挂住，
打印自己的 pid，另开一个终端：

```bash
ls -l /proc/<pid>/fd          # 第 1 张表: 编号 -> 文件
cat  /proc/<pid>/fdinfo/3     # 第 2 张表: 这个 fd 背后的 pos 和 flags
```

**本机实测：**

```text
    lr-x------ ... 3 -> /home/glorinz/fio-lab/data.txt
    lr-x------ ... 4 -> /home/glorinz/fio-lab/data.txt
    lr-x------ ... 5 -> /home/glorinz/fio-lab/data.txt

    fd 3:  pos: 1   flags: 0100000
    fd 4:  pos: 0   flags: 0100000
    fd 5:  pos: 1   flags: 0100000
```

三个编号指向同一个文件，`pos` 却是 1 / 0 / 1。
**内核自己把"中间那张表存在"这件事报出来了。**

### 2.4 open 两次和 dup 一次，差别在哪一层

把 2.3 的结果画出来，就是三种"复制"的全部区别：

```text
    open 两次              dup / dup2                fork
    fd[3] --> file(pos)    fd[3] --+                 父 fd[3] --+
    fd[4] --> file(pos)            +--> file(pos)               +--> file(pos)
              两个 f_pos   fd[5] --+                 子 fd[3] --+
              各算各的             共用一个 f_pos               也是共用
```

- **`open` 两次**：fd 表加两格，各建一个 `struct file`。
- **`dup`**：fd 表加一格，指向已有的 `struct file`。
- **`fork`**：整张 fd 表复制给子进程，但指向的还是父进程那些 `struct file`。

第三条解释了一个天天遇到的现象：`(./a; ./b) > log` 里两个程序共用一个
`struct file`，写位置接着走；而 `./a > log; ./b > log` 是两次独立的重定向，
第二次把第一次的内容清掉了。

`close(fd)` 关的是 fd 表里那一格，不是 `struct file`。
`struct file` 上有引用计数，减到 0 才真关。第 6 节的代码要用到这一条。

### 2.5 [做 L2] 用 dup2 把 printf 骗进文件

**先自己想：** `printf` 是往 `stdout` 写的，你没法改它的实现。
但你想让它写进一个文件，而且不许改任何一行 `printf`。怎么做？

线索：`printf` 认的不是"终端"，是**数字 1**。

答案是 `dup2(fd, 1)`：把 fd 表的第 1 格改成指向 `fd` 指的那个 `struct file`。
资料仓 `07_dup/dup2.c` 就是这个。自己写一遍：

```c
    int fd = open(argv[1], O_RDWR | O_CREAT | O_TRUNC, 0644);
    dup2(fd, 1);
    printf("hello, world\n");
```

- `dup2(oldfd, newfd)`：让 `newfd` 指向 `oldfd` 指的那个 `struct file`。
  如果 `newfd` 本来开着，**先把它关掉**。
- 和 `dup(oldfd)` 的区别：`dup` 由内核挑一个最小的空编号，
  `dup2` 由你指定编号。想覆盖 0/1/2 就必须用 `dup2`。

**这一步有个坑，跑之前先想：** 上面这段代码跑完，文件里有内容吗？

有，但**不是因为 `printf` 把它写下去了**，是因为程序退出时 C 库的收尾代码
自动 `fflush` 了。把 `printf` 后面加一个 `_exit(0)`（下划线那个，不走 C 库收尾），
文件就是空的。为什么，见第 4 节。

### 2.6 [判] 第 2 节的判据

    [ ] 说得出 fd 为什么是下标不是指针（一句话：指针给出去没法验证）
    [ ] open 两次 + dup 一次，三个 fd 读出的字节是 A / A / B，位置是 2 / 1 / 2
    [ ] /proc/<pid>/fdinfo/N 里 dup 出来那个 fd 的 pos 与源 fd 相同
    [ ] 说得出 fd 0/1/2 是谁填的（shell，通过 fork 继承）
    [ ] dup2(fd,1) 之后 printf 落进文件；换成 _exit(0) 收尾则文件为空

**注错见红。** 把 `dup(fd1)` 改成再 `open` 一次：

```c
    int fd3 = open("data.txt", O_RDONLY);   /* 原来是 dup(fd1) */
```

预期：`fd3` 读到的从 `'B'` 变成 `'A'`，`pos` 从 2 变成 1。
**改回来之前先跑一遍确认它真的变了** —— 不会红的判据等于没有判据。

## 3 第二段：read / write 的真相

### 3.0 看哪里

    源码    03_write/write.c、04_read/read.c、03_write/write_in_pos.c、copy.c

### 3.1 第一性原理：返回值是"实际做成了多少"，不是"你要的多少"

```c
    ssize_t read (int fd, void *buf, size_t count);
    ssize_t write(int fd, const void *buf, size_t count);
```

两个函数的返回值都是 `ssize_t`，含义是**这次实际搬了几个字节**。
它可以小于 `count`，而且这不是错误。

为什么会少？因为 `count` 是你的愿望，能不能满足取决于对面：

```text
    read  少读:  文件读到末尾了
                 从管道读, 里面暂时只有 5 个字节
                 从终端读, 用户只按了回车前的那几个字符
                 被信号打断

    write 少写:  管道 / socket 的缓冲区满了
                 磁盘满了
                 被信号打断
```

**本机实测**（管道里只放 5 个字节，然后要读 100 个）：

```text
    read(要 100) 实际返回 5
```

写也一样。把管道设成非阻塞，一次写 1 MiB：

```text
    write(要 1048576) 实际返回 65536
    管道满时再 write(1) 返回 -1, errno=11 (Resource temporarily unavailable)
```

65536 正是本机管道的容量（16 页 × 4096）。

所以正确的写法只有两种：**要么检查返回值等于你要的量、不等就当错误处理，
要么循环直到搬完。** 资料仓的 `03_write/write.c` 用的是前者：

```c
    len = write(fd, argv[i], strlen(argv[i]));
    if (len != strlen(argv[i])) { perror("write"); break; }
```

对普通文件来说前者够用（普通文件的 `write` 除非磁盘满，否则总是全写）。
一旦对面是管道、socket、串口，就必须用后者。第 06 章网络通信会正面撞上这个。

读的那一侧还有个细节，`04_read/read.c` 里的：

```c
    len = read(fd, buf, sizeof(buf) - 1);   /* 为什么是 -1 */
    buf[len] = '\0';                        /* 因为这里要放一个结束符 */
    printf("%s", buf);
```

`read` **不会**给你补 `'\0'`，它只搬字节。要当字符串用就得自己补，
所以得给结束符留一格。少这个 `-1`，`buf[len]` 就写出界了。

### 3.2 [做 L2] O_APPEND 和 lseek+write 不是一回事

**先自己想：** 两个进程同时往一个日志文件追加内容。
写法 A 是 `open(..., O_APPEND)` 然后循环 `write`；
写法 B 是每次 `lseek(fd, 0, SEEK_END)` 再 `write`。
两种写法看起来都是"写到末尾"，结果一样吗？

写一个程序，参数是 `<文件> <append|seek> <条数>`，每条写固定的 17 字节。然后：

```bash
N=2000
./app a.txt append $N & ./app a.txt append $N & wait
stat -c %s a.txt      # 期望 2 * 2000 * 17 = 68000
```

- `&` 把两条命令都放到后台，两个进程真正同时在写。
- `wait` 等两个都结束。
- `stat -c %s`：只打印文件大小的字节数；`%s` 是 stat 的格式符，不是 printf 的。

**本机实测**，两种写法各跑 5 遍：

```text
    append 版:  68000  68000  68000  68000  68000     每次都一字不差
    seek   版:  46325  38964  34085  49062  45305     每次都不一样, 每次都少
```

丢的量没有规律，因为它取决于两个进程的指令怎么交错。

**原因在 [基础 06] 第 3.3 节**：`O_APPEND` 让内核在 `write` 内部
把"定位到末尾"和"写"放在同一把锁里，是**一个**原子操作。
自己写 `lseek` + `write` 是**两个**系统调用，中间那一瞬别人插进来写了，
你手里那个"末尾"就过期了，你的数据盖在别人头上。

这不是理论风险。第 6 节 `project/` 的日志文件就是用 `O_APPEND` 开的，
理由就是这条实测。

### 3.3 [做 L1] lseek 造一个空洞：文件大小和占盘大小是两个数

**先在 WSL 的原生目录里做，不要在 `/mnt/e` 下做**，理由见第 9 节。

资料仓 `03_write/write_in_pos.c` 是 `lseek` 到偏移 3 再写。把跨度放大：
写 4 个字节，`lseek` 到 1 MiB，再写 4 个字节。

```bash
cd ~ && mkdir -p fio-lab && cd fio-lab
gcc -Wall -o hole hole.c && ./hole sparse.bin
ls -l  sparse.bin       # 逻辑大小
du -h  sparse.bin       # 实际占盘
stat   sparse.bin       # %s 是字节数, %b 是 512 字节块数
dd if=sparse.bin bs=1 skip=100 count=8 2>/dev/null | xxd    # 空洞里是什么
```

- `du` 默认按**占盘**算，`ls -l` 按**逻辑大小**算。平时两者接近，所以容易以为是一回事。
- `dd bs=1 skip=100 count=8`：一次一字节、跳过 100 字节、取 8 字节。
- `xxd` 把这 8 字节按十六进制打出来。

**本机实测（ext4）：**

```text
    ls -l  逻辑大小 = 1048580
    du -h  实占     = 8.0K
    stat            = 1048580 字节, 16 个 512B 块
    空洞里读出来      00000000: 0000 0000 0000 0000
```

逻辑 1 MiB，实占 8 KiB。中间那段从没写过的区域叫**空洞**：
文件系统压根没给它分配块，读它的时候内核返回 0。

这解释了一件平时会碰到的怪事：拷贝一个稀疏文件，
拷出来的可能比原文件占盘大得多 —— 拷贝程序老老实实把那些 0 读出来又写了回去。

### 3.4 [做 L3] 自己写一个 copy

**不看资料仓的 `copy.c`，自己写。** 目标：

    ./mycopy <源文件> <目标文件>

要求（每一条都对应上面某一小节）：

1. 参数不是 3 个就打用法并返回非 0。
2. 源文件打不开时用 `perror` 报错，不要只打印 "error"。
3. 循环读写，**处理 `read` 少读和 `write` 少写**（3.1）。
4. 目标文件用 `O_WRONLY | O_CREAT | O_TRUNC` 打开，mode 给 `0644`。
5. 两个文件都要 `close`。

写完之后拿判据验：

```bash
head -c 8388608 /dev/urandom > big.bin
./mycopy big.bin copy.bin && cmp big.bin copy.bin && echo SAME
./mycopy /etc/hostname /tmp/x && cat /tmp/x
: > empty.bin && ./mycopy empty.bin e2.bin && ls -l e2.bin    # 空文件也要能拷
```

- `head -c N /dev/urandom`：取 N 个随机字节。内容随机才验得出"少拷了一段"这种错。
- `cmp`：逐字节比较，一样时没有任何输出、退出码 0。
- `: > f`：`:` 是什么都不做的内建命令，配合 `>` 就是把文件清成 0 字节。

**判据的关键是 `cmp`，不是"看起来对"。** 拷贝程序最典型的 bug 是
最后不满一个缓冲区的那几百字节丢了，用文本文件肉眼看很难发现，`cmp` 一比就出来。

### 3.5 mode 和 umask：0777 传下去不会原样落地

`open` 带 `O_CREAT` 时那第三个参数叫 mode，是**请求**的权限，不是最终权限。
内核落地的是：

```text
    最终权限 = mode & ~umask
```

资料仓 `02_create/create.c` 写的是 `0777`。**本机实测**（umask 是 0022）：

```text
    mode 参数写 0777, 实际得到: 755  -rwxr-xr-x
    umask 000 时:            777  -rwxrwxrwx
    umask 077 时:            700  -rwx------

    0777 & ~022 = 755
```

umask 的用处是让系统管理员统一压掉一批权限位，而不用改每个程序。
**所以程序里不要试图靠 mode 精确控制权限**，要精确控制就 `open` 完再 `fchmod`。

顺便记住四种最常见的开法：

| 组合 | 语义 |
|---|---|
| `O_RDONLY` | 只读，文件必须已存在 |
| `O_WRONLY \| O_CREAT \| O_TRUNC` | 写，不存在就建，存在就清空。**建新文件用这个** |
| `O_WRONLY \| O_CREAT \| O_APPEND` | 写，不存在就建，存在就接着末尾写。**日志用这个** |
| `O_WRONLY \| O_CREAT \| O_EXCL` | 写，**必须不存在**，已存在就失败。用来抢锁 |

### 3.6 [做 L1] 让 open 失败，看清 errno

`open` 失败返回 -1，具体原因在全局变量 `errno` 里。写一个小程序试四种失败：

**本机实测：**

```text
    打开不存在的文件                 fd= -1  errno= 2  No such file or directory
    用 O_RDWR 打开一个目录           fd= -1  errno=21  Is a directory
    用 O_RDONLY 打开一个目录         fd=  3  errno= 0
    O_CREAT|O_EXCL 打开已存在的文件  fd= -1  errno=17  File exists
```

第三行值得停一下：**目录可以用 `O_RDONLY` 打开，只是不能 `read`。**
这个 fd 拿去干什么？`fstat` 查目录信息，或者作为 `openat` 的相对基准。

报错三种写法，选一种，别混着用：

```c
    printf("errno = %d\n", errno);          /* 只有数字, 要查表, 不推荐 */
    printf("err: %s\n", strerror(errno));   /* 转成字符串, 自己拼上下文 */
    perror("open");                         /* 打印 "你给的前缀: 原因" */
```

`perror` 最省事，但它只往 stderr 打、格式固定。写库的时候用 `strerror`。

**`errno` 只在函数确实失败之后才有意义。** 成功的调用不会把它清零，
里面留的是上一次失败的残值。所以永远是先判返回值，再看 `errno`。

## 4 第三段：标准 IO 那层 buffer

### 4.0 看哪里

    PDF     166 页（4.1）那张图里 "用户空间分配的 buffer" 那个框
    源码    06_app_libc_kernel/06_app_libc_kernel.c

这一节是整章最容易出事的地方，而 PDF 只用了一句话带过。

### 4.1 第一性原理：进一次内核很贵，所以先攒着

`printf` 不是系统调用，`write` 才是。中间隔着 C 库的一块 buffer：

```text
    printf("line 0\n")  --> 抄进 buffer, 返回。没进内核。
    printf("line 1\n")  --> 抄进 buffer, 返回。
    ...
    buffer 满了(4096)   --> 这时才 write(1, buffer, 4096), 进一次内核
```

**为什么值得这么干**：一次系统调用要保存现场、切特权级、走 VFS、
回来再恢复现场。攒 4096 字节发一次，比发几百次便宜得多。

### 4.2 [做 L1] 用 strace 把这件事数出来

**先自己想：** 一个循环 `printf` 1000 行的程序，
输出到终端、输出到文件、输出到管道，底下的 `write` 系统调用各发生多少次？
三个数一样吗？

```bash
gcc -Wall -o buf buf.c                                    # 循环 printf 1000 行
strace -f -e trace=write -o t_file.txt ./buf > out.txt    # 输出到文件
strace -f -e trace=write -o t_pipe.txt ./buf | cat > /dev/null
script -q -c "strace -f -e trace=write -o t_tty.txt ./buf" /dev/null
```

- `strace -e trace=write`：只跟踪 `write` 这一个系统调用，别的不打。
- `-f`：跟踪 fork 出来的子进程。**加了 `-f` 之后每行前面会多一个 pid**，
  数行数时正则要写成 `(^|[0-9]+ +)write\(`，光写 `^write(` 会数成 0。
- `-o 文件`：把 strace 自己的输出写到文件，不和程序输出混在一起。
- `script -q -c "命令" /dev/null`：给命令造一个假终端，
  用来测"输出到终端"这一种情况。`/dev/null` 是 script 的记录文件，我们不要。

**本机实测**（同一个程序，1000 行，共 8890 字节）：

| stdout 接到哪 | 缓冲方式 | write 调用次数 |
|---|---|---:|
| 文件 | 全缓冲 | **3** |
| 管道 | 全缓冲 | **3** |
| 终端 | 行缓冲 | **1000** |
| （对照）自己循环调 `write` | 没有中间层 | 1000 |
| （对照）`fprintf(stderr,...)` 到文件 | 无缓冲 | 1000 |

3 这个数不是巧合，能算出来：

```text
    三次 write 的长度分别是 4096、4096、698
    4096 + 4096 + 698 = 8890 = 输出总字节
    ceil(8890 / 4096) = 3
```

行缓冲那一行，每次 `write` 正好 7 字节，就是 `"line 0\n"` 的长度。

**这是本章最硬的一条判据**：它是计数型的，而且能和总字节数对上账，没法蒙混。

### 4.3 三种缓冲方式，以及谁决定用哪种

```text
    无缓冲   _IONBF   每次调用立刻 write            stderr 恒定是这个
    行缓冲   _IOLBF   遇到 \n 或 buffer 满才 write  stdout 接到终端时
    全缓冲   _IOFBF   只有 buffer 满才 write        stdout 接到文件/管道时
```

**关键在于：谁接在后面，是 C 库在 `main` 之前自己探测的。**
它对 `stdout` 调一次 `isatty(1)`，是终端就选行缓冲，不是就选全缓冲。

所以**同一个程序，`./prog` 和 `./prog > log` 的输出时机完全不同**。
这就是那个人人踩过的坑：程序在终端里跑得好好的，一重定向到文件，
日志就"延迟"了，或者干脆看不见。

想自己定，用 `setvbuf`，而且必须在对这个流做任何 IO 之前调：

```c
    setvbuf(stdout, NULL, _IONBF, 0);   /* 关掉 stdout 的缓冲 */
```

- 第二个参数 `NULL`：让 C 库自己分配缓冲区。
- 第三个参数是模式，第四个是大小；`_IONBF` 时大小被忽略。

### 4.4 [做 L1] 缓冲区里的数据会在崩溃时丢掉

**先自己想：** 程序 `printf` 一行然后 `abort()`，输出重定向到文件。
文件里有那一行吗？`fprintf(stderr, ...)` 那一行呢？

```c
    printf("to stdout\n");
    fprintf(stderr, "to stderr\n");
    abort();
```

**本机实测**（`./crash > c_out.txt 2> c_err.txt`）：

```text
    退出码 = 134            134 = 128 + 6, 6 号信号是 SIGABRT
    c_out.txt = 0 字节      printf 那一行没了
    c_err.txt = "to stderr" stderr 那一行在
```

`stdout` 重定向到文件是全缓冲，那一行还压在用户态的 buffer 里，
进程被信号打死时这块内存直接消失了，内核不知道也不管。
`stderr` 是无缓冲的，`fprintf` 当场就变成了 `write`，数据已经在内核里。

**这就是为什么日志要走 stderr。** 板子跑到一半掉电、程序段错误、
看门狗复位 —— 这三种情况下 stdout 的最后几 KB 全都拿不回来。
第 6 节 `project/` 的日志走 stderr，理由就是这条实测，不是习惯。

三个层次的"落盘"，别搞混：

```text
    fflush(fp)    把 C 库 buffer 里的东西交给内核。交完了内核可能还没写磁盘。
    fsync(fd)     让内核把这个文件的脏页真的写到磁盘, 返回时才算落盘。
    O_SYNC        打开时就要求每次 write 都等到落盘再返回。最慢。
```

`fflush` 管不到内核那一层，`fsync` 管不到 C 库那一层。
一个 `FILE *` 想真正落盘，两个都要调，顺序是先 `fflush` 再 `fsync(fileno(fp))`。

### 4.5 为什么访问驱动不能用标准 IO

PDF 只给了结论。原因有三条，都是上面几节的直接推论：

**第一，时机不可控。** 往 `/dev/fb0` 写一帧图像，你要的是"现在就写下去"。
夹一层全缓冲的 buffer，写下去的时机变成了"攒够 4096 字节"。

**第二，标准 IO 没有 `ioctl`。** 设备的参数（分辨率、波特率、采样率）
全靠 `ioctl(fd, 请求码, 参数)` 设置，而 `FILE *` 这套接口里根本没有这个函数。
你得用 `fileno(fp)` 把 fd 抠出来，那还不如一开始就用 fd。

**第三，缓冲会把数据切碎。** 设备驱动的 `write` 常常是有语义边界的 ——
一次 `write` 就是一个数据包、一帧、一条命令。
C 库那层攒够 4096 才发，会把两条命令粘在一次 `write` 里，
或者把一条切成两次。驱动那边收到的就不是你写的东西了。

所以规矩很简单：**碰 `/dev` 下的东西，一律 `open`/`read`/`write`/`ioctl`/`close`。**
第 03 章操作 framebuffer、第 09 章操作串口，全都按这条来。

### 4.6 [判] 第 4 节的判据

    [ ] printf 1000 行, 输出到文件时 write 次数是 3, 到终端是 1000
    [ ] 三次 write 的长度是 4096 + 4096 + 698, 加起来等于输出总字节 8890
    [ ] fprintf(stderr) 1000 行到文件, write 次数是 1000
    [ ] abort 之后 stdout 那一行丢了、stderr 那一行还在, 退出码 134
    [ ] 说得出 fflush 和 fsync 各管到哪一层
    [ ] 说得出访问 /dev 下的设备为什么不用标准 IO（三条理由）

**注错见红。** 在 `printf` 循环之前加一行 `setvbuf(stdout, NULL, _IONBF, 0);`：

```text

```

## 5 第四段：mmap

### 5.0 看哪里

    PDF     这一章没讲 mmap。它在 441 页（第 2 阶段"驱动程序基石"）才出现
    源码    copy_mmap.c
    基础    [基础 07] notes/00_基础/07_虚拟内存与mmap.md

**但这一章必须讲它**，因为第 03 章 framebuffer 上来就要用。

### 5.1 第一性原理：把那次拷贝去掉

`read` 一次，数据走了两段路：磁盘到页缓存，页缓存到你的 `buf`。
第二段是内核替你做的一次 `memcpy`。

`mmap` 的想法是：**页缓存本来就是内存，为什么不让你的指针直接指过去。**

```c
    void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
```

| 参数 | 给什么 | 管什么 |
|---|---|---|
| `addr` | 一般给 `NULL` | 想映射到哪个地址；给 NULL 让内核挑 |
| `length` | 文件大小（`fstat` 查） | 映射多长 |
| `prot` | `PROT_READ` / `PROT_WRITE` | 这段内存能读还是能写 |
| `flags` | `MAP_SHARED` / `MAP_PRIVATE` | 写进去算不算数（见 [基础 07] 第 4 节） |
| `fd` | 已经 `open` 的文件 | 映射谁 |
| `offset` | 一般 0 | 从文件第几字节开始；**必须是页的整数倍** |

返回的是一个指针，之后就当普通内存用。失败返回 `MAP_FAILED`（不是 NULL）。

**调用返回时一个字节都还没读。** 真正的读发生在你第一次访问那块地址、
触发缺页异常的时候。这是 [基础 07] 的主题。

### 5.2 [做 L2] 数一数系统调用

**先自己想：** 8 MiB 的文件，用 4096 字节缓冲区的 `read`/`write` 循环拷，
和用 `mmap` + 一次 `write` 拷，各发多少次系统调用？耗时会差多少倍？

第二个问题**先写下你的预测**，等会儿对答案。

```bash
head -c 8388608 /dev/urandom > big.bin
strace -f -e trace=read,write -o t_rw.txt   ./cp_rw   big.bin c1.bin
strace -f -e trace=read,write -o t_mmap.txt ./cp_mmap big.bin c2.bin
```

**本机实测**（8388608 字节 = 2048 页）：

```text
    cp_rw    read 2050 次 + write 2048 次 = 4098
             其中 1 次 read 是动态加载器在读可执行文件的 ELF 头(832 字节),
             拷贝本身是 2048 次满读 + 1 次读到 0 + 2048 次写
    cp_mmap  2 次
             1 次是加载器读 ELF 头, 拷贝本身只有 1 次 write(8388608 字节)
    两个结果都通过 cmp 逐字节一致
```

系统调用次数差了 2000 倍。**那耗时呢？**

```text
    各跑 3 轮, 每轮 10 次:
        轮 1   cp_rw 171 ms   cp_mmap 158 ms
        轮 2   cp_rw 152 ms   cp_mmap 166 ms
        轮 3   cp_rw  77 ms   cp_mmap  81 ms
```

**三轮里各赢一次，看不出稳定差别。** 这和很多文章里"mmap 快好几倍"的说法不一样。

原因是：这个规模下两者真正的开销都是搬那 8 MiB 数据本身。
一次系统调用几百纳秒，2000 次也就零点几毫秒，淹没在数据搬运和页缓存的噪声里。
**"系统调用少了 2000 倍"和"快了 2000 倍"完全是两回事。**

这条要记住，因为它是一类错误的模板：**报次数容易，报时间要真去测；
两个数不会自动互相印证。**

那 `mmap` 什么时候真的赢？随机访问一个大文件的时候 ——
`read` 要 `lseek` + `read` 两次调用换一小块数据，`mmap` 就是一次解引用。
顺序整读整写这种用法，它赢的只是好看。

### 5.3 三个边界

**空文件不能映射。** `length` 为 0 时返回 `MAP_FAILED`，`errno` 是 `EINVAL`。
**本机实测**：`mmap: Invalid argument`，退出码 1。
资料仓的 `copy_mmap.c` 没处理这一支，拿它拷空文件会报错退出。

**映射按页取整，文件不按。** 文件 5000 字节，映射拿到的是两页 8192 字节。
5000 到 8191 这段读出来是 0，写进去不进文件。
（**本机实测**：拷 5000 字节的文件 `cmp` 一致 —— 因为 `write` 只写了 `st_size` 个字节。）

**摸出文件末尾所在页之外，是 SIGBUS。** **本机实测**：

```text
    文件 3 字节, 映射 8192 字节
      p[0]     = 'a'       正常
      p[100]   = 0         第一页里、文件外: 读到 0
      p[5000]              第二页, 完全在文件外 --> Bus error, 退出码 135
```

135 = 128 + 7，7 号信号是 `SIGBUS`。
**看到 SIGBUS 先怀疑映射长度**，它和 SIGSEGV 是两种不同的毛病。

### 5.4 [判] 第 5 节的判据

    [ ] cp_rw 的 read+write 次数是 4098, cp_mmap 是 2, 且两者 cmp 都一致
    [ ] 说得出 4098 是怎么凑出来的（2048 满读 + 1 次读到 0 + 2048 写 + 1 次加载器）
    [ ] 计时结果说得出"次数差 2000 倍, 时间看不出稳定差别"
    [ ] 空文件 mmap 返回 MAP_FAILED, errno 是 EINVAL
    [ ] 越过末尾页访问是 SIGBUS(135), 不是 SIGSEGV(139)

**这一节的注错见红是一条"故意不红"的。** 把 `cp_mmap` 里的 `MAP_SHARED`
改成 `MAP_PRIVATE`：

```text
    预期: 拷贝结果不变, cmp 仍然一致, 判据全绿。
```

## 6 落进项目：日志能落到文件了

### 6.1 为什么这一章交出的是这个

按[路线图](../03_项目/Todo/项目路线图-对齐电子产品量产工具.md)第四节，
第 02 章不新增一层 —— framebuffer 那些要等第 03 章。
但这一章的知识在 `project/` 里有一个当下就用得上的落点：

**板子上只有一根串口。日志刷过去就没了，没法回头翻，也没法事后对比两次运行。**
量产工具最终要记录每一项测试的结果，这个能力迟早要有。

于是本章给 `project/` 加一个函数：

```c
    int log_redirect(const char *path);      /* project/include/common.h */
```

设了环境变量 `LOG_FILE`，`main` 就调它，之后所有日志落进那个文件；
没设就照旧打到串口。

### 6.2 三个设计决定，每一个都来自这一章

**第一，用 `dup2` 换 2 号槽，不给每层加日志参数。**

六层的代码里全是 `LOG_INFO(...)`，它展开成 `fprintf(stderr, ...)`。
要让这些输出改去处，有两条路：

```text
    路 A  把 LOG_RAW 改成写一个全局的 FILE* / fd, 每层都得跟着改
    路 B  不动任何一行日志代码, 只把 fd 表的第 2 格改成指向文件
```

选 B。理由就是第 2 节那句话：**`fprintf(stderr,...)` 认的不是终端，是数字 2。**
换掉第 2 格，六层一行代码都不用改，日志格式和 `LOG_LEVEL` 开关也全都不动。

**第二，`O_APPEND` 不是 `O_TRUNC`。**

表面理由是"多次开机的记录要接着写"。真正的理由是第 3.2 节那个实测：
以后 business 层可能起多个进程各自写日志，
`O_APPEND` 是原子的，`lseek` + `write` 不是。现在选对了，以后不用回来改。

**第三，日志走 stderr 不走 stdout。**

第 4.4 节实测过：`stdout` 重定向到文件之后是全缓冲，
崩溃或掉电时最后几 KB 全丢。`stderr` 恒定无缓冲，写一行进一次内核。
对一个要在板子上跑、随时可能被复位的程序，这是硬要求。

这一条在判据里有守门人（见 6.4）：把 `fprintf(stderr` 改成 `fprintf(stdout`，
判据必须变红。

## 7 上板

这一章的东西在板子上和在 WSL 里没有本质差别，但有两处要注意。

**第一，板子的 `/tmp` 是 tmpfs。** 第 01 章实测过，重启就没。
日志要留住得写到别的地方，或者跑完及时拷回来。

**第二，`O_SYNC` 和 `fsync` 在 eMMC 上是真有代价的。**
掉电安全和写入速度在这里正面冲突。
不要因为"安全"就给日志加 `O_SYNC`，那会让每条日志都等一次 flash 擦写。
本章的 `log_redirect` 没有用 `O_SYNC`，靠的是 stderr 无缓冲 —— 
数据进到内核就算，剩下的交给内核的回写。

上板步骤沿用[第一节上板实操](../../refs/第一节上板实操.md)：

## 9 已知的坑

**坑 1：不要在 `/mnt/e` 下做稀疏文件和 mmap 实验。**

同一个 `hole` 程序，两个文件系统上的结果：

| | ext4（WSL 原生目录） | `/mnt/e`（drvfs 挂的 NTFS） |
|---|---|---|
| `ls -l` 逻辑大小 | 1048580 | 1048580 |
| `du -h` 实占 | **8.0K** | **1.1M** |
| `stat` 块数 | **16** | **2056** |

`/mnt/e` 那一列里空洞被老老实实写成了真的 0，
在那里做第 3.3 节的实验会得出完全相反的结论。
**这不是 WSL 的 bug，是文件系统能力差异。**
板子上的 eMMC 用 ext4，行为和左边那列一样。

**坑 2：`strace -f` 之后行首多了 pid，正则要跟着改。**

数 `write` 次数时写 `grep -c '^write('` 会得到 0 ——
加了 `-f` 且真有多个进程时，strace 在每行前面加了 pid 和空格。
正确写法是 `grep -cE '(^|[0-9]+ +)write\('`。
这个坑在写本章判据时踩过一次：第一版数出来是 0，
差点得出"终端下 printf 一次系统调用都不发"的结论。

**坑 3：`LOG_FILE=x strace ./prog` 把变量给了 strace。**

环境变量前缀只对紧跟着的那个命令生效。要给被跟踪的程序设变量，
得写成 `strace ... env LOG_FILE=x ./prog`。

**坑 4：`errno` 只在失败之后才有意义。**

成功的系统调用不会把 `errno` 清零。先判返回值，再看 `errno`，顺序不能反。

**坑 5：`mmap` 失败返回 `MAP_FAILED` 不是 `NULL`。**

`MAP_FAILED` 是 `(void *)-1`。写 `if (p == NULL)` 永远判不出来。
