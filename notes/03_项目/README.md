# 03 项目：project/ 的工程文档

`project/` 这棵代码树的工程文档。体例照搬 `Loongarch_NPU_SoC/Engineering/`，
两个仓的读者是同一个人，没必要换一套写法。

和 `notes/` 前面几章的关系：`00_基础/`、`01_应用编程/`、`02_驱动开发/` 是教材，
读者是正在学这门课的人，按 PDF 和视频的章节推进；本章是工程文档，
读者是要接手改 `project/` 的人，按代码结构和开发时间线推进。
同一件事在两边都出现是正常的，但落点不同：前面几章讲"这个知识点怎么学会"，
本章讲"这段代码为什么长这样、这一行在算什么"。

## 流转规则

1. 开工前在 `Todo/` 建文件，写明要解决什么、如何切分、判据是什么。
2. 开工后同一文件继续记录，用作开发日志。
3. 过程中出现修不掉的问题，在 `Bugs/` 另开一条，注明现有判据为什么没覆盖到它。
4. 工作点完成并且 `project/check.sh` 全绿之后，在 `TechReports/` 对应系列增加一章。
5. 代码定稿后，在 `CodeReading/` 补齐或订正逐行讲解。
6. 删除 `Todo/` 中该文件。

## 项目规则：提交即更新文档

**每一次 commit，都要在同一次 commit 里把它影响到的文档改完。**
文档滞后于代码，等价于文档不存在：读者会照着旧行号去找一段已经不在那里的代码，
比没有文档更浪费时间。

对照表如下。左列发生了，右列就必须在同一个 commit 里改到位。

| 改动 | 必须同步的文档 |
|---|---|
| 任何 `project/**` 下的 `.c` / `.h` / `Makefile` 增删改 | `CodeReading/project/` 对应篇的**正文与行号区间** |
| 新增一个源文件 | 归入所在层的那一篇 `CodeReading/`，订正正文与行号；`CodeReading/project/README.md` 篇目表的行数列 |
| 新增或修改一层的对外接口 | `CodeReading/` 对应篇的"消费者"一节 |
| 完成一个工作点（一层从空壳变成有实现、构建系统换法、判据体系变化） | `TechReports/project/` 增加一章，并删掉 `Todo/` 里对应的文件 |
| `check.sh` 判据条数变化 | `CodeReading/project/check脚本-逐行精读.md`，并更新仓库根 `README.md` 的 PASS 数 |
| 发现一个改不掉的缺陷 | `Bugs/` 新增一条，写明现有判据为什么没覆盖到 |
| `notes/` 某一章完成 | 仓库根 `README.md` 的进度栏 |

两条硬约束：

**一层一篇。** 同一层的 manager、内部头与后端合进一篇 CodeReading，构建
（Makefile）与判据（三个 check 脚本）各一篇；行号区间按被覆盖的每个文件
给出，代码增删时定位不受影响。新增、删除或重命名文件时，所在篇目的正文、
行号与 `CodeReading/project/README.md` 的篇目表在同一次改动中同步。

**先讲行为，再给术语。** 面向初学者的正文和代码注释，第一次出现 `fd`、`stderr`、
`dup2`、`mmap` 等名字时，必须先说明“输入是什么、执行后能观察到什么、失败时怎样”，
再补技术名称和内部原理。不能用“2 号槽”“换一格”“指向 `struct file`”这类简称
代替解释。代码标识符可以保留，但读者不应为了看懂一句注释再去查另一篇术语表。

**行号必须准。** `CodeReading/` 的每一节标题都带行号区间。
代码增删行之后，全篇行号一并订正，不允许只改正文不改行号。
订正方法是重新 `grep -n '' <文件>` 对一遍，不靠记忆。

**判据数字必须是跑出来的。** 文档里出现的 PASS 数、体积、行数、耗时，
一律以本机或板上实测为准。改完代码先跑 `bash project/check.sh`，
拿到的数字再写进文档。

## 检查方式

提交前自问三条，答不上就是文档没跟上：

    1. 这次改的每个文件，在 CodeReading/ 里对应哪一篇？那篇的行号还对吗？
    2. 这次改动算不算一个"工作点"？算的话 TechReports/ 那一章写了吗？
    3. check.sh 的 PASS 数变了吗？变了的话根 README.md 改了吗？
