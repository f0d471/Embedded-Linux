# 同一 SYN 帧里的普通键事件被 pointer 分支丢掉

## 现象

`input/input_manager.c` 的 `parse_raw` 在 `SYN_REPORT` 到来时，如果本帧同时有 pointer 变化和普通键事件，先进入 `g_pointer_changed` 分支，构造一个 pointer 事件，调用 `reset_frame()` 并返回。`g_key_code/g_key_value` 因此被清空；调用者再也拿不到这次普通键。若反过来优先 key，pointer 会被丢掉。

最小回放可在一帧内放三条记录：

```text
1 100 2 0 1
1 110 1 30 1
1 120 0 0 0
```

假屏 64×32、初始 (32,16) 时，当前程序只会产生 `pointer x=33 y=16 dx=1 dy=0 buttons=0`；不会产生 `key code=30 value=1`。这是按当前代码分支推导出的待补测试例，尚未作为自动判据运行。

## 为什么现有判据没抓到

`project/unittest/input_replay.txt` 的五个完整帧把普通键和 pointer 变化分在不同帧。`check_font_input.sh` 只比对那五帧输出，所以 pointer 与 key 同帧的路径从未执行。原有“只有 SYN_REPORT 才提交”的判据检查了封口时机，没有检查一帧中多种动作是否都交付。

## 预期与修复边界

先定公开接口契约：一次 `input_get_event` 返回一个应用事件时，如果一帧里有两类动作，manager 需要暂存至少一个待交付事件，下一次调用再返回；或者修改接口一次返回复合事件。不能只交换两个 `if` 的顺序。应增加同时含 REL_X、普通键和 SYN_REPORT 的 fixture，断言两类动作均出现且顺序稳定；还要覆盖 BUTTON 与普通键同帧、timeout=0 时待交付事件的返回、exit 时待交付状态清空。
