# 从零开始读写 project 代码

这篇给只会最基础 C 语法的读者使用。它相当于精读的共用基础篇：不是"术语表"，而是一套读代码、自己写代码的固定动作。后面的逐层精读在正文里引用对应源码；遇到陌生语法先回这里做最小实验，再回原文件。

## 0. 一次只做一件事

读一个函数，按以下顺序写在纸上：

1. **输入**：参数是什么？每个参数能取什么值？`NULL`、负数、空字符串有没有意义？
2. **状态**：函数会读或改哪个变量？全局变量、堆内存、文件、设备，还是只算一个数？
3. **输出**：返回值是什么？输出参数有没有被写入？屏幕、文件、日志会有什么变化？
4. **失败**：哪一步会失败？失败时哪些资源已经拿到，谁负责归还？
5. **判据**：给一个具体输入，手算出返回值和状态；运行后比较。

不要一次把 300 行看完。先用目录找到函数，再沿着调用关系一次走一条路径。比如启动路径：`main → layers_init → display_init`。只读完这条路径，再看失败回滚。

## 1. 从一个最小 C 程序开始

```c
#include <stdio.h>

int add(int a, int b)
{
    int result = a + b;
    return result;
}

int main(void)
{
    int answer = add(2, 3);
    printf("%d\n", answer);
    return 0;
}
```

逐句拆开：

- `#include <stdio.h>` 把 `printf` 的声明带进来。声明告诉编译器“这个函数叫什么，收什么参数，返回什么类型”。它不会把函数实现复制到本文件。
- `int add(int a, int b)` 定义函数。第一个 `int` 是返回值类型；括号里的两个 `int` 是输入类型；`a`、`b` 是本函数里的局部变量。
- `int result = a + b;` 新建变量，同时算出并存入 5。单个等号是赋值，不是比较；比较写 `==`。
- `return result;` 把值交回调用处。执行到这里，`add` 就结束。
- `int main(void)` 是进程入口。`void` 表示没有参数。
- `add(2, 3)` 先运行 `add`，得到 5，再把 5 存入 `answer`。
- `printf("%d\n", answer)` 用 `%d` 放进一个十进制整数；`\n` 是换行。
- `return 0` 是把成功状态交给操作系统。项目里的 `ERR_OK` 是内部函数协议；最终仍由 `main` 映射为进程的 0/1。

先自己敲一遍，再把 `2, 3` 改成 `-2, 3`，预测输出。之后删掉 `return result;`，看编译器怎样报错或警告。**从可观察的报错反推语法规则**，比死记定义有效。

## 2. 读懂“变量、数组、结构体”

### 2.1 变量是一块有类型的存储

`int x = 3;` 可以理解成：“留一块能放 `int` 的位置，名字叫 `x`，现在放 3”。类型约束读写方式和大小。项目中常见 `int`、`size_t`、`uint8_t`、`uint32_t`：前者通常保存返回码或坐标，`size_t` 保存字节数，固定宽度整数适合像素、编码和设备协议。看到变量，不要只抄名字；写下“它的单位”，例如宽度是**像素**，`line_length` 是**字节/行**，`pitch` 是**字节/字形行**，`advance` 是 **1/64 像素**。单位不同的数不能直接相加。

### 2.2 数组是相邻的多个同类元素

```c
int values[3] = {10, 20, 30};
int first = values[0];
```

下标从 0 开始，合法下标是 0、1、2。`values[3]` 超出边界，C 不会自动抛异常。项目里显示层按 `y * stride + x * bytes_per_pixel` 算像素地址前，必须先检查 `x/y` 的边界。把“先算地址再判断”写反，可能已经越界。

### 2.3 结构体把相关字段绑在一起

```c
struct point {
    int x;
    int y;
};

struct point p = { .x = 4, .y = 7 };
int left = p.x;
```

`struct point` 是类型，`p` 是这个类型的一个值。`p.x` 取它的 `x` 字段。显示层的 `disp_info`、输入层的 `input_event_data` 都是同一想法：一组必须一起解释的字段放进一个结构体。写结构体时先列出“使用方需要知道什么”，再确定字段和单位；不要为了方便把所有内部状态都暴露出来。

## 3. 指针到底是什么

指针保存一个地址；`int *p` 说的是“`p` 指向一个 `int`”。先分清三个动作：

```c
int x = 7;
int *p = &x;  // &x：取得 x 的地址
int y = *p;   // *p：沿地址读取，y 得到 7
*p = 9;       // 沿地址写回，x 现在是 9
```

`NULL` 表示没有有效对象。`*NULL` 不是“得到空值”，而是非法访问。看到 `foo->bar`，可暂时翻译成 `(*foo).bar`：先找 `foo` 指向的结构体，再取 `bar`。项目中的 provider、display 后端、FreeType 对象大量使用这一写法。

### 3.1 输出参数

C 函数只能直接 `return` 一个值，但可以让调用者给一块地址：

```c
int divide(int a, int b, int *answer)
{
    if (answer == NULL || b == 0)
        return -1;
    *answer = a / b;
    return 0;
}

int value = 0;
int status = divide(8, 2, &value);
```

这里 `status` 回报成败，`value` 接收计算结果。项目中的 `log_redirect(..., &os_errno)`、`font_measure_utf8(..., &metrics, &bad_offset)` 都按这个思路设计。每次看到输出参数，都问：**失败时它会不会被写？**不能先假设。

### 3.2 指针的生命周期

地址本身不会让对象活得更久。局部变量在函数返回后结束；`malloc` 分配的对象要由 `free` 归还；`mmap` 要用 `munmap`；`open` 返回的描述符要用 `close`；FreeType 的 face/library 要按配对 API 释放。`font_bitmap.buffer` 是借用 provider 的位图，下一次 render/close 后就不能再用。精读里碰到指针，要在旁边标“谁创建、谁借用、何时失效、谁释放”。

## 4. 控制流：一条路径一条路径走

`if` 是条件分支；`for` 和 `while` 是重复。读循环时必须写出：初始值、继续条件、每轮变化、最坏轮数。

```c
for (int i = 0; i < 3; i++) {
    printf("%d\n", i);
}
```

输出 0、1、2。`i < 3` 在每一轮开头判断；`i++` 在每一轮末尾执行。项目里 `layers_exit(n)` 从 `n - 1` 倒数到 0，是因为后初始化的层要先退出；若从 `n` 开始，第一步就越过“已成功初始化的前 n 层”。

看一个带资源的函数，要画**成功路径**和**每一条失败路径**。例如：打开文件成功，映射失败，就必须关闭文件；映射成功，后续初始化失败，就要先解除映射再关闭文件。不要只画“全部成功”的流程。

## 5. 函数指针和链表：项目的两个新概念

### 5.1 函数指针是“函数也能放进表里”

```c
struct layer {
    const char *name;
    int (*init)(void);
    void (*exit)(void);
};
```

`int (*init)(void)` 意思是：`init` 保存某个函数的地址；那个函数不收参数，返回 `int`。括号不能随便删。`main.c` 用一张 `g_layers` 表把六层的 `init/exit` 排好。循环中调用 `g_layers[i].init()`，实际会跳到当前元素保存的函数。手写一张两元素的小表，再打印调用顺序，之后再读六层版本。

### 5.2 单链表是“每个节点记着下一个”

```c
struct node {
    int value;
    struct node *next;
};
```

若 `a.next = &b`，从 `a` 就能找到 `b`；`b.next = NULL` 表示到尾。项目的 display/font/input provider 注册都用了链表。头插可以写成：

```c
new_node->next = head;
head = new_node;
```

第一行先把旧头保存为新节点的后继；第二行才改头。顺序反过来会丢掉旧链。重启层时若复用静态节点，也要重设 `next`，否则可能指向自己，遍历永远结束不了。读链表函数时，画出每一步前后的箭头；不要只看“注册成功”的返回码。

## 6. 整数、位运算、字节和颜色

设备给的不是抽象“颜色”，而是一串位。`&` 是按位与，常用来取某些位；`|` 是按位或，常用来合并；`<<`/`>>` 移动位。与逻辑运算 `&&`/`||` 不同。

```c
unsigned int buttons = 0;
buttons |= 1u;   // 置位最低位：左键按下
buttons &= ~1u;  // 清除最低位：左键释放
```

自己算一遍二进制：`0000 | 0001 = 0001`；`0001 & 1110 = 0000`。输入层维护“持续按着哪些按钮”，因此不能只记本帧“按下动作”。

像素颜色 `0x00RRGGBB` 是项目的公共表达；真实 framebuffer 可能是 RGB565，也可能是 32 位。写入前要查运行时红绿蓝位段和一行的字节数，不能把 `width * 4` 当成所有显示器的一行。字形灰度 0..255 表示“前景覆盖背景多少”，它也不是颜色。混色需要前景、背景和 alpha 三者：

```text
结果 = (前景 × alpha + 背景 × (255 - alpha) + 127) / 255
```

先用 alpha=0、128、255 手算，再看 `disp_blend_pixel`。alpha=0 应保持背景，255 应完全变成前景。

## 7. 字符串和 UTF-8：字符不等于一个字节

C 字符串以值为 0 的字节结束。`strlen` 数的是终止 0 之前的**字节数**，不是汉字个数。“A中g”有 3 个 Unicode 码点，但 UTF-8 的“中”占 3 个字节，所以这串文本占 5 个内容字节，后面另有一个终止 0。font 层先把字节解码成码点，再找字形。

读解码器时，每读一个字节，都标出它是首字节还是续字节；遇到坏输入，要记录**第一个坏字节的偏移**。不要把 `char` 的负值直接当码点；在位运算前转成 `unsigned char`。练习：分别输入 ASCII、一个汉字、截断的三字节序列，预测 `used` 和错误位置。

## 8. 错误码、系统错误和资源回滚

项目函数一般返回 `ERR_OK` 或其他项目错误码；操作系统调用失败时还可能设置 `errno`。两个信息层级不同：前者给调用者稳定的项目协议，后者说明某次系统调用的具体原因。`main.c` 的日志重定向同时保留两者，方便分辨“项目拒绝了参数”和“文件系统拒绝了打开”。

写一个新函数，先列出成功路径，再逐个插入失败点：

| 已取得资源 | 下一步失败 | 要做的清理 |
|---|---|---|
| 无 | 参数不合法 | 直接返回 |
| 文件描述符 | mmap 失败 | close |
| 文件描述符、映射 | 后续初始化失败 | munmap，再 close |
| FreeType library、face | 字号设置失败 | 先释放 face，再释放 library |

“谁成功创建，谁负责在失败路径归还”是每个 CodeReading 都要检查的句子。可重复调用 `close/exit` 的函数通常把资源句柄清成无效值，避免第二次释放。

## 9. 不是 C 的文件也要会读

### 9.1 Makefile

`target: prerequisites` 表示“目标依赖哪些文件”；下一行以 **Tab** 开头的命令负责生成目标。`$@` 是目标名，`$<` 是第一个依赖，`$^` 是全部依赖。先在 `project/` 跑 `make -n` 只看命令，不真正构建；再运行 `make`。`-MMD -MP` 生成头文件依赖，防止改了 .h 却没重编相应 .c。`CROSS=arm-linux-gnueabihf-` 会换编译器前缀并把产物放进另一棵树。

### 9.2 Bash

`set -e` 使某些失败立刻退出，但它不是完整的错误处理；`if`、`!`、管道和子 shell 有细节。`"$var"` 的引号保护空格和通配符，不是装饰。`mktemp -d` 建临时目录，`trap ... EXIT` 在退出时清理。check 脚本里 `PASS/FAIL/SKIP` 的数字必须来自实际判据，不能手动写死。

### 9.3 Python

`def` 定义函数；缩进决定代码块；`with open(...) as f` 离开块时关文件；`struct.unpack` 按指定字节序把原始字节转成数字。`count.py` 从假显存读像素、数颜色，它独立于 C 的绘图实现，所以能抓到两边不一致。

### 9.4 回放数据

`input_replay.txt` 每行的五个数字是 `秒 微秒 type code value`，不是应用事件。多行原始记录到 `SYN_REPORT` 才合成一个应用事件。写 fixture 前先在纸上列“本帧相对移动、按钮状态、普通按键、最后坐标”，再把它们编码成记录；否则很容易出现自以为有 5 帧、实际只有 4 帧的假判据。

## 10. 从空文件重写一个模块的具体顺序

以输入层为例，不必先懂 Linux 的全部接口：

1. **写公开头文件**：先确定上层要拿到的事件字段和错误返回。用一段假数据手写预期输出。
2. **写内部头文件**：定义后端向 manager 交什么原始记录，写清 buffer/指针的所有权。
3. **写 replay**：先让一行文本能解析，再让 EOF、注释、畸形行各自得到不同结果。
4. **写 manager 的一帧**：先只支持 REL_X/Y 和 `SYN_REPORT`。用 2 条记录预测一次输出。
5. **逐项加状态**：按钮位图、ABS 缩放、丢帧、半帧 EOF、总 deadline；每加一项先写一个会失败的例子。
6. **最后接 evdev**：把真实设备记录转成与 replay 相同的内部结构。这样硬件问题不会和状态机问题混在一起。
7. **跑检查并故意改坏**：把某个边界判断反转，确认对应判据变红；恢复后再确认变绿。

同样的施工法也适合 display/font：先定公开契约，再用不依赖硬件的后端验证算法，最后接真实设备。

## 11. 每篇精读怎么练

每个代码段都按四轮走：

1. **遮住解释**，读源码，写出“输入、状态、输出、失败”。
2. **看解释并修正**，每个没懂的变量写上类型和单位，每个指针写上所有权。
3. **手算一例**，例如坐标 `(-3, 20)` 在 64×32 假屏会落在哪里，或 alpha=128 会混成什么颜色。
4. **最小改错**，在临时副本改一个条件或边界，跑对应 `check.sh`，记录哪条判据变红，再恢复。不要在唯一工作树里留下故意错误。

读完一篇的标准不是“看完了”，而是能在不看原文件的情况下，先写出函数接口、成功路径、失败清理，再敲出关键循环，最后用判据证明它满足契约。
