# 层管理器空壳 逐行精读

对应代码：六层各一对文件，`.c` 各 27 行，`.h` 各 13 行。

```
    project/display/disp_manager.{c,h}
    project/input/input_manager.{c,h}
    project/font/font_manager.{c,h}
    project/ui/ui_manager.{c,h}
    project/page/page_manager.{c,h}
    project/business/business_manager.{c,h}
```

六份的结构完全相同，只有三处不同：函数名前缀、日志里的层名、`TODO` 注释的内容。
本篇以 `display` 为样本讲，行号对六份都成立。

前置：无。这是本目录里最短的一篇。

---

## 1. 文件定位

一层的最小形状。这六份文件现在不干任何活，它们存在的理由有三个：

**让 `main.c` 的层表有六个真实的符号可以填。** 层表里放的是函数指针，
指向一个不存在的函数是链接期错误。

**让判据能数出六。** 判据数的是运行时输出里 `init OK` 出现几行。
空目录数不出来，空文件也数不出来，必须有一个真的会打日志的函数。

**把"以后往哪填"这件事固定在代码里而不是文档里。**
每个 `_init()` 里都有一条 `TODO` 注释，写明哪一章来填这里。
文档会忘记看，代码里的 `TODO` 在改这个文件时一定会看到。

## 2. 头文件（`disp_manager.h` 全文 13 行）

```c
#ifndef __DISP_MANAGER_H
#define __DISP_MANAGER_H

/*
 * display 层对外接口。
 * 这里只放函数声明, 不放内部结构体定义 -- 别的层看不见本层的内部状态,
 * 才谈得上以后能整层换掉。
 */

int  display_init(void);
void display_exit(void);

#endif /* __DISP_MANAGER_H */
```

**头文件里只有函数声明，一个结构体都没有。** 这是本仓最重要的一条约定，
写在注释里而不是靠自觉。它的后果是：别的层想用 display，
只能通过这两个函数；它拿不到 display 的内部状态，也就没法依赖那些状态的形状。
以后把 HDMI 换成 LCD 时，改动被关在 `display/` 目录里。

课程配套项目那边的做法不同：`include/disp_manager.h` 里定义了 `DispBuff`、`DispOpr`
两个结构体，还导出 `RegisterDisplay()` 让底层驱动往链表里挂自己。
那是一种更强的形状（支持运行时选择显示后端），本仓做到第 03 章会引进来。
届时这个头文件会大改，改动记在 TechReports 的下一章。

**返回类型是 `int` 和 `void`，不对称。** `init` 会失败，
所以返回 `common.h` 里那套错误码；`exit` 不允许失败，
所以没有返回值。这不是省事：如果 `exit` 也能失败，
`main.c` 里那个反序回滚的循环就要处理"回滚到一半又失败了"的情况，
而那种情况下没有任何合理的动作可做。把它从接口上排除掉，比处理它更正确。

包含保护用双下划线加文件名。六个头文件的保护宏名字互不相同
（`__DISP_MANAGER_H`、`__INPUT_MANAGER_H`……），
因为它们跟文件名走而不是跟目录名走。

**这个头文件不包含 `common.h`。** 它不需要：它只用到了 `int` 和 `void`。
包含关系保持最小，改 `common.h` 时被卷进来重编的文件就少一些。
`.c` 那边自己包含 `common.h`。

## 3. 实现文件（`disp_manager.c` 全文 27 行）

### 3.1 两个包含与一个文件级状态（第 1 到 4 行）

```c
#include "common.h"
#include "display/disp_manager.h"

static int g_inited;
```

第一个包含用双引号，找的是 `-Iinclude` 指定的目录（见 Makefile 精读第 30 行）。

第二个包含带了目录前缀，写成 `"display/disp_manager.h"` 而不是 `"disp_manager.h"`。
这不是为了让编译器找得到（`-I.` 已经在了），是为了让人一眼看出跨层引用。
以后 `ui/ui_manager.c` 里出现 `#include "font/font_manager.h"` 时，
读代码的人立刻知道这是一条跨层的边，可以对照分层图检查方向对不对。
写成不带前缀的形式，这条信息就没了。

`static int g_inited;` 是文件作用域的静态变量。`static` 在这里的含义是
**这个符号不进全局符号表**：六个 `.c` 里都有一个叫 `g_inited` 的变量，
去掉 `static` 就是六个同名全局符号，链接时报重复定义。

它不显式初始化。C 标准规定文件作用域的静态变量默认初始化为 0，
它落在 `.bss` 段里，不占文件空间，由加载器负责清零。
写成 `= 0` 效果相同，但会让一些编译器把它挪到 `.data` 段，反而占空间。

### 3.2 初始化（第 6 到 16 行）

```c
int display_init(void)
{
	if (g_inited)
		return ERR_OK;

	/* TODO 第 03 章 Framebuffer: 打开 /dev/fb0, 取 fb_var_screeninfo, mmap 出显存 */

	g_inited = 1;
	LOG_INFO("display init OK");
	return ERR_OK;
}
```

开头那三行是**幂等保护**：已经初始化过就直接返回成功，不重复做。
现在的函数体是空的，重复执行没有代价，所以这三行看起来是多余的。
它是为以后写的：`display_init()` 真正开始 `mmap` 显存之后，
调两次就会漏掉一次 `munmap`。此处假设各层的 `init` 只被 `main.c` 调用一次，
由层表的循环保证；这三行是在这个前提失效时兜底。

日志放在 `g_inited = 1;` 之后。顺序有意义：日志的语义是"这一层现在是好的"，
在标志位置起来之前打，说的就不是这件事了。

`TODO` 注释里写的是三个具体动作而不是"这里以后填 framebuffer"。
六份 `TODO` 各不相同：

| 层 | TODO 内容 |
|---|---|
| display | 第 03 章 Framebuffer：打开 `/dev/fb0`，取 `fb_var_screeninfo`，`mmap` 出显存 |
| input | 第 05 章 输入系统：打开 `/dev/input/eventX`，起线程循环读 `input_event` |
| font | 第 04 章 文字显示：装载 ASCII 点阵 / HZK16 中文 / freetype 矢量字体 |
| ui | 按钮等控件，依赖 display 出图和 font 出字，所以必须排在这两层后面 |
| page | 页面管理，依赖 ui 画界面和 input 收事件 |
| business | 业务逻辑，项目整合阶段填，这里是整个程序真正干活的地方 |

后三条没有章号，因为它们不对应 PDF 的某一章，对应的是项目整合阶段。
它们写的是依赖关系，也就是这一层为什么排在层表的那个位置。

### 3.3 退出（第 18 到 27 行）

```c
void display_exit(void)
{
	if (!g_inited)
		return;

	/* TODO 释放 display_init 里申请的资源, 顺序与申请时相反 */

	g_inited = 0;
	LOG_INFO("display exit OK");
}
```

和 `init` 镜像。开头那三行的作用比 `init` 那边大：
`main.c` 在初始化失败时会回滚已成功的层，如果回滚的边界算错了，
对一个没 `init` 过的层调 `exit`，这三行会挡住它。
也就是说，这里是 `main.c` 那个回滚逻辑的第二道防线。

`TODO` 里"顺序与申请时相反"这句话是给以后的自己看的：
一层内部也有依赖顺序，先 `open` 后 `mmap`，就要先 `munmap` 后 `close`。
这和层与层之间反序退出是同一个道理，只是尺度不同。

## 4. 执行顺序

六份文件在运行时的执行顺序完全由 `main.c` 的层表决定，
这六个文件自身不含任何顺序信息。把两者摊平：

| 步 | 谁在跑 | 这一步的可观测结果 |
|---|---|---|
| 1 | `main()` -> `layers_init()` | 无 |
| 2 | `display_init()` | `g_inited` 由 0 变 1，`stderr` 多一行 `display init OK` |
| 3 | `input_init()` | 同上，层名换成 `input` |
| 4-7 | font / ui / page / business | 同上 |
| 8 | `main_loop()` | 一行 `framework is up, no page to run yet` |
| 9 | `layers_exit(6)` -> `business_exit()` | `g_inited` 由 1 变 0，一行 `business exit OK` |
| 10-14 | page / ui / font / input / display | 同上，反序 |

第 2 步到第 7 步之间，六个 `g_inited` 是六个互相独立的变量，
分别在六个 `.o` 的 `.bss` 段里。它们同名但不同址，这是 `static` 的作用。

## 5. 容易读错的地方

**六个 `g_inited` 不是同一个变量。** 名字相同，`static` 让它们各自独立。
`gdb` 里 `p g_inited` 会问你要哪一个。

**幂等保护现在看起来是多余的**，它是为函数体填上之后写的。
删掉它，判据一条都不会红——这是本目录里明确没有判据覆盖的一处，
因为在函数体为空的情况下，重复初始化确实没有可观测差异。

**`display_exit()` 没有返回值不是漏写。** 见第 2 节。

**`#include "display/disp_manager.h"` 里的目录前缀不能省。**
省了照样能编过（`-I.` 在），但跨层引用的痕迹就没了。

## 6. 消费者

| 文件 | 用到的部分 |
|---|---|
| `main.c` 第 15 到 20 行 | 六个头文件全部包含 |
| `main.c` 第 32 到 39 行 | 十二个函数名，填进层表 |
| `check.sh` 第 32 到 33 行 | 六个层名，写死成期望的启停顺序 |
| `check.sh` 第 45 行 | 用 `sed` 删掉层表里 `business` 那一行做注错 |

`check.sh` 第 32 到 33 行那两个字符串是六个层名的**第二份副本**，
和 `main.c` 的层表各写各的。改层名或调整顺序时两处都要改，
目前没有任何机制保证它们一致。这是这份代码里唯一一处双写。
它没有被消掉，是因为判据的期望值本来就应该独立于被测对象写死——
如果期望值也从 `main.c` 里读，那么改坏 `main.c` 时期望值会跟着变，判据永远绿。
