# 层管理器空壳 逐行精读

对应代码：五层各一对文件，`.c` 各 27 行，`.h` 各 13 行。

```
    project/input/input_manager.{c,h}
    project/font/font_manager.{c,h}
    project/ui/ui_manager.{c,h}
    project/page/page_manager.{c,h}
    project/business/business_manager.{c,h}
```

五份的结构完全相同，只有三处不同：函数名前缀、日志里的层名、`TODO` 注释的内容。
本篇以 `input` 为样本讲，行号对五份都成立。

第六层 `display/` 原本也是这个形状，第 03 章已经把它填成了真实现，
篇幅和结构都和这里不同，单独成篇见 [display 层逐行精读](display层-逐行精读.md)。
本篇留下的这五份，是它填之前的样子，也是后面每一层被填之前的样子。

前置：无。这是本目录里最短的一篇。

---

## 1. 文件定位

一层的最小形状。这五份文件现在不干任何活，它们存在的理由有三个：

**让 `main.c` 的层表有真实的符号可以填。** 层表里放的是函数指针，
指向一个不存在的函数是链接期错误。

**让判据能数出六。** 判据数的是运行时输出里 `init OK` 出现几行。
空目录数不出来，空文件也数不出来，必须有一个真的会打日志的函数。
`display` 填上实现之后这条判据一个字都没改，因为它打的还是同一行日志——
这正是"接口不变，实现可换"想要的效果。

**把"以后往哪填"这件事固定在代码里而不是文档里。**
每个 `_init()` 里都有一条 `TODO` 注释，写明哪一章来填这里。
文档会忘记看，代码里的 `TODO` 在改这个文件时一定会看到。

## 2. 头文件（`input_manager.h` 全文 13 行）

```c
#ifndef __INPUT_MANAGER_H
#define __INPUT_MANAGER_H

/*
 * input 层对外接口。
 * 这里只放函数声明, 不放内部结构体定义 -- 别的层看不见本层的内部状态,
 * 才谈得上以后能整层换掉。
 */

int  input_init(void);
void input_exit(void);

#endif /* __INPUT_MANAGER_H */
```

**头文件里只有函数声明，一个结构体都没有。** 这是这五份文件现在的形状，
注释里写着理由：别的层想用 input，只能通过这两个函数；
它拿不到 input 的内部状态，也就没法依赖那些状态的形状。

`display` 那一层填实现时突破了这条：`disp_manager.h` 现在导出了
`struct disp_buf`、`struct disp_ops` 和四个画图函数。这不是违约，
是这条约定本来的边界——**上层要用的数据形状必须导出，内部状态不导出**。
`disp_manager.h` 里没有 `g_fd`、`g_mem`、`g_list` 的任何痕迹，
`linux/fb.h` 也没有进这个头文件。判据 `[10]` 守的就是这一条。
剩下这五层被填的时候，各自也会长出自己的一小段接口，形状参考 display 那篇。

**返回类型是 `int` 和 `void`，不对称。** `init` 会失败，
所以返回 `common.h` 里那套错误码；`exit` 不允许失败，
所以没有返回值。这不是省事：如果 `exit` 也能失败，
`main.c` 里那个反序回滚的循环就要处理"回滚到一半又失败了"的情况，
而那种情况下没有任何合理的动作可做。把它从接口上排除掉，比处理它更正确。

包含保护用双下划线加文件名。六个头文件的保护宏名字互不相同
（`__INPUT_MANAGER_H`、`__FONT_MANAGER_H`……），
因为它们跟文件名走而不是跟目录名走。

**这个头文件不包含 `common.h`。** 它不需要：它只用到了 `int` 和 `void`。
包含关系保持最小，改 `common.h` 时被卷进来重编的文件就少一些。
`.c` 那边自己包含 `common.h`。

## 3. 实现文件（`input_manager.c` 全文 27 行）

### 3.1 两个包含与一个文件级状态（第 1 到 4 行）

```c
#include "common.h"
#include "input/input_manager.h"

static int g_inited;
```

第一个包含用双引号，找的是 `-Iinclude` 指定的目录（见 Makefile 精读）。

第二个包含带了目录前缀，写成 `"input/input_manager.h"` 而不是 `"input_manager.h"`。
这不是为了让编译器找得到（`-I.` 已经在了），是为了让人一眼看出跨层引用。
`unittest/disp_test.c` 里的 `#include "display/disp_manager.h"` 就是这条约定的用处：
一眼看出这是跨层的边，可以对照分层图检查方向对不对。
写成不带前缀的形式，这条信息就没了。

`static int g_inited;` 是文件作用域的静态变量。`static` 在这里的含义是
**这个符号不进全局符号表**：五个 `.c` 里都有一个叫 `g_inited` 的变量，
去掉 `static` 就是五个同名全局符号，链接时报重复定义。

它不显式初始化。C 标准规定文件作用域的静态变量默认初始化为 0，
它落在 `.bss` 段里，不占文件空间，由加载器负责清零。
写成 `= 0` 效果相同，但会让一些编译器把它挪到 `.data` 段，反而占空间。

### 3.2 初始化（第 6 到 16 行）

```c
int input_init(void)
{
	if (g_inited)
		return ERR_OK;

	/* TODO 第 05 章 输入系统: 打开 /dev/input/eventX, 起线程循环读 input_event */

	g_inited = 1;
	LOG_INFO("input init OK");
	return ERR_OK;
}
```

开头那三行是**幂等保护**：已经初始化过就直接返回成功，不重复做。
现在的函数体是空的，重复执行没有代价，所以这三行看起来是多余的。
它是为以后写的。`display` 那层填完之后这件事已经不是假设了：
`display_init()` 里重复注册后端会让链表节点指向自己，
下一次按名字查找就是死循环——见 display 篇第 3.3 节。

日志放在 `g_inited = 1;` 之后。顺序有意义：日志的语义是"这一层现在是好的"，
在标志位置起来之前打，说的就不是这件事了。

`TODO` 注释里写的是几个具体动作而不是"这里以后填输入系统"。
六份 `TODO` 各不相同：

| 层 | TODO 内容 |
|---|---|
| display | 已完成，第 03 章填的，见 [display 层逐行精读](display层-逐行精读.md) |
| input | 第 05 章 输入系统：打开 `/dev/input/eventX`，起线程循环读 `input_event` |
| font | 第 04 章 文字显示：装载 ASCII 点阵 / HZK16 中文 / freetype 矢量字体 |
| ui | 按钮等控件，依赖 display 出图和 font 出字，所以必须排在这两层后面 |
| page | 页面管理，依赖 ui 画界面和 input 收事件 |
| business | 业务逻辑，项目整合阶段填，这里是整个程序真正干活的地方 |

后三条没有章号，因为它们不对应 PDF 的某一章，对应的是项目整合阶段。
它们写的是依赖关系，也就是这一层为什么排在层表的那个位置。

### 3.3 退出（第 18 到 27 行）

```c
void input_exit(void)
{
	if (!g_inited)
		return;

	/* TODO 释放 input_init 里申请的资源, 顺序与申请时相反 */

	g_inited = 0;
	LOG_INFO("input exit OK");
}
```

和 `init` 镜像。开头那三行的作用比 `init` 那边大：
`main.c` 在初始化失败时会回滚已成功的层，如果回滚的边界算错了，
对一个没 `init` 过的层调 `exit`，这三行会挡住它。
也就是说，这里是 `main.c` 那个回滚逻辑的第二道防线。

`TODO` 里"顺序与申请时相反"这句话是给以后的自己看的：
一层内部也有依赖顺序，先 `open` 后 `mmap`，就要先 `munmap` 后 `close`。
`display/framebuffer.c` 的 `fb_close()` 就是按这句话写的，
它先 `munmap` 后 `close`。这和层与层之间反序退出是同一个道理，只是尺度不同。

## 4. 执行顺序

这些文件在运行时的执行顺序完全由 `main.c` 的层表决定，
它们自身不含任何顺序信息。把两者摊平：

| 步 | 谁在跑 | 这一步的可观测结果 |
|---|---|---|
| 1 | `main()` -> `layers_init()` | 无 |
| 2 | `display_init()` | 选中一个后端并打开它，`stderr` 多一行 `display init OK`（见 display 篇） |
| 3 | `input_init()` | `g_inited` 由 0 变 1，`stderr` 多一行 `input init OK` |
| 4-7 | font / ui / page / business | 同上 |
| 8 | `main_loop()` | 一行 `framework is up, no page to run yet` |
| 9 | `layers_exit(6)` -> `business_exit()` | `g_inited` 由 1 变 0，一行 `business exit OK` |
| 10-14 | page / ui / font / input / display | 同上，反序 |

第 3 步到第 7 步之间，五个 `g_inited` 是五个互相独立的变量，
分别在五个 `.o` 的 `.bss` 段里。它们同名但不同址，这是 `static` 的作用。

## 5. 消费者

| 文件 | 用到的部分 |
|---|---|
| `main.c` 第 6 到 11 行 | 六个头文件全部包含 |
| `main.c` 第 20 到 27 行 | 十二个函数名，填进层表 |
| `check.sh` 第 37 到 38 行 | 六个层名，写死成期望的启停顺序 |
| `check.sh` 第 50 行 | 用 `sed` 删掉层表里 `business` 那一行做注错 |

`check.sh` 第 37 到 38 行那两个字符串是六个层名的**第二份副本**，
和 `main.c` 的层表各写各的。改层名或调整顺序时两处都要改，
目前没有任何机制保证它们一致。这是这份代码里唯一一处双写。
它没有被消掉，是因为判据的期望值本来就应该独立于被测对象写死——
如果期望值也从 `main.c` 里读，那么改坏 `main.c` 时期望值会跟着变，判据永远绿。
