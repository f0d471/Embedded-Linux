# 质检业务嫁接：inspect 层与产品化四件套

这份文件是 [项目路线图-网络视频终端](项目路线图-网络视频终端.md) 的增补，不取代它。
它回答一个问题：一份外部参考项目（边缘视觉质检终端）里，哪些东西值得吸收进
`project/`，用什么形态吸收，以及怎么验证吸收进来的东西是对的。

## 一、结论

**终点不变，仍是网络视频终端。质检不是第二个终点，是挂在同一副骨架上的第二个业务。**

新增的东西只有两类：

    inspect 层      规则注册链表 + 五条检测规则, 纯 C 实现
    产品化四件套    配方 / 本地追溯 / 异常恢复与看门狗 / OTA 与远程运维

第二类正是网络视频终端路线图第八节点名的那四样：那一节判定原终点"真产线工具的
主体是 OTA、看门狗、崩溃恢复、结果上报留档，成品版一件也没有"。参考项目恰好把
这四样都做了，所以它的价值在**产品化维度**，不在视觉算法维度。

"工业巡检终端"本来就写在网络视频终端路线图第二节的产品原型里。质检业务是那句话的
具体落地，不是方向变更。

## 二、参考项目能给什么，不能给什么

来源：`E:\Workspace\基于Linux和IMX6ULL的边缘视觉质检终端产品级项目`。
付费课程资料，作者已申请软著并明示禁止转载与上传代码托管平台。

**约束：只吸收设计，不搬运源码。本仓不出现来自该项目的任何一行 C++ 代码，
也不复制它的文档原文。** 本文件引用它时只描述"它解决了什么问题"，不抄它怎么写。

它的代码形态与本仓的冲突是结构性的，按层实测过一遍（对其 `src/` 逐文件检查
Qt 头文件引用得到）：

| 参考项目的层 | 实现方式 | 与本仓的关系 |
|---|---|---|
| `ui/` 十个文件 | Qt5 Widgets | 冲突。Qt 的 linuxfb 后端独占 `/dev/fb0`，与本仓 display 层抢同一个设备 |
| `io/` 设备联动 | QObject + QSocketNotifier | 冲突。本仓走 input 层已有的 poll 循环 |
| `system/health_monitor` | QObject + QTimer | 冲突。本仓无 Qt 事件循环 |
| `camera/` | 名为 v4l2，内部是 `cv::VideoCapture` | 无参考价值，等于没写 V4L2 |
| `core/inspection_core/` | C++ + OpenCV | 算法思路可借鉴，实现方式不采用，见第三节 |
| `core/recipe_parse/` | nlohmann/json | 设计可借鉴（ROI/阈值/规则三元组），解析器自己写 |
| `data/` | SQLite3 + CSV + 日志 | 表结构与字段设计可借鉴，`sqlite3` 本身就是 C 库 |
| `system/ota/` | 自写 manifest + sha256 校验 | 升级包格式与校验流程可借鉴 |
| `deploy/nginx/` | 服务端配置 | 与语言无关，可直接参照 |

另一处硬差异：参考项目面向正点原子 ALPHA 板与 NXP Poky 根文件系统，本仓是
100ASK_IMX6ULL Pro。它文档里写死的 sysfs 路径、input 事件号、库版本一律不能照抄，
**全部以本板实测为准**。

## 三、为什么不把 OpenCV 搬上板

三条理由，按重要性排列：

1. **说不出所以然的代码不算能力。** `cv::matchTemplate` 一行调用背后是归一化互相关，
   自己写过和调过是两回事。本仓从第 00 章起的做法就是"自己写一遍才算学会"，
   引 OpenCV 等于在这个项目最核心的一层上破例。

2. **本板根文件系统没有 OpenCV。** 参考项目能直接用是因为 Poky 根文件系统自带
   `libopencv_core.so.3.1`。本仓要用就得先交叉编译一整套 OpenCV 并塞进 rootfs，
   代价远大于手写五条规则。

3. **规则本身不复杂。** 五条规则里三条是遍历像素做统计（均值、颜色面积计数、
   二值质心），剩下两条（边缘、模板匹配）是标准算法，不是研究性难题。

不引 OpenCV 上板，不等于不用它。**它的正确位置是判据的金标准**：

    1  WSL 里用 OpenCV 对一组固定输入算一遍, 结果存成 fixture
    2  同一组输入交给纯 C 实现, 在 x86 上算一遍
    3  同一个纯 C 实现交叉编译后, 在板上算一遍
    4  三份结果逐项比对, 不一致就是纯 C 实现错了

板上比对时只读 fixture，不需要 OpenCV 在场。

这是本仓判据体系的自然延伸，和第 03 章"假显存预演，板上复算，计数逐项相等"、
第 04 章"x86 与 ARM 同一组 glyph 计数一致"是同一个形状。它比"我用了 OpenCV"
强一个量级：证明的是实现正确性，不是调用能力。

金标准参照值在 WSL 里生成后存成定值文件进 `project/` 的 fixture，板上比对时
不需要 OpenCV 在场。

## 四、与既有刀的关系

质检业务不自带采集、解码、显示、线程模型，这些全部复用网络视频终端的既有刀：

| 既有刀 | 质检业务用它做什么 |
|---|---|
| 刀 0 假摄像头后端 | 直接当样本图回放器用，OK/NG 样本目录就是帧源 |
| 刀 1 V4L2 UVC 后端 | 触发采图 |
| 刀 2 解码与显示 | 解出 RGB 交给 inspect，同时上屏预览 |
| 刀 3 多线程流水线 | 检测线程挂成解码队列的第二个消费者，与显示线程并列 |
| 刀 4 OSD | 画 ROI 框、NG 区域高亮、良率与计数 |
| 刀 5 net 层 HTTP | OTA 下载与 NG 图上传复用同一个 HTTP 客户端 |
| 刀 6 UART | 触发源之一 |
| 刀 9 ui/page/business/config | 质检页面与配方解析落在这一刀里 |

**新增只有 inspect 与 record 两层**，以及产品化那几项跨层行为。
加一层仍然只动两处（`Makefile` 的 `SUBDIRS`、`main.c` 的 `g_layers` 表），
成本在第 01 章已经压到最低。

流水线上的位置，自上而下一条直线，RGB 队列后分成两个并列的消费者：

    采集线程 -> 帧队列 -> 解码线程 -> RGB 队列
      |
      +-> 消费者甲  显示线程 -> fb0
      |
      +-> 消费者乙  检测线程 -> inspect -> record
                                  |
                                  +-> IO 联动

检测线程与显示线程互不阻塞。这一条对应参考项目需求 3.4.8"检测执行期间不能阻塞
界面响应"，是它的功能需求里最值得吸收的一条。

## 五、分刀施工

刀号用 Q 前缀独立编号，避免与网络视频终端的刀 0-11 混淆。
Q1/Q2 在刀 3 完成后即可开始；Q3 起与刀 9 合流。

每刀判据都要能注错见红：写完判据先故意改坏一处，看它红一次，再改回来。
判据脚本并入 `project/check.sh`，单层功能测进 `unittest/`。

### Q1  inspect 层骨架与第一条规则

照 display / font / input 三层已经用熟的形状：`struct` + 函数指针 + 链表注册。
一条规则就是一个 `.c` 文件加一行注册。先只做 `mean_gray`（ROI 内灰度均值与阈值比较），
把"帧进来、规则跑完、结果出去"整条链路打通。

规则接口至少要能表达：ROI 矩形、阈值、算出来的实测值、判定结果、失败原因码。
失败原因码不能只有"NG"，要能区分"低于阈值""ROI 越界""模板缺失"。

    判据  注册两条同名规则时第二条被拒绝, 链表长度不变
          ROI 完全落在图像外时返回越界错误码, 不是崩溃也不是 NG
          ROI 部分越界时按裁剪后的有效区域计算, 与手工裁剪后再算的结果相等
          同一张图连算 100 次结果完全相同, 证明无状态残留
    注错  把 ROI 越界判断的边界条件从 >= 改成 >, 越界判据必须失败

### Q2  四条规则补齐与金标准比对

补 `color_area`（RGB 转 HSV 后在色相/饱和度/明度区间内计数）、
`position_offset`（二值化后求质心，与期望位置比距离）、
`edge_contour`（Sobel 或 Canny 后数边缘像素）、
`template_match`（归一化互相关 NCC）。

每条规则先在 WSL 用 OpenCV 对同一组输入算出参照值，存成 fixture；
纯 C 实现的输出与 fixture 比对。浮点结果给出容差并写明容差怎么定的。

    判据  五条规则在同一组 OK/NG 样本上的判定与 OpenCV 参照逐项相同
          浮点中间值与参照的相对误差在写明的容差内, 容差来源在文档里有推导
          x86 与 ARM 两个二进制跑同一组样本, 判定结果逐项相同
          单帧五条规则总耗时在板上有实测值, 写进文档
    注错  把 HSV 转换里 H 的取值范围从 0-179 改成 0-255, 颜色面积判据必须失败
    注错  把 NCC 的分母去掉归一化项（退化成朴素相关）, 模板匹配判据必须失败

**性能预期全部未实测。** A7 单核跑全图 NCC 会慢，慢多少上板才知道。
这一刀结束时必须给出实测的单帧耗时，第一次跑出真数就回来替换本段。
如果耗时超出可接受范围，优化手段（ROI 裁剪、积分图、定点化、降采样金字塔）
按实测瓶颈决定用哪个，不预先设计。优化前后的数字都要留档。

### Q3  配方：一份文件决定检测什么

配方描述"这个产品型号要检查哪几个点位、每个点位用哪条规则、ROI 在哪、阈值多少"。
参考项目用 JSON，本仓的 `config` 层在刀 9 落地，格式随刀 9 的选型走，
不为配方单独引一个 JSON 解析库。

要点在于版本与回滚，不在于格式：配方带版本号，切换配方要留操作记录，
配方非法（缺模板、参数越界、版本不匹配）时**禁止进入检测状态**，而不是带病运行。

    判据  只改配方文件不重编, ROI 与阈值生效, 检测结果随之改变
          配方缺字段时走默认值并告警, 不崩溃
          配方版本与当前产品型号不匹配时, 进入检测被拒绝且给出具体原因
          回滚到上一版配方后, 检测结果与上一版当时的结果逐项相同
    注错  把版本匹配检查恒真, 不匹配拒绝判据必须失败

### Q4  record 层：本地追溯

每次检测落一条记录：时间、产品型号、配方版本、总结果、失败项与原因码、操作者。
图片按 日期/型号/结果 分目录存，三种策略（只存 NG、全存、按比例抽样）。
支持按时间段、型号、结果过滤查询，支持导出 CSV。

`sqlite3` 是 C 库，交叉编译方式照 `00_基础/12 第三方库` 那篇 FreeType 的隔离构建法，
用 ELF Machine 与 SONAME 链验收 ARM staging。

    判据  连测 N 次后数据库记录数为 N, 无丢失无重复
          按结果过滤查询的条数与按结果统计的计数相等
          导出的 CSV 行数等于查询条数, 字段数每行相同, 含逗号的字段被正确转义
          只存 NG 策略下, 图片数等于 NG 数
          记录里的图片路径全部真实存在, 无悬空引用
    注错  把 CSV 的转义函数改成直接拼接, 含逗号字段的判据必须失败
    注错  在图片写盘失败时仍然落库, 悬空引用判据必须失败

### Q5  设备联动与异常恢复

联动：OK/NG 驱动板上 LED 与（若有）蜂鸣器；连续 NG 达到阈值升级告警；
提供强制复位，防止告警卡死。sysfs 路径与按键事件号**以本板实测为准**，
不照抄参考项目里正点原子的路径。

异常恢复对应参考项目需求 3.4.10，逐条都要有可观测行为：

    相机断开        停止检测, 界面提示, 写异常日志, 禁止继续出结果
    采图超时        明确提示, 不静默重试到死
    配方非法        禁止启动检测（Q3 已覆盖）
    磁盘不足        主动清理最旧日期的 OK 图片并告警; 仍不足则停止存图并记录
    进程异常退出    守护进程拉起并写日志
    硬件看门狗      定期喂狗; 主循环卡死时由看门狗复位

    判据  拔掉摄像头后不再产生检测记录, 且异常日志新增一条
          把磁盘填到阈值以上, 清理逻辑触发且删除的是最旧日期的 OK 目录
          清理后仍不足时, 存图停止但检测与落库继续
          kill 掉进程后在设定时间内被重新拉起, 日志记录了这次重启
          连续 NG 达到阈值时告警升级, 强制复位后计数归零
    注错  把磁盘阈值判断反向, 清理触发判据必须失败
    注错  让主循环故意死循环不喂狗, 看门狗复位判据必须成立

本板是否有蜂鸣器、`/dev/watchdog` 是否已编入内核，**两项均未确认**，上板第一件事确认。
没有蜂鸣器就用两个 LED 的闪烁模式区分告警等级，不硬凑硬件。

### Q6  OTA 与远程运维

升级包 + 清单文件（版本号、下载地址、SHA-256）。设备比对版本，下载，**校验通过才替换**，
替换前备份旧版本，启动失败自动回滚。服务端用刀 5 已经写好的 HTTP server，
不为 OTA 另起一套；参考项目用 Nginx，本仓不需要，因为服务端本来就是自己写的。

    判据  清单版本高于本地时才触发下载, 相等或更低不动
          SHA-256 不匹配时拒绝安装且旧版本完好可用
          安装后版本号变化, 重启后仍是新版本
          新版本启动失败时自动回滚, 回滚后旧版本可用
          断网中途下载中断, 重连后不产生半个包被当成完整包
    注错  把 SHA-256 比对改成恒真, 篡改升级包的判据必须失败
    注错  把回滚逻辑去掉, 坏包安装后的可用性判据必须失败

### Q7  质检业务与页面

`business` 里的质检调度：触发 -> 采图 -> 检测 -> 显示 -> 联动 -> 落库。
页面复用刀 9 的 ui/page：主页（实时画面、当前型号、最近结果、OK/NG 计数、良率、
设备状态）、结果页（失败项、原因、NG 区域高亮）、日志页、历史查询页。

触发去抖、超时保护、重复触发抑制要显式实现并可统计，不靠"应该不会那么快按两次"。

    判据  单次触发只产生一条记录, 连按十次在去抖窗口内只记一次
          检测进行中界面仍响应输入（切页、滚动可操作）
          单次检测闭环耗时有实测值; 目标 500ms 以内, 达不到就写实测值并分析瓶颈
          页面切换后前一页资源全部释放（valgrind 无增长）
          CLI 与 GUI 两条路径对同一张图的判定结果相同
    注错  去掉去抖窗口, 连按判据必须失败

保留 CLI 路径不是冗余：GUI 起不来时仍能检测、查询、导出，这是参考项目需求
3.4.10 最后一条，也是本仓 `unittest/` 一贯的做法。

## 七、原创边界

哪些是自己做的，哪些是照行业惯例做的，分清楚，面试时才不会说错话。

自己做的：

    inspect 层的接口设计与注册机制（把 display 层的形状推广到规则引擎）
    五条规则的纯 C 实现，含定点化与性能优化
    金标准比对的验证方法与 fixture 生成流程
    检测线程挂进既有流水线的方式与背压策略
    全部判据与注错用例

照惯例做的（照抄不丢人，但要知道是惯例）：

    检测记录的字段构成（时间/型号/结果/原因/操作者/配方版本）
    图片按 日期/型号/结果 分目录
    OTA 清单的字段（版本/地址/校验和）
    CSV 导出格式

不碰的：参考项目的任何源码与文档原文。
