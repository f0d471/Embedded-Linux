# 项目路线图：对齐电子产品量产工具

这份文件回答一个问题：`project/` 现在这个骨架，
和课程配套项目 `06_实战项目/01_电子产品量产工具` 是不是一回事，
以及照着往下走能不能走到那个终点。

对照对象（记为 `$P`）：

```
    E:\Workspace\01_all_series_quickstart-master
      \06_实战项目\01_电子产品量产工具\source\02_视频配套源码\
```

`$P` 下有 32 个递增的步骤目录，从 `01_display_struct` 到 `32_improve_touch`，
每一步在上一步的基础上加一两个文件。最后一步 `32_improve_touch` 就是成品。

## 一、结论

**分层是一回事，形状还不是。**

对齐的部分：六个层名、层的顺序、调用方向、`include/common.h` 这个位置，
全部取自 `$P`，一一对应。照着往下填，能走到那个终点。

没对齐的部分有四处，其中两处是有意的偏离，两处是还没做到。
逐条列在第三节。

## 二、目标形状是什么

`$P` 的 32 步不是随机排的，它有一个固定节奏，一层走四拍：

```
    struct      先定这一层的数据结构和函数指针表, 只有 .h, 没有实现
      |
      v
    device      写一个具体的底层实现, 把自己注册进去
      |
      v
    manager     写管理层: 遍历链表选一个、把统一接口暴露给上层
      |
      v
    unittest    写一个只测这一层的 main(), 单独编成一个程序跑
```

对着 32 步数一遍：

| 层 | struct | device | manager | unittest |
|---|---|---|---|---|
| display | 01 | 02 framebuffer | 03 | 04 |
| input | 05 | 06 touchscreen / 08 netinput | 10 framework / 11 环形缓冲 | 07 / 09 / 12 |
| font | 13 | 14 freetype | 15 | 16 / 17 |
| ui | 18 | 19 button | （并入 19） | 20 |
| page | 21 | 23 main_page | 22 | 23 |
| business | 24 framework | 25 config / 26 gui / 27 input | （即 main.c） | 28 |

最后四步 29 到 32 是打磨：按钮文字、对外 API、命令执行、触摸改进。

**这一层的核心形状是"结构体加函数指针加链表注册"。** 以 display 为例：

```c
    typedef struct DispOpr {
        char *name;
        int (*DeviceInit)(void);
        int (*DeviceExit)(void);
        int (*GetBuffer)(PDispBuff ptDispBuff);
        int (*FlushRegion)(PRegion ptRegion, PDispBuff ptDispBuff);
        struct DispOpr *ptNext;          /* 链表指针 */
    } DispOpr, *PDispOpr;

    void RegisterDisplay(PDispOpr ptDispOpr);   /* 底层实现把自己挂上来 */
    int  SelectDefaultDisplay(char *name);      /* 按名字挑一个 */
    int  InitDefaultDisplay(void);              /* 初始化挑中的那个 */
```

底层实现（`framebuffer.c`）定义一个 `DispOpr` 变量填好五个字段，
在自己的 `FramebufferInit()` 里调 `RegisterDisplay(&g_tFramebufferOpr)` 挂进链表。
上层只调 `PutPixel()` / `FlushDisplayRegion()`，不知道底下是 framebuffer 还是别的。

这套东西在 input、font 三层是同一个形状，字段名不同而已：
`InputDevice` + `RegisterInputDevice`，`FontOpr` + `RegisterFont`，
`PageAction` + `PageRegister`。

**它解决的问题**：换一个显示后端、加一个输入源，
不用改任何上层代码，也不用改 `main`。加一个 `.c`，
在里面调一次 `RegisterXxx` 就完事。

## 三、当前的四处不对齐

截至第 03 章，3.1 和 3.4 各完成了一半：注册链表在 display 层已经有了，
`unittest/` 目录已经建起来了。3.2 和 3.3 是有意偏离，不打算改。

### 3.1 注册链表（display 层已补齐，其余五层还没做到）

第 03 章把这个形状引进了 display 层，做法记在
[TechReports 03](../TechReports/project/03-display层-两个后端与一张能数的图.md)。

`disp_manager.h` 从 13 行变成 45 行，多出 `struct disp_buf`、`struct disp_ops`
和 `disp_register`；`display/` 下多出两个后端 `framebuffer.c` 和 `memdisp.c`。
`CodeReading/project/层管理器空壳-逐行精读.md` 按计划拆成了两篇，
新的那篇是 [display 层逐行精读](../CodeReading/project/display层-逐行精读.md)。

当初记下的风险是两套启动模型不兼容：`$P` 的 `main` 里是三步，

```c
    DisplayInit();                  /* 触发各底层实现注册自己 */
    SelectDefaultDisplay("fb");     /* 挑一个 */
    InitDefaultDisplay();           /* 初始化挑中的 */
```

而本仓的层表里一层只有一个 `init`。**实际采用的办法是让 `display_init()`
内部把三步做完**，"挑哪一个"来自环境变量 `DISP_DEV`（缺省 `fb`）。
`main.c` 一个字都没改，第 01 章的判据一条都没改。

环境变量这个选法是权宜的：它和 `LOG_FILE` 是同一个路子，
等 `config/` 那一层到位之后（见 3.4），后端名字应该从配置文件来。

**剩下五层**照这个形状补，各自在自己的章节里做：input 在第 05 章
（那时会有两个真实设备挂同一条链表，见第四节的表），font 在第 04 章。

### 3.2 头文件的位置（有意偏离）

| | `$P` | 本仓 |
|---|---|---|
| 位置 | 全部集中在 `include/` | 各层自己目录下，只有 `common.h` 在 `include/` |
| 引用写法 | `#include <disp_manager.h>` | `#include "display/disp_manager.h"` |
| 编译选项 | `-I$(TOPDIR)/include` | `-I.` 加 `-Iinclude` |

偏离的理由是跨层引用要看得出来。
`#include <disp_manager.h>` 看不出这是哪一层的东西，
`#include "display/disp_manager.h"` 一眼就能对着分层图检查方向。

代价是照抄 `$P` 的代码时要改包含语句。这个代价是可控的，
因为本仓的规矩本来就是不抄源码。

**这一条不打算改回去。**

### 3.3 构建系统（有意偏离）

`$P` 用的是课程视频 4_3-6、4_3-7 讲的那份"通用 Makefile"，
仿 Linux 内核的递归构建：

```
    顶层 Makefile          定 CFLAGS / LDFLAGS / TARGET / obj-y
    Makefile.build         递归引擎, 被 make -f 反复调用
    display/Makefile       obj-y += disp_manager.o framebuffer.o
    input/Makefile         obj-y += ...
    ...

    每个目录: 各自的 .o 用 ld -r 并成一个 built-in.o
              子目录的 built-in.o 再并进上一层
              顶层的 built-in.o 链接成 app
```

本仓用的是单份非递归 Makefile，理由与代价写在
[TechReports 第 01 章第 3.3 节](../TechReports/project/01-先立骨架-分层启停与两棵产物树.md)。

一句话：那套东西的三项能力（任意深的目录树、按目录设编译选项、
按单文件设编译选项）本仓当前一项都用不上，
而它的代价是构建过程分散在七个文件里。

**但它必须学。** 内核和 U-Boot 的构建就是这套，第 2 阶段躲不开。
所以它以实验的形式进了 `notes/01` 第 4 节，从零复现一遍，
不作为 `project/` 的构建系统。

**重新评估的触发条件**：`SUBDIRS` 里出现嵌套目录，
或者某一层需要单独的编译选项（比如 freetype 那一层要加 `-I` 到 freetype 头文件）。
后者更可能先发生，届时先试 `CFLAGS_font/xxx.o` 这类按目标变量，
仍不够用再考虑换。

### 3.4 缺一个目录：config/（unittest/ 已补齐）

`$P` 有七个目录，本仓现在有七个：六层加 `unittest/`。还缺的是 `config/`：

```c
    /* $P/include/config.h */
    #define CFG_FILE  "/etc/test_gui/gui.conf"

    typedef struct ItemCfg {
        int  index;
        char name[100];
        int  bCanBeTouched;
        char command[100];      /* 点这个按钮要执行的命令 */
    } ItemCfg, *PItemCfg;
```

它读一个配置文件，决定界面上有几个按钮、每个按钮叫什么、点下去执行什么命令。
量产工具"不改代码就能换一套测试项"的能力全在这一层。
它在 `$P` 的第 25 步引入，属于 business 阶段。

**补齐时机**：项目整合阶段，跟 business 层一起做。
届时 `SUBDIRS` 加一个 `config`，`main.c` 的层表加一行。
层表里它应该排在 `business` 之前、`page` 之后，
因为 page 要按配置项建按钮。

`unittest/` 是另一件事，第 03 章已经建起来了。`$P` 每写完一层就配一个
只测这一层的 `main()`，单独编成一个可执行程序（`disp_test`、`input_test`、
`font_test`、`ui_test`、`page_test`）。本仓现在有 `unittest/disp_test.c`，
后面每层各加一个。

**这两者不冲突，都要有。** 分工是：

| | `check.sh` | `unittest/` |
|---|---|---|
| 量什么 | 框架约定：启停顺序、构建行为、加文件不改 Makefile | 单层功能：这一层的接口调用之后现象对不对 |
| 在哪跑 | WSL 跑 x86 产物；板上跑 ARM 产物 | 同左 |
| 自动判定 | 有，PASS/FAIL 计数 | 有：程序只画图，计数交给 `unittest/count.sh` |

本仓的 `unittest/` 比 `$P` 那边多一条：**判定不靠肉眼**。
单测程序自己不统计任何东西，画完把整块显存倒出来，由独立的计数脚本去数。
在板上就是 `dd` 读回显存再喂给同一个脚本。肉眼只用来确认最后那一眼颜色和位置。

`unittest/` 有一个必须处理的问题：那些文件里各有一个 `main()`，
和 `main.c` 的 `main()` 冲突。`$P` 靠递归构建时不把 `unittest/` 编进 `obj-y` 来避开。
本仓的 `SUBDIRS` 白名单天然能避开——不把 `unittest` 加进去就行——
但那样它也编不出来。`Makefile` 里加的是一个 `test` 目标：
每个 `unittest/*.c` 各自链接成一个同名程序，
和 `$(OBJS)` 里除 `main.o` 之外的全部 `.o` 一起链（`filter-out` 一个函数就够）。

## 五、硬件差异（会改变实现，不改变分层）

板子是 100ASK_IMX6ULL Pro，与 `$P` 录制时的配置有三处不同。

**没有 LCD 屏，用板载 HDMI 接普通显示器。**
对 display 层没有影响：两者都是 `/dev/fb0`，
只有分辨率和 bpp 不同，而这两个值本来就是运行时从
`ioctl(FBIOGET_VSCREENINFO)` 读出来的。

**没有触摸屏，用 USB 鼠标。** 这一条有影响。
`$P` 的 `input/touchscreen.c` 用的是 tslib（链接 `-lts`），
tslib 只认触摸设备。USB 鼠标同样是 `/dev/input/eventX`，
但要直接读 `struct input_event` 自己解析 `EV_REL` / `EV_KEY`，
而且鼠标给的是相对位移，要自己累加成绝对坐标并做边界钳制。

也就是说 input 层的底层实现要自己写一个 `mouse.c`，
而不是照抄 `touchscreen.c`。**这正好是注册链表这个形状的用武之地**：
`InputDevice` 结构体和 `input_manager.c` 一行不用改，
只是挂上去的那个实现换了一个。第 05 章要把这一点作为判据来验。

**`$P` 的 `-lts` 依赖要去掉。** 顶层 Makefile 的 `LDFLAGS` 里那个 `-lts`
在本仓不需要，工具链里也没有这个库，照抄会链接失败。
