# 技术分享

记录 `project/` 每个工作点的开发过程。一层一个系列，第一篇讲从零到一的骨架，
之后每完成一个工作点增加一章。

## 记录单元

一章记录一个工作点，由事件、行为、结果三部分构成，三者齐备才算记完。

| 部分 | 内容 | 举例 |
|---|---|---|
| 事件 | 触发这次改动的观测 | 判据变红、板上黑屏、改了头文件却不重编 |
| 行为 | 针对事件做了什么 | 改代码、加判据、换实现 |
| 结果 | 行为带来的可测量变化 | check.sh 的 PASS 数、产物体积、板上帧率 |

不做重点摘要。被排除的方案、走错的判断、失败的尝试都要写进对应章节。

## 章节结构

每章按以下六节组织，节序固定。

### 一、动机

从上一章的结论接起，把因果链逐环写完，不跳环。每一环回答为什么不是另一种选择。

### 二、为什么是这几步

先完整列出这个工作点拆成哪几步，再从对象自身的性质推出为什么正好是这几步。
读者读完应能得到两条信息：这个工作点的总工作量，以及为什么少一步都不成立。

### 三、每一步做了什么

一步一节，每节回答两个问题：这一步解决什么问题，用什么办法解决。

- 描述写在行为级：这一步对数据、对构建过程做了什么。
  代码逐行怎么读属于 [`../CodeReading/`](../CodeReading/)。
- 以图为主。分层、调用方向、目录树、时间顺序，能画图的一律画图。
- 办法分两类，写明属于哪一类：常规做法一句话带过；特定手段写明是什么、
  为什么需要、代价是什么。

### 四、遇到的问题

一个问题按四段写：第一现场（当时的错误输出）、解读（这个输出说明什么、
排除了哪些可能）、定位（从现象到根因的路径，包含判断错误的那一次）、
根因与修法（改了什么、为什么有效）。结尾补一句：原判据为什么没有覆盖到它。

### 五、结果

本机或板上的实测数字，与改动前对比。写明测量方法、测量对象、已知误差来源。

### 六、还欠什么

本工作点留下的账，指向 [`../Todo/`](../Todo/) 的条目。没有则写没有。

## 写法约束

读者是没有参与过本项目、也没看过这门课的工程师。

| 项 | 约束 |
|---|---|
| 开头 | 先写明这是什么板子、要做成什么东西，再给数据；不以内部名词开篇 |
| 专有名词 | 首次出现时当场解释一句 |
| 不确定的内容 | 注明是推测还是未裁决 |
| 最终实现 | 只写定稿形态；中间版本写入"遇到的问题" |
| 不写的内容 | 已推翻且无教学价值的方案、待办清单（属于 `Todo/`） |
| 对举句式 | 不用"不是 X，是 Y"，直接写 Y |
| 加粗 | 限术语首次出现和硬性结论，不逐段加粗 |
| 表格 | 只放实测数据，不用于概念对比 |
| 结尾 | 不复述全文，不列条数式小结 |
| 符号 | 不用 emoji，不用符号代替措辞 |
