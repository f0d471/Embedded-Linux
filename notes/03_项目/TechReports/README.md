# 技术分享

记录 `project/` 每个工作点的开发过程。一个层一个系列，第一篇讲从零到一的骨架，
之后每完成一个工作点增加一章。

## 记录单元

一章记录一个工作点，由事件、行为、结果三部分构成，三者齐备才算记完。

| 部分 | 内容 | 举例 |
|---|---|---|
| 事件 | 触发这次改动的观测 | 判据变红、板上黑屏、改了头文件却不重编 |
| 行为 | 针对事件做了什么 | 改代码、加判据、换实现 |
| 结果 | 行为带来的可测量变化 | check.sh 的 PASS 数、产物体积、板上回读字节数 |

不做重点摘要。被排除的方案、走错的判断、失败的尝试都要写进对应章节。

## 章节结构

每章按以下六节组织，节序固定。

### 一、动机

从上一章的结论接起，把因果链逐环写完，不跳环。每一环回答为什么不是另一种选择。

### 二、为什么是这几步

先完整列出这个工作点拆成哪几步，再从对象自身的性质推出为什么正好是这几步。
读者读完应能得到两条信息：这个工作点的总工作量，以及为什么少一步都不成立。

### 三、每一步做了什么

一步一节，每节回答两个问题：这一步解决什么问题，用什么办法解决。

- 描述写在行为级：这一步对数据、对构建过程做了什么，哪些字节搬到哪里。
  代码逐行怎么算属于 [`../CodeReading/`](../CodeReading/)，这里只贴关键几行。
- 位段切分、数据流向、状态转移、资源生命周期，能画图的一律画图；
  架构图用 SVG 放在 `project/fig/`，结构图与流程图用 ASCII 放在正文。
- 办法分两类，写明属于哪一类：常规做法一句话带过；特定手段写明是什么、
  为什么需要、代价是什么。

### 四、遇到的问题

一个问题按四段写，本节篇幅不设上限。

| 段 | 内容 | 约束 |
|---|---|---|
| 第一现场 | 当时的错误输出或反常计数 | 只贴输出。原始记录丢失时按当时的问题描述还原，并注明哪些是反推的 |
| 解读 | 逐行说明该输出的含义 | 说明哪个字段是关键、该数值指向什么结论、排除了哪些可能 |
| 定位 | 从现象到根因的路径 | 写明试过什么、排除什么、依据是什么，包含判断错误的那一次 |
| 根因与修法 | 改了什么、为什么这样改有效 | 结尾补一句：原判据为什么没有覆盖到它 |

### 五、结果

本机或板上的实测数字，与改动前对比。写明测量方法、测量对象、已知误差来源。
没有实测的数字标明是估算或推测。

### 六、还欠什么

本工作点留下的账，指向 [`../Todo/`](../Todo/) 与 [`../../Bugs/`](../../Bugs/) 的条目。
没有则写没有。

## 写法约束

读者是没有参与过本项目的工程师。教学性的分步练习、手算路线、自测题属于
`notes/` 的主线章节，本章不承担。

| 项 | 约束 |
|---|---|
| 开头 | 先写明这是什么板子、要做成什么东西，再给数据；不以内部名词开篇 |
| 专有名词 | 首次出现时当场解释一句 |
| 不确定的内容 | 注明是反推值还是未裁决 |
| 最终实现 | 只写定稿形态；中间版本写入「遇到的问题」 |
| 不写的内容 | 已推翻且无教学价值的方案、待办清单（属于 `Todo/`）、教学复走路线（属于 `notes/`） |
| 对举句式 | 不用「不是 X，是 Y」，直接写 Y |
| 拟人动词 | 使用工程对象和可观测行为：判据覆盖缺陷、判据见红、PASS 数上升 |
| 加粗 | 限术语首次出现和硬性结论，不逐段加粗 |
| 表格 | 只放实测数据与字段契约，不用于概念对比 |
| 符号 | 不用符号代替措辞，不用 emoji |
| 结尾 | 不复述全文，不列条数式小结 |
