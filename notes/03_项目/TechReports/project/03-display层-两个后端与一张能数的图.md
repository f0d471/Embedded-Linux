# 03 display 层：两个后端与一张能数的图

## 一、动机

这个项目跑在一块 100ASK_IMX6ULL 开发板上，目标是把课程配套的"电子产品量产工具"
按自己的构建方式重做一遍：一个分六层的用户态程序，最终要在板子的屏幕上画出
按钮和文字，用 USB 鼠标操作。六层自底向上是 display、input、font、ui、page、business。

前两章把骨架立起来了：六层各有一对 `*_manager.{c,h}`，每层的 `init` 只置一个标志、
打一行日志，`main.c` 按一张层表顺序启动、反序关闭，`check.sh` 用 29 条判据守住
这个形状（[第 01 章](01-先立骨架-分层启停与两棵产物树.md)），日志能整条接到文件上
（[第 02 章](02-日志落文件-让现有LOG自动写入文件.md)）。

骨架立完，下一步要填哪一层不需要挑：层表里 display 排第一，上面四层都要靠它出图。
ui 层画按钮要它，font 层把字模变成像素也要它，没有它，上面的层连"画到哪里去"
都定义不了。

填这一层要面对一件前两章没有过的事：**这一层有一块真实硬件，而开发是在电脑上做的。**
前两章的代码在 WSL 和板子上行为完全一致，判据在哪跑都一样。
显存不是这样——WSL 里没有 `/dev/fb0`，`/proc/devices` 里有 29 号 fb 主设备号，
但没有任何实例；手动 `mknod` 出一个节点，`open` 会返回 `ENODEV`。
内核没有编进 `CONFIG_FB_VIRTUAL`，没有办法在这台电脑上造出一个帧缓冲设备。

于是有两条路。一条是这一层只写真实现，每改一次都上板验一次。
板子通过串口连着，传一个 70 KB 的可执行文件要先 gzip 再 base64 分块发，
一轮验证以分钟计，而且串口会静默丢字节（[第 02 章](02-日志落文件-让现有LOG自动写入文件.md)
的上板小节记过这件事）。另一条是让这一层支持两个后端，其中一个用 `malloc`
出来的内存冒充显存，在电脑上把除"硬件本身"之外的一切都验完，板子只做最后一次确认。

选第二条。多写一个后端的代价是 112 行代码，换来的是这一层的判据可以在秒级重跑，
而且可以随便注错——把代码改坏、跑一次、看判据红不红，这件事在板子上做不了几次。

## 二、为什么是这几步

拆成五步：

```
    D1  定公共类型            上层看得见什么形状的画布
    D2  manager + 假显存后端  注册、选择、启停；能在电脑上跑通整条链路
    D3  画点、填矩形、单测    真正做事的三个函数，加一张能数的图
    D4  真显存后端            open + ioctl + mmap
    D5  判据固化              把 D2 到 D4 的验证全部写进 check.sh
```

这个顺序由一条约束定死：**每一步结束时都要有能立刻跑的验证**。

D1 必须最先，因为后面四步都要用 `struct disp_buf`。它单独成一步而不是
边写边定，是因为这个结构体决定了"上层能看见什么"，定错了后面四步都要返工。
它的验证是一条编译命令：只 include 这个头文件能不能编过。

D2 必须在 D4 前面。反过来的话，写完真后端在电脑上一行都验不了，
只能靠读代码判断对错。假显存先到位，D4 写完只需要验"换一个后端，同一套画图代码还对"。

D3 夹在中间，因为画点需要一块能画的内存（D2 给的），而 D4 的真后端要验证的
正是"同一个 `disp_put_pixel` 在真显存上也对"。D3 如果放在 D4 后面，
D4 完成时没有任何东西能画，验不了。

D5 放最后，因为判据的期望值要用前四步的实测输出填。提前写只能写成"大概是多少"。

少一步都不成立：没有 D1 就没有共同语言，没有 D2 就只能上板开发，
没有 D3 就没有可观测的行为，没有 D4 就上不了板，没有 D5 则这一切下一次改动时全部失效。

## 三、每一步做了什么

### 3.1 第 1 步：定公共类型

`disp_manager.h` 从 13 行变成 45 行。加进去的是三个结构体和四个函数声明。

画一个点要回答两个问题，这决定了结构体里有什么：

```
    写到哪个地址  = base + y * line_length + x * (bpp / 8)
    写进去什么值  = 红 << 红offset | 绿 << 绿offset | 蓝 << 蓝offset
```

两个公式里出现的量，就是 `struct disp_buf` 的全部字段：
`xres`、`yres`、`bpp`、`line_length`、三个 `struct disp_field`（各含 offset 和 length）、
`base`。

`line_length` 是一行占的字节数。它不一定等于 `xres * bpp / 8`，
硬件对齐会让行尾多出一段不显示的填充。这个差别是这一层最容易写错的地方，
也是第 2 步那个假显存后端存在的第二个理由。

位段用自定义的 `struct disp_field` 而不是内核的 `struct fb_bitfield`，
两者前两个成员完全相同。这么做是为了让这个头文件不包含 `linux/fb.h`：
包含了的话，以后 font 层、ui 层、单测程序全都会看见帧缓冲的完整 API，
"只有 display 认识硬件"这条分层就没有了强制力。

`display_init` 和 `display_exit` 的签名保持不变。这是硬约束：
`main.c` 的层表不动，第 01 章的判据一条都不用改。

后端用 `struct disp_ops` 描述，三个函数指针加一个 `next`：

```
    g_list ──► [mem] ──► [fb] ──► NULL
                 │         │
                 │         └─ open: /dev/fb0 + ioctl + mmap
                 └─ open: malloc
```

这是课程配套项目 `DispOpr` 那个形状，[路线图](../../Todo/项目路线图-对齐电子产品量产工具.md)
3.1 条记的"注册链表"到这里补上了。

### 3.2 第 2 步：manager 加假显存后端

manager 做三件事：让各后端把自己挂上链表、按名字选一个、把选中那个的 `open`
填出来的画布存进 `g_buf`。

后端名字来自环境变量 `DISP_DEV`，缺省 `fb`。**缺省不做"fb 打不开就退回 mem"的回退**：
回退的后果是板上显示出问题时程序默默画进一块没人看的内存，
现象是"屏幕没反应但日志说一切正常"。启动失败比这种现象好查。
代价是本机跑判据要显式设 `DISP_DEV=mem`。

假显存后端 `memdisp.c` 用 `malloc` 要一块内存，几何参数从 `DISP_MEM` 来，
缺省 `64x32x32x320`。这个缺省值里藏着这个后端的主要价值：

```
    一行像素 64 x 32 / 8 = 256 字节
    行宽                   320 字节
    ┌──────── 320 ────────┐
    │████ 256 像素 ████│░ 64 ░│   ░ 处填 0xAA
```

行尾那 64 个字节填 `0xAA` 当哨兵。谁把像素写出了界，就会冲掉几个 `0xAA`，
事后数一数还剩几个就知道有没有越界。板子上 `line_length` 是 4096，
而 1024 x 4 也是 4096，行尾没有填充，这类错在板上画出来的图是对的。

关闭时，如果设了 `DISP_MEM_DUMP`，就把整块内存原样写进那个文件。
**只倒原始字节，不在程序里统计**：让被测程序自己数自己画了几个红点，
它数错和画错会一起错，判据永远绿。统计交给第 3 步那个外部脚本。

### 3.3 第 3 步：画点、填矩形、单测

`disp_put_pixel` 把第 1 步那两个公式实现出来。拼色不写 `switch (bpp)`：

```c
static unsigned int pack_field(unsigned int c8, const struct disp_field *f)
{
	return (c8 >> (8 - f->length)) << f->offset;
}
```

上层给的分量是 8 位，硬件要 `length` 位，右移 `8 - length` 丢掉低位再左移到 `offset`。
`length` 为 8 时右移 0 位，所以 32 位色和 16 位色走同一个公式。
这一点在这块板子上不是理论问题：插上 HDMI 显示器时，驱动会读显示器的 EDID
然后自己把模式从 1024x600x32 改成 1280x720x16，dmesg 里一行日志都不留
（[03 章笔记](../../../01_应用编程/03_Framebuffer显示.md) 6.2 节有实测）。
按位段算的程序两种模式都对，而且不用重新编译。

写内存那一步必须按 bpp 分支，因为"一次写几个字节"写在指针类型里，没法用变量表达：

```c
	switch (g_buf.bpp) {
	case 16: *(unsigned short *)p = v; break;
	case 32: *(unsigned int *)p = v; break;
	}
```

单测 `unittest/disp_test.c` 画一张固定图案。每一笔都对应一个要验的性质：

| 画什么 | 验什么 |
|---|---|
| 全屏黑 | 给计数一个干净底 |
| (1,1) 红 4x3、(6,1) 绿 4x3、(11,1) 蓝 4x3 | 三个分量的位段；坐标不从 0 开始，行宽错会整体偏 |
| (xres-1, yres-1) 白点 | 最后一行最后一列 |
| (xres-2, 5) 黄 4x2 | 只有 2x2 在屏内，验右边界裁剪 |
| (xres, 0) 白点 | 越界必须被拒，返回值打出来 |

计数由两个外部脚本做：`count.py` 和 `count.sh`，输出格式一样。
`count.sh` 只用 `od` 和 `awk`，是为了上板准备的——板上没有 python。
判据里有一条专门比对两者的输出是否逐字节相同，两个独立实现互校，
一个写错了另一个不会跟着错。

单测有自己的 `main`，`Makefile` 里加了一个 `test` 目标把它单独链成一个程序，
链接时带上除 `main.o` 外的全部 `.o`（`$(filter-out $(BUILD)/main.o,$(OBJS))`）。
`unittest/` 没有加进 `SUBDIRS`，否则它的 `main` 会被链进 `product_tool`。

### 3.4 第 4 步：真显存后端

`framebuffer.c` 的三个动作是 `open` + 两次 `ioctl` + `mmap`。
这一步的重点不在这三个调用，在失败路径。

`fb_open` 有三处可能失败，每处手上已有的资源都不同。
写成一个幂等的 `fb_close`，三个分支都调它：

```c
static void fb_close(void)
{
	if (g_base != MAP_FAILED) { munmap(g_base, g_size); g_base = MAP_FAILED; }
	if (g_fd >= 0)            { close(g_fd);            g_fd = -1; }
}
```

每种资源自己判断在不在，所以它可以被"半初始化"状态调用。
课程配套项目那边的失败路径漏了 `close(fd)`，正是因为清理代码写在了每个分支里。

映射长度取 `fix.line_length * var.yres` 而不是 `fix.smem_len`。
板上 `smem_len` 是 32 MiB，一屏只用 2.4 MiB。多映射出来的 30 MiB
会把越界写变成静默写坏；只映射一屏，越界就是 SIGSEGV，当场暴露。

设备路径可以用 `DISP_FB` 覆盖。这不是为了灵活，是为了第 5 步那条判据：
`/dev/null` 能 `open` 成功但 `ioctl` 必定 `ENOTTY`，
程序正好停在"fd 已开、ioctl 失败"这一步，让失败路径能在没有帧缓冲的电脑上验。

### 3.5 第 5 步：判据固化

`check.sh` 从 166 行长到 305 行，判据从 29 条到 52 条。新增的 23 条分四组：

| 组 | 条数 | 量什么 |
|---|---|---|
| `[7]` `[7r1]`-`[7r6]` | 15 | 像素分布、哨兵、抽查坐标、越界返回值、两种位深、两个计数脚本互校，以及六种注错 |
| `[8]` `[8r]` | 3 | fb 后端 ioctl 失败时的系统调用序列 |
| `[9]` `[9r]` | 3 | ASan 查假显存泄漏 |
| `[10]` `[10r]` | 2 | `display/` 以外的源文件里不许出现 `/dev/fb` |

其中两条注错是**故意不红**的，它们记录的是"这个错在什么条件下查不出来"：

`[7r2]` 把行宽算成 `xres * bpp / 8`，在有填充的假显存上三原色各从 12 个掉到 8 个、
哨兵从 2048 个掉到 448 个；同一个错换成 `64x32x32x256`（行尾无填充）时，
计数和坐标与正确版完全一样。板上正是后一种情况。

`[7r6]` 把 `fill_rect` 的右边界裁剪删掉，判据不红，因为 `put_pixel` 自己挡了越界。
裁剪留着的理由是不白跑屏外的点，以及将来 `fill_rect` 绕开 `put_pixel`
直接写内存时仍有一道边界。

## 四、遇到的问题

### 4.1 链表节点指向自己，第二次启动就死循环

**第一现场。** 这个现场是主动造出来的。`display_init` 里两个 register 调用之前有一行
`g_list = NULL;`，试着把它删掉，写一个连跑两轮 `display_init` / `display_exit`
的小程序，用 `timeout 5` 限时：

```
    DISP_DEV=mem   ->  init1 0 / init2 0 / done,  退出码 0
    DISP_DEV=nosuch ->  没有任何输出, 退出码 124
```

**解读。** 124 是 `timeout` 杀掉进程时的退出码，说明程序卡在某个循环里出不来。
两个变量只差一个后端名字，而按名字查找是唯一会遍历链表的地方，
所以问题在遍历，不在 `open`。`DISP_DEV=mem` 之所以看不出问题，
是因为 `mem` 正好在链表头，第一次比较就命中，根本没走到第二个节点。

**定位。** `disp_register` 做的是头插：

```c
	ops->next = g_list;
	g_list = ops;
```

第一轮结束后 `g_list` 指向 `mem` 那张表。`display_exit` 只清 `g_cur`，不动 `g_list`。
第二轮再注册一次，此时 `g_list` 已经是 `ops` 自己，于是 `ops->next = ops`。
链表变成一个自环，`disp_find` 找一个不存在的名字就永远走不到 `NULL`。

**根因与修法。** 每轮启动前把链表清空，也就是那行 `g_list = NULL;`。
后端表是 `static` 变量不是 `malloc` 的，清空链表不会泄漏任何东西。

**原判据为什么没覆盖到。** `main.c` 只调一次 `display_init`，现有判据全都只跑一轮，
这个 bug 在当前代码里永远不发作。它属于"以后加一个切换显示设备的功能时立刻发作"
的那一类，现在没有判据覆盖它，只有代码里那行注释记着。

### 4.2 加了单测文件之后，"全量重编"判据变红

**第一现场。**

```
    FAIL  重编文件数: got [10] want [11]
```

**解读。** 这条判据的做法是：完整编一次，`touch include/common.h`，再编一次，
数输出里有几行 `  CC `，期望值是 `NSRC`（脚本自己 `find` 数出来的 `.c` 个数）。
实际值比期望值少 1，说明有一个 `.c` 被数进了期望值却没有被 `make` 编。

**定位。** 新增的文件正好是 1 个：`unittest/disp_test.c`。
`make` 不编它，编它的是 `make test`。而 `find` 把它数进去了。

**根因与修法。** 期望值的口径错了。`make` 不编 `unittest/` 是对的——
那里面每个文件都自带 `main`，进了 `SRCS` 就会和 `main.c` 撞车。
所以改判据，给 `find` 加一条 `-not -path './unittest/*'`。

**原判据为什么没覆盖到。** 这条判据本身没问题，它的期望值假设"所有 `.c` 都由 `make` 编"，
而这个假设在引入单测那一刻失效了。这类失效是判据体系正常的一部分：
它红了，说明它真的在盯着，而不是一直绿着装样子。

### 4.3 判据取错了输出行

**第一现场。**

```
    FAIL  越界 put_pixel 被拒: got [[I] display/disp_manager.c:79 display exit OK]
                               want [out of range put_pixel ret -1]
```

**解读。** 拿到的是 `display exit OK`，说明取到的行不对，不是程序算错了。
判据原本写的是 `sed -n 2p`（取第 2 行）。

**定位。** 单测的输出有两个来源：`printf` 走 stdout，日志宏走 stderr。
判据里用 `>"$W/d.out" 2>&1` 把两者合到一个文件里，而 stdout 有缓冲、stderr 没有，
两股输出交错的位置不固定。第 2 行是什么，取决于缓冲刷新的时机。

**根因与修法。** 按行号取内容，前提是行的顺序稳定。改成按内容锚定：
`grep '^out of range'`。取出来的仍然是整行，仍然和完整的期望字符串比，
不是"输出里含某个词"那种判据。

**原判据为什么没覆盖到。** 这条判据是新写的，问题出在写判据的方式上。
教训是：**同时收 stdout 和 stderr 的时候，不能按行号定位**。

### 4.4 分层判据的口径定错了

**第一现场。**

```
    FAIL  display/framebuffer.c 以外提到 /dev/fb 的文件数: got [1] want [0]
```

**解读。** 有一个文件提到了 `/dev/fb`，而判据认为只有 `framebuffer.c` 可以提。

**定位。** 那个文件是 `display/memdisp.c`，命中的是它开头的说明注释：
"WSL 上没有 /dev/fb0，本后端让整条链路在电脑上跑通"。

**根因与修法。** 这条判据要守的性质是"帧缓冲设备只出现在 display 层"，
写成"只出现在 framebuffer.c"收紧了一档，而收紧的那一档没有对应的设计约束——
同一层内部的文件互相解释对方是正常的。把口径改回目录级：
`grep -cv '^\./display/'`。

**原判据为什么没覆盖到。** 这是判据自身的定义问题。
这类问题的信号是：红了以后发现"代码没错，是判据要求得过多"。

### 4.5 ARM 产物在板上根本起不来

**第一现场。** 把交叉编译出来的单测传上板，第一次运行：

```
    ./disp_test: /lib/libc.so.6: version `GLIBC_2.38' not found (required by ./disp_test)
    ./disp_test: /lib/libc.so.6: version `GLIBC_2.34' not found (required by ./disp_test)
    RC=1
```

**解读。** 这是动态链接器在解析符号版本时的报错，程序一行代码都没执行。
它要的是 GLIBC 2.38 和 2.34 两个版本节点，板上的 `libc.so.6` 里没有。
和 display 层的任何代码都无关。

**定位。** 两边各查一次：

| | 版本 |
|---|---|
| 交叉工具链 | `arm-linux-gnueabihf-gcc` 15.2.0（Ubuntu 26.04 的包，带 glibc 2.41 的头和库） |
| 板上 | `GNU C Library (Buildroot) stable release version 2.30`，`/lib/libc.so.6 -> libc-2.30.so`，2024 年 7 月构建 |

开发机的 glibc 比板子新了十几个版本。动态链接的程序把"我需要 GLIBC_2.38"
写进了自己的符号版本需求里，板上的旧 glibc 满足不了。

**根因与修法。** 静态链接：`make CROSS=arm-linux-gnueabihf- LDFLAGS=-static`。
`LDFLAGS` 在 Makefile 里是 `:=` 赋的空值，命令行传的变量优先级更高，直接覆盖。
产物从 72 KB 变成 495 KB，从 `dynamically linked, interpreter /lib/ld-linux-armhf.so.3`
变成 `statically linked`，板上一次跑通。

**原判据为什么没覆盖到。** `check.sh` 的 `[2]` 组只验 ARM 产物的 `Machine` 字段是 `ARM`，
这个字段和 glibc 版本无关。**交叉编译成功和能在目标板上运行是两件事**，
判据只覆盖了前一件。这条缺口现在也没补上：要补就得有一份板上 glibc 的
版本信息或者一个 sysroot，判据才能在开发机上判断"这个产物在那块板子上跑得起来"。

## 六、还欠什么

**插 HDMI 那一组没测。** 板上验过的是不接显示器的 1024x600x32。
接上 HDMI 之后驱动会自己把模式改成 1280x720x16，期望值是
`921559 / f800:12 07e0:12 001f:12 ffe0:4 ffff:1`（已在假显存上预演，见第五节）。
要验的是同一个二进制不重新编译仍然画对，以及肉眼确认左上角三个色块
和右边缘的半个黄块。此外拔掉显示器之后模式是否变回 1024x600x32 也一直没测过。

**判据没有覆盖"这个产物在板上跑不跑得起来"。** 见 4.5 节。
现在靠的是上板时试一次，试不起来再改成静态链接。

**板上那一步没有进 `check.sh`。** 上板的每一步都是手动发串口命令。
它进不了 `check.sh` 的原因是那个脚本跑在开发机上、不认识板子；
要自动化得另起一个脚本，负责传文件、停 GUI、跑、读回、比对、恢复 GUI。

**双缓冲没有。** 两个后端的 `flush` 都是空实现。现在是单缓冲直接写显存，
画到一半的画面会被扫描出去。等 ui 层开始重画整块区域时再处理。

**font 层的接口还没对。** 第 04 章的字体层要按 `0x00RRGGBB` 的约定调
`disp_put_pixel` 画字模，两边的规格在 [04 章笔记](../../../01_应用编程/04_文字显示.md)
3.4 节写了，但还没有一行代码对接过。

**切换显示后端的功能没有。** 链表和按名字查找都已经在了，
但没有对外的"运行时换一个后端"接口。4.1 节那个自环 bug 就在这条路上等着，
现在靠 `g_list = NULL;` 挡住，没有判据覆盖。
