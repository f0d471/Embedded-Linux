# 02 日志落文件：让现有 LOG 输出自动写入文件

## 一、动机

上一章立起来的是一个空骨架：六层、层表驱动的启停、两棵产物树、18 条判据。
它能跑，但它跑完之后什么都不留下。

这在开发机上无所谓 —— 终端往上翻就是了。到板子上就不行了。
这块板子（100ASK_IMX6ULL Pro）和电脑之间只有一根 USB 转串口线，
所有输出都从这根线出来，看完就没。想比较"改之前"和"改之后"两次运行的日志，
只能靠人眼记，或者靠串口终端的软件自己存 —— 而串口终端存下来的东西里
混着登录提示符、命令回显、shell 提示符，不是干净的程序输出。

更要紧的是这棵树的终点。它对标的是课程配套项目"电子产品量产工具"：
工人拿着板子，点一个按钮跑一项测试，工具要记下每一项的结果。
那件事没有日志文件做不了。

所以这一章要交出的能力是：**程序的日志能落到一个文件里，
而且这个能力不能要求六层里任何一处代码改动。**

后半句是硬约束，不是偷懒。六层是分六章写出来的，中间隔着几个月；
如果"换个日志去处"这种事都要动到每一层，那这棵树的分层就是假的。

## 二、为什么是这几步

拆成三步，每一步解决一个独立的问题：

```text
    第 1 步   决定怎样统一改变所有日志的去向
              -- 改每一条日志? 还是在一个地方把终端换成文件?
                 |
                 v
    第 2 步   把 open 的 flag 定死, 并说明为什么不是别的 flag
                 |
                 v
    第 3 步   给这条通路配判据, 包括两次注错见红
```

**为什么正好是三步，少一步都不成立：**

第 1 步不做，后面两步无从谈起 —— 在哪一层动手决定了要写多少代码。

第 2 步看起来只是"填参数"，但 `O_APPEND` 换成 `O_TRUNC` 会让这个功能
在"跑第二次"的时候悄悄失效，而且不报任何错。这类"参数选错不报错"的地方
必须当成一个独立的工作点对待。

第 3 步不做，前两步等于没做。这棵树的规矩是没有判据的功能不算完成。
而这一章的判据有一个特殊之处：**光量"文件里有没有内容"是不够的**，
还要量"是怎么写进去的"。理由在第 3.3 节。

## 三、每一步做了什么

### 3.1 第 1 步：让所有现有日志一起改变去向

六层的日志全部走同一个宏：

```c
    #define LOG_RAW(tag, fmt, ...) \
        fprintf(stderr, "[%s] %s:%d " fmt "\n", tag, __FILE__, __LINE__, ##__VA_ARGS__)
```

先把 `stderr` 翻译清楚：它叫“标准错误输出”，是程序的一条公共输出通道，
默认通常连接终端。本项目的所有 `LOG_*` 最终都写到这里。

要让这些输出改去处，有三条路：

| 路 | 做法 | 后果 |
|---|---|---|
| A | 给每层的函数都增加“日志写到哪里”参数 | 六层接口和以后所有调用都要改 |
| B | 把日志宏改成依赖一个全局文件变量 | 要管理这个全局变量何时创建、何时失效 |
| C | 保持所有日志仍写 `stderr`，只统一改变 `stderr` 的去向 | 新增一个函数，六层零改动 |

选 C。程序里写 `fprintf(stderr, ...)` 的意思是“把文字交给标准错误输出”，
并没有把“终端”这个目的地写死。因此，只要把 `stderr` 的目的地改成文件，
已有日志就会全部跟着过去。

```text
    改之前：LOG_INFO / LOG_ERR -> stderr -> 终端

    open(path, ...) 打开日志文件后：
             fd -----------------------> 日志文件
             stderr -------------------> 终端

    dup2(fd, STDERR_FILENO) 成功后：
             fd ------------+
                            +-----------> 日志文件
             stderr --------+
```

`open` 成功时返回一个非负整数 `fd`。它只是系统分配的“已打开文件编号”，
后续操作用这个编号找到日志文件。`STDERR_FILENO` 是 `stderr` 的固定编号，值为 2；
代码写常量名，读者不需要记“第几个位置”。

`dup2(来源, 要改变的目标)` 把目标的去向改成来源所指的文件。
所以 `dup2(fd, STDERR_FILENO)` 的意思是：“让标准错误输出以后写到 `fd` 对应的
日志文件。”之后六层里的 `LOG_INFO` 一个字都不用改，输出却自动进入文件。

落地的是一个函数，加在 `common` 里：

```c
    int log_redirect(const char *path);
```

触发方式是环境变量 `LOG_FILE`。选环境变量而不是命令行参数，
是因为这棵树现在还没有参数解析（`main` 里那两行 `(void)argc; (void)argv;`
就是证据），为了一个日志路径引进一套 `getopt` 不划算。
以后 business 层做配置文件时，这个路径会挪进配置里。

调用点必须在 `layers_init()` 之前。这不是风格问题：
挪到后面，六层的 6 条 `init OK` 已经打到终端去了，日志文件只剩 7 行。

### 3.2 第 2 步：打开日志文件时把行为说完整

```c
    fd = open(path, O_WRONLY | O_CREAT | O_APPEND, 0644);
```

这行可以直接拆成四句话：

- `O_WRONLY`：只写这个文件。
- `O_CREAT`：文件不存在时创建它。
- `O_APPEND`：新日志接在旧内容后面，多次运行不清空旧记录。
- `0644`：文件拥有者可以读写，其他人只读；系统的默认权限限制还可能继续收紧它。

`O_APPEND` 还有一个并发写日志时需要的保证：系统会在每一次写入发生前重新确认
当前文件末尾，然后立即写入。若程序自己先用 `lseek` 查到末尾，再单独调用 `write`，
两步之间另一个进程可能已经写了新内容；此时双方拿着同一个旧位置写，就会互相覆盖。

这不是纸上推理。两个进程各写 2000 条 17 字节，跑 5 遍：

| 写法 | 5 次的文件大小（期望 68000） |
|---|---|
| `O_APPEND` | 68000 / 68000 / 68000 / 68000 / 68000 |
| `lseek(END)` + `write` | 46325 / 38964 / 34085 / 49062 / 45305 |

右边一列每次都不一样，因为丢多少取决于两个进程的指令怎么交错。

现在这棵树只有一个进程，选哪个都看不出差别。**选 `O_APPEND` 是为了以后**：
business 层跑测试项时很可能起子进程，那时再回头改，
会是一个"改之前一直是对的、改之后才发现一直是错的"的 bug。

`0644` 是允许权限的上限，不是对最终结果的强制要求。系统还会应用当前的默认
权限限制，这个限制的技术名称是 `umask`。本机的限制值为 022，所以最终仍是 0644。

### 3.3 第 3 步：判据，以及为什么要量"怎么写"

八条判据，分三段。

**第一段，四条正判据加一条错误路径。** 每条排除一种不同的失效方式：

| 判据 | 期望 | 它单独能排除什么 |
|---|---|---|
| 不设 `LOG_FILE` 时终端行数 | 13 | 程序根本没跑起来 |
| 设了之后终端行数 | 0 | 日志去向没有从终端改成文件 |
| 第一次跑完文件行数 | 13 | 去向改了但内容写丢了 |
| 第二次跑完文件行数 | 26 | `O_APPEND` 被换成了 `O_TRUNC` |
| 路径打不开时退出码 | 1 | 打不开时静默降级、继续跑 |

13 和 26 是算出来的不是抄来的：六层各一行 `init OK`、各一行 `exit OK`，
加 `main_loop` 那行，一次运行 13 行。以后加一层，这两个数变成 15 和 30。

**第二段，一条量"怎么写"的判据。**

上面五条有一个共同的盲区：如果把日志宏从 `fprintf(stderr, ...)`
改成 `fprintf(stdout, ...)`，再把 `dup2` 的目标从 2 改成 1，
五条判据仍然可以全绿 —— 数据照样进了文件，只是写的时机完全变了。

而"走 stderr"恰恰是这个设计的地基。C 标准规定 `stderr` 不带缓冲：
每条 `fprintf` 当场变成一次 `write`。`stdout` 接到文件时是全缓冲，
攒够 4096 字节才下去一次。对一块随时可能掉电或被看门狗复位的板子，
这个差别是"最后几 KB 日志还在不在"。

所以补一条数系统调用的判据：

```bash
    strace -f -e trace=write -o "$W/tw.txt" env LOG_FILE=$LOGF ./build/x86/product_tool
    ck "13 条日志对应 13 次 write(2,...)" \
       "$(grep -cE '(^|[0-9]+ +)write\(2,' "$W/tw.txt")" "13"
```

13 条日志正好 13 次 `write`，一行一次。这是**目前唯一一条量"实现方式"
而不是"实现结果"的判据**。

没装 `strace` 的机器上走 `skip` 而不是 `FAIL`，
和第 2 组交叉工具链缺席时的处理一致。

**第三段，两次注错见红。**

```text
    [6r]   O_APPEND -> O_TRUNC            第二次跑完从 26 行掉回 13 行
    [6r2]  不执行 dup2                     日志仍去终端，文件 0 行
```

第二处的改法是特意挑的。直接删掉整个 `if` 块会改变 `fd` 的使用路径，
`-Wall -Wextra` 下未必编得干净；把条件写成恒假，编译器只是把那一支优化掉，
其余代码原样。**注错本身必须编得过**，否则量到的是"编译失败"而不是"判据变红"。

两次注错之间从 `$SRC` 复制一份 `common.c` 还原。一次只坏一个地方，
否则红了也说不清是哪一处造成的。

## 四、遇到的问题

### 4.1 数 write 次数数出了 0

**第一现场。** 写第二段那条判据时，第一版正则是这样的：

```bash
    grep -c '^write(' t_tty.txt
```

跑出来是 **0**。而同一个 strace 输出文件，`wc -l` 是 1001 行。

**解读。** 0 和 1001 同时成立只有两种可能：要么那 1001 行里一行 `write` 都没有
（那 strace 的 `-e trace=write` 就是失效的），要么行首不是 `write`。
`head -5` 一看就清楚了：

```text
    31595 write(1, "line 0\n", 7)           = 7
```

行首是 pid。**`strace -f` 在跟踪到多个进程时会给每行加上 pid 前缀**，
只跟踪一个进程时不加。这个实验是用 `script` 造 pty 跑的，
`script` 自己 fork 了一层，于是前缀出现了。

**定位。** 中间判断错过一次：第一反应是"终端下 `printf` 被 C 库
直接优化掉了、一次系统调用都不发"，还准备把这个"发现"写进笔记。
是 `wc -l` 那个 1001 和"1000 行输出"对得太整齐才回头去看原始行的。

**根因与修法。** 正则改成 `(^|[0-9]+ +)write\(`，同时容纳有前缀和无前缀两种。
`check.sh` 里那条判据用的是同一个写法。

**原判据为什么没覆盖到它。** 因为当时那还不是判据，是一次探索性测量。
探索阶段的数字没有"注错见红"这一步兜底 —— 一个错误的测量方法，
和一个正确的测量方法测出"确实是 0"，长得一模一样。
**这条的教训是：一个数字如果和别的数字对不上账（0 次 write 却有 1001 行输出），
先怀疑测量方法，别急着解释现象。**

### 4.2 环境变量给错了进程

**第一现场。** 把上面那条判据写进 `check.sh` 之后，日志文件是空的，判据红。

**解读。** 手工跑同样的程序是好的，只有套上 `strace` 之后才空。
说明问题出在 `strace` 这一层，不在程序里。

**根因与修法。** 原来写的是：

```bash
    LOG_FILE=$LOGF strace -f -e trace=write -o out ./build/x86/product_tool
```

shell 的环境变量前缀只对**紧跟着的那个命令**生效。
这里 `LOG_FILE` 给的是 `strace`，被跟踪的程序继承不到它 ——
`strace` 不会把自己的环境变量传给子进程里那个变量名。
程序看到 `getenv("LOG_FILE")` 是 `NULL`，于是走了"不重定向"那一支，
日志全打到终端，文件当然是空的。

修法是加一层 `env`：

```bash
    strace -f -e trace=write -o out env LOG_FILE=$LOGF ./build/x86/product_tool
```

**原判据为什么没覆盖到它。** 这一条其实是被判据抓住的 —— 判据红了，
所以它没有变成一个潜伏的缺陷。值得记下来的是它**长得像程序的 bug**：
现象是"日志文件空的"，和 `dup2` 失效的现象一模一样。
排除方法是"手工跑和套工具跑对比"，先确定问题在被测对象还是在测量工具。

## 五、结果

本机（Ubuntu 26.04 on WSL2，gcc 15.2.0）实测：

| | 改动前 | 改动后 |
|---|---|---|
| `check.sh` | PASS=18 FAIL=0 SKIP=0 | **PASS=26 FAIL=0 SKIP=0** |
| `include/common.h` | 61 行 | 72 行 |
| `common.c` | 15 行 | 62 行（当前注释展开后的行数） |
| `main.c` | 90 行 | 107 行 |
| `check.sh` | 106 行 | 148 行 |
| 六层的 `*_manager.c` / `.h` | — | **一个字都没改** |

功能实测：

```text
    ./build/x86/product_tool                        终端 13 行
    LOG_FILE=/tmp/run.log ./build/x86/product_tool  终端 0 行, 文件 13 行
    再跑一次                                        文件 26 行
    LOG_FILE=/no/such/dir/x.log ...                 退出码 1
    strace 数 write(2,...)                          13 次
```

交叉编译一并验过：`make CROSS=arm-linux-gnueabihf-` 出的 ARM 产物
在 `check.sh` 第 2 组里 `readelf -h` 的 Machine 字段是 `ARM`。

测量方法与已知误差来源：行数用 `wc -l`；系统调用次数用
`strace -f -e trace=write` 加 `grep -cE '(^|[0-9]+ +)write\(2,'`，
计数只统计对 fd 2 的写，动态加载器读 ELF 头那次 `read` 不在统计范围内。
**这一章没有性能数字** —— 每条日志一次系统调用的开销在 13 条这个量级上
测不出来，与其给一个噪声里的数不如不给。

## 六、还欠什么

三条，都记在 `Todo/` 里或本节：

**日志文件会一直长，没有轮转。** 板子上 `/tmp` 是 tmpfs，
写爆了就是内存被吃光。现在一次运行只写 13 行，问题不存在；
business 层开始按测试项写日志时必须解决。

**没有上板验证。** 上面所有数字都是 x86 产物在 WSL 上跑出来的。
ARM 产物只验到"能编出来、Machine 字段对"。板上要验的是同一组判据，
路径换成板上的 `/tmp/run.log`。

**`log_redirect` 没有配对的还原函数。** 现在没有“让日志重新显示到终端”的需求，
所以没写。真需要恢复，必须在改变去向之前先保存原来的终端输出入口。
这一条不进 `Todo/`，因为它不是欠账，是**有意不提前写**。
