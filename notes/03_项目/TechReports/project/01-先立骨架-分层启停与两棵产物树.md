# 01 先立骨架：分层、启停顺序与两棵产物树

## 一、动机

这个仓要在 100ASK_IMX6ULL Pro 开发板上做出一个电子产品量产工具：
板子接一块屏，屏上画出若干个按钮，点一个按钮就跑一项测试或者烧一次固件，
测试结果回显在屏上。它要读 `/dev/fb0` 出图，读 `/dev/input/eventX` 收触摸，
要能画中文，要有页面和控件，最后要有一层业务逻辑把这些串起来。

代码不是一次写完的，是跟着课程一章一章长出来的：学完 framebuffer 才有显示层，
学完输入系统才有输入层，学完 freetype 才有字体层。也就是说，
**这棵树在长成之前，要以半成品状态存在十几章的时间。**

半成品状态下有一件事会出问题：加一层的时候要改多少地方。
如果每加一层都要动构建脚本、动主程序、动别的层的代码，那么十几章下来，
每一章的精力都会有一部分花在维护上，而不是花在那一章的知识点上。
更糟的是，早期随手写下的耦合会在后期变成拆不动的东西——
显示层直接被业务层 `open("/dev/fb0")` 之后，就再也换不成别的显示后端了。

所以第一件事不是写显示层，是把"以后每加一层要动哪些地方"这个数字压到最小。
这一章做的就是这件事：先立一个六层都在、但每层都是空壳的骨架，
把加一层的代价固定下来，再往里填。

代价的目标值是三处：新建一个 `.c`、在主程序的层表里加一行、往对应的 `Makefile`
变量里加一个目录名。这一章做完之后实测是两处，第三处被消掉了，见第三节。

这一章不产生任何功能。它的产出是一套约束和一套判据。

## 二、为什么是这几步

这个工作点拆成四步，因为"加一层的代价"由四件互相独立的事决定。

**第一步，定分层与调用方向。** 决定一共有哪几层、谁能调谁。
这一步不定，后面三步都无从谈起：不知道有几层，就不知道构建系统要收几个目录，
也不知道主程序要按什么顺序拉起它们。

**第二步，定启停顺序与失败回滚。** 有了层次就有了依赖，有依赖就有先后。
这一步单独成立，是因为它有一个不显然的部分：初始化到一半失败时该退出哪几层。
这部分写错不会立刻出现象，会在某一层第一次初始化失败的那天才炸。

**第三步，定构建系统。** 前两步是源码组织，这一步是从源码到产物。
它单独成立的理由是它要同时满足两个互相拉扯的要求：
本机 x86 编出来在 WSL 里调逻辑，交叉编出来拿去上板，两份产物要能并存。

**第四步，把前三步变成判据。** 前三步都是"约定"，约定不会自己成立。
没有判据的约定会在三章之后被自己破坏掉，而且破坏的时候没有任何提示。

少一步都不成立：不做第一步会得到一个平铺的目录；不做第二步会在退出路径上留
一个只在失败时触发的洞；不做第三步会在每次上板前手工改编译命令；
不做第四步，前三步写在文档里的东西和代码里实际的东西会各走各的。

## 三、每一步做了什么

### 3.1 分层与调用方向

六层，自底向上：

```
    +-------------------------------------------------+
    |  business    业务逻辑, 决定点了按钮之后干什么   |  高层
    +-------------------------------------------------+
    |  page        页面调度, 一个页面是一屏内容       |
    +-------------------------------------------------+
    |  ui          控件, 目前规划里只有按钮           |
    +-------------------------------------------------+
    |  font        取字模: ASCII 点阵 / HZK16 / freetype |
    +-------------------------------------------------+
    |  input       事件源: /dev/input/eventX 等        |
    +-------------------------------------------------+
    |  display     出图: /dev/fb0 等                   |  底层
    +-------------------------------------------------+

    调用方向只能向下。
```

这个分法直接取自课程配套项目 `06_实战项目/01_电子产品量产工具`，
它的 32 个演进步骤就是按 display / input / font / ui / page / business 这个顺序推的，
目录名也是这六个。照搬它是为了让本仓的每一层都能和那边的某一步对上，
学到哪一步就能拿那边的代码做对照。差异之处记在
[`../../Todo/项目路线图-对齐电子产品量产工具.md`](../../Todo/项目路线图-对齐电子产品量产工具.md)。

调用方向靠两条落地：

一是每层只暴露一个头文件，头文件里只有函数声明，没有结构体定义。
本层的内部状态别的层看不见，才谈得上以后整层换掉。
`display/disp_manager.h` 现在只有两行声明，就是这个约定的形状。

二是 `main.c` 站在这栋楼外面。它不 `open` 任何设备节点，不认识 `/dev` 下的任何路径，
只认每层的 `init` / `exit` 两个函数指针。这一条写进了 `main.c` 的文件头注释。

### 3.2 启停顺序与失败回滚

初始化自底向上，退出自顶向下：

```
    init 正序                         exit 反序

    1 --> display   init OK           display   exit OK <-- 6
    2 --> input     init OK           input     exit OK <-- 5
    3 --> font      init OK           font      exit OK <-- 4
    4 --> ui        init OK           ui        exit OK <-- 3
    5 --> page      init OK           page      exit OK <-- 2
    6 --> business  init OK           business  exit OK <-- 1
```

反序的理由是资源的生命周期必须包含使用者的生命周期：
`business` 还在用 `page` 的数据时，`page` 不能先关。这是栈式管理，
和 C++ 的构造析构顺序、Linux 内核模块的 `module_init` / `module_exit` 是同一件事。

不显然的是失败路径。初始化到第三层失败时，已经成功的是前两层，
第三层自己没成功，不能对它调 `exit`：

```
    display OK --> input OK --> font FAIL
                                  |
                                  v
                        只回滚前两层, 顺序 input -> display
                        font 没 init 成功, 不能 exit
```

实现上把"退出前 n 层"抽成一个函数，正常退出传层数，失败回滚传已成功的层数，
两条路径共用一份代码，不会出现只改了一边的情况。

顺序本身写成一张表，加一层就是加一行。表里同时存着层名，
日志和判据都从这个层名来，不另写一份字符串。

### 3.3 构建：一棵源码树，两棵产物树

```
    源码树                          build/x86/                 build/arm/
    ------------------------        --------------------       -------------------
    main.c                 --->     main.o   main.d            main.o   main.d
    common.c               --->     common.o common.d          common.o common.d
    display/disp_manager.c --->     display/disp_manager.o     display/...
    ...                                  |                          |
                                         v                          v
                                  product_tool (x86-64)      product_tool (ARM)

    make                              -> ARCH=x86
    make CROSS=arm-linux-gnueabihf-   -> ARCH=arm
```

三个决定：

**产物按架构分目录，不放在源码旁边。** 两棵产物树互不覆盖，
x86 版在 WSL 里调逻辑、ARM 版拿去上板，中间不用 `make clean`。
副作用是源码树永远干净，`.gitignore` 里一条 `build/` 就够。

**架构名从工具链前缀算出来，不手写。** `arm-linux-gnueabihf-` 按 `-` 切开取第一段
得到 `arm`，前缀为空则是 `x86`。手写会出现前缀和目录名对不上的构型，
而那种构型编出来的东西看不出错。

**头文件依赖交给编译器生成。** 编译时加 `-MMD -MP`，
编译器顺带吐出一份"这个 `.o` 依赖哪些 `.h`"的规则文件，`make` 再把它们读回来。
不做这一步的后果不是慢，是错：改了一个头文件里的结构体定义，
只有一部分 `.c` 重编，两边对同一块内存的理解不一致，编译零警告，运行行为诡异。

源文件用 `$(wildcard)` 按目录收集。代价是删掉一个 `.c` 而忘了删它的引用时，
报错发生在链接期而不是编译期；收益是加一层时不必回来改文件清单。
第二步说的"加一层的代价三处"，被这一条消掉了一处，剩两处：
新建 `.c`，以及在 `main.c` 的层表里加一行。

这里有一个和课程明确分歧的地方。课程的第 4_3-6、4_3-7 两节给了一份"通用 Makefile"，
形状是仿 Linux 内核的递归构建：每个目录一份 `Makefile` 声明 `obj-y`，
顶层 `Makefile.build` 递归进各子目录，每个目录先把自己的 `.o` 用 `ld -r` 并成一个
`built-in.o`，再层层并上去，最后链接。本仓的 `project/` 没有采用它，理由是
这份骨架只有六个平铺的子目录，递归构建带来的能力（任意深的目录树、
按目录设编译选项、按单个文件设编译选项）当前一个都用不上，
而它的代价是构建过程分散在七个文件里，出问题时要跨文件追。

这不等于那套东西不用学。它的价值在第 2 阶段：Linux 内核和 U-Boot 的构建就是这套，
读内核 Makefile 时躲不开。所以它被放进了 `notes/01` 的动手部分，
作为一个从零复现的实验，而不是作为 `project/` 的构建系统。

### 3.4 把前三步变成判据

判据落在 `project/check.sh`，`bash check.sh` 跑一次给出 PASS / FAIL / SKIP 计数。

两条原则：

**判据做成计数型或序列型，不做"某条输出里有某个词"型。**
"输出里有 display" 这种判据，在六层只剩一层能跑的时候照样绿。
现在数的是 `init OK` 出现几行、这六行按什么顺序出现，少一层立刻从 6 变 5。

**每条正判据后面跟一次注错见红。** 故意把代码或 Makefile 改坏，
判据必须变红。注错不红的判据等于没有判据——它当时是绿的，
但你不知道它是因为代码对而绿，还是因为它根本量不到东西而绿。

破坏性操作全部在临时副本里做，`mktemp -d` 出一个目录，把整个工程复制进去，
`trap` 挂在 `EXIT` 上保证退出时清掉。工作区一个字节不动。

四组注错分别打在四个位置：删掉层表里的一行、把 `wildcard` 换成写死的文件清单、
去掉 `-MMD -MP`、以及第二组里的 `make clean` 与 `distclean` 的区别。
每一处对应上面三步里的一条约定。

## 四、遇到的问题

骨架是一次写成的，没有留下调试记录，所以本节记的不是事故，
是两个"换一种写法会怎样"的当场实测。两段输出都是在本机跑出来的，
命令附在各自段落里，可以复现。

### 4.1 判据的字段为什么锚行尾而不是行首

日志宏会在每行前面加级别标签和文件行号，所以层名不在行首：

```
    [I] display/disp_manager.c:14 display init OK
     ^                             ^
     $1                            $(NF-2)
```

同一份输出，两种取法的实测结果：

```
    $ echo "$out" | grep 'init OK' | awk '{print $1}'       | tr '\n' ' '
    [I] [I] [I] [I] [I] [I]

    $ echo "$out" | grep 'init OK' | awk '{print $(NF-2)}'  | tr '\n' ' '
    display input font ui page business
```

取 `$1` 得到的是六个相同的值。这样的判据既区分不出层，也区分不出顺序，
它的输出与代码是否正确无关——它是一条恒定输出的判据。

`awk` 里 `NF` 是本行的字段总数，`$(NF-2)` 是倒数第三个字段。
行尾三个字段固定是 `<层名> init OK`，所以锚行尾。
额外的好处是日志前缀以后再变（加时间戳、加线程号），这条判据不用跟着改。

### 4.2 "词存在型"判据在少了一层的时候仍然是绿的

把 `main.c` 层表里 `business` 那一行删掉，六层变五层，然后用三种判据量同一份输出：

```
    --- 删掉 business 层之后的输出行数: 11
    --- 词存在型  输出里有 "init OK"   : PASS
    --- 词存在型  输出里有 "display"   : PASS
    --- 计数型    init OK 恰好 6 行    : FAIL
```

前两条在功能已经缺了六分之一的情况下照样绿。这就是 `check.sh` 开头那条原则
"判据尽量做成计数型或序列型"的来历：词存在型判据的通过条件太宽，
它在代码正确时是绿的，在代码错成这样时也是绿的，所以它不携带信息。

这一段同时说明了注错见红这个动作本身在检验什么：
它检验的不是代码，是判据。判据注错之后仍然是绿的，就说明它是上面那种。

## 五、结果

本机 WSL2 Ubuntu 26.04、gcc 15.2.0、arm-linux-gnueabihf-gcc 15.2.0，
`bash project/check.sh` 实测：

```
    PASS=18  FAIL=0  SKIP=0
```

十八条的构成：

| 组 | 条数 | 量的是什么 |
|---|---:|---|
| [1] 构建 + 启停顺序 | 5 | 退出码、init 行数、exit 行数、init 顺序、exit 反序 |
| [1r] 注错：删掉层表里 business | 2 | init 行数由 6 变 5（红）、其余五层照常启停 |
| [2] 交叉编译 | 5 | ARM 产物 Machine、x86 产物 Machine、两份并存、clean 只清一边、distclean 清干净 |
| [3] 新增 .c 不改 Makefile | 1 | 新文件的 .o 出现 |
| [3r] 注错：wildcard 换成写死清单 | 1 | 那个 .o 消失（红） |
| [4] 头文件自动依赖 | 1 | touch include/common.h 后重编 8 个文件 |
| [4r] 注错：去掉 -MMD -MP | 1 | 重编数变成 0（红） |
| [5] 日志整体关闭 | 2 | LOG_LEVEL=0 时输出 0 行、退出码仍为 0 |

其中"重编 8 个文件"这个数不是写死的，是 `check.sh` 自己数出来的源文件个数，
所以以后加层加文件时这条判据不用跟着改。

代码规模：8 个 `.c`、7 个 `.h`、`Makefile` 70 行、`check.sh` 106 行。
两份产物都能编出来，`readelf -h` 分别显示 `ARM` 和 `Advanced Micro Devices X86-64`。

**没有上板。** ARM 产物只验到"是 ARM 格式且能编出来"，
没有拷到板子上跑过，所以"六层能在板子上按顺序起来"这件事目前没有证据。
板子已到货，这条补在下一章。
