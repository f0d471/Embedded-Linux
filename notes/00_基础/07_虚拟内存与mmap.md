# 07 虚拟内存与 mmap

## 1 一句话

**`mmap` 是在页表里加几行，不是把文件读进内存。** 调用返回的时候一个字节都还没读，
真正的读发生在你第一次访问那块地址、触发缺页异常的时候。

## 2 和你已知的东西对照

你做过带 TLB 的核，页表这套机制不用从头讲。这里只对三处差异：

| | 你在硬件那边看到的 | 用户态程序看到的 |
|---|---|---|
| 页表 | 一张树，TLB 里缓存几十项 | 看不见，只看见"这段地址能访问" |
| 缺页 | 一次异常，软件填 TLB 或硬件走页表 | 一次停顿，几微秒，然后代码继续跑 |
| 谁建的表项 | 内核的 `handle_mm_fault` | `mmap` / `brk` / `execve` 各建一批 |

关键差别是**建表和填表被分开了**。`mmap` 只做前半段：
在内核的 `vm_area_struct` 链表里记一笔"这段虚拟地址对应那个文件的那一段"，
页表项一个都不建。等你真的去读那个地址，MMU 找不到页表项，发缺页异常，
内核这才去查那笔记录、把文件那一页读进页缓存、把页表项填上、
让那条访存指令重跑一遍。

**这套"先记账、用到才兑现"就是懒分配。** 好处是 `mmap` 一个 8 GiB 的文件也是瞬间返回，
只有你摸到的那几页才真的花钱。

## 3 一个进程的地址空间长什么样

`/proc/<pid>/maps` 把这张账本直接打出来。**本机实测**（一个映射了 8 MiB 文件的程序）：

```text
    603e14664000-603e14665000 r--p  .../mapshow        程序自己: 只读数据
    603e14665000-603e14666000 r-xp  .../mapshow        程序自己: 代码
    603e14668000-603e14669000 rw-p  .../mapshow        程序自己: 已初始化的全局变量
    603e40387000-603e403a9000 rw-p  [heap]             malloc 的地盘
    760ac1200000-760ac1a00000 r--s  .../big.bin        <-- 我们 mmap 出来的那 8 MiB
    760ac1c00000-760ac1c28000 r--p  .../libc.so.6      C 库
    760ac1c28000-760ac1dc0000 r-xp  .../libc.so.6      C 库的代码
```

三件事从这张表里能直接读出来：

**第一，程序本身就是 mmap 进来的。** 上面 `mapshow` 那几行不是谁调 `mmap` 建的，
是 `execve` 建的。加载一个可执行文件从来就不是"把它读进内存"，
而是"给它的每个 segment 建一段映射"。这一点在
[01 ELF 与程序加载](01_ELF与程序加载.md) 里是从 ELF 那头讲的，这里是从内存这头看同一件事。

**第二，权限位是按段给的。** `r-xp` 是代码（能执行不能写），`rw-p` 是数据（能写不能执行）。
写代码段会当场吃 SIGSEGV，这条保护是页表项里那几位实现的。

**第三，最后一位 `p` / `s` 是 `MAP_PRIVATE` 和 `MAP_SHARED` 的区别。**
我们那行是 `r--s`，因为传了 `MAP_SHARED`。

## 4 MAP_SHARED 与 MAP_PRIVATE

```text
    MAP_SHARED                          MAP_PRIVATE
    你写这块内存                         你写这块内存
        |                                   |
        v                                   v
    直接改页缓存里那一页                 内核先复制一份给你 (写时复制)
        |                                   |
        v                                   v
    别的进程 mmap 同一个文件也看得见      别人看不见, 文件也不变
    最终由内核写回磁盘                    这份副本随进程一起消失
```

- 拿 `mmap` 当"共享内存"用，选 `MAP_SHARED`。
- 加载动态库的数据段用 `MAP_PRIVATE`：库里的全局变量每个进程一份，改了不能互相影响，
  但没改过的页大家共用同一份物理内存。上面表里 libc 那几行是 `p`，就是这个原因。
- 操作 framebuffer 必须 `MAP_SHARED`：你要的就是"写内存等于写显存"，
  写到一份私有副本里屏幕不会有任何变化。第 03 章会用到这一条。

## 5 页缓存：为什么"少一次拷贝"

`read` 走的路：

```text
    磁盘 --> 页缓存(内核内存) --> 你的 buf(用户内存)
                              ^
                              +-- 这一次拷贝是 read 自己干的
```

`mmap` 走的路：

```text
    磁盘 --> 页缓存(内核内存)
                 ^
                 +-- 页表直接指向它, 没有第二次拷贝
```

省掉的是内核内存到用户内存那一次 `memcpy`。**但省掉它不一定省时间** —— 
02 章第 5.3 节把这件事量了：8 MiB 的文件，`read`/`write` 版发了 4096 次系统调用，
`mmap` 版只发 1 次，**耗时在本机三轮测试里各赢一次，看不出稳定差别。**
系统调用次数和耗时不是一回事，别只报次数。

## 6 三个必须知道的边界

**空文件不能映射。** `mmap` 的 `length` 参数为 0 时直接返回 `MAP_FAILED`，
`errno` 是 `EINVAL`。**本机实测**：`mmap: Invalid argument`，程序退出码 1。
写拷贝工具时这是必须单独处理的一支。

**映射是按页取整的，文件不是。** 映射一个 3 字节的文件，内核给你一整页 4096 字节。
第 3 字节到第 4095 字节读出来是 0，写进去不会进文件。

**摸到文件末尾所在页之外，是 SIGBUS 不是 SIGSEGV。** **本机实测**：

```text
    文件 3 字节, mmap 了 8192 字节(两页)
      p[0]     = 'a'      正常
      p[100]   = 0        第一页里、文件外: 读到 0
      p[5000]              第二页, 完全在文件之外 --> Bus error, 退出码 135
```

135 = 128 + 7，7 号信号是 `SIGBUS`。**记住这个信号名**：
调试时看到 SIGBUS 而不是 SIGSEGV，八成是映射长度算过头了，
或者映射之后文件被别人截短了。

## 7 稀疏文件：文件大小和占盘大小是两个数

和 `mmap` 同一条原理的另一件事：文件系统也是按块记账的，
从没写过的块干脆不分配。

用 `lseek` 跳过 1 MiB 再写 4 个字节，**本机实测**（ext4）：

```text
    ls -l   逻辑大小 = 1048580 字节
    du -h   实际占盘 = 8.0K
    stat    16 个 512 字节块
    空洞里读出来 = 全 0
```

逻辑一兆，实占八千字节。中间那段叫**空洞**，读它返回 0，但不占盘。

**这条实验必须在 ext4 上做。** 同一个程序在 `/mnt/e`（WSL 挂的 Windows NTFS）上跑，
**本机实测**是 `du` 报 1.1M、2056 个块 —— 空洞被老老实实写成了真的 0。
在那里做这个实验会得出完全相反的结论。见 02 章第 9 节。

## 8 亲手验证

```bash
getconf PAGESIZE                 # 本机 4096
cat /proc/<pid>/maps             # 看这个进程的所有映射, 最后一列是文件名
cat /proc/<pid>/smaps_rollup     # 看这些映射里真正占了多少物理内存
ls -l  file; du -h file          # 逻辑大小 vs 实际占盘, 稀疏文件时不相等
stat file                        # %s 是字节数, %b 是 512 字节块数
```

- `/proc/<pid>/maps` 每行是 `起止地址 权限 文件内偏移 设备 inode 路径`。
- 权限第 4 位 `p`/`s` 区分 `MAP_PRIVATE` 和 `MAP_SHARED`。
- `du` 默认按占盘算，`du -b` 按逻辑大小算，两个数不等就说明文件是稀疏的。
