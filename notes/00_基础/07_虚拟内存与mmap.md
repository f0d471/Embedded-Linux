## 没看懂也先记住

页表怎么走可以后面再理解。现在先记“映射成功、实际占内存、修改文件、数据落盘”
是不同的事，遇到问题分别检查。

### 先带走这 5 条

1. **普通 Linux 用户程序里的指针是虚拟地址，不是直接拿来操作的物理地址。** 内核维护映射，CPU 的 MMU（地址翻译硬件）负责转换；不同进程里一样的地址数字不一定指向同一块内存。
2. **`mmap` 建立映射，不代表整个文件已读进物理内存。** 普通文件映射通常按访问需要补齐；缺页是访问时需要内核处理映射的一种异常，很多缺页处理完就继续执行，不等于程序崩溃，也不一定要读磁盘。
3. **`PROT_READ` / `PROT_WRITE` 管能不能读写，`MAP_SHARED` / `MAP_PRIVATE` 管修改如何共享。** 对普通文件，可写 `SHARED` 映射的修改会反映到文件；可写 `PRIVATE` 映射改的是私有副本，不写回原文件。共享也不自动解决并发访问的同步。
4. **`mmap` 失败要和 `MAP_FAILED` 比，长度必须大于 0，文件偏移要按页大小对齐。** 映射长度大于文件长度不会自动扩展文件；要写新增区间，先把文件扩到需要的大小并检查结果。
5. **少一次拷贝、少一些系统调用，不等于一定更快。** `MAP_POPULATE` 尝试提前准备映射页，可能减少后续缺页，但不能保证总体更快或之后零缺页；性能要比较实际访问在内的总耗时。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| 映射很大，实际驻留内存却很小 | 映射大小与已经用到的物理内存不是一回事，先看是否真正访问了那些页 |
| 写映射不报错，文件内容却没变 | 先查是否用了 `MAP_PRIVATE`；对它调用 `msync` 也不会把私有修改变成文件更新 |
| 普通文件映射访问时收到 `SIGBUS` | 优先核对访问位置与当前文件长度，尤其是否被截短；超出文件尾所在页的访问是本篇的典型原因 |
| 收到 `SIGSEGV` | 查地址是否有效、映射是否还在、读写权限是否允许；它不只表示“地址没映射” |
| 共享修改已可见，想确认何时同步到文件 | 区分“看得见”和“已同步”，按需使用 `msync(..., MS_SYNC)` 并检查返回值 |
| `ls -l` 很大、`du` 却很小 | 可能是稀疏文件：逻辑大小与实际占盘不同；换文件系统后要重新验证 |

这里的文件修改规则针对普通文件；设备映射还受驱动实现约束。信号也不只有表中一种成因。
API 边界可核对 Linux 手册 [mmap(2)](https://man7.org/linux/man-pages/man2/mmap.2.html)。

### 反复看这 3 组问答

- **问：`mmap` 返回成功，访问任意映射位置都安全吗？答：不能这样推，还要满足权限、文件范围等条件，文件被截短也可能使后续访问失败。**
- **问：想通过映射修改普通文件，应记住什么？答：文件打开方式允许写、映射允许写、使用 `MAP_SHARED`，并检查边界和同步需要。**
- **问：关闭原 fd 会取消已有映射吗？答：不会；解除映射用 `munmap`，之后不能再用原映射指针访问。**

想补原理时：按需映射看第一至三节，内存布局和拷贝看第四、五节，共享看第六节，边界看第七节，稀疏文件看第八节。

## 一、"映射"这个词，指的是什么

01 篇里加载器干的活是"把每条 LOAD segment 映射进内存"。
当时含糊过去了。现在正面讲。

先看一个数字对不上的现象。你的程序访问的地址，比如
`&g_init = 0x5ea4b54dd010` —— 这是个 94 TB 量级的地址。
但这台机器可能只有 8 GB 内存。

**所以这个地址不可能是真的内存条上的地址。**

> **虚拟地址**：程序里所有的地址（指针、`&x` 取出来的、跳转目标）
> 都是虚拟地址，是"假的"。
> **物理地址**：内存条上真实的位置。
> 两者之间隔着一层由内核维护、由 CPU 里的 **MMU** 硬件实时翻译的对应关系。

```
    你的程序                        MMU（CPU 里的硬件）                内存条
    mov  rax, [0x5ea4b54dd010]  ->  查一张表，把这个地址翻译成 ->  0x3f2a1010
                                     |
                                     +-- 表里没这一项怎么办？ 见第三节
```

**为什么要多这一层？** 三个理由，每一个单独都足以证明它必要：

    1. 隔离    每个进程一张自己的对应关系表。
               进程 A 的 0x1000 和进程 B 的 0x1000 翻译到不同的物理地址。
               A 写坏自己的内存，碰不到 B —— 它连 B 的物理地址都表达不出来

    2. 不必连续   程序看到的是一整段连续地址，
                  背后可以是内存条上东一块西一块的碎片

    3. 可以先记账，不兑现   这一条是本篇的主题，第三节讲

有了这层翻译，`mmap` 才有意义：

> **`mmap`**：在这张对应关系表里加一段记录，说
> "这段虚拟地址，对应那个文件的那一段内容"。
> **它不读文件。** 调用返回的时候，一个字节都还没从磁盘上读出来。

这句话听着很反直觉 —— 那数据什么时候读？下一节用实验回答。

## 二、实验 1：mmap 到底读没读文件

### 2.1 先自己想

要证明"mmap 没读文件"，得找到一个能量的东西。有三个候选：

    mmap 调用本身花了多长时间     真读 64 MiB 要几十毫秒，不读就是微秒级
    进程占用的物理内存涨了多少     真读进来就得占 64 MiB 物理内存
    缺页次数                       见下

第三个需要先解释一个词：

> **缺页（page fault）**：CPU 访问一个虚拟地址，MMU 去查表，
> **发现这一项还没建**，于是触发一次异常，把控制权交给内核。
> 内核这才去干真正的活（分配物理内存 / 从磁盘读数据 / 把表项填上），
> 然后让那条访存指令**重新执行一遍**。
>
> 分两种：`minor fault`（次缺页，不需要读磁盘）
> 和 `major fault`（主缺页，要读磁盘）。

**缺页次数就是"内核被迫兑现承诺"的次数。** 这个数内核记着，
`getrusage()` 能拿到（`ru_minflt` 字段）。

物理内存占用也能拿：读 `/proc/self/status` 里的 `VmRSS`。

**思路成型了：在三个时刻各量一次这三个数。**

    [1] mmap 之前
    [2] mmap 之后，但一个字节都还没碰
    [3] 把每一页都摸一下之后

如果 mmap 真的读了文件，[2] 的物理内存就该涨 64 MiB。
如果没读，那涨在 [3]。

### 2.2 动手

`lazymap.c`（完整代码在实验目录，这里是骨架）：

```c
#define MB   64
#define SIZE ((size_t)MB * 1024 * 1024)

/* 次缺页次数 */
static long minflt(void)
{
	struct rusage ru;
	getrusage(RUSAGE_SELF, &ru);
	return ru.ru_minflt;
}

/* 本进程真正占用的物理内存，KB */
static long rss_kb(void)
{
	FILE *f = fopen("/proc/self/status", "r");
	char line[128];
	long kb = -1;
	while (fgets(line, sizeof line, f))
		if (!strncmp(line, "VmRSS:", 6)) { sscanf(line + 6, "%ld", &kb); break; }
	fclose(f);
	return kb;
}

int main(int argc, char **argv)
{
	...
	fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
	ftruncate(fd, SIZE);                 /* 造一个 64 MiB 的文件 */

	f0 = minflt(); r0 = rss_kb();        /* [1] */

	t0 = now_ms();
	p = mmap(NULL, SIZE, PROT_READ, MAP_SHARED, fd, 0);
	t1 = now_ms();
	f1 = minflt(); r1 = rss_kb();        /* [2] */

	t0 = now_ms();
	for (i = 0; i < npages; i++)
		sink += p[(size_t)i * pagesz];   /* 每页只摸一个字节 */
	t1 = now_ms();
	f2 = minflt(); r2 = rss_kb();        /* [3] */
	...
}
```

**逐个参数解释 `mmap` 那一行**，六个参数一个都不能瞎填：

    mmap(NULL,                地址由内核挑。给 NULL 是常规做法
         SIZE,                映射多长
         PROT_READ,           这段内存的权限：只读。想写就 |PROT_WRITE
         MAP_SHARED,          改动要写回文件、且别的进程看得见（第六节详解）
         fd,                  映射哪个文件
         0)                   从文件的第几个字节开始。必须是页大小的整数倍

    ftruncate(fd, SIZE)       把文件撑到 64 MiB。
                              不撑的话文件是 0 字节，映射后一碰就 SIGBUS（第七节）

编译运行（注意数据文件放 ext4）：

    cd labs/00_basics/03_vm_and_mmap
    mkdir -p ~/vmlab
    gcc lazymap.c -o lazymap
    ./lazymap ~/vmlab/big.bin

### 2.3 本机实测

```
文件 64 MiB，页大小 4096 字节，共 16384 页

[1] mmap 之前     缺页 85       物理内存 1752 KB
[2] mmap 之后     缺页 89       物理内存 1880 KB   （mmap 本身耗时 0.003 ms）
    -> 比上一步多了 4 次缺页，128 KB 物理内存

[3] 每页摸一下后  缺页 601      物理内存 67416 KB   （摸完耗时 22.029 ms）
    -> 比上一步多了 512 次缺页，65536 KB 物理内存
    -> 摸了 16384 页，缺页涨了 512 次
```

### 2.4 逐行读，三个结论加一个意外

**结论 1：mmap 64 MiB 花了 0.003 毫秒。**

三微秒。真从磁盘读 64 MiB 不可能这么快。**它没读。**

**结论 2：mmap 之后物理内存只涨了 128 KB。**

如果文件被读进来了，这里该涨 65536 KB。只涨了 128 KB
（那是程序自己跑 `printf` 之类用掉的，跟 mmap 无关）。
**64 MiB 的文件，映射完占用的物理内存约等于 0。**

**结论 3：摸完之后，物理内存精确涨了 65536 KB = 64 MiB。**

    65536 KB = 64 x 1024 KB = 64 MiB，一个字节不差

**数据是在"摸"的那一刻才进内存的**，而且注意：每页我只读了一个字节
（`p[i * 4096]`），内核给我的是整整一页。**内存的最小交易单位是页，不是字节。**

这三条合起来就是懒分配：

> **懒分配（lazy allocation）**：`mmap` 只在内核的记录里加一笔
> "这段虚拟地址将来对应那个文件"，页表项一个都不建。
> 等你真的访问那个地址，MMU 查不到表项 -> 缺页 -> 内核这才去读那一页、
> 填表项、让指令重跑。**用到才兑现。**

好处很直接：`mmap` 一个 8 GB 的文件也是瞬间返回，只有你真正摸过的页才花钱。
`read` 做不到这一点 —— `read(fd, buf, 8G)` 必须老老实实读完 8 GB。

### 2.5 那个意外：16384 页，为什么只缺页 512 次

**按上面的道理，摸 16384 页应该触发 16384 次缺页。实测只有 512 次。**

    16384 / 512 = 32

差整整 32 倍，而且连跑三轮都是 512，纹丝不动。

**这不是测错了，是内核的一个优化**：一次缺页进内核已经很贵了
（切上下文、查记录、可能读磁盘），既然都进来了，就顺手把**相邻的 32 个页表项**
一起填上。这叫 **fault-around**。

    你摸第 0 页    -> 缺页一次，内核顺手填好第 0..31 页的表项
    你摸第 1..31 页 -> 表项已经在了，MMU 直接翻译，不缺页
    你摸第 32 页   -> 又缺一次

    16384 / 32 = 512    对上了

**这条的价值不在 fault-around 本身，在于：**
书上会告诉你"每访问一个没建表项的页就缺页一次"，
按这句话你会预期 16384。**实测 512。** 差 32 倍。

    数字必须自己跑。跑出来和预期不符时，先假设自己的模型漏了东西，
    去把那个东西找出来 —— 而不是把实测数字改成"应该"的样子。

（想直接看内核的这个参数：`cat /sys/kernel/debug/fault_around_bytes`，
本机 debugfs 没挂载，读不到，所以上面 32 这个数是从实测倒推的。
`32 x 4096 = 131072`，也就是 128 KB。）

### 2.6 判据

    [ ] mmap 64 MiB 的耗时是微秒量级（本机 0.003 ms）
    [ ] mmap 之后物理内存增量 < 1 MB
    [ ] 摸完每一页之后，物理内存增量精确等于 65536 KB
    [ ] 缺页增量远小于页数，且连跑三轮数值稳定
    [ ] 能算出"缺页增量 x 32 == 页数"

    注错见红：只摸前四分之一的页：

        for (i = 0; i < npages / 4; i++)

    本机实测，三个数精确地按 1/4 缩放：

                        摸全部        只摸 1/4
        缺页增量        512           128          （512 / 4）
        物理内存增量    65536 KB      16384 KB     （64 MiB / 4）
        耗时            22.029 ms     4.266 ms

    **三个数同时按比例变，才说明它们量的是同一件事。**
    顺便这也再次验证了 fault-around：4096 页 / 32 = 128 次缺页，对上了。
    （注意程序最后那行仍打印 "摸了 16384 页"，它打的是总页数不是实际摸的次数，
    别被它带偏 —— 这是程序的一个小瑕疵，看前两行的增量即可。）

## 三、实验 2：把"懒"关掉，看差别

### 3.1 先自己想

懒分配是默认行为，但内核给了一个开关能关掉它：`MAP_POPULATE` 标志，
意思是"别懒了，现在就把页表全填好"。

**做一个对照实验，能一次性验证前面所有结论。** 预测一下：

    mmap 耗时           应该从微秒变成毫秒（活提前干了）
    mmap 后物理内存      应该直接涨到 64 MiB
    摸的时候的缺页        应该是 0（表项都建好了）
    摸的耗时             应该大幅下降

### 3.2 动手

只改一个标志：

    sed 's|MAP_SHARED, fd, 0)|MAP_SHARED \| MAP_POPULATE, fd, 0)|' lazymap.c > pop.c
    gcc pop.c -o pop
    ./pop ~/vmlab/big2.bin

### 3.3 本机实测

```
[1] mmap 之前     缺页 87       物理内存 1756 KB
[2] mmap 之后     缺页 1116     物理内存 67420 KB   （mmap 本身耗时 12.012 ms）
    -> 比上一步多了 1029 次缺页，65664 KB 物理内存

[3] 每页摸一下后  缺页 1116     物理内存 67420 KB   （摸完耗时 0.197 ms）
    -> 比上一步多了 0 次缺页，0 KB 物理内存
    -> 摸了 16384 页，缺页涨了 0 次
```

### 3.4 并排看

| | 默认（懒） | MAP_POPULATE（不懒） |
|---|---|---|
| mmap 耗时 | 0.003 ms | 12.012 ms |
| mmap 后物理内存增量 | +128 KB | +65664 KB |
| 摸 16384 页的耗时 | 22.029 ms | 0.197 ms |
| 摸的时候缺页 | 512 次 | 0 次 |
| **总耗时** | **22.03 ms** | **12.21 ms** |

**四行预测全中。** 而且多出来一个没预料到的结论：

**总时间上 `MAP_POPULATE` 反而快了将近一倍**（12.21 vs 22.03 ms）。

因为批量建 16384 个页表项，比分 512 次陷入内核便宜得多。

**所以懒分配省的不是时间，是"你可能根本不会用到的那部分"的开销。**

    确定要全部用到      MAP_POPULATE 更快
    只会用到一小部分     默认的懒更省（省的是没摸过的那些页）
    映射一个超大文件     必须懒，否则物理内存直接爆掉

### 3.5 判据

    [ ] MAP_POPULATE 版的 mmap 耗时比默认版大三个数量级
    [ ] MAP_POPULATE 版 mmap 之后物理内存就已经涨满 64 MiB
    [ ] MAP_POPULATE 版摸页时缺页增量为 0
    [ ] 两版的总耗时相比，POPULATE 版更小

    注错见红：把 MAP_POPULATE 加到一个 8 GiB 的文件上（把 MB 改成 8192）。
    本机内存不够，mmap 会卡很久甚至失败 ——
    而默认的懒版本映射 8 GiB 仍然是微秒返回。
    这条直接说明为什么懒是默认行为。

## 四、实验 3：地址空间长什么样

### 4.1 动手

第一节说"每个进程一张自己的对应关系表"。内核把这张表的摘要开在
`/proc/<pid>/maps` 里。00 篇 5.2 已经读过一次，这里看带文件映射的完整版。

沿用 00 篇的 `maps.c` 即可，或者直接看任意一个正在跑的进程：

    cat /proc/self/maps        # shell 自己的（cat 进程的）

**本机实测**（一个映射了 8 MiB 文件的程序，节选）：

```
603e14664000-603e14665000 r--p  .../mapshow      程序自己：只读数据
603e14665000-603e14666000 r-xp  .../mapshow      程序自己：代码
603e14668000-603e14669000 rw-p  .../mapshow      程序自己：已初始化的全局变量
603e40387000-603e403a9000 rw-p  [heap]           malloc 的地盘
760ac1200000-760ac1a00000 r--s  .../big.bin      <-- mmap 出来的那 8 MiB
760ac1c00000-760ac1c28000 r--p  .../libc.so.6    C 库
760ac1c28000-760ac1dc0000 r-xp  .../libc.so.6    C 库的代码
```

### 4.2 逐行读，三件事

**第一，程序本身就是 mmap 进来的。**

前三行（`mapshow` 那几行）不是谁调 `mmap` 建的，是 `execve` 建的。
**加载一个可执行文件从来就不是"把它读进内存"，
而是给它的每条 LOAD segment 建一段映射** —— 和你在第二节手动 mmap 一个文件
是完全相同的机制。

01 篇是从 ELF 那头讲这件事（program header 里的 FileSiz/MemSiz），
这里是从内存这头看同一件事。**两头对上了。**

顺带解释 01 篇一个没细说的点：程序启动为什么那么快？
因为 `execve` 也是懒的 —— 它只建映射，代码是执行到哪一页才读哪一页。
一个 800 KB 的静态链接程序，真正被读进内存的可能只有几十 KB。

**第二，权限是按段给的。**

`r-xp` 是代码（能执行不能写），`rw-p` 是数据（能写不能执行）。
00 篇 5.5 节那个"往代码段写数据必崩"的实验，就是这几位在起作用。

**第三，最后一位 `p` / `s` 是本篇第六节的主题。**

`big.bin` 那行是 `r--s`，其余全是 `p`。`s` = MAP_SHARED，`p` = MAP_PRIVATE。

## 五、页缓存：mmap 比 read 少一次拷贝

在讲 `p`/`s` 之前，先补一个概念，第六节要用。

> **页缓存（page cache）**：内核在内存里给磁盘文件留的缓存。
> 你 `read` 一个文件，数据先从磁盘进页缓存，再从页缓存拷进你的 buf。
> 第二次读同一个文件就不碰磁盘了，直接从页缓存拷。

两条路的区别：

```
    read 走的路：
        磁盘 --> 页缓存（内核内存） --> 你的 buf（用户内存）
                                   ^
                                   +-- 这一次 memcpy 是 read 自己干的

    mmap 走的路：
        磁盘 --> 页缓存（内核内存）
                     ^
                     +-- 页表直接指向它。没有第二次拷贝，
                         你的指针访问的就是页缓存那块物理内存
```

**mmap 省掉的正是"内核内存到用户内存"那一次 memcpy。**

**但省掉它不一定省时间。** 02 章第 5.3 节量过：8 MiB 的文件，
`read`/`write` 版发了 4096 次系统调用，`mmap` 版只发 1 次，
**耗时在本机三轮测试里各赢一次，看不出稳定差别。**

    系统调用次数少 4096 倍 ≠ 快 4096 倍。
    报性能必须报时间，只报系统调用次数是在暗示一个没测到的结论。

## 六、实验 4：MAP_SHARED 与 MAP_PRIVATE

### 6.1 先自己想

第五节说 mmap 让你的指针直接指向页缓存。那么：

**你往这块内存写东西，是不是就等于改了页缓存、进而改了文件？**

如果总是这样，问题就大了：动态库的数据段也是 mmap 进来的，
一个进程改了自己的全局变量，会波及所有用同一个库的进程，还会写回 .so 文件。

所以必须有两种模式，`mmap` 的第四个参数就是选这个：

    MAP_SHARED    写就是写页缓存。别的进程看得见，最终写回文件
    MAP_PRIVATE   写的时候内核先复制一份给你，你改的是副本。
                  别人看不见，文件也不变

**怎么验证？让一个进程写，另一个进程读，再看文件本身。三方对质。**

### 6.2 动手

`shared_private.c` 核心：

```c
static void try_flag(const char *path, int flag, const char *name)
{
	int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
	char *p, buf[16] = {0};

	write(fd, "AAAAAAAAAA", 10);          /* 文件初始内容：10 个 A */

	p = mmap(NULL, 10, PROT_READ | PROT_WRITE, flag, fd, 0);
	memcpy(p, "BBBBB", 5);                /* 往映射区写 5 个 B */

	fflush(stdout);   /* fork 前必须刷干净，否则缓冲区会被子进程连同复制、再打一遍 */
	if (fork() == 0) {                    /* 另一个进程映射同一个文件 */
		char *q = mmap(NULL, 10, PROT_READ, MAP_SHARED, fd, 0);
		printf("  %-12s 另一个进程映射同一文件看到: %.10s\n", name, q);
		exit(0);
	}
	wait(NULL);

	msync(p, 10, MS_SYNC);                /* 要求把改动同步回文件 */
	munmap(p, 10);

	lseek(fd, 0, SEEK_SET);
	read(fd, buf, 10);                    /* 用普通 read 看文件里到底存了什么 */
	printf("  %-12s 文件里最终存的是          : %.10s\n\n", name, buf);
	close(fd);
}
```

**那句 `fflush(stdout)` 不是装饰。** 第一次跑这个程序时我漏了它，
输出乱成一团、还重复打印了一遍 —— 因为 `printf` 的内容还压在
stdout 缓冲区里没刷出去，`fork` 把缓冲区连同内容一起复制给了子进程，
子进程退出时又刷了一遍。**这是 fork + 标准 IO 的经典坑**，
和 02 章第 4 节讲的缓冲是同一件事。

    gcc shared_private.c -o shared_private
    ./shared_private ~/vmlab

### 6.3 本机实测

```
往映射区写 5 个 B（文件原本是 10 个 A）：

  MAP_SHARED   另一个进程映射同一文件看到: BBBBBAAAAA
  MAP_SHARED   文件里最终存的是          : BBBBBAAAAA

  MAP_PRIVATE  另一个进程映射同一文件看到: AAAAAAAAAA
  MAP_PRIVATE  文件里最终存的是          : AAAAAAAAAA
```

### 6.4 逐条读

**同一段 `memcpy(p, "BBBBB", 5)`，两种标志下结果完全相反：**

    MAP_SHARED    别的进程看到 B，文件里也是 B     -> 真的改到了页缓存
    MAP_PRIVATE   别的进程看到 A，文件里还是 A     -> 改的是一份私有副本

**`MAP_PRIVATE` 那次写并没有报错，`msync` 也返回成功。** 数据只是无声地
留在了那份副本里，进程一退出就没了。**这是最难查的一类 bug**：
没有任何错误提示，只是你写的东西"不见了"。

> **写时复制（copy-on-write, COW）**：`MAP_PRIVATE` 的实现方式。
> 映射刚建立时并不复制，大家共用同一份物理页（只读）。
> 谁第一次往某一页写，MMU 发现这页不可写，触发缺页，
> 内核这才复制那**一页**给他。
> 没写过的页，永远共用同一份物理内存。

这解释了 4.1 节那张 maps 表里的现象：libc 那几行是 `p`。
系统上跑一百个程序，libc 的代码段只有一份物理内存；
数据段虽然是 `p`，但只有被改过的那几页才会各自分裂出副本。

### 6.5 什么时候用哪个

    共享内存（进程间通信）      MAP_SHARED，这是它的主要用法之一
    加载动态库的数据段          MAP_PRIVATE，各进程改各的
    操作 framebuffer            **必须 MAP_SHARED**
                                你要的就是"写内存等于写显存"。
                                写进私有副本里，屏幕不会有任何变化
    只是想快速读一个大文件       MAP_PRIVATE 或 PROT_READ 都行

**framebuffer 那条是 03 章的第一个坑**，写错标志的现象是：
程序不报错、逻辑全对、屏幕一片漆黑。

### 6.6 判据

    [ ] MAP_SHARED：另一个进程看到 BBBBBAAAAA，文件里也是 BBBBBAAAAA
    [ ] MAP_PRIVATE：另一个进程看到 AAAAAAAAAA，文件里也是 AAAAAAAAAA
    [ ] MAP_PRIVATE 那次写没有任何报错

    注错见红：把 MAP_PRIVATE 那一行改成 MAP_SHARED，两组输出应完全相同。
    改回来必须再次不同。**这条是整篇里唯一一处"只改一个常量、
    行为彻底反转"的地方，值得亲手来回切两次。**

## 七、实验 5：映射的边界在哪

### 7.1 先自己想

文件是 3 字节，页是 4096 字节。`mmap` 按页干活，那映射一个 3 字节的文件，
第 3 到第 4095 字节是什么？再往后呢？

**分三段猜：**

    文件里真有的部分（0..2）        肯定正常
    第一页里、文件外（3..4095）     内核给了整页，这部分是什么？
    第二页（4096 以后）             文件完全够不着，会怎样？

### 7.2 动手

`sigbus.c`：

```c
int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
write(fd, "abc", 3);                                  /* 文件只有 3 字节 */
p = mmap(NULL, 8192, PROT_READ, MAP_SHARED, fd, 0);   /* 却映射两页 */

/* 模式 0：安全范围 */
printf("p[0]    = '%c'\n", p[0]);
printf("p[100]  = %d\n",   p[100]);
printf("p[4095] = %d\n",   p[4095]);

/* 模式 1：越界 */
printf("p[5000] = %d\n",   p[5000]);
```

    gcc sigbus.c -o sigbus
    ./sigbus ~/vmlab/tiny.bin 0     # 安全范围
    ./sigbus ~/vmlab/tiny.bin 1     # 越界

### 7.3 本机实测

```
$ ./sigbus ~/vmlab/tiny.bin 0
p[0]    = 'a'   （文件里真有这个字节）
p[100]  = 0     （第一页里、文件外：读到 0，不报错）
p[4095] = 0     （第一页最后一个字节，仍然安全）

$ ./sigbus ~/vmlab/tiny.bin 1
正要读 p[5000]（第二页，完全在文件之外）...
Bus error
退出码=135
```

对照一个普通的空指针解引用：

```
$ ./segv            # *(int*)0 = 1;
Segmentation fault
退出码=139
```

### 7.4 逐条读

**三段猜想全部验证：**

    p[0..2]      文件内容
    p[3..4095]   读到 0，不报错。内核给了整整一页，多出来的部分清了零
    p[5000]      Bus error

**注意退出码，两种崩法是不同的信号：**

    135 = 128 + 7    7 号信号 SIGBUS    映射越界
    139 = 128 + 11  11 号信号 SIGSEGV   访问了根本没映射的地址

> **SIGBUS 与 SIGSEGV 的区别**：
> SIGSEGV 是"这个虚拟地址压根没有映射"（比如空指针）。
> SIGBUS 是"映射是有的，但底下没有对应的东西可以兑现"
> —— 你告诉内核这段地址对应那个文件，但文件根本没那么长。

**这条在实际调试里很值钱：**

    看到 SIGSEGV  -> 八成是野指针、数组越界、用了已经 free 的内存
    看到 SIGBUS   -> 八成是 mmap 长度算过头了，
                     或者映射之后文件被别人截短了

第二种情况尤其阴险：程序跑得好好的，别人 `truncate` 了那个文件，
你下次访问就崩。

**还有一个必须知道的边界**：空文件不能映射。
`mmap` 的 `length` 为 0 时直接返回 `MAP_FAILED`，`errno` 是 `EINVAL`，
本机报错是 `mmap: Invalid argument`。
写文件拷贝工具时这是必须单独处理的一支 —— 见 02 章第 5 节。

### 7.5 判据

    [ ] p[0] 是 'a'，p[100] 和 p[4095] 都是 0 且不崩
    [ ] 读 p[5000] 崩，退出码 135
    [ ] 空指针解引用崩，退出码 139
    [ ] 能说出 135 和 139 分别是几号信号、名字是什么

    注错见红：不改代码，把文件撑到两页那么长（加一行 ftruncate(fd, 8192)）。
    本机实测 p[5000] 读出 0，不崩，退出码 0。
    **同一行 p[5000]，文件短就 SIGBUS、文件够长就正常** ——
    崩不崩取决于底下有没有东西可兑现，这正是 SIGBUS 的定义。

    另外提醒一个不可靠的注错方式：把 mmap 长度从 8192 改成 4096，
    指望 p[5000] 变成 SIGSEGV。**本机实测它没崩，读出 0，退出码 0。**
    因为映射区之外那块地址未必真的空着，可能被别的映射占了。
    "越界访问必崩"是个错误的直觉 —— 越界的后果是未定义，
    不崩比崩更常见，也更难查。

## 八、实验 6：稀疏文件 —— 同一条原理在文件系统上

### 8.1 先自己想

懒分配的思路是"没用到就不兑现"。文件系统也按块记账，
那么：**跳过一大段不写，那段会不会真的占磁盘？**

    lseek 到 1 MiB 处，写 4 个字节。
    文件的逻辑大小显然是 1048580 字节。
    但中间那 1 MiB 从没写过 —— 磁盘上真的分配了吗？

### 8.2 动手

不用写 C，`dd` 就够：

    mkdir -p ~/vmlab && cd ~/vmlab
    dd if=/dev/zero of=sp.bin bs=1 count=4 seek=1048576 status=none

    bs=1            每次处理 1 字节
    count=4         写 4 字节
    seek=1048576    先跳过 1048576 字节再写（这就是造空洞的动作）
    status=none     别打进度

    stat -c %s sp.bin      # 逻辑大小，字节
    du -h sp.bin           # 实际占盘
    stat -c %b sp.bin      # 占了几个 512 字节块

### 8.3 本机实测

```
ls -l  逻辑大小: 1048580 字节
du -h  实际占盘: 4.0K
stat   占了 8 个 512 字节块 = 4096 字节
空洞里读出来: [ 0 0 0 0]
```

逻辑一兆，实占四千字节。

> **空洞（hole）**：文件里从没被写过的区间。文件系统不给它分配磁盘块，
> 只在元数据里记一句"这段是空的"。读它返回 0，但不占盘。
> 带空洞的文件叫**稀疏文件**。

**和第二节的懒分配是同一个思路**：先记账，用到才兑现。
一个发生在内存里（页表项），一个发生在磁盘上（磁盘块）。

### 8.4 关键：这条实验换个目录就会得出相反结论

**同样一条 `dd` 命令，在仓库所在的 Windows 盘上跑：**

```
逻辑大小: 1048580 字节
实际占盘: 1.1M = 2056 个块
```

    ext4（~/vmlab）            8 个块      空洞有效
    v9fs（/mnt/e，Windows 盘） 2056 个块   空洞被老老实实写成了真的 0

**差 257 倍，结论完全相反。**

WSL 把 Windows 盘挂成 `v9fs`，这层转换不支持稀疏文件。
查文件系统类型：

    stat -f -c '%n: %T' . /tmp ~
    .: v9fs                      <- 仓库在这里
    /tmp: tmpfs
    /home/glorinz: ext2/ext3     <- 实验数据要放这里

**这是本篇最实际的一条教训**，而且不限于这个实验：

    "在我机器上跑出来是这样"这句话，必须带上是在哪个文件系统上跑的。
    换个目录结论就可能翻转，而报错一个都不会有。

02 章第 9 节也踩到过同一件事。

### 8.5 判据

    [ ] 在 ext4 上：逻辑大小 1048580，占盘 8 个块
    [ ] 空洞里读出来全是 0
    [ ] 在 /mnt/e 上跑同一条命令，占盘变成 2000 块以上
    [ ] 能用 stat -f 查出这两个目录的文件系统类型不同

    注错见红：把实验目录改到 /mnt/e 再核对第 1 条判据，它必须失败。
    **如果它没失败，说明你的 ~ 也在 Windows 盘上**，
    那本篇第八节的所有数据都要重新跑。

## 九、顺带一提：和你在硬件那边做过的对照

**没做过带 MMU 的核也不影响，跳过即可，本篇不依赖这一节。**

如果你做过带 TLB 的处理器核，这里只对三处差异：

| | 你在硬件那边看到的 | 用户态程序看到的 |
|---|---|---|
| 页表 | 一张树，TLB 里缓存几十项 | 看不见，只看见"这段地址能访问" |
| 缺页 | 一次异常，软件填 TLB 或硬件走页表 | 一次停顿，几微秒，然后代码继续跑 |
| 谁建的表项 | 内核的 `handle_mm_fault` | `mmap` / `brk` / `execve` 各建一批 |

**关键差别是"建表"和"填表"被分开了。**

你在硬件那边看到的是"填表"那一半（TLB miss、页表遍历）。
`mmap` 干的是"建表"那一半，而且它连页表项都不建 ——
只在内核的 `vm_area_struct` 链表里记一笔
"这段虚拟地址将来对应那个文件的那一段"。

    mmap        往 vm_area_struct 链表里加一条记录。页表项：0 个
    第一次访问   MMU 找不到页表项 -> 缺页异常 -> 内核查那条记录 ->
                把文件那一页读进页缓存 -> 填页表项 -> 重跑那条指令

第二节量到的 512 次缺页、22 毫秒，就是这个过程发生了 512 次的代价。
