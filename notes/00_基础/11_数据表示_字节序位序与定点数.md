# 11 数据表示：字节序、位序与定点数

## 这一篇到底在讲什么

> **数值本身没有“先放哪一边”。** 内存和文件只是一排字节，字库又把一个字节拆成 8 个点；
> 必须再约定“高权重的字节放前还是放后”“最高位画左边还是右边”“哪几位算整数”，
> 收发两边按同一份约定解释，才会得到同一个数和同一幅图。

### 你是从哪儿撞见它的

第 04 章连续出现三个看起来很像、其实不在一个层次的问题：

```text
UTF-16LE 里的“中”       2d 4e          为什么不是 4e 2d？
HZK16 一行点阵           0x62           为什么画成 .##...#.？
FreeType 的 advance.x    1536           为什么实际是 24 像素？
```

如果只背三条答案，会觉得它们毫无关系。把问题压到底层，它们其实都在问同一件事：
**一串没有标签的 0 和 1，要按哪份规格赋予权重？**

### 它们是被什么逼出来的

第一，内存能逐个寻址的最小单位通常是**字节**，不是“一个 `uint32_t`”。
一个 32 位数要拆成 4 个字节，必须约定权重最高的那个字节放低地址还是高地址，
否则写文件的一方和读文件的一方会把 `0x12345678` 看成两个不同的数。

第二，一根线上只能按时间先后发 bit，一行点阵也只能按 bit 编号保存。
`0x62` 里有三个 1，但这三个 1 对应左起哪三个像素，必须由字库格式约定。
CPU 是小端并不能替 HZK16 决定“最高位画左边”还是“最低位画左边”。

第三，整数运算便宜、可重复，但像素位置有时不是整数。FreeType 要保存 24.5 像素，
又不想让每次排版都依赖浮点，于是约定低 6 位表示小数。二进制点并没有真的存进去，
双方都知道它藏在低 6 位前面就够了。

所以这三件事不是 CPU 自己猜出来的，都是**生产数据的一方和消费数据的一方签的协议**。

### 关键细节放在一张图里

同一串位只有结合表示规则才有含义：

| 原始值 | 问题 | 规则 | 解释结果 |
|---|---|---|---|
| `0x4E2D` | 两个字节按什么权重排列？ | 小端：低权重字节在低地址 | 内存顺序 `2D 4E` |
| `0x4E2D` | 两个字节按什么权重排列？ | 大端：高权重字节在低地址 | 内存顺序 `4E 2D` |
| `0x62 = 0b01100010` | 哪一位对应最左像素？ | MSB-first | `.##...#.`，用于 HZK16 和本章 8×16 字库 |
| `0x62 = 0b01100010` | 哪一位对应最左像素？ | LSB-first | `.#...##.`，与上一行左右镜像 |
| 整数 `1536` | 二进制点放在哪里？ | 26.6 定点数 | `1536 / 64 = 24.0` 像素 |
| 整数 `1536` | 二进制点放在哪里？ | 普通整数 | `1536` 像素，比正确值大 64 倍 |

## 结论先贴出来

下面每条都能直接背走。正文每一节至少对应一条，没有为了整齐凑条数。

1. **端序只管“一个多字节数的字节权重怎么排”，不管字符串里字符的先后顺序。**
   `A中` 在小端机器上仍然先存 A；只有 UTF-16 中每个 16 位编码单元内部的两个字节受 LE/BE 约定影响。
2. **小端是低权重字节放低地址，大端是高权重字节放低地址。**
   `0x4E2D` 的 UTF-16LE 字节是 `2d 4e`，UTF-16BE 是 `4e 2d`。
3. **文件、协议和设备寄存器按自己的格式解释，不能拿 CPU 端序替它做决定。**
   x86 和 ARM 都是小端，也不代表网络包、PNG 文件、HZK16 点阵自动变成小端格式。
4. **字节序不等于位序。** `0x62` 这个字节在内存里不再拆成“两个更小地址”；
   画点时 bit 7 对应左边还是 bit 0 对应左边，由字库规格单独约定。
5. **UTF-8 是字节序列，没有 UTF-8LE/UTF-8BE。** 它用每个字节的前缀标明边界，
   BOM `ef bb bf` 只是文件标记，不是在声明端序。
6. **定点数是“整数 + 默认二进制点位置”。** 26.6 表示低 6 位是小数，
   所以 1 像素是 64，10.5 像素是 672；FreeType 的 `advance.x`、`pen.x` 大量使用它。
7. **有负数时不要随手用除法代替向下取整。** C 的整数除法向 0 截断，
   `-33 / 64` 得 0，而几何外框向下取整应得 -1。
8. **最可靠的判据是让同一组字节按两份约定各解释一次。** 如果两次结果居然一样，
   样本可能选坏了：例如左右对称的 `A` 很难抓住点阵位序镜像，应该再用 `F`。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `ff fe` / `fe ff` | UTF-16 BOM，在声明后续编码单元的端序 |
| 中文码点从 `0x4e2d` 变成 `0x2d4e` | 两个字节的权重放反了 |
| 点阵字能认，但整个左右镜像 | 一个字节内部的位序用反了 |
| FreeType 坐标大约是预期的 64 倍 | 忘了它是 26.6 定点数 |
| 负坐标贴左边时差 1 像素 | 把向下取整写成了 C 的向 0 截断 |
| 网络字段在本机读成一个很大的怪数 | 先查协议端序，再查是否做了 `ntoh*` 转换 |

想补原理时：字节序看第二节，位序看第三节，定点数看第四节。

## 一、先把三个“序”拆开

> **地址顺序**：内存地址从小到大，或文件偏移从小到大。
>
> **字节序（endianness）**：一个多字节数拆开后，各字节按权重放进地址顺序的办法。
>
> **位序（bit order）**：一个字节里的各 bit 对应空间位置或线上时间位置的办法。

再加一个经常混进来的概念：

> **字符顺序**：文本里字符出现的先后。例如 `A中` 永远先是 A 再是中，
> 不会因为 CPU 是小端就变成 `中A`。

用 UTF-16LE 保存 `A中`，四个内容字节是：

```text
字符顺序            A                     中
编码单元          U+0041                U+4E2D
小端拆字节         41 00                 2d 4e
文件偏移        0     1               2     3
```

小端只在每个 16 位编码单元内部交换权重，并没有把字符队伍倒过来。

`UTF-8` 更简单：它的最小组成单位本来就是字节，规范已经把字节顺序写死。
“中”永远是 `e4 b8 ad`，所以不存在 UTF-8LE 和 UTF-8BE。

## 二、实验 1：同两个字节，解释出两个数

### 2.1 先自己想

内存从低地址到高地址摆着两个字节：

```text
地址低                       地址高
  2d                           4e
```

线索：十六进制一位代表 4 bit，一个字节有两位十六进制数。

先回答：

1. 如果低地址那个字节权重是 `2^0`，结果是什么？
2. 如果低地址那个字节权重是 `2^8`，结果又是什么？
3. 这两个字节是不是已经“自带小端标签”？

第三问的答案是否定的。内存里只有 `2d 4e`，解释规则在程序或文件格式里。

### 2.2 动手

```bash
cd /mnt/e/Workspace/embedded-linux/labs/00_basics/10_data_representation
gcc -Wall -Wextra -Werror -O2 -o repr repr.c
./repr
```

- `-Wall -Wextra`：打开常见和额外警告。
- `-Werror`：本实验很小，任何警告都当失败，防止注错版悄悄带着未使用参数通过。
- `-O2`：按日常发布优化编译；结果不依赖优化级别。

核心不是强转指针，而是把权重明确写出来：

```c
little = p[0] | (p[1] << 8);   /* 低地址字节乘 2^0 */
big    = (p[0] << 8) | p[1];   /* 低地址字节乘 2^8 */
```

生产代码处理外部字节流时也应该这样，或者调用格式库提供的读取函数。
不要把任意地址直接强转成 `uint16_t *`：那会再引入未对齐访问、别名规则和宿主端序三个变量。

### 2.3 本机实测

```text
native bytes: 78 56 34 12
2d 4e as LE=0x4e2d as BE=0x2d4e
0x62 MSB-first: .##...#.
0x62 LSB-first: .#...##.
26.6: one_pixel=64 ten_and_half=672 raw_672_floor=10 raw_672_round=11
26.6 negative: raw_-33_floor=-1 raw_-33_round=-1
```

### 2.4 逐行读

第一行把 `uint32_t value = 0x12345678` 用 `memcpy` 拿成四个独立字节。
低地址先看到 `78`，说明这台 x86-64 是小端：最低权重的 `0x78` 放在最低地址。

第二行故意不改原始字节，只改解释公式：

```text
小端：0x4e * 256 + 0x2d = 0x4e2d = “中”的 Unicode 码点
大端：0x2d * 256 + 0x4e = 0x2d4e = 另一个数
```

**同一排字节没有唯一答案，除非格式先告诉你端序。**

### 2.5 注错见红

`BUG_ENDIAN` 把小端读取函数里的两项权重对调：

```bash
gcc -Wall -Wextra -Werror -O2 -DBUG_ENDIAN -o repr_bad repr.c
./repr_bad | head -2
```

实测第二行的小端结果从 `0x4e2d` 变成 `0x2d4e`。
判据不是“程序没崩”，而是**已知字节必须还原成已知码点**。

### 2.6 判据

```text
[ ] 本机 0x12345678 的内存字节是 78 56 34 12
[ ] 2d 4e 按小端解释等于 0x4e2d
[ ] 2d 4e 按大端解释等于 0x2d4e
[ ] 交换小端公式的两项权重，0x4e2d 判据必须失败
```

## 三、实验 2：字节序对了，点阵仍可能镜像

### 3.1 第一性原理：一个字节内部没有“更低地址的 bit”

取字节 `0x62`：

```text
bit 编号     7 6 5 4 3 2 1 0
bit 值       0 1 1 0 0 0 1 0
```

这些 bit 一起住在同一个字节地址里。“内存是小端”只讨论多个字节，
并不能推出把 bit 0 画在左边还是 bit 7 画在左边。

本章使用的 Linux 8x16 字库和 HZK16 都约定 **MSB-first**：bit 7 对应最左边，
因此 `0x62` 画成：

```text
.##...#.
```

如果循环写成 `byte & (1 << x)`，就会变成：

```text
.#...##.
```

两个图的亮点都是 3 个。**只数亮点抓不住镜像错误。**

### 3.2 为什么不能只用 A 测

大写 `A` 接近左右对称。把每行 bit 反过来，肉眼仍可能觉得它是 A；
亮点总数更是完全不变。第 04 章实验因此同时画 `F`：

```text
正确 MSB-first             错误 LSB-first
#######.                   .#######
.##...#.                   .#...##.
.##...#.        对照       .#...##.
```

测试样本也属于判据设计。**输入没有打到错误的敏感方向，程序错了也会绿。**

### 3.3 动手、输出和注错

`repr` 已经把两种位序放在同一份输出里。运行完整判据：

```bash
bash check.sh
```

其中 `BUG_BIT_ORDER` 强制两条路径都从 bit 0 开始。实测：

```text
PASS  注错见红：把字库约定的 MSB-first 写成 LSB-first 变成 [.#...##.]
```

### 3.4 判据

```text
[ ] 0x62 的 MSB-first 图案等于 .##...#.
[ ] 0x62 的 LSB-first 图案等于 .#...##.
[ ] 第 04 章用 F 检查左右方向，不只用接近对称的 A
[ ] 注错后亮点数虽然不变，逐行图案判据必须变红
```

## 四、实验 3：整数 1536 为什么是 24 像素

### 4.1 定点数是被什么逼出来的

排版会遇到半像素、四分之一像素：某个字的步进可能是 24.5 像素，
旋转后的坐标也很少恰好落在整数上。直接只存整数会在每个字后面丢一点，
一整行累计后明显漂移。

可以用浮点，但字体库还要运行在没有快速浮点的老机器上；更重要的是，
很多几何操作只需要固定的小数精度。于是 FreeType 采用 **26.6 定点数**：

> **26.6 定点数**：一个有符号整数，低 6 位被解释为小数，剩余位表示整数。
> 二进制点约定放在低 6 位之前，所以数值和像素之间相差 `2^6 = 64` 倍。

```text
实际像素        26.6 保存的整数
1.0             64
10.0            640
10.5            672
24.0            1536
```

FreeType 类型名里常见 `FT_Pos`、`FT_F26Dot6`；字段 `advance.x`、传给
`FT_Set_Transform` 的 `pen.x` 都可能使用这种尺度。第 04 章实测宋体 48 像素时，
字母 A 的 `advance.x=1536`，正好是 24 像素。

### 4.2 先自己想

把 672 变回像素有两种需求：

```text
向下取整    10.5 -> 10
四舍五入    10.5 -> 11
```

非负数时：

```c
floor = value >> 6;
round = (value + 32) >> 6;
```

但负数要停一下。C 规定整数除法向 0 截断，`-33 / 64 == 0`；
几何里的 floor 是向负无穷，`floor(-33/64) == -1`。贴着左边界排字时，
这一像素决定外框是否漏掉最左一列。

### 4.3 本机实测与逐行读

```text
26.6: one_pixel=64 ten_and_half=672 raw_672_floor=10 raw_672_round=11
26.6 negative: raw_-33_floor=-1 raw_-33_round=-1
```

- `one_pixel=64`：尺度不是百分制，也不是千分制。
- `ten_and_half=672`：`10*64 + 32`。
- `raw_672_floor=10` / `round=11`：同一个原始整数，根据用途选择舍入。
- `raw_-33_floor=-1`：负数分支没有让 C 的向 0 截断混进几何定义。

### 4.4 注错见红

`BUG_FIXED_100` 故意把它当成百分制：

```text
正确：672 / 64  -> 四舍五入 11
错误：672 / 100 -> 四舍五入 7
```

实测判据：

```text
PASS  注错见红：把 26.6 错当成百分制，672 四舍五入变成 [7]
```

### 4.5 判据

```text
[ ] 1 像素的 26.6 原始值等于 64
[ ] 10.5 像素的原始值等于 672
[ ] 672 向下取整等于 10、四舍五入等于 11
[ ] -33 向下取整等于 -1
[ ] 把尺度错写成 100 后，四舍五入判据从 11 变成 7
```

## 五、顺带一提：和 RISC-V / 龙芯寄存器对照

没做过也不影响，跳过即可。

你在 ysyx 里把一条 32 位指令拆成 opcode、rd、rs1、立即数时，做的是**位段解释**；
在龙芯 SoC 里读设备寄存器后用 mask/shift 取字段，也是在按硬件手册解释权重。

```text
指令 / 寄存器       一整个 32 位数里的不同 bit 各管什么
UTF-16 文件          两个字节合成 16 位编码单元时谁权重大
HZK16 字库           一个字节的 bit 7..0 各对应哪一列
FreeType 26.6        一个整数的低 6 位被解释成小数
```

共同点不是“都要移位”，而是：**裸数据不会自述含义，必须拿生产者的规格来解释。**
