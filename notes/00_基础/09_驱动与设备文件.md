# 09 驱动与设备文件：/dev、/sys 与 dmesg

## 这一篇到底在讲什么

> **驱动是内核里专门伺候某一种硬件的那段代码。**
> 你的程序碰不到硬件，想用它，就打开 `/dev` 下对应的那个文件，读、写、发控制命令，
> 内核把这些请求转给驱动去办。**`/dev` 下的这个文件里没有数据，只存着两个数字**，
> 告诉内核该找哪个驱动、找它管的第几个设备。

### 你是从哪儿撞见它的

第 03 章在板子上敲 `ls -l /dev/fb0`：

```text
crw-rw---- 1 root video 29, 0 Jan  1 00:00 /dev/fb0
```

普通文件在这个位置显示的是大小，这里却是 `29, 0`。

再往下，板子的启动日志里有几行你没见过的：

```text
[    1.169617] 100ask, drivers/video/fbdev/mxsfb.c mxsfb_probe 2341
[    1.194368] mxsfb 21c8000.lcdif: initialized
```

还有一个目录 `/sys/class/graphics/fb0/`，里面的 `device` 是个链接，指向 `21c8000.lcdif`。

然后你回到 WSL，照着板子上的号码自己造了一个一模一样的 `29, 0`，`open` 却报 `No such device`。

`29, 0` 是什么，`mxsfb` 是谁，`21c8000.lcdif` 又是什么，为什么号码一样却打不开，这一篇讲清楚。

### 驱动和设备文件是被什么逼出来的

[基础 05] 讲过：用户程序没有权限碰硬件，只能请内核代劳。那内核就得会操作世界上所有的硬件。

**第一个问题：硬件千差万别。** 同样是"显示"，i.MX6ULL 上是 LCDIF 控制器，
换一颗芯片寄存器全都不一样。内核主体不可能把每块板子的每个芯片都写死在里面。
办法是把"操作某一种硬件"的代码单独拆出来，一种硬件一份，需要哪份就编进内核或者临时加载。
**这一份份代码就是驱动。**

**第二个问题：程序怎么告诉内核"我要用哪个硬件"。**
要是每来一种硬件就加一个新的系统调用，系统调用表会无限膨胀。
[基础 06] 第七节已经有一套现成的办法：`open`/`read`/`write` 这几个调用不变，
内核在 `open` 的时候看你打开的是什么，往 `f_op` 里填不同的函数表。
**那就给每个硬件起一个文件名，让它看起来像个文件。** 这就是设备文件。

**第三个问题：名字靠不住。** 文件名是给人看的，可以改名，可以重复。
内核需要一个稳定、查表快的编号。于是设备文件里存两个数：
**主设备号选哪个驱动，次设备号选这个驱动管的第几个设备。**

**第四个问题：有些操作不是"读一串字节""写一串字节"能表达的。**
问显示屏分辨率多少、把串口波特率设成 115200，这类事塞不进 `read`/`write`。
于是有了 `ioctl`：给一个请求编号，再给一块内存，驱动按编号往里填或者从里取。

**第五个问题：出了问题怎么查。** 系统里到底有哪些硬件、各归哪个驱动管、
驱动启动时说了什么，都得有地方看。内核把设备档案公开在 `/sys` 下，把驱动的话记在日志里，用 `dmesg` 读。

### 放在一张图里

从 `/dev/fb0` 到 LCDIF 硬件可以分层看：

| 层 | 能看到什么 | 它告诉下一层什么 |
|---|---|---|
| 用户态设备节点 | `/dev/fb0` 是字符设备，号码为 `29:0` | 主设备号 29 选择 fb 核心；次设备号 0 选择第 0 个实例 |
| 内核 fb 实例 | 由 `mxsfb` 驱动创建，并提供 `f_op` | `open` 后把操作表放入 `struct file` |
| 系统调用入口 | `ioctl(fd, 请求码, &var)`、`read/write/mmap` | 分派到 `f_op` 中对应的驱动函数 |
| 硬件 | `0x021c8000` 处的 LCDIF 控制器 | 真正执行显示相关操作 |

旁证来自两处：`/sys/class/graphics/fb0/dev` 显示 `29:0`，`device` 链接指向 `21c8000.lcdif`；`dmesg` 保存驱动启动日志。

## 结论先贴出来

下面每条都能直接背走，看不懂推导也不影响用。条数按本篇实际有几个独立结论来定，
不凑数：正文每一节至少对应下面一条，没对上就是漏了。

1. **驱动是内核里的代码，设备实例是它管着的一个具体东西。** 一份驱动可以同时管好几个同类设备。
2. **`/dev` 下的设备文件只存类型和两个号。** 类型是 `c`（字符设备）或 `b`（块设备）；
   主设备号选驱动，次设备号选实例。**文件名随便起，行为只看号码。**
3. **主设备号要和类型一起看。** 本机实测同一个 1 号，字符设备那边是 `mem`，块设备那边是 `ramdisk`。
4. **打开设备失败，三种 errno 各指一层：** `ENXIO` 是这个号码没有驱动登记；
   `ENODEV` 是驱动登记了，但这个次设备号对应的实例不存在；
   连 root 都报 `EACCES`，先查节点所在的挂载点是不是带了 `nodev`。
5. **设备节点只能建在允许它的本地文件系统上。** 本机实测：WSL 的 `/tmp` 带 `nodev`，建了也打不开；
   `/mnt/e`（Windows 盘）连 `mknod` 都直接失败。
6. **`/dev` 下的节点不是人手工建的。** 驱动登记设备时，内核在 `devtmpfs` 里自动建好节点，
   名字和权限就是 `/sys` 里 `uevent` 文件写的那几项。
7. **`/sys/class/<类>/<设备>/` 是这个设备的档案。** `dev` 文件是它的号码，和 `/dev` 节点一致；
   `device` 链接指向背后的硬件；`device/driver` 指向管它的驱动。
   背后没有硬件的虚拟设备（比如 `/dev/null`）没有 `device` 链接。
8. **`ioctl` 装的是文件接口表达不了的操作：一个请求码加一块内存。**
   新式请求码把方向、类型、序号、那块内存的大小都编了进去；
   **framebuffer 用的是老式请求码，大小那一段是 0**，结构体用错了内核也发现不了。
9. **驱动不认识的请求码一律返回 `ENOTTY`**，报错文字是 `Inappropriate ioctl for device`。
10. **`dmesg` 是内核的日志，驱动启动、出错时往里写，每行开头是开机后的秒数。**
    反过来，**驱动没写的事 `dmesg` 里就没有**：第 03 章插上显示器，驱动改了分辨率，日志一行都没多。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `ls -l` 大小那一栏是 `29, 0` 这种 | 设备文件：主设备号 29、次设备号 0 |
| `open` 报 `No such device or address` | `ENXIO`：这个主设备号没有驱动登记，驱动没编进内核或没加载 |
| `open` 报 `No such device` | `ENODEV`：驱动在，这个实例不在。硬件没探测到，或者次设备号写错了 |
| root 打开设备也是 `Permission denied` | `findmnt -T <路径>` 看挂载选项里有没有 `nodev` |
| `mknod` 报 `Operation not supported` | 这个文件系统不支持设备节点，换到 ext4 这类本地文件系统上 |
| `ioctl` 报 `Inappropriate ioctl for device` | 这个驱动不认这个请求码：文件打错了，或者请求码用错了 |
| 想知道某个设备归哪个驱动管 | `readlink /sys/class/<类>/<设备>/device/driver` |
| 想知道驱动启动时有没有报错 | `dmesg \| grep <驱动名或硬件地址>` |
| 驱动明明做了一件事，`dmesg` 里查不到 | 正常，驱动不是什么都写日志。去 `/sys` 或者用 `ioctl` 查现状 |

想补原理时：名词看第一节，设备号看第二、三节，打不开的原因看第四节，
`/sys` 看第五节，`ioctl` 看第六节，`dmesg` 看第七节。

## 一、先把三个名词摆清楚

> **驱动（driver）**：内核里负责操作某一种硬件的一段代码。
> 它知道这种硬件的寄存器在哪、怎么初始化、怎么收发数据，
> 然后把这些本事包装成一张 `file_operations` 表（[基础 06] 第七节）交给内核。

> **设备实例**：驱动管着的一个具体的东西。板子上有两个串口，就是串口驱动的两个实例；
> 同一份驱动代码，每个实例各有自己的一份状态。

> **字符设备 / 块设备**：设备文件的两种类型。
> 字符设备按字节流读写，串口、显示、`/dev/null` 都是；
> 块设备按固定大小的块读写，磁盘、eMMC 是。本篇只讲字符设备。

还有一类"设备"背后根本没有硬件，比如 `/dev/null`（写进去的都扔掉）和 `/dev/zero`（读出来全是 0）。
它们也有驱动，只是驱动里什么硬件都不碰。**正好拿来做实验**：不用板子，WSL 里就有，行为又好认。

## 二、实验 1：设备文件里存的是什么

### 2.1 先自己想

普通文件 `ls -l` 时，第 5 列是大小。设备文件那一列却是两个数。
这两个数存在哪？文件内容里？还是别的地方？

线索：

    stat 命令能按格式打印文件的元信息，%F 是类型，%s 是大小，
    %t 和 %T 是设备号的两个部分（十六进制）
    /proc/devices 是内核里"号码 -> 名字"的登记表，分字符设备和块设备两段

### 2.2 动手

从 Windows PowerShell 进 root：

```powershell
wsl -u root
```

然后在 WSL 里：

```bash
mkdir -p ~/devlab && cd ~/devlab
printf 'ABCDEFGH' > data.txt
ls -l /dev/null /dev/zero /dev/full data.txt
stat -c '%-10n %F  大小=%s  设备号(十六进制)=%t,%T' /dev/null data.txt
sed -n '/^Character/,/^$/p' /proc/devices | head -4
sed -n '/^Block/,$p' /proc/devices | head -4
```

- `printf 'ABCDEFGH' > data.txt`：造一个 8 字节的普通文件做对照。
- `stat -c '格式'`：按格式打印。`%-10n` 是文件名左对齐占 10 格。
- `sed -n '/^Character/,/^$/p'`：`-n` 不自动打印，`/A/,/B/p` 打印从匹配 A 的行到匹配 B 的行，
  这里就是从 `Character devices:` 到下一个空行，也就是字符设备那一段。
- `sed -n '/^Block/,$p'`：从 `Block devices:` 一直到文件末尾（`$`）。

### 2.3 本机实测

```text
crw-rw-rw- 1 root root 1, 7 Sep 15 10:59 /dev/full
crw-rw-rw- 1 root root 1, 3 Sep 15 10:59 /dev/null
crw-rw-rw- 1 root root 1, 5 Sep 15 10:59 /dev/zero
-rw-r--r-- 1 root root    8 Sep 15 11:00 data.txt
/dev/null  character special file  大小=0  设备号(十六进制)=1,3
data.txt   regular file  大小=8  设备号(十六进制)=0,0
Character devices:
  1 mem
  4 /dev/vc/0
  4 tty
Block devices:
  1 ramdisk
  7 loop
  8 sd
```

### 2.4 逐行读

**第一列第一个字符**：三个设备是 `c`（字符设备），`data.txt` 是 `-`（普通文件）。

**`ls -l` 的第 5 列**：`data.txt` 是 `8`，就是 8 个字节。三个设备是 `1, 7`、`1, 3`、`1, 5`。

**`stat` 那两行把话说明白了**：`/dev/null` 的大小是 `0`，设备号是 `1,3`；
`data.txt` 大小 8，设备号 `0,0`（普通文件没有设备号）。
**设备文件没有内容，大小是 0。那两个数不在文件内容里，而是和权限、属主一样，记在文件的元信息里。**

**`/proc/devices` 的字符设备段**：`1 mem`。三个设备主设备号都是 1，所以都归 `mem` 这个驱动管。
次设备号 3、5、7 区分它管的三个实例：`null`、`zero`、`full`。

**块设备段也有一个 1 号，叫 `ramdisk`。** 同一个数字，在字符设备那边是 `mem`，在块设备这边是 `ramdisk`，
两者毫无关系。**所以说号码的时候要连类型一起说：`c 1,3` 才是 `/dev/null`。**

`4` 号在字符设备段不止出现一次（这里截到了 `/dev/vc/0` 和 `tty`）。
同一个主设备号可以按次设备号的范围分给不同的登记者，本篇不展开。

> **主设备号（major）/ 次设备号（minor）**：设备文件元信息里的两个数。
> `open` 时内核先按"类型 + 主设备号"找到驱动，再把次设备号交给驱动，由驱动决定这是它的哪个实例。

### 2.5 判据

    [ ] /dev/null 是 character special file，大小 0，设备号 1,3
    [ ] data.txt 的设备号是 0,0
    [ ] /proc/devices 字符设备段 1 号叫 mem，块设备段 1 号叫 ramdisk

    注错见红见下一节：号码一换，行为就跟着换。

## 三、实验 2：名字无所谓，号码说了算

### 3.1 先自己想

既然设备文件只有类型和两个号，那**自己造一个同样号码、名字不同的文件**，
它的行为应该和原来那个一模一样。反过来，**名字不变、号码换掉**，行为就该变。

怎么判断"行为一样"？挑三个行为很好认的：

    /dev/null   读：马上返回 0（没有数据）   写：全部吞掉，报告写成功
    /dev/zero   读：要多少给多少个 0 字节     写：同样吞掉
    /dev/full   读：和 zero 一样             写：永远报"磁盘满了"

线索：造设备文件的命令是 `mknod`，参数是 名字、类型、主设备号、次设备号。

### 3.2 动手

实验目录里的 `devopen.c` 对每个路径做四件事，各打一段结果：
`stat` 看类型和设备号、`open`、`read` 8 个字节打成十六进制、`write` 1 个字节。
核心就是 [基础 06] 第七节那段"只换路径，代码一个字不改"：

```c
fd = open(p, O_RDWR);                      /* 同一个 open */
n = read(fd, buf, sizeof buf);             /* 同一个 read，最多读 8 字节 */
n = write(fd, "A", 1);                     /* 同一个 write，写 1 字节 */
```

编译，然后造三个设备文件：

```bash
D=/mnt/e/Workspace/embedded-linux/labs/00_basics/08_driver_devfile
gcc -Wall -O2 -o $D/devopen $D/devopen.c
cd ~/devlab
mknod mynull c 1 3
mknod myzero c 1 5
mknod myfull c 1 7
ls -l mynull myzero myfull
$D/devopen data.txt /dev/null mynull myzero myfull
```

- `mknod mynull c 1 3`：在当前目录建一个叫 `mynull` 的文件，类型 `c`（字符设备），主设备号 1，次设备号 3。
  它不会去问内核"1,3 存不存在"，只是把这几个数写进文件元信息。
- `$D/devopen`：程序在 Windows 盘上，设备文件在 `~/devlab`，所以用变量拼出程序的完整路径。

### 3.3 本机实测

```text
crw-r--r-- 1 root root 1, 7 Sep 15 11:00 myfull
crw-r--r-- 1 root root 1, 3 Sep 15 11:00 mynull
crw-r--r-- 1 root root 1, 5 Sep 15 11:00 myzero
data.txt   普通文件    8字节  read=8 [4142434445464748]  write=1
/dev/null  字符设备   1,3    read=0 []  write=1
mynull     字符设备   1,3    read=0 []  write=1
myzero     字符设备   1,5    read=8 [0000000000000000]  write=1
myfull     字符设备   1,7    read=8 [0000000000000000]  write 失败 ENOSPC
```

### 3.4 逐行读

**`data.txt`**：读到 8 个字节，`41 42 ... 48` 就是 `A` 到 `H` 的 ASCII 码。写 1 字节成功。

**`/dev/null` 和 `mynull` 两行，除了名字一个字都不差**：读返回 0，写返回 1。
`mynull` 是 3 秒钟前在 `~/devlab` 里随手造的，内核照样把它当 `/dev/null` 办。

**`myzero`**：读到 8 个 `00`。**`myfull`**：读也是 8 个 0，但写报 `ENOSPC`（No space left on device）。
写的动作一样，结果不同，因为次设备号 7 让内核把请求交给了 `full` 那个实例的函数。

**`ls -l` 那三行的权限是 `crw-r--r--`**，而 `/dev/null` 是 `crw-rw-rw-`。
权限和号码是分开存的，`mknod` 用的是当前的默认权限。所以普通用户能写 `/dev/null`，
却写不了你造的 `mynull`（本节是 root 在跑，看不出来）。

### 3.5 注错见红

**名字不变，只把号码换成 1,5：**

```bash
rm mynull; mknod mynull c 1 5; $D/devopen mynull
```

```text
mynull     字符设备   1,5    read=8 [0000000000000000]  write=1
```

同一个名字，读出来从"0 字节"变成了"8 个 0"。**它现在就是 `/dev/zero`。**

### 3.6 判据

    [ ] mynull(c 1,3) 和 /dev/null 两行 read/write 结果完全相同
    [ ] myzero(c 1,5) 读出 8 个 00
    [ ] myfull(c 1,7) 写报 ENOSPC
    [ ] 注错见红：名字不变、号码改成 1,5 后，mynull 读出 8 个 00

> **结论**：设备文件的名字只是给人看的门牌。`/dev/fb0` 叫 `fb0` 是约定，
> 改叫 `abc` 照样能用；内核认的只有 `c 29,0` 这几个数。

## 四、实验 3：打不开的几种下场

### 4.1 先自己想

上一节的号码都"有人认领"。如果号码**没人认领**呢？分两种：

    主设备号在 /proc/devices 里根本没有            比如 200
    主设备号登记了，但驱动没有这个次设备号的实例    比如 29 号 fb，WSL 里没有任何显示设备

这两种情况 `open` 应该报同一个错吗？

另外，第一节说节点要建在 `~/devlab`，**同样的 `c 1,3` 建在 `/tmp` 或 `/mnt/e` 下会怎样？**

### 4.2 动手

```bash
cd ~/devlab
mknod nobody c 200 0
mknod fbfake c 29 0
$D/devopen nobody fbfake
echo "200 号在 /proc/devices 里出现的次数: $(sed -n '/^Character/,/^$/p' /proc/devices | grep -cE '^ *200 ')"
echo "29 号: $(sed -n '/^Character/,/^$/p' /proc/devices | grep -E '^ *29 ')"
echo "/sys/class/graphics: $(ls /sys/class/graphics)"
mknod /tmp/mynull c 1 3; $D/devopen /tmp/mynull; rm -f /tmp/mynull
findmnt -no TARGET,FSTYPE,OPTIONS /tmp
mknod /mnt/e/Workspace/embedded-linux/.devtest c 1 3; echo "mknod rc=$?"
findmnt -no TARGET,FSTYPE /mnt/e
```

- `grep -cE '^ *200 '`：`-c` 只数匹配的行数，`^ *200 ` 是"行首若干空格、然后 200、然后一个空格"。
- `/sys/class/graphics`：内核按类整理的设备档案目录，显示类的都在这下面（第五节细讲）。
- `findmnt -no TARGET,FSTYPE,OPTIONS /tmp`：查 `/tmp` 这个挂载点。`-n` 不打表头，`-o` 选列。

### 4.3 本机实测

```text
nobody     字符设备 200,0    open 失败 ENXIO (No such device or address)
fbfake     字符设备  29,0    open 失败 ENODEV (No such device)
200 号在 /proc/devices 里出现的次数: 0
29 号:  29 fb
/sys/class/graphics: fbcon
/tmp/mynull 字符设备   1,3    open 失败 EACCES (Permission denied)

mknod: Operation not supported (os error 95)
mknod rc=255

```

### 4.4 逐行读，四种下场

**`nobody`（200,0）报 `ENXIO`**，而 `/proc/devices` 里 200 号一次都没出现。
内核按主设备号去找驱动，**没人登记，连驱动这一层都没走到**。

**`fbfake`（29,0）报 `ENODEV`。** 29 号是登记了的（`29 fb`），所以内核找到了 fb 核心。
但 fb 核心再按次设备号 0 去找实例，**WSL 里 `/sys/class/graphics` 下只有 `fbcon`，没有 `fb0`**，
于是由驱动那一层回了"没有这个设备"。

> **fbcon**：framebuffer console，内核用 framebuffer 画文字终端的那部分代码。
> 它只是 fb 类下面的一个功能模块，不是显示设备，所以有它不代表有 `fb0`。

**两个 errno 对应请求走到了哪一层：**

`open("fbfake")` 的判定顺序：

| 步骤 | 查询内容 | 找不到时 | 找到时 |
|---|---|---|---|
| 1 | 按“字符设备 + 主设备号”查驱动 | `ENXIO`；例如主设备号 200 没人登记 | 进入对应核心；29 号是 fb 核心 |
| 2 | 驱动按次设备号查实例 | `ENODEV`；例如系统没有 `fb0` 实例 | `open` 成功，`f_op` 填为该驱动的操作表 |

**`/tmp/mynull` 报 `EACCES`，而且是 root 在跑。** 号码和第三节一模一样，
区别只在它建在 `/tmp` 下。`findmnt` 那一行的选项里有 **`nodev`**：

> **nodev**：挂载选项，意思是"这个文件系统上的设备文件一律不认"。
> 常用在 `/tmp` 这种谁都能写的目录上，防止有人在里面造一个指向磁盘的设备文件绕过权限。

**`/mnt/e` 上连 `mknod` 都失败了**（`Operation not supported`，95 号 errno）。
`/mnt/e` 的类型是 `9p`，是 WSL 用来访问 Windows 盘的网络式文件系统，**Windows 那边没有设备文件这个概念**。

这也是 03 章第 2.2 节那个 `mknod` 必须在 `~` 下做的原因。

### 4.5 判据

    [ ] 200,0 报 ENXIO，且 /proc/devices 里没有 200
    [ ] 29,0 报 ENODEV，且 /proc/devices 里有 29 fb、/sys/class/graphics 下没有 fb0
    [ ] 同样的 1,3 建在 /tmp 下：root 也报 EACCES，/tmp 的挂载选项里有 nodev
    [ ] /mnt/e 上 mknod 失败

    注错见红：第三节里建在 ~/devlab 的 mynull 能用，同样的号码搬到 /tmp 就打不开。
    行为跟着挂载点变，号码没变。

## 五、实验 4：/sys 是内核公开出来的设备档案

### 5.1 先自己想

前面每次都是自己 `mknod`。但 `/dev/null`、板子上的 `/dev/fb0` 显然不是谁手工建的。
**是谁建的？它怎么知道该用什么名字、什么号码、什么权限？**

另外，第 03 章看到 `/sys/class/graphics/fb0/device -> ../../../21c8000.lcdif`。
这个目录里还有什么？

线索：

    /sys/class/<类>/<设备>/dev       一个文本文件
    /sys/class/<类>/<设备>/uevent    一个文本文件
    mount 看 /dev 挂的是什么文件系统

### 5.2 动手

```bash
ls /sys/class/mem/
for d in /sys/class/mem/*; do
	n=${d##*/}; s=$(cat "$d/dev"); t=$(stat -c '%t %T' "/dev/$n")
	printf '%-8s sysfs dev=%-5s  /dev/%-8s %d:%d\n' "$n" "$s" "$n" "0x${t% *}" "0x${t#* }"
done
cat /sys/class/mem/null/uevent
stat -c '/dev/null 权限位 %a' /dev/null
readlink /sys/class/mem/null/device || echo "(mem/null 没有 device 链接)"
mount | grep -E ' on /dev | on /sys '
```

- `${d##*/}`：bash 的字符串截取，去掉最后一个 `/` 及之前的部分，剩下目录名，比如 `null`。
- `stat -c '%t %T'`：两个号，十六进制。`${t% *}` 取空格前面那段，`${t#* }` 取空格后面那段。
- `printf '%d' 0x1b`：`printf` 认 `0x` 前缀，按十六进制转成十进制。
- `readlink ... || echo`：`readlink` 读链接指向；链接不存在时它失败，`||` 后面那句才执行。

再看两个背后有硬件的设备：

```bash
for c in net/eth0 rtc/rtc0; do
	echo "$c: device -> $(readlink /sys/class/$c/device)"
	echo "$c: driver -> $(readlink /sys/class/$c/device/driver)"
done
echo "hv_netvsc 驱动目录: $(ls /sys/bus/vmbus/drivers/hv_netvsc/ | tr '\n' ' ')"
echo "rtc_cmos  驱动目录: $(ls /sys/bus/pnp/drivers/rtc_cmos/ 2>/dev/null | tr '\n' ' ')"
echo "rtc0 dev=$(cat /sys/class/rtc/rtc0/dev)"; ls -l /dev/rtc0
```

- `eth0` 是 WSL 的网卡，`rtc0` 是实时时钟（断电也能走时的那颗小钟）。
- `tr '\n' ' '`：把换行换成空格，让列表挤在一行里。

### 5.4 逐行读

**`/sys/class/mem/` 下的 7 个名字，正好是 `mem` 驱动管的 7 个实例。**
每个实例的 `dev` 文件里写着它的号码，和 `/dev` 下同名节点的号码 **7 个全部相等**。

**`uevent` 文件四行**：`MAJOR=1`、`MINOR=3`、`DEVNAME=null`、`DEVMODE=0666`。
而 `/dev/null` 的权限位正好是 `666`。**`/dev/null` 这个节点的名字、号码、权限，全都写在这里。**

**`/dev` 挂的是 `devtmpfs`。** 把这几条连起来，就是节点的来历：

设备节点的生成顺序：

1. 驱动登记一个设备实例，例如 mem 驱动登记 `null`。
2. 内核在 `/sys/class/mem/null/` 建档案，并在 `uevent` 中写入 `MAJOR`、`MINOR`、`DEVNAME`、`DEVMODE`。
3. devtmpfs 根据这些字段在 `/dev` 建立节点，照抄设备号和权限。
4. 用户态的 udev 收到通知后，还可以修改权限、属组或增加别名链接。本机进程列表中有 `systemd-udevd`，板子的启动脚本中有 `S10udev`。

> **devtmpfs**：内核维护的一个内存文件系统，挂在 `/dev`。驱动登记设备时内核直接往里建节点，
> 所以开机后 `/dev` 下就是现成的，不需要谁手工 `mknod`。
> **sysfs**：挂在 `/sys` 的内核文件系统。内核把设备、驱动、总线的关系摆成目录和链接给你看，
> 文件内容是读的那一刻现生成的。

**`mem/null` 没有 `device` 链接**：`/dev/null` 背后没有任何硬件。

**`eth0` 和 `rtc0` 都有，而且各有两层：**

    rtc0 -> device -> 00:00         背后的硬件：总线上编号为 00:00 的那颗时钟芯片
                  -> driver -> rtc_cmos   管这颗芯片的驱动叫 rtc_cmos

反过来看驱动目录 `rtc_cmos/` 里，**有一个名叫 `00:00` 的链接**，指回这个硬件。
`hv_netvsc/` 里那串 `63f1e711-...` 也正是 `eth0` 的 `device` 链接的名字。
**设备指向驱动，驱动也指回设备，两边对得上。** 一个驱动管几个实例，它的目录里就有几个这样的链接。

**`rtc0 dev=249:0`，`/dev/rtc0` 也是 `249, 0`**，和 `mem` 类一样对得上。
它的属组是 `clock`、权限 `rw-rw----`，所以普通用户读不了这个设备，第六节要 root。

**回到板子**，第 03 章那一行现在能读懂了：

```text
lrwxrwxrwx 1 root root 0 Jan  1 00:04 /sys/class/graphics/fb0/device -> ../../../21c8000.lcdif
```

`fb0` 这个实例背后的硬件叫 `21c8000.lcdif`：物理地址 `0x021c8000` 处的 LCDIF 显示控制器。
管它的驱动，启动日志里已经自报家门了，就是 `mxsfb`。

### 5.5 判据

    [ ] /sys/class/mem 下每个设备的 dev 文件，和 /dev 同名节点的号码逐个相等
    [ ] null 的 uevent 里 DEVMODE=0666，和 /dev/null 的权限位 666 相等
    [ ] /dev 挂的是 devtmpfs
    [ ] mem/null 没有 device 链接；eth0、rtc0 有 device 和 driver 两层
    [ ] 驱动目录里有一个链接，名字和设备的 device 链接指向的名字相同

    注错见红：拿 /sys/class/mem/zero/dev 去和 /dev/null 比，必须对不上（1:5 != 1:3）。

## 六、实验 5：ioctl 和它的请求码

### 6.1 先自己想

[基础 06] 第七节用 `TIOCGWINSZ` 问终端窗口有几行几列，第 03 章用 `FBIOGET_VSCREENINFO` 问显示分辨率。
这两个名字都是宏，展开以后是一个整数，叫**请求码**。

> **ioctl**：`ioctl(fd, 请求码, 指针)`。给驱动一个编号和一块内存，
> 驱动按编号决定干什么：往这块内存里填数据，或者从里面取参数。

问题是：**驱动怎么确定你给的那块内存有多大？** 要是你给的结构体比驱动以为的小，
它往里填的时候就写出界了。

线索：请求码不只是一个序号。内核头文件 `asm-generic/ioctl.h` 里有一组宏
`_IOC_DIR`、`_IOC_TYPE`、`_IOC_NR`、`_IOC_SIZE`，能把请求码拆开。本机查到的位宽：

    _IOC_NRBITS    8     序号
    _IOC_TYPEBITS  8     类型（通常是一个字母，代表哪一类驱动）
    _IOC_SIZEBITS  14    那块内存的大小
    _IOC_DIRBITS   2     方向：0 不传数据，1 用户写给驱动，2 驱动读给用户

### 6.2 动手

`ioctlcode.c` 把四个请求码拆开，再和 `sizeof` 真实的结构体大小并排打印：

```c
show("RTC_RD_TIME", RTC_RD_TIME, sizeof(struct rtc_time));
show("TIOCGWINSZ", TIOCGWINSZ, sizeof(struct winsize));
show("FBIOGET_VSCREENINFO", FBIOGET_VSCREENINFO, sizeof(struct fb_var_screeninfo));
show("FBIOGET_FSCREENINFO", FBIOGET_FSCREENINFO, sizeof(struct fb_fix_screeninfo));
```

给了路径的话，再对那个文件真发两次：一次 `RTC_RD_TIME`（读实时时钟），一次 `FBIOGET_VSCREENINFO`。

```bash
gcc -Wall -O2 -o $D/ioctlcode $D/ioctlcode.c
$D/ioctlcode /dev/rtc0
$D/ioctlcode data.txt | tail -2
date -u '+系统时间(UTC) %F %T'
```

- `tail -2`：只看最后两行，也就是真发 `ioctl` 的那两行结果。
- `date -u`：按 UTC 打印系统时间，和实时时钟对照。

### 6.3 本机实测

```text
RTC_RD_TIME          0x80247009  方向=2  类型=0x70'p'  序号=9    大小=36   sizeof=36
TIOCGWINSZ           0x00005413  方向=0  类型=0x54'T'  序号=19   大小=0    sizeof=8
FBIOGET_VSCREENINFO  0x00004600  方向=0  类型=0x46'F'  序号=0    大小=0    sizeof=160
FBIOGET_FSCREENINFO  0x00004602  方向=0  类型=0x46'F'  序号=2    大小=0    sizeof=80
ioctl(RTC_RD_TIME)         成功: 2026-09-15 03:00:15 (UTC)
ioctl(FBIOGET_VSCREENINFO) 失败: Inappropriate ioctl for device
ioctl(RTC_RD_TIME)         失败: Inappropriate ioctl for device
ioctl(FBIOGET_VSCREENINFO) 失败: Inappropriate ioctl for device
系统时间(UTC) 2026-09-15 03:00:15
```

### 6.4 逐行读

**`RTC_RD_TIME` 是 `0x80247009`**，拆开：

```text
    0x80247009 = 10 00000000100100 01110000 00001001
                 ^^ ^^^^^^^^^^^^^^ ^^^^^^^^ ^^^^^^^^
                 方向  大小=0x24=36   类型'p'   序号 9
                 2=读
```

大小 36，而 `sizeof(struct rtc_time)` 也是 36。**请求码自己就带着"我要一块 36 字节的内存"。**
头文件里它的定义是 `_IOR('p', 0x09, struct rtc_time)`，`_IOR` 这个宏把 `sizeof` 编进了请求码。
驱动收到请求码，有能力核对"你用的结构体和我认为的一样大"。

**`TIOCGWINSZ` 和两个 `FBIOGET_*` 的方向、大小全是 0。** 它们是这套编码出现之前就定下来的老请求码，
只有类型和序号：`0x46` 是字母 `F`，`0x4600` 就是"F 类第 0 号"。
**请求码里没有大小，结构体用错了，内核核对不出来。**

这就是第 03 章那个现象的根源：`fb_fix_screeninfo` 在 x86-64 上 80 字节，ARM 上 68 字节
（上面 `sizeof=80` 是 x86 编出来的），而 `FBIOGET_FSCREENINFO` 两个平台都是 `0x4602`。
用错了头文件，程序不会报错，只会读到错位的数据。

**真发 `ioctl` 的四行：**

    /dev/rtc0 + RTC_RD_TIME           成功，03:00:15，和系统时间同一秒
    /dev/rtc0 + FBIOGET_VSCREENINFO   失败 ENOTTY
    data.txt  + RTC_RD_TIME           失败 ENOTTY
    data.txt  + FBIOGET_VSCREENINFO   失败 ENOTTY

**实时时钟驱动不认 fb 的请求码，普通文件两个都不认，报的是同一个 `ENOTTY`。**
名字里的 TTY 是历史遗留，`ioctl` 最早是给终端用的，意思其实是"这个对象不适用这个请求"。

### 6.5 判据

    [ ] RTC_RD_TIME 请求码 0x80247009，拆出的大小 36 == sizeof(struct rtc_time)
    [ ] FBIOGET_VSCREENINFO 拆出的大小是 0
    [ ] TIOCGWINSZ 请求码 0x00005413
    [ ] 对普通文件发两个请求码，都报 ENOTTY
    [ ] 对 /dev/rtc0 发 RTC_RD_TIME 成功，日期和 date -u 一致

    注错见红：对 /dev/rtc0 发 fb 的请求码，报 ENOTTY。
    同一个 fd，换一个请求码就失败：认不认由驱动决定。

## 七、实验 6：dmesg 是驱动写的日志

### 7.1 先自己想

第 03 章板上 `dmesg` 里那几行，行首的 `[    1.194368]` 是什么？
驱动什么时候往里写？应用程序能不能往里写？

线索：`/sys/class/mem/` 下有一个 `kmsg`，号码 `1:11`。

### 7.2 动手

```bash
dmesg | head -2
echo "dmesg 行数: $(dmesg | wc -l)"
echo "devlab: marker-$$" > /dev/kmsg
dmesg | grep "marker-$$"
echo "uptime: $(cut -d' ' -f1 /proc/uptime)"
dmesg | grep -iE 'rtc_cmos|hv_netvsc' | head -4
su glorinz -c 'echo hi > /dev/kmsg'; echo "rc=$?"
```

- `echo ... > /dev/kmsg`：往内核日志里写一行。`$$` 是当前 shell 的 PID，拿来当一个不会重复的记号。
- `/proc/uptime`：第一个数是开机到现在的秒数。`cut -d' ' -f1` 按空格切，取第 1 段。
- `su glorinz -c '...'`：换成普通用户（这里的用户名是本机的，换成你自己的）执行一条命令。

### 7.3 本机实测

```text

[    0.000000] Command line: initrd=\initrd.img WSL_ROOT_INIT=1 panic=-1 nr_cpus=20 hv_utils.timesync_implicit=1 console=hvc0 debug pty.legacy_count=0 WSL_ENABLE_CRASH_DUMP=1

[    0.162479] rtc_cmos 00:00: RTC can wake from S4

[    0.164021] rtc_cmos 00:00: setting system clock to 2026-09-15T02:59:45 UTC (1789441185)

```

### 7.4 逐行读

**前两行时间戳是 `0.000000`**：内核刚开始跑，第一件事就是报版本号和启动参数。

**我们写进去的那一行，时间戳 `29.885680`，`/proc/uptime` 是 `29.88`。**
**时间戳就是开机后的秒数。** 所以板子上 `[    1.194368] mxsfb 21c8000.lcdif: initialized`
的意思是：开机 1.19 秒时，`mxsfb` 驱动把 `21c8000.lcdif` 这个设备初始化好了。

> **dmesg**：读内核日志缓冲区的命令。内核和驱动用 `printk` 往这块缓冲区里写，
> 用户态也可以通过 `/dev/kmsg` 写一行进去（要 root）。缓冲区大小有限，老日志会被新日志挤掉。

**`rtc_cmos` 那三行**是驱动启动时的自我介绍，格式是"驱动名 设备名: 说了什么"：

    rtc_cmos 00:00: registered as rtc0

和第五节对上了：驱动 `rtc_cmos`、硬件 `00:00`、登记成 `rtc0`。
板子上那行 `mxsfb 21c8000.lcdif: initialized` 是同一个格式。

**`hv_vmbus: registering driver hv_netvsc`**：这一行是驱动在登记自己，比设备出现得早。

**普通用户写 `/dev/kmsg` 被拒绝。** `/sys/class/mem/` 下看过它的权限是 `crw-r--r--`，只有 root 能写。

**反过来要记住一点：日志里有什么，全看驱动写没写。** 第 03 章插上 HDMI 显示器，
驱动把分辨率从 1024x600 改成了 1280x720，`dmesg` 里一行都没多。
**查现状要去 `/sys` 或者用 `ioctl` 问，不能靠日志。**

### 7.5 判据

    [ ] 往 /dev/kmsg 写一行，dmesg 里能读到
    [ ] 那一行的时间戳 == /proc/uptime（精确到 0.01 秒）
    [ ] rtc_cmos 的日志里写着 registered as rtc0，和 /sys/class/rtc/rtc0 对得上

    注错见红：普通用户写 /dev/kmsg，Permission denied。

## 八、顺带一提：和你在 ysyx、龙芯 SoC 那边做过的对照

**没做过这两个项目也不影响，跳过即可，本篇不依赖这一节。**

如果你在 ysyx 里写过 AM 的 IOE（`io_read(AM_GPU_CONFIG)` 这类）：
那是"一个编号 + 一块结构体"，和 `ioctl` 是同一个形状。
区别在于 AM 里调用方和设备代码在同一个特权级，编号用错了顶多读到错数据；
Linux 里中间隔着内核，驱动至少能用 `ENOTTY` 拒绝不认识的编号。

如果你在 NEMU 里给设备做过 `add_mmio_map`：那是"一段地址对应一个设备的回调函数"。
Linux 驱动里操作寄存器，最终也是往某个物理地址读写，只是那段地址先被内核映射好，
而且只有驱动能碰。第 03 章 `21c8000.lcdif` 里的 `21c8000`，就是你在 SoC 地址空间表里会写的那种基地址。

如果你在龙芯 SoC 上挂过外设：设备树（第 2 阶段会讲）告诉内核"`0x021c8000` 有一个 LCDIF"，
内核据此创建设备，再去找能管它的驱动。本篇第五节 `device -> ../21c8000.lcdif` 这个名字就是从那里来的。
