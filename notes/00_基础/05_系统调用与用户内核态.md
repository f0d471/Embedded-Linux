# 05 系统调用与用户态/内核态

被 01 章第 5 节用到。

## 一句话

系统调用是用户程序请内核干活的唯一入口；`printf` 不是系统调用，`write` 才勉强算
（它是对系统调用的一层薄封装）；真正跨过那道门的指令，ARM 上叫 `svc`。

## 一、先跟 ysyx 对上

    ysyx / NEMU                          Linux
    -------------------------------      --------------------------------
    你实现过 ecall 和 trap 处理           同一件事，只是 ARM 叫 svc
    riscv 的 M/S/U 特权级                 ARM 的 EL0(用户) / EL1(内核)
                                          ARMv7 里叫 User 模式 / SVC 模式
    a7 放系统调用号，a0-a5 放参数         r7 放系统调用号，r0-r5 放参数
    am 的 io_write 直接读写 MMIO          用户态碰不到 MMIO，必须走 syscall
    你自己写的 nanos-lite 处理 SYS_write  Linux 内核的 sys_write

    最大的认知差异：
      ysyx 里你的程序就是全世界，想读哪个地址读哪个地址。
      Linux 下用户程序被关在一个盒子里，任何越出盒子的操作
      （碰硬件、读文件、创建进程）都必须敲门，敲门方式就是 svc。

## 二、那道门长什么样

    用户态 (User mode)                          内核态 (SVC mode)
    ------------------------------------        ----------------------------
    你的代码                                    内核代码
    只能访问自己的虚拟地址空间                     能访问所有物理内存
    不能执行特权指令                              能配 MMU、开关中断
    不能直接读写外设寄存器                         能

              |                                          ^
              |  svc #0                                  |
              |  这一条指令做三件事：                       |
              |    1. 切到 SVC 模式（特权级提升）           |
              |    2. 保存返回地址到 lr_svc                |
              |    3. 跳到向量表里的固定入口                |
              +------------------------------------------+
                                                    |
                                                    v
                                                vector_swi
                                                    |
                                            查 sys_call_table[r7]
                                                    |
                                                    v
                                               sys_write(...)

    注意：不是"调用"了内核的函数，是**触发了一个异常**。
    CPU 硬件强制跳到一个内核预先设定好的固定地址，用户程序无法指定跳到哪。
    这就是安全边界：你只能说"我要 20 号服务"，不能说"跳到内核的 0xC0301234"。

## 三、本机实测：找到那条 svc

编译一个静态链接的 ARM 程序，反汇编找 svc：

    arm-linux-gnueabihf-gcc -static -O1 -o w_arm w.c
    arm-linux-gnueabihf-objdump -d w_arm | grep -B6 'svc'

本机实测，最干净的一个例子是 getpid：

    00016990 <__getpid>:
       16990:   push    {r7}
       16992:   mov.w   r7, #20        <-- 系统调用号 20 = __NR_getpid
       16996:   svc     0              <-- 敲门

    整个 getpid 函数就三条指令。r7 装号，svc 进内核，内核按号查表。

    通用一点的封装长这样：

    00010780 <__libc_do_syscall>:
       10780:   push    {r7, lr}
       10782:   mov     r7, ip         <-- 号是调用者通过 ip 传进来的
       10784:   svc     0

    整个静态程序里一共有 15 条 svc（本机实测）：
        arm-linux-gnueabihf-objdump -d w_arm | grep -c 'svc'
    每一条对应一类系统调用的封装。动态链接的程序里是 0 条，
    因为这些封装都在 libc.so.6 里，没链进来。

    跟 RISC-V 对照：
        r7 = 号，svc 0           <-->    a7 = 号，ecall
        返回值在 r0              <-->    返回值在 a0
        出错时 r0 是负的 errno    <-->    同上

## 四、printf 到内核的完整路径

    printf("hello, %s\n", name)
        |
        |  用户态，全在 libc 内部，没跨任何边界
        v
    vfprintf()          解析 %s，拼出最终字符串 "hello, world\n"
        |
        v
    stdout 的缓冲区（FILE 结构体里的一块 malloc 出来的内存）
        |
        |  什么时候冲刷，取决于缓冲模式：
        |    行缓冲  stdout 接终端时。遇到 \n 就冲
        |    全缓冲  stdout 接管道或文件时。攒满 4096 字节，或程序正常退出时才冲
        |    无缓冲  stderr 永远是这个。立刻走
        v
    write(1, "hello, world\n", 13)
        |
        |  ============== 用户态 / 内核态 分界线 ==============
        v
    svc #0              r7 = 4 (__NR_write), r0 = 1(fd), r1 = buf, r2 = 13(len)
        |
        v
    内核 sys_write()
        |
        v
    VFS -> tty 驱动 -> 串口 -> 你看到的字符

## 五、缓冲这件事，用 strace 看得一清二楚

`strace` 能把一个进程发出的所有系统调用打出来。它是排查"到底谁在读写什么"的第一工具。

源码故意让 printf 在前、write 在后：

    #include <unistd.h>
    #include <stdio.h>
    int main(void) {
        printf("A_printf\n");
        write(1, "B_write\n", 8);
        return 0;
    }

本机实测（stdout 接管道，所以是全缓冲）：

    $ strace -e trace=write ./w
    write(1, "B_write\n", 8)   = 8          <-- 后写的先到内核
    write(1, "A_printf\n", 9)  = 9          <-- 先写的后到内核
    +++ exited with 0 +++

    $ ./w | cat
    B_write
    A_printf

    源码顺序是 printf 在前，实际到达内核的顺序反过来了。
    因为 printf 的内容躺在用户态缓冲区里，一直等到 main return、libc 做清理
    时才冲刷；而 write 是直接进内核的，没有中间商。

**这直接解释了嵌入式调试里最气人的现象**：程序跑飞了，你加的 printf 一个字都没出来。

本机实测：

    #include <stdio.h>
    int main(void) {
        printf("before crash\n");
        *(int*)0 = 1;                /* 故意空指针写，触发 SIGSEGV */
        return 0;
    }

    $ ./c > out.txt ; cat out.txt
    （out.txt 是空的）

    printf 确实执行了，字符串确实拼好了，但它还在缓冲区里。
    进程被 SIGSEGV 干掉时不会走正常退出流程，缓冲区连同整个地址空间一起消失。

    三个解法，按可靠性排序：
        write(2, "msg\n", 4)          最可靠，直接进内核，还走 stderr
        fprintf(stderr, ...)          stderr 无缓冲
        printf(...); fflush(stdout);  手动冲刷
        setvbuf(stdout, NULL, _IONBF, 0);   开头设一次，全程无缓冲

    板子上调串口时，第三条最常用。

## 六、亲手验证

先自己想：

    问题 1  怎么知道一个程序都发了哪些系统调用？
            线索：工具名以 s 开头，"跟踪系统调用"的缩写。
    问题 2  怎么只看 write 不看别的（一个 hello world 会发几十个系统调用）？
            线索：strace 有个 -e trace= 选项。
    问题 3  怎么证明 printf 最终也是 write？
    问题 4  怎么让缓冲的差异显现出来？
            线索：同一个程序，一次直接跑，一次 | cat，比较输出顺序。

答案：

    sudo apt install -y strace          # 已经装好了

    strace ./w                          # 全部系统调用，会很长
    strace -e trace=write ./w           # 只看 write
    #            ^^^^^^^^^^^ 逗号分隔可以写多个，如 trace=write,openat
    strace -c ./w                       # -c 统计各系统调用次数和耗时
    strace -f ./w                       # -f 跟踪子进程

    注意：strace 只能跟踪本机架构的程序。ARM 的可执行文件在 x86 上跑不起来，
    自然也 strace 不了。要看 ARM 程序的系统调用，得在板子上装 strace。

[判] 判据

    [ ] strace 输出里，printf 和 write 都表现为 write(1, ...) 系统调用
    [ ] 在 ARM 反汇编里找得到 mov r7, #号 后面紧跟 svc 0 的模式
    [ ] 静态链接的 ARM 程序里 svc 条数大于 0，动态链接的是 0，说得出为什么
    [ ] 全缓冲场景下，后写的 write 反而先到达内核
    [ ] 崩溃程序的 printf 内容丢失，加 fflush 之后不丢

    注错见红：在 printf 后面加一行 fflush(stdout);，重跑第五节那个崩溃例子。
    这次 out.txt 里应该有 before crash。
    如果加了 fflush 还是空的，检查是不是编译的旧文件。
