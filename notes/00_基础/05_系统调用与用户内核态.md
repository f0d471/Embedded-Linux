## 没看懂也先记住

先分清两件事：“这次有没有请内核干活”和“数据现在停在哪一层”。
遇到日志没出现、输出顺序不对时，这两个问题就够你开始排查。

### 先带走这 5 条

1. **普通应用在用户态执行，需要内核提供服务时可以发起系统调用。** 用户态和内核态是执行权限的区别；进了系统调用仍是在为当前进程办事，不等于另起了一个进程。
2. **普通函数调用不等于系统调用。** `printf` 是 C 库函数，会先格式化并可能缓存文字；真正提交输出时才会进一步调用 `write` 等接口。
3. **源码里的库函数名不一定等于实际系统调用名。** 本篇环境中 `open` 可以由 libc 转成 `openat`；要知道到底请求了什么，用 `strace` 看。
4. **本篇 32 位 ARM Linux EABI 用 `r7` 放系统调用号，`r0` 起放参数，`svc #0` 进入内核。** 普通 C 函数调用常见的 `bl` 是另一回事；换到 x86-64，寄存器和指令规则都不同。
5. **输出要分三层：C 库缓冲区 → 内核 → 存储设备。** `fflush` 把 C 库缓存交给底层输出接口，不等于已经落盘；`write` 成功也不能直接当成断电不丢。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `printf` 写在前面，`write` 的文字却先出现 | 先查 `printf` 的文字是不是还留在用户态缓冲区 |
| 终端上有输出，重定向到文件后迟迟没有 | stdout 默认连终端通常行缓冲，连普通文件通常全缓冲；换目标可能改变刷新时机 |
| 加了换行，崩溃前的日志还是丢了 | 换行通常只触发行缓冲刷新；普通文件的全缓冲不靠换行保证输出 |
| 想确认实际写出了几次 | 看 `strace` 中的系统调用；调用了几次 `printf` 不等于调用了几次 `write` |

### 反复看这 3 组问答

- **问：`printf` 返回了，文字一定到内核了吗？答：不一定，可能还在 C 库缓冲区。**
- **问：`fflush` 成功，断电就不会丢吗？答：不能这样推；普通文件持久化还要考虑 `fsync` 等同步操作及其错误处理。**
- **问：程序异常崩溃会自动把 stdout 缓冲刷完吗？答：不能依赖它，关键日志要安排明确的刷新时机。**

想补原理时：进内核的规则看第二至四节，输出顺序看第五节，崩溃丢日志和缓冲层次看第六、七节。

## 一、你的程序被关在一个盒子里

先摆一个事实：**你的程序不能直接碰硬件。**

想往串口打一个字符，硬件层面是"往某个物理地址写一个字节"。
但你的程序里 `*(char*)0x02020040 = 'a'` 这么写，只会当场吃 SIGSEGV
（07 篇 7.4 节讲过这个信号）。

**为什么不让？** 因为一台机器上跑着几十个程序。
如果谁都能直接写硬件寄存器，任何一个程序都能：

    关掉别人的中断、改掉 MMU 的页表（于是能读所有人的内存）、
    把磁盘控制器指向别人的文件、把串口占死

所以 CPU 硬件提供了**特权级**：

> **用户态 / 内核态**：CPU 的两种运行模式。
> ARMv7 上叫 User 模式和 SVC 模式（ARMv8 叫 EL0 和 EL1）。
>
>     用户态                          内核态
>     只能访问自己的虚拟地址空间        能访问所有物理内存
>     不能执行特权指令                 能配 MMU、开关中断
>     不能直接读写外设寄存器            能

**那用户程序怎么读文件、怎么往串口打字？** 只有一条路：**求内核代劳。**

> **系统调用（system call）**：用户程序请内核干活的唯一入口。
> `open`、`read`、`write`、`mmap`、`fork` 都是系统调用。

**注意一个常见误解：`printf` 不是系统调用。** 它是 libc 里的一个普通函数，
在用户态跑，最后才调用 `write` 这个系统调用。第五节会把这两者的差别测出来。

## 二、那道门长什么样

**关键问题：用户程序怎么"进入"内核？**

不能是普通的函数调用 —— 如果用户程序能 `bl 内核里的某个地址`，
那它就能跳到内核代码的任意位置，特权级形同虚设。

**实际的做法是：触发一次异常。**

```
    用户态                                       内核态
    ------------------------------               ---------------------------
    你的代码
              |
              |  svc #0
              |  这一条指令做三件事：
              |    1. 切到 SVC 模式（特权级提升）
              |    2. 保存返回地址
              |    3. 跳到向量表里的一个固定入口
              +--------------------------------------->  vector_swi
                                                              |
                                                    查 sys_call_table[r7]
                                                              |
                                                              v
                                                         sys_write(...)
```

**跳到哪，是内核预先设定好的固定地址，用户程序无法指定。**

这就是安全边界的实现：你只能说"我要 4 号服务"，
不能说"跳到内核的 0xC0301234"。号不对，内核直接返回 `-ENOSYS`。

    ARM 上这条指令叫 svc（supervisor call，旧名 swi）
    调用号放 r7，参数放 r0-r5，返回值在 r0

下面把这条指令找出来。

## 三、实验 1：找到那条 svc

### 3.1 先自己想

`write(1, "hi\n", 3)` 这行 C 代码，最终必然要执行到一条 `svc`。
**它藏在哪？**

不在你的代码里 —— 你写的是 `write(...)`，一个函数调用。
所以它在 libc 里的 `write` 那个函数体内。

**怎么才能看到 libc 的代码？** 动态链接的话，libc 的代码在
`libc.so.6` 里，不在你的可执行文件里（04 篇第四节）。
**所以要静态链接**，把 libc 整个抄进来，才能反汇编看到。

**这本身就是一条可验证的推论：静态链接的程序里有 svc，动态链接的没有。**

### 3.2 动手

```c
#include <unistd.h>
int main(void) { write(1, "hi\n", 3); return 0; }
```

```bash
arm-linux-gnueabihf-gcc -static -O1 w.c -o w_static
arm-linux-gnueabihf-gcc         -O1 w.c -o w_dyn

arm-linux-gnueabihf-objdump -d w_static | grep -c '\bsvc\b'
arm-linux-gnueabihf-objdump -d w_dyn    | grep -c '\bsvc\b'
```

    grep -c    只数行数，不打印内容
    \b         单词边界，避免把别的含 svc 的名字算进来

### 3.3 本机实测

```
静态链接的程序里有 15 条 svc
动态链接的程序里有 0 条 svc
```

**推论验证成功。** 动态版不是不用系统调用，是那些封装都在 `libc.so.6` 里，
没被链进来 —— 04 篇第四节讲的那件事，在这里表现为"反汇编里一条都看不到"。

### 3.4 看最干净的一个例子

```bash
arm-linux-gnueabihf-objdump -d w_static | grep -B4 'svc'
```

    -B4   连同匹配行前面 4 行一起打印（Before）

本机实测，`getpid` 是最短的一个：

```
00016990 <__getpid>:
   16990:	b480      	push	{r7}
   16992:	f04f 0714 	mov.w	r7, #20        <-- 调用号 20 = __NR_getpid
   16996:	df00      	svc	0              <-- 敲门
```

**逐行读：**

    push {r7}        r7 是 callee-saved（02 篇 3.4 节），要用先存
    mov.w r7, #20    把系统调用号装进 r7
    svc 0            进内核

**整个 `getpid` 函数就三条指令。** libc 在这里几乎没做任何事，
纯粹是把"20 号"这个约定翻译出来。

再看通用一点的封装：

```
00010780 <__libc_do_syscall>:
   10780:	b580      	push	{r7, lr}
   10782:	4667      	mov	r7, ip         <-- 号由调用者通过 ip 传进来
   10784:	df00      	svc	0
   10786:	bd80      	pop	{r7, pc}
```

同样的形状：**装号、svc、返回**。

### 3.5 判据

    [ ] 静态链接的 ARM 程序里 svc 条数大于 0，动态链接的是 0
    [ ] 能说出动态版为什么是 0
    [ ] 找得到 "mov r7, #号" 紧跟 "svc 0" 的模式
    [ ] __getpid 里的号是 20

    注错见红：把 w.c 里的 write 换成一个纯计算（比如 return 1+2;），
    仍然静态链接。本机实测 svc 条数不会变成 0 —— 还是十几条。
    因为程序启动和退出本身就要用系统调用（exit_group、brk 之类），
    **和你写没写 write 无关。**
    这条提醒：数出来的条数是"libc 里带的封装数"，不是"你的程序调了几次"。

## 四、实验 2：绕过 libc，自己敲门

### 4.1 先自己想

既然系统调用的全部内容就是"把号装进寄存器、执行一条指令"，
**那能不能不用 libc，自己写这几条指令？**

能。而且这是理解"libc 只是个封装"最直接的方式。

用本机 x86-64 做（**要真的跑起来看结果**，ARM 程序在 x86 上跑不了）。
x86-64 的约定和 ARM 形状一样、寄存器名不同：

    调用号放 rax，参数依次放 rdi、rsi、rdx，指令是 syscall
    write 的调用号是 1

    提示：C 里嵌汇编用 __asm__ volatile (...)。

### 4.2 动手

`rawsys.c`：

```c
/* 绕过 libc，自己发一条系统调用 */

static long raw_write(int fd, const void *buf, unsigned long n)
{
	long ret;
	__asm__ volatile (
		"syscall"
		: "=a"(ret)      /* 输出：返回值从 rax 出来 */
		: "a"(1),        /* rax = 1 = __NR_write */
		  "D"(fd),       /* rdi = 第 1 个参数 */
		  "S"(buf),      /* rsi = 第 2 个参数 */
		  "d"(n)         /* rdx = 第 3 个参数 */
		: "rcx", "r11", "memory"    /* syscall 会破坏 rcx 和 r11 */
	);
	return ret;
}

int main(void)
{
	const char msg[] = "hello from raw syscall\n";
	raw_write(1, msg, sizeof msg - 1);
	return 0;
}
```

**约束串逐个解释**（`"a"` `"D"` `"S"` `"d"` 是 gcc 规定的寄存器代号）：

    "=a"(ret)     = 表示输出，a 表示用 rax，写回变量 ret
    "a"(1)        输入：把 1 放进 rax
    "D"(fd)       输入：把 fd 放进 rdi
    "S"(buf)      rsi        "d"(n)  rdx
    最后一行      告诉编译器"这条指令会破坏 rcx、r11 和内存"，
                  别把有用的东西留在那儿

    volatile      别优化掉它（它没有"返回值被用到"这种理由留下来）

```bash
gcc rawsys.c -o rawsys
./rawsys
strace -e trace=write ./rawsys
```

### 4.3 本机实测

```
$ ./rawsys
hello from raw syscall

$ strace -e trace=write ./rawsys 2>&1 >/dev/null
write(1, "hello from raw syscall\n", 23) = 23
```

**那句 `2>&1 >/dev/null` 不是多余的。** 不加的话，本机实测长这样：

```
write(1, "hello from raw syscall\n", 23hello from raw syscall
) = 23
```

程序自己的输出插进了 strace 那一行中间，把它断成了两行。
因为 strace 的日志走 stderr、程序的输出走 stdout，两股流写的是同一个终端。

    2>&1 >/dev/null    先把 stderr 指到当前的 stdout，再把 stdout 丢掉
                       顺序不能反：写成 >/dev/null 2>&1 就两个都丢了

**这个坑在实际调试里很常见** —— 用 strace 看一个话多的程序时，
不分流就没法读。

### 4.4 逐条读

**这个程序没有 `#include <stdio.h>`，没调用 libc 的任何输出函数，
字符照样打出来了。**

`strace` 那行证明它确实发了一次真正的 `write` 系统调用 ——
和 `printf` 最终发的是同一个。

**结论：**

    libc 的 write()      = 把参数摆好 + 一条 svc/syscall + 检查返回值设 errno
    libc 的 printf()     = 格式化 + 缓冲 + 最后调 write()

**libc 不是"更底层"，它是一层用户态的便利封装。** 真正的边界只有那条指令。

（实际写代码不要这么干 —— libc 还帮你处理了错误码、信号重启、
不同架构的差异。这个实验的价值在于看清边界在哪。）

### 4.5 判据

    [ ] rawsys 不包含 stdio.h，也能打出字符串
    [ ] strace 显示它发了 write(1, ..., 23) 且返回 23
    [ ] 能说出 rax、rdi、rsi、rdx 各装了什么

    注错见红：把 "a"(1) 改成 "a"(2)（2 号是 open，参数完全对不上）。
    本机实测：程序什么都不打印，退出码仍然是 0，没有任何报错。
    strace 里能看到内核真的按 open 的规矩解释了那三个参数：

        open(0x1, O_RDONLY|O_CREAT|O_EXCL|O_NOCTTY|O_TRUNC|...|0xe0800020, 027)
             = -1 EINVAL (Invalid argument)

    fd 1 被当成了路径指针，字符串指针被当成了 flags，长度 23 被当成了权限位。
    **号错了不会有任何提示，只是安静地做了另一件事然后失败** ——
    而返回值你没检查。这就是为什么该用 libc 就用 libc。

## 五、实验 3：printf 和 write，谁先到内核

### 5.1 先自己想

上一节说 `printf` 最终也调 `write`。**那这段代码的输出顺序是什么？**

```c
printf("A_printf\n");            /* 先写的 */
write(1, "B_write\n", 8);        /* 后写的 */
```

直觉是 A 先 B 后。**但 `printf` 中间隔着一层缓冲：**

> **标准 IO 缓冲**：`printf` 不会每次都发系统调用（那太贵了）。
> 它先把内容攒在用户态的一块内存里，攒够了或者遇到特定条件才一次性 `write`。
> 三种模式：
>
>     行缓冲   遇到 \n 就冲刷。stdout 接终端时默认是这个
>     全缓冲   攒满（通常 4096 字节）或程序正常退出时才冲。
>              stdout 接管道或文件时默认是这个
>     无缓冲   立刻走。stderr 永远是这个

**`write` 没有这一层，直接进内核。**

**所以顺序可能反过来 —— 而且取决于 stdout 接的是什么。** 三种情况都测一遍。

### 5.2 动手

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
	printf("A_printf\n");
	write(1, "B_write\n", 8);
	return 0;
}
```

```bash
gcc order.c -o order

script -qc './order' /dev/null | tr -d '\r'    # stdout 是终端
./order | cat                                   # stdout 是管道
./order > f.txt; cat f.txt                      # stdout 是文件
```

    script -qc '命令' /dev/null
        在一个伪终端里跑命令。直接 ./order 的话，输出被上层的管道接走，
        就测不到"接终端"这一档了。-q 安静，/dev/null 表示不存录像
    tr -d '\r'
        伪终端会加回车符，去掉它免得看着乱

### 5.3 本机实测

```
=== stdout 是终端（伪终端）===
A_printf
B_write

=== stdout 是管道 ===
B_write
A_printf

=== stdout 是文件 ===
B_write
A_printf
```

### 5.4 用 strace 看真实到达顺序

```bash
strace -e trace=write ./order
```

    strace          跟踪一个进程发出的所有系统调用
    -e trace=write  只看 write（一个 hello world 会发几十个系统调用）

本机实测（stdout 接管道，全缓冲）：

```
write(1, "B_write\n", 8)   = 8          <-- 后写的先到内核
write(1, "A_printf\n", 9)  = 9          <-- 先写的后到内核
+++ exited with 0 +++
```

### 5.5 逐条读

**同一个程序，三种输出目标，两种顺序。源码一个字没改。**

    接终端    A 先    行缓冲：printf 遇到 \n 立刻冲刷，赶在 write 前面
    接管道    B 先    全缓冲：printf 的内容一直躺在用户态缓冲区，
    接文件    B 先    等到 main return、libc 做退出清理时才冲刷

`strace` 那两行是决定性的：**内核实际收到的顺序就是 B 在前**。
不是显示顺序的问题，是真的后发先至。

**这条最直接的后果：调试时你看到的输出顺序不一定是代码执行顺序。**
`printf` 和 `write`（或 `fprintf(stderr,...)`）混用时尤其容易被骗。

## 六、实验 4：崩溃时 printf 的内容会丢

### 6.1 先自己想

上一节说全缓冲要等"程序正常退出"才冲刷。**那不正常退出呢？**

    printf("before crash\n");
    *(int *)0 = 1;              /* 触发 SIGSEGV */

进程被信号打死，不会走 libc 的退出清理。**缓冲区连同整个地址空间一起消失。**

**这正是嵌入式调试里最气人的现象：程序跑飞了，你加的 printf 一个字都没出来，
于是你以为它没执行到那里。**

### 6.2 动手

```bash
gcc crash.c -o crash
./crash > out.txt
stat -c %s out.txt      # 看文件大小
cat out.txt
```

### 6.3 本机实测

```
out.txt 大小: 0 字节  内容: []
```

### 6.4 逐条读

**0 字节。** `printf` 确实执行了，字符串确实拼好了，
但它还躺在用户态缓冲区里，随着进程被杀一起没了。

**注意这里有个陷阱**：如果你直接 `./crash` 在终端上看，
会看到 `before crash` 正常打印 —— 因为终端是行缓冲。
**重定向到文件才会丢。** 而板子上的日志往往正是重定向到文件或串口的。

**四个解法，按可靠性排序：**

    write(2, "msg\n", 4)                 最可靠，直接进内核，绕过所有缓冲
    fprintf(stderr, ...)                 stderr 永远无缓冲
    printf(...); fflush(stdout);         手动冲刷
    setvbuf(stdout, NULL, _IONBF, 0);    开头设一次，全程无缓冲

**板子上调串口时第四条最常用** —— 在 `main` 第一行设一次，
后面所有 `printf` 都立刻出来，代价是慢一些。

### 6.5 判据

    [ ] ./crash > out.txt 之后，out.txt 是 0 字节
    [ ] 直接在终端跑（不重定向）时，能看到 before crash
    [ ] 能说出这两种情况差别的原因

    注错见红：在 printf 后面加一行 fflush(stdout);，重新编译再跑。
    本机实测 out.txt 变成 13 字节，内容是 before crash。
    **一行 fflush 就是有和没有的差别。**

## 七、printf 到内核的完整路径

把前面几节串起来：

```
    printf("hello, %s\n", name)
        |
        |  以下全在用户态、全在 libc 内部，没跨任何边界
        v
    vfprintf()           解析 %s，拼出最终字符串 "hello, world\n"
        |
        v
    stdout 的缓冲区      FILE 结构体里一块 malloc 出来的内存
        |
        |  什么时候冲刷，取决于第五节那三种模式
        v
    write(1, "hello, world\n", 13)
        |
        |  ===== 用户态 / 内核态 分界线（第二节那道门）=====
        v
    svc #0               r7 = 4 (__NR_write)，r0 = 1 (fd)，
        |                r1 = buf，r2 = 13 (len)
        v
    内核 sys_write()
        |
        v
    VFS，按 fd 查三张表找到 f_op        <-- 06 篇第七节
        |
        v
    tty 驱动 -> 串口硬件 -> 你看到的字符
```

**这条链上，只有 `svc` 那一步跨了特权级。** 上面全是用户态的库函数，
下面全是内核代码。第四节的 `rawsys` 证明了：你可以从最上面一步跳到 `svc`，
中间那些都不是必须的。

`strace` 的常用法：

    strace ./prog                    全部系统调用，很长
    strace -e trace=write ./prog     只看某几种（逗号分隔可写多个）
    strace -c ./prog                 统计各系统调用的次数和耗时
    strace -f ./prog                 跟踪子进程

**`strace` 只能跟踪本机架构的程序。** ARM 程序在 x86 上跑不起来，
自然也 strace 不了。要看板子上程序的系统调用，得在板子上装 strace。

## 八、顺带一提：和 ysyx 的对照

**没做过 ysyx 也不影响，跳过即可。**

    ysyx / NEMU                        Linux
    ------------------------------     ------------------------------
    你实现过 ecall 和 trap 处理         同一件事，ARM 叫 svc
    RISC-V 的 M/S/U 特权级              ARM 的 User 模式 / SVC 模式
    a7 放调用号，a0-a5 放参数           r7 放调用号，r0-r5 放参数
    返回值在 a0                         返回值在 r0
    am 的 io_write 直接读写 MMIO        用户态碰不到 MMIO，必须走系统调用
    你写的 nanos-lite 处理 SYS_write    Linux 内核的 sys_write

**最大的认知差异**（也是第一节那句"关在盒子里"的具体含义）：

    ysyx 里你的程序就是全世界，想读哪个地址读哪个地址。
    Linux 下任何越出盒子的操作（碰硬件、读文件、创建进程）都必须敲门。

你在 nanos-lite 里写的那个 `do_syscall`，对应的就是本篇第二节图里的
`vector_swi` 加 `sys_call_table` 那两步。
