# 08 进程与信号

## 这一篇到底在讲什么

> **进程就是一个正在跑的程序，内核给它建了一份档案。**
> 档案里记着它的编号、谁把它启动的、打开了哪些文件、占着哪些内存。
> **信号是贴在这份档案上的一张通知条**，比如"请你退出""你刚才访问了不该访问的地址"。
> 进程下一次要继续执行自己的代码时，先看到这张条，再按条上的事处理。

### 你是从哪儿撞见它的

第 03 章上板，出厂系统开着一个图形界面程序 `mxapp2`，一直在往显存里画东西。
你照着它的启动脚本停掉它，隔 1 秒查一下它还在不在。做了两次，结果不一样：

```text
第一次:  GUI pid after stop: []
第二次:  after stop: [5512]
```

同一条停止命令，第二次停完它还在，再过几秒去查，又没了。

再早一点，基础 07 篇里程序崩了，终端上打出 `Segmentation fault`，退出码是 139。
你翻遍代码，没有哪一行写着 139。

这两件事是同一套机制在起作用。

### 进程和信号是被什么逼出来的

一块板子上同时跑着几十个程序：串口登录的 shell、网络服务、图形界面、你自己的程序。
它们轮流用同一颗 CPU、共用同一片内存。

**第一个问题：内核怎么分清它们。**
它给每个正在跑的程序发一个编号，建一份档案，记下这个程序跑到哪、用了什么资源，轮流让它们上 CPU。
**"一份档案 + 正在运行"合起来就是进程。**

**第二个问题：怎么在一个程序不知情的时候跟它说一句话。** 这种需求到处都是：

- 你按了 Ctrl+C，想让前台那个程序停下。
- 启动脚本要让图形界面退出。
- CPU 发现它访问了一个非法地址，这是硬件报的异常，得告诉它"你出事了"。

程序正埋头执行自己的指令，不会每隔一会儿去问一句"有没有人找我"。
所以内核的办法是：**先把这件事记在它的档案上，等它下一次要回到自己的代码里继续跑时，先处理这条记录。**
这条记录就是信号。

**第三个问题：信号到了之后谁说了算。**
大部分信号，程序可以事先登记一个处理函数：收到"请退出"，先保存数据、释放资源，再自己退出。
**所以"发了停止命令"和"进程真的没了"之间，隔着程序收拾东西的那段时间。**
但总得有一种程序拒绝不了的办法，不然一个卡死的程序谁也停不掉。
那就是 `SIGKILL`：内核直接动手，程序连处理函数都装不上。

**第四个问题：进程结束之后，档案什么时候销毁。**
启动它的那个进程（父进程）往往想知道：它是正常退出的，还是被杀的？
所以进程结束以后，内核先把档案里的结果留着，**等父进程来取走才销毁**。取走之前那段状态叫**僵尸**。
父进程要是先结束了，孩子的档案得有人接手，这叫**过继**。

### 放在一张图里

`killall slowstop` 发出信号后，实际按这个顺序发生：

1. 启动脚本在**用户态**调用 `kill(753, SIGTERM)`。
2. 内核找到 PID 753 的进程档案，在“待处理信号”中记下 `SIGTERM`。
3. `kill` 随即返回 0；它不等待 753 号进程退出。
4. 753 号进程下次准备返回用户态时，内核检查到这个待处理信号。
5. 处理方式由信号和进程设置决定：

   | 情况 | 内核接下来做什么 |
   |---|---|
   | `SIGTERM` 且登记了处理函数 | 先执行处理函数，结束后回到原执行位置 |
   | `SIGTERM` 且没有处理函数 | 执行默认动作：结束进程 |
   | `SIGKILL` | 不查询处理函数，直接结束进程 |

6. 进程结束后先成为僵尸；父进程用 `waitpid` 取走结果，内核才销毁档案。

"回到用户态"就是 [基础 05] 讲的那条从内核返回的路，系统调用返回、中断和异常处理完，都要走这条路。

## 结论先贴出来

下面每条都能直接背走，看不懂推导也不影响用。条数按本篇实际有几个独立结论来定，
不凑数：正文每一节至少对应下面一条，没对上就是漏了。

1. **程序是磁盘上的文件，进程是它跑起来之后内核里的一份档案。**
   同一个程序跑两次就是两个进程，两个不同的编号（PID）。`/proc/<PID>/` 就是这份档案公开出来的样子。
2. **进程名最多 15 个字符，而且不唯一。** 按名字找进程会遇到截断和重名，**要精确就用 PID**。
   本机实测 `pidof` 认全名不认截断的名字，`pgrep` 正好相反。
3. **信号是一张通知，`kill` 和 `killall` 只负责把它递到。** 递到就返回，不等对方结束。
   它们不带参数时发的是 `SIGTERM`（15 号）。
4. **收到信号怎么办由进程自己定，只有 `SIGKILL` 和 `SIGSTOP` 例外。**
   本仓实测：装了处理函数的进程，`SIGTERM` 之后又活了约 2 秒；`SIGKILL` 14 毫秒就没了，
   处理函数想装都装不上（`EINVAL`）。
5. **shell 里的 `$?` 是 shell 自己编的数。** 正常退出就是退出码；被第 N 号信号杀死，就写成 128+N。
   所以 **`exit(139)` 和段错误在 `$?` 上一模一样**，要分清得看父进程 `waitpid` 拿到的状态字。
6. **进程结束、父进程还没 `waitpid` 之前，它是僵尸**，`ps` 里状态是 `Z`。
   僵尸不再运行，只剩一份等人来取的结果。`pidof` 不把僵尸算进去。
7. **父进程先结束，子进程会被过继**：交给最近的一个声明过"我负责收养"的祖先进程，没有就交给 1 号进程。
   本机 WSL 里实测接手的是 `Relay`，不是 1 号。
8. **启停脚本的 `stop` 必须等进程真的消失才能返回。** 只发一个信号就返回的 `stop`，
   返回那一刻进程多半还在，紧接着做的事就会和它撞上。
9. **常用信号的编号在 x86 和本板用的 32 位 ARM 上相同**：2 `SIGINT`、7 `SIGBUS`、9 `SIGKILL`、
   11 `SIGSEGV`、15 `SIGTERM`、17 `SIGCHLD`、19 `SIGSTOP`（本仓用交叉编译器核对过）。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `$?` 大于 128 | 多半是被信号杀的，减去 128 就是信号编号：137 是 9 `SIGKILL`，139 是 11 `SIGSEGV`，143 是 15 `SIGTERM`。也可能是程序自己 `exit` 了这个数，要确认得用 `waitpid` |
| `killall` 之后 `pidof` 还查得到 | 信号递到了，它在收拾。轮询等它消失，等太久再 `kill -9` |
| `ps` 里某行状态是 `Z` | 僵尸：它已经结束了，是它的父进程还没来取结果 |
| `pidof` 查不到，程序明明在跑 | 名字超过 15 个字符被截断了，看 `/proc/<PID>/comm` |
| `pgrep -f` 多出来一个 PID | 可能是发起 `pgrep` 的那个 `sh -c` 自己，它的命令行里也有这个名字 |
| 程序装了处理函数，还是被立刻杀掉 | 发的是 `SIGKILL`，或者处理函数装在了别的信号上 |

想补原理时：进程是什么看第一、二节，退出码看第三节，信号怎么递、怎么处理看第四节，
僵尸和过继看第五节，启停脚本看第六节。

## 一、程序和进程不是一回事

> **程序**：磁盘上的一个可执行文件。它是静止的，放在那里不占 CPU。
> **进程**：程序被 `execve` 加载起来、正在运行的一个实例。
> 内核给每个进程维护一份档案（Linux 源码里叫 `task_struct`），记着它跑到哪、用着什么资源。
> **PID**：进程的编号。**PPID**：它的父进程的编号。

进程都是别的进程"生"出来的：父进程调 `fork` 复制出一个几乎一样的自己，
子进程再调 `execve` 把自己换成另一个程序（[基础 06] 第五节做过 `fork`）。
你在 shell 里敲 `./hold`，就是 shell 做了这两步，所以 `hold` 的父进程是这个 shell。

磁盘上只有一个 `hold` 文件，但执行两次会产生两个独立进程：

| `execve` 次数 | 内核中的进程档案 | 在 `/proc` 中看到 |
|---|---|---|
| 第一次 | PID 456、PPID 445、状态 `sleep` | `/proc/456/` |
| 第二次 | PID 457、PPID 445、状态 `sleep` | `/proc/457/` |

**一个文件，两份档案。** 下面的实验就是把这张图量出来。

## 二、实验 1：同一个程序跑两次

### 2.1 先自己想

同一个程序跑两次，内核里有几份档案？它们的编号一样吗？
怎么证明这两个进程跑的是同一个文件、而且都是当前这个 shell 启动的？

线索：

    $!        刚放到后台的那个进程的 PID
    $$        当前 shell 自己的 PID
    ps -o     自己挑要显示的列
    /proc/<PID>/exe      一个链接，指向这个进程跑的程序文件
    /proc/<PID>/status   文本文件，逐行是这份档案的各个字段

### 2.2 动手

实验目录里的 `hold.c` 只做两件事：打印自己的 PID 和父进程 PID，然后睡到有信号来。

```c
printf("pid=%d ppid=%d\n", getpid(), getppid());
fflush(stdout);
pause();		/* 睡到有信号来；默认动作会直接结束进程 */
```

```bash
cd /mnt/e/Workspace/embedded-linux/labs/00_basics/07_process_signal
gcc -Wall -o hold hold.c
./hold & P1=$!
./hold & P2=$!
sleep 0.2
echo "shell 自己的 PID: $$"
ps -o pid,ppid,stat,comm -p $$,$P1,$P2
ls -l /proc/$P1/exe /proc/$P2/exe
grep -E '^(Name|State|PPid)' /proc/$P1/status
echo "pidof hold: $(pidof hold)"
kill $P1; sleep 0.1
echo "杀掉一个之后 pidof hold: $(pidof hold)"
kill $P2; wait 2>/dev/null
```

- `./hold &`：`&` 让它在后台跑，shell 不等它结束就往下走。
- `P1=$!`：马上把它的 PID 存起来，下一个后台进程会覆盖 `$!`。
- `sleep 0.2`：给两个进程一点时间启动并打印。
- `ps -o pid,ppid,stat,comm -p ...`：`-o` 选四列：编号、父进程编号、状态、进程名；`-p` 只看这几个 PID。
- `pidof hold`：按进程名找 PID。
- `wait`：等后台进程都结束，不让它们留到脚本外面去。

### 2.3 本机实测

```text
pid=457 ppid=445
pid=456 ppid=445
shell 自己的 PID: 445
    PID    PPID STAT COMMAND
    445     331 S+   bash
    456     445 S+   hold
    457     445 S+   hold
lrwxrwxrwx 1 glorinz glorinz 0 Sep 15 11:16 /proc/456/exe -> /mnt/e/Workspace/embedded-linux/labs/00_basics/07_process_signal/hold
lrwxrwxrwx 1 glorinz glorinz 0 Sep 15 11:16 /proc/457/exe -> /mnt/e/Workspace/embedded-linux/labs/00_basics/07_process_signal/hold
Name:	hold
State:	S (sleeping)
PPid:	445
pidof hold: 457 456
杀掉一个之后 pidof hold: 457
```

### 2.4 逐行读

**头两行**：两个 `hold` 自己打印的，PID 分别是 457 和 456，父进程都是 445。
457 比 456 先打印出来，两个进程谁先抢到 CPU 不确定，**先启动的不一定先跑**。

**`shell 自己的 PID: 445`**：正好是两个 `hold` 的 PPID。

**`ps` 那三行**：`bash` 是 445，它的父进程 331 是再上一层；两个 `hold` 是 456 和 457，父进程都是 445。
`STAT` 一栏的 `S` 是睡着（在 `pause` 里等），`+` 表示它属于终端的前台这一组。

**两个 `/proc/<PID>/exe` 指向同一个文件。** 一个程序文件，两份档案。

**`/proc/456/status`** 里 `Name: hold`、`State: S (sleeping)`、`PPid: 445`，
和 `ps` 打的一致：`ps` 本来就是去读这些文件拼成表格的。

**`pidof hold` 找到两个**，杀掉一个剩一个。

> **`/proc/<PID>/`**：内核把每个进程的档案公开成一个目录，读里面的文件就是在查档案。
> 进程结束、档案销毁之后，这个目录就没了。

### 2.5 名字不是身份证

`pidof hold` 找到了两个，说明**名字不唯一**。名字还有另一个问题：长度。

```bash
cp hold a_very_long_program_name
./a_very_long_program_name & P=$!
sleep 0.2
echo "comm: $(cat /proc/$P/comm)"
echo "pidof 全名  : [$(pidof a_very_long_program_name)]"
echo "pidof 前15个: [$(pidof a_very_long_pro)]"
echo "pgrep 全名  : [$(pgrep a_very_long_program_name 2>&1)]"
echo "pgrep 前15个: [$(pgrep a_very_long_pro)]"
echo "pgrep -f    : [$(pgrep -f a_very_long_program_name)]"
echo "sh -c 里 pgrep -f: [$(sh -c 'pgrep -f a_very_long_program_name' | tr '\n' ' ')]"
kill $P; wait $P 2>/dev/null
```

- `/proc/<PID>/comm`：档案里记的进程名。
- `pgrep 名字`：另一个按名字找进程的工具。`-f` 表示拿名字去匹配**完整的命令行**，而不只是进程名。
- `2>&1`：把 `pgrep` 的报错也收进来一起打印。
- `sh -c '...'`：另起一个 `sh` 来执行引号里的命令。

**本机实测：**

```text
pid=466 ppid=445
comm: a_very_long_pro
pidof 全名  : [466]
pidof 前15个: []
pgrep 全名  : [pgrep: pattern that searches for process name longer than 15 characters will result in zero matches
Try `pgrep -f' option to match against the complete command line.]
pgrep 前15个: [466]
pgrep -f    : [466]
sh -c 里 pgrep -f: [466 476 ]
```

**逐行读：**

- **`comm` 是 `a_very_long_pro`**，15 个字符。档案里给进程名留了 16 个字节，最后一个是字符串结尾的 0。
- **`pidof` 用全名找得到，用截断的名字反而找不到**；**`pgrep` 正好反过来**，还专门打了一句提示：
  超过 15 个字符的名字一个都匹配不上，让你改用 `-f`。
- **`pgrep -f` 匹配完整命令行**，找到了。
- **放进 `sh -c` 里跑，多出来一个 476。** 那是 `sh` 自己：它的命令行是
  `sh -c pgrep -f a_very_long_program_name`，里面也有这个名字。
  写脚本时用 `pgrep -f` 去 `kill`，小心把自己杀掉。

> **结论**：**名字是给人看的，PID 才是身份证。** 启停脚本应该在启动时记下 PID（第六节就这么做），
> 而不是停止时按名字去找。

### 2.6 判据

    [ ] 同一个程序跑两次，两个 PID 不同，两个 /proc/<PID>/exe 指向同一个文件
    [ ] status 里的 PPid 等于启动它的 shell 的 $$
    [ ] pidof hold 找到 2 个，杀掉一个后剩 1 个
    [ ] comm 被截成 a_very_long_pro（15 个字符）
    [ ] pidof 认全名不认截断名；pgrep 认截断名不认全名；pgrep -f 认全名
    [ ] sh -c 里跑 pgrep -f，结果多出 1 个

    注错见红：杀掉一个 hold 后，"pidof hold 找到 2 个"那条必须变成 1 个。

## 三、实验 2：`$?` 里的 139 是谁编的

### 3.1 先自己想

基础 07 篇里段错误之后退出码是 139，`kill` 掉的进程是 143。
程序里没写这些数，它们是谁定的？

线索有两条。第一，`bash` 的手册（本机 `man bash`）EXIT STATUS 一节原话：

    When a command terminates on a fatal signal N, bash uses the value of 128+N as the exit status.

第二，父进程拿子进程的结果用的是 `waitpid`，它往一个 `int` 里填一个**状态字**，
C 库给了一组宏来拆：`WIFEXITED`（是不是正常退出）、`WEXITSTATUS`（退出码）、
`WIFSIGNALED`（是不是被信号杀的）、`WTERMSIG`（哪个信号）。

**那么问题来了：一个程序自己 `exit(139)`，和一个程序段错误，`$?` 能分开吗？`waitpid` 呢？**

### 3.2 动手

两个小程序。`child.c` 按参数选一种方式结束自己：

```c
if (!strcmp(argv[1], "exit"))
	exit(argc > 2 ? atoi(argv[2]) : 0);	/* 正常退出，退出码由参数给 */
if (!strcmp(argv[1], "segv"))
	*(volatile int *)0 = 1;			/* 往 0 地址写，CPU 报异常，内核发 SIGSEGV */
if (!strcmp(argv[1], "term"))
	raise(SIGTERM);				/* 自己给自己发 SIGTERM */
```

`waiter.c` 扮演父进程：`fork` 出子进程去跑命令行上给的程序，然后 `waitpid` 拿状态字、拆开打印：

```c
waitpid(pid, &st, 0);			/* 等它结束，内核把状态字填进 st */
printf("状态字=0x%04x  ", st);
if (WIFEXITED(st))
	printf("正常退出，退出码 %d\n", WEXITSTATUS(st));
else if (WIFSIGNALED(st))
	printf("被信号 %d (%s) 杀死\n", WTERMSIG(st), strsignal(WTERMSIG(st)));
```

```bash
gcc -Wall -o child child.c
gcc -Wall -o waiter waiter.c
./child exit 3;   echo "\$?=$?"
./child exit 139; echo "\$?=$?"
./child segv;     echo "\$?=$?"
./child term;     echo "\$?=$?"
./waiter ./child exit 3
./waiter ./child exit 139
./waiter ./child segv
./waiter ./child term
```

- `echo "\$?=$?"`：前一个 `\$?` 加了反斜杠，原样打出 `$?` 三个字；后一个 `$?` 才是真正的值。

### 3.3 本机实测

```text
$?=3
$?=139
bash: line 38:   491 Segmentation fault         ./child segv
$?=139
Terminated                 ./child term
$?=143
状态字=0x0300  正常退出，退出码 3
状态字=0x8b00  正常退出，退出码 139
状态字=0x000b  被信号 11 (Segmentation fault) 杀死
状态字=0x000f  被信号 15 (Terminated) 杀死
```

### 3.4 逐行读

**`bash: line 38:   491 Segmentation fault`**：这一行不是程序打的，是 `bash` 发现子进程 491 死于段错误，
替你报了一句。`line 38` 是这条命令在脚本里的行号，你的行号不一样。直接在终端里敲只会看到 `Segmentation fault`。
**程序自己没来得及说任何话**，它在那条非法写入的指令上就被内核结束了。

**`$?` 那四行**：3、139、139、143。**第二行和第三行一模一样**，只看 `$?`，
你分不出"程序自己 `exit(139)`"和"程序段错误"。

**`waiter` 那四行，状态字是不一样的**：

Linux 等待状态字的低 16 位这样解释：

| 位 | 含义 |
|---|---|
| 15～8 | 正常退出时的退出码 |
| 7 | `c`：是否留下 core 文件 |
| 6～0 | 导致进程结束的信号编号；正常退出时为 0 |

| 结束方式 | 状态字 | 解读 | 结论 |
|---|---|---|---|
| `exit(3)` | `0x0300` | 高 8 位为 3，低 7 位为 0 | 正常退出 |
| `exit(139)` | `0x8b00` | 高 8 位为 139，低 7 位为 0 | 正常退出 |
| 段错误 | `0x000b` | 低 7 位为 11 | 被 11 号信号杀死 |
| `SIGTERM` | `0x000f` | 低 7 位为 15 | 被 15 号信号杀死 |

本机 `ulimit -c` 为 0，不生成 core 文件，所以这些例子的 `c` 都是 0。

**`0x8b00` 和 `0x000b` 完全是两个数。** 内核交给父进程的信息是全的，
**是 `bash` 为了把它塞进一个 0-255 的 `$?`，才把"被 N 号信号杀死"压成了 128+N。**

> **退出码**：程序调 `exit(n)` 或 `main` 返回 `n` 时交出的那个数，只有低 8 位有效，所以是 0-255。
> **状态字**：`waitpid` 填的 `int`。它同时能表达"正常退出 + 退出码"和"被哪个信号杀死"。

### 3.5 注错见红

把 `waiter` 改成只取退出码，不管是不是被信号杀的（`-DBUG_ONLY_EXITSTATUS`）：

```bash
gcc -Wall -DBUG_ONLY_EXITSTATUS -o waiter_bug waiter.c
./waiter_bug ./child exit 139
./waiter_bug ./child segv
```

```text
状态字=0x8b00  退出码 139
状态字=0x000b  退出码 0
```

**段错误被报成了"退出码 0"**，看起来像是成功了。
写守护进程、测试框架时，**只看退出码不看信号，崩溃就会被当成成功**。

### 3.6 判据

    [ ] exit(3) 之后 $? 是 3；exit(139) 之后 $? 是 139
    [ ] 段错误之后 $? 是 139；被 SIGTERM 杀死之后 $? 是 143
    [ ] waiter：exit(139) 的状态字 0x8b00、认成正常退出
    [ ] waiter：段错误的状态字 0x000b、认成被信号 11 杀死

    注错见红：只取退出码时，段错误被报成"退出码 0"。

## 四、实验 3：kill 只是递了一张通知

### 4.1 先自己想

> **信号（signal）**：内核记在进程档案上的一个编号，表示发生了某件事，要这个进程处理。
> **默认动作**：进程没有专门处理这个信号时，内核替它做的事，多数是直接结束进程。
> **处理函数（handler）**：进程事先用 `sigaction` 登记的一个函数，信号来了就先执行它。

常用的几个。编号取自本机 `kill -l`，并用交叉编译器核对过 ARM 头文件里是同样的数；
默认动作取自本机 `man 7 signal`：

| 编号 | 名字 | 典型的来源 | 默认动作 | 能不能装处理函数 |
|---|---|---|---|---|
| 2 | `SIGINT` | 在终端里按 Ctrl+C | 结束进程 | 能 |
| 7 | `SIGBUS` | 访问 `mmap` 超出文件的部分（[基础 07] 第七节） | 结束进程并留 core 文件 | 能 |
| 9 | `SIGKILL` | `kill -9` | 结束进程 | **不能** |
| 11 | `SIGSEGV` | 访问没有映射的地址 | 结束进程并留 core 文件 | 能 |
| 15 | `SIGTERM` | `kill`、`killall` 不带参数时发的 | 结束进程 | 能 |
| 17 | `SIGCHLD` | 子进程结束时，内核发给父进程 | 忽略 | 能 |
| 19 | `SIGSTOP` | `kill -STOP` | 暂停进程 | **不能** |

`killall` 的手册（本机 `man killall`）写着不指定信号时发 `SIGTERM`。第 03 章那个出厂启动脚本的 `stop()` 就是一句 `killall mxapp2`。

**问题是：`killall` 返回的时候，进程结束了没有？**
如果进程装了 `SIGTERM` 的处理函数、要花 2 秒收拾，`killall` 会等这 2 秒吗？

线索：量时间。发信号前记一个时间，然后反复查 `/proc/<PID>` 还在不在，消失的那一刻再记一个时间。

### 4.2 动手

`slowstop.c` 模拟一个 GUI 程序：收到 `SIGTERM` 先花 2 秒收拾，再退出。

```c
static void on_term(int sig)
{
	(void)sig;
	g_stop = 1;		/* 处理函数里只记一笔，真正的活回到主循环再干 */
}
...
	if (sigaction(SIGKILL, &sa, NULL) < 0)			/* 试着给 SIGKILL 装处理函数 */
		printf("给 SIGKILL 装处理函数: 失败 (%s)\n", strerror(errno));
#ifndef NO_HANDLER
	sigaction(SIGTERM, &sa, NULL);				/* 给 SIGTERM 装处理函数 */
#endif
	while (!g_stop)
		sleep(1);	/* 信号一来 sleep 会提前返回，回到循环检查标志 */
	printf("收到 SIGTERM，开始收拾（2 秒）\n");
	sleep(2);
	printf("收拾完，退出\n");
```

- **处理函数里只设一个标志**：处理函数可能在主程序执行到任何一条指令时插进来，
  在里面做复杂的事（比如 `printf`）不安全。通行的写法是只记一笔，回到主循环再处理。
- `volatile sig_atomic_t`：告诉编译器这个变量会在"看不见的地方"被改，每次都要老老实实去内存里读。

一个量时间的函数，对同一个程序分别发 `SIGTERM`、`SIGKILL`，再拿不装处理函数的版本发 `SIGTERM`：

```bash
gcc -Wall -o slowstop slowstop.c
gcc -Wall -DNO_HANDLER -o slowstop_nh slowstop.c
measure() {
	./$1 > .$1.log & P=$!
	sleep 0.5
	t0=$(date +%s%N)
	kill -$2 $P
	n=0
	while [ -e /proc/$P ] && [ $n -lt 1000 ]; do sleep 0.01; n=$((n + 1)); done
	t1=$(date +%s%N)
	wait $P; rc=$?
	echo "$1 发 SIG$2 后又活了 $(( (t1 - t0) / 1000000 )) ms, 退出码 $rc"
	sed 's/^/    | /' .$1.log
}
measure slowstop TERM
measure slowstop KILL
measure slowstop_nh TERM
```

- `date +%s%N`：从 1970 年起的秒数接上纳秒，拼成一个很大的整数，两次相减除以 1000000 就是毫秒。
- `kill -$2 $P`：`kill -TERM 1234`、`kill -KILL 1234`，信号名前面加减号。
- `while [ -e /proc/$P ]`：档案目录还在就继续等，每 10 毫秒看一次，最多等 10 秒。
- `wait $P; rc=$?`：取回这个子进程的结果。
- `sed 's/^/    | /'`：在程序自己打的日志每行前面加个竖线，和测量结果区分开。

### 4.3 本机实测

```text
slowstop 发 SIGTERM 后又活了 2008 ms, 退出码 0
    | 给 SIGKILL 装处理函数: 失败 (Invalid argument)
    | pid=522 开始干活
    | 收到 SIGTERM，开始收拾（2 秒）
    | 收拾完，退出
bash: line 64:   696 Killed                     ./$1 > .$1.log
slowstop 发 SIGKILL 后又活了 14 ms, 退出码 137
    | 给 SIGKILL 装处理函数: 失败 (Invalid argument)
    | pid=696 开始干活
slowstop_nh 发 SIGTERM 后又活了 14 ms, 退出码 143
    | 给 SIGKILL 装处理函数: 失败 (Invalid argument)
    | pid=702 开始干活
```

### 4.4 逐行读，三种下场

**装了处理函数 + `SIGTERM`：又活了 2008 毫秒，退出码 0。**
日志里"收到 SIGTERM，开始收拾""收拾完，退出"都打出来了。
**`kill` 那一行在发完信号的瞬间就返回了**，后面这 2 秒是进程自己在收拾。
退出码是 0，因为它最后是自己从 `main` 返回的，**在 `$?` 看来这是一次正常退出**。

**`SIGKILL`：14 毫秒，退出码 137 = 128 + 9。**
日志里没有"收到"那一行：处理函数根本没机会执行。`bash` 替它报了一句 `Killed`。
14 毫秒里大部分是测量循环自己的 10 毫秒轮询间隔。

**不装处理函数 + `SIGTERM`：同样 14 毫秒，退出码 143 = 128 + 15。**
**同一个信号，装没装处理函数，下场完全不同。**

**每份日志第一行**：`给 SIGKILL 装处理函数: 失败 (Invalid argument)`。
内核直接拒绝了，`SIGKILL` 就是设计来让程序没法拒绝的。

**回到第 03 章**：出厂启动脚本的 `stop()` 就是 `killall mxapp2`，发的是 `SIGTERM`。
`mxapp2` 是个 Qt 图形程序，完全可能在收到信号后先收拾一阵。所以停完 1 秒去查，有时它还在。
**这不是停止失败，是停止还没完成。**

### 4.5 判据

    [ ] 装了处理函数：SIGTERM 之后又活了 1800 ms 以上，退出码 0，日志里有"收拾完，退出"
    [ ] 给 SIGKILL 装处理函数失败，Invalid argument
    [ ] SIGKILL：200 ms 内消失，退出码 137
    [ ] 7 个常用信号的编号，x86 和 ARM 头文件里相同

    注错见红：去掉处理函数（-DNO_HANDLER），SIGTERM 之后 200 ms 内消失，退出码 143。

## 五、实验 4：僵尸与孤儿

### 5.1 先自己想

上一节 `measure` 里有一句 `wait $P`。如果父进程**一直不 `wait`**，结束了的子进程会怎样？
反过来，**父进程先结束**，子进程还在跑，它的 PPID 会变成什么？

### 5.2 动手

`zombie.c`：子进程立刻结束；父进程先睡 3 秒才 `waitpid`，再睡 3 秒才退出。
`orphan.c`：父进程 0.2 秒后结束；子进程在父进程结束前后各查一次自己的父进程是谁。

```c
/* zombie.c */
if (c == 0)
	_exit(7);	/* 子进程：什么都不干，直接结束 */
sleep(3);		/* 这 3 秒里子进程是僵尸 */
waitpid(c, NULL, 0);

/* orphan.c */
if (c == 0) {
	show_parent("父进程退出前");	/* 打印 getppid() 和 /proc/<ppid>/comm 里的名字 */
	sleep(1);
	show_parent("父进程退出后");
	_exit(0);
}
usleep(200000);				/* 父进程 0.2 秒后就返回了 */
```

`zombie` 再编一个注错版 `-DREAP_NOW`：父进程不睡，马上 `waitpid`。

```bash
gcc -Wall -o zombie zombie.c
gcc -Wall -DREAP_NOW -o zombie_reap zombie.c
for z in zombie zombie_reap; do
	echo "-- $z"
	./$z & P=$!
	sleep 1; echo "1 秒:"; ps -o pid,ppid,stat,comm --ppid $P; echo "pidof $z: [$(pidof $z)]"
	sleep 3; echo "4 秒:"; ps -o pid,ppid,stat,comm --ppid $P
	wait $P
done
gcc -Wall -o orphan orphan.c
./orphan; sleep 1.5
echo "1 号进程: $(ps -p 1 -o comm=)"
```

- `ps --ppid $P`：列出父进程是 `$P` 的所有进程，也就是它的孩子。
- `ps -p 1 -o comm=`：1 号进程叫什么，`comm=` 表示这一列不要表头。

### 5.3 本机实测

```text
-- zombie
父 718  子 720（子进程已经结束）
1 秒:
    PID    PPID STAT COMMAND
    720     718 Z+   zombie
pidof zombie: [718]
父进程 waitpid 完成
4 秒:
    PID    PPID STAT COMMAND
-- zombie_reap
父 728  子 730（子进程已经结束）
父进程 waitpid 完成
1 秒:
    PID    PPID STAT COMMAND
pidof zombie_reap: [728]
4 秒:
    PID    PPID STAT COMMAND
子 747 父进程退出前: 父进程 746 (orphan)
父 746 退出
子 747 父进程退出后: 父进程 327 (Relay(331))
1 号进程: systemd
```

### 5.4 逐行读

**`zombie` 第 1 秒**：子进程 720 早就结束了，`ps` 还能看到它，状态是 **`Z`**。

> **僵尸（zombie）**：进程已经结束，所有内存、打开的文件都还掉了，
> 只剩档案里那份"它是怎么结束的"，等父进程 `waitpid` 来取。取走之前它就是 `Z`。

**`pidof zombie` 只找到 718（父进程）**，不算 720。**`ps` 看得到的，`pidof` 不一定算。**

**第 4 秒**：父进程已经 `waitpid` 过了，`ps --ppid` 下面空了，档案销毁。

**`zombie_reap`（注错版）**：父进程马上 `waitpid`，第 1 秒时就已经一个孩子都没有了。
**僵尸存在多久，完全取决于父进程什么时候来取。**
父进程要是永远不取、自己又不退出，僵尸就一直挂在那里，每个都占着一个 PID。

**`orphan`**：父进程 746 退出前，子进程 747 的父进程是 746；
退出后，**父进程变成了 327，名字叫 `Relay(331)`**，而 1 号进程是 `systemd`。

> **孤儿与过继**：父进程先结束，子进程就成了孤儿。Linux 把它过继给
> **最近的一个还活着、并且声明过自己负责收养的祖先**（这种祖先叫 subreaper）；
> 一路往上都没有，就交给 1 号进程。新的父进程负责替它 `waitpid`，所以孤儿不会变成永久的僵尸。

出处是本机 `man 2const PR_SET_CHILD_SUBREAPER`，原话：

```text
A subreaper fulfills the role of init(1) for its descendant processes.  When a process becomes  orphaned  (i.e.,
its immediate parent terminates), then that process will be reparented to the nearest still living ancestor sub‐
reaper.
```

同一页还写着 `systemd` 这类 init 框架就会用这个机制。

**本机接手的是 `Relay`，不是 1 号。** 按上面这条规则，`Relay` 就是 WSL 在这个会话里安排的收养者。
所以"孤儿一定归 1 号"这句话在 WSL 里不成立。换到板子上，收养者是谁要实测，不能照搬这个结论。

### 5.5 判据

    [ ] zombie 第 1 秒：子进程状态是 Z；pidof zombie 只找到父进程
    [ ] zombie 第 4 秒：父进程 waitpid 之后，子进程消失
    [ ] orphan：父进程退出前 ppid 是 orphan，退出后换成另一个进程
    [ ] 本机接手的是 Relay，1 号进程是 systemd

    注错见红：父进程马上 waitpid（-DREAP_NOW），第 1 秒就没有僵尸。

## 六、实验 5：启停脚本的 stop 要等

### 6.1 先自己想

**板子开机以后，那个 GUI 是谁启动的？**

> **1 号进程（init）**：内核启动完成后运行的第一个用户态进程，其余进程都是它的子孙。
> 它负责按配置把系统服务一个个拉起来。本机 WSL 里 1 号是 `systemd`。

第 03 章板上看到的是另一种做法：`/etc/init.d/` 目录下一批 `S` 加两位数字开头的脚本，
每个脚本接受 `start`、`stop` 参数。那个 GUI 的脚本 `S99myirhmi2` 里关键的几行（板上）：

```sh
/usr/bin/mxapp2 --plugin tslib:$TSLIB_TSDEVICE &
...
stop() {
	killall mxapp2
}
```

`start` 用 `&` 把 GUI 放到后台，脚本自己马上结束，GUI 就成了孤儿，被过继出去（第五节）。
`stop` 只有一句 `killall`。

**根据第四节，这个 `stop` 返回的时候，GUI 结束了吗？
要是紧接着就去写显存，会发生什么？应该怎么写一个靠得住的 `stop`？**

### 6.2 动手

`demo_service.sh` 仿照出厂脚本，管理 `slowstop`，提供两种 stop：

```sh
start() {
	"$DIR/slowstop" > "$DIR/.slowstop.log" 2>&1 &	# & 放到后台，脚本自己马上结束
	echo $! > "$PIDFILE"				# 启动时就把 PID 记到文件里
	echo "start: pid=$(cat "$PIDFILE")"
}

stop_naive() {
	killall slowstop				# 照出厂脚本：只发了 SIGTERM
	echo "stop-naive 返回时: pidof=[$(pidof slowstop)]"
}

stop() {
	pid=$(cat "$PIDFILE" 2>/dev/null) || { echo "stop: 没有 pid 文件"; return 1; }
	kill "$pid" 2>/dev/null
	n=0
	while [ -d /proc/"$pid" ] && [ "$n" -lt 50 ]; do	# 最多等 50 x 0.1 秒
		sleep 0.1
		n=$((n + 1))
	done
	if [ -d /proc/"$pid" ]; then
		kill -9 "$pid"				# 5 秒还没退，才动用 SIGKILL
		echo "stop: 5 秒没退出，发了 SIGKILL"
	fi
	rm -f "$PIDFILE"
	echo "stop 返回时: 等了约 $((n * 100)) ms, pidof=[$(pidof slowstop)]"
}
```

- **PID 文件**：启动时把 `$!` 写进文件，停止时按 PID 找，不按名字找（第 2.5 节）。
- **先 `SIGTERM`、等、超时再 `SIGKILL`**：给程序收拾的机会，但不让一个卡死的程序把 `stop` 永远拖住。

```bash
sh demo_service.sh start
sleep 0.5
SP=$(cat .slowstop.pid)
PP=$(ps -o ppid= -p $SP | tr -d ' ')
echo "slowstop pid=$SP ppid=$PP ($(ps -o comm= -p $PP))"
sh demo_service.sh stop-naive
sleep 3
echo "3 秒后: pidof=[$(pidof slowstop)]"
sh demo_service.sh start
sleep 0.5
sh demo_service.sh stop
sed 's/^/    | /' .slowstop.log
```

### 6.3 本机实测

```text
start: pid=753
slowstop pid=753 ppid=327 (Relay(331))
stop-naive 返回时: pidof=[753]
3 秒后: pidof=[]
start: pid=771
stop 返回时: 等了约 2000 ms, pidof=[]
    | 给 SIGKILL 装处理函数: 失败 (Invalid argument)
    | pid=771 开始干活
    | 收到 SIGTERM，开始收拾（2 秒）
    | 收拾完，退出
```

### 6.4 逐行读

**`slowstop` 的 PPID 是 327（`Relay`）**：启动它的 `sh demo_service.sh start` 早就结束了，
它被过继了，和第五节的孤儿一样。出厂 GUI 也是这样被启动脚本放出去的。

**`stop-naive 返回时: pidof=[753]`：停止命令已经返回，进程还在。**
3 秒后再查才没了。**这就是第 03 章"停完 1 秒还在"的现场复现。**

**等待型 `stop`：等了约 2000 毫秒才返回，返回时 `pidof` 已经是空的**，
日志里"收拾完，退出"也打出来了。**`stop` 返回，就意味着进程确实没了**，后面的步骤可以放心做。

### 6.5 判据

    [ ] slowstop 的 PPID 不是启动它的 sh（已被过继）
    [ ] stop-naive 返回时 pidof 非空，3 秒后为空
    [ ] 等待型 stop 返回时 pidof 为空，等了 1800 ms 以上

    注错见红：stop-naive 就是"去掉等待循环"的注错版，返回时进程还在。

**所以第 03 章做显示实验前停 GUI，要么用等待型的写法，要么停完之后轮询 `pidof mxapp2` 为空再往下走。**

## 七、顺带一提：和 ysyx 的对照

**没做过 ysyx 也不影响，跳过即可，本篇不依赖这一节。**

如果你在 nanos-lite 里写过 PCB 和上下文切换：那个 `PCB` 结构体就是本篇说的"档案"的缩小版，
`schedule()` 轮流挑一个 PCB 恢复上下文，就是"轮流让它们上 CPU"。

差别有两处：

    nanos-lite           一个固定大小的 PCB 数组，没有父子关系，没有信号
    Linux                task_struct 按需创建，每个都记着父进程；
                         信号记在档案上，在"从内核返回用户态"那一步检查

后一句你在 NPC 里做异常返回（`mret`）时就能对上：Linux 正是在准备 `mret`/`eret` 之前的那段内核代码里，
看一眼这个进程有没有待处理的信号，有就先把返回地址改到处理函数上。
