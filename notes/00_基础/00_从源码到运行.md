# 00 从源码到运行：四个程序和它们的交接

## 这一篇到底在讲什么

> **CPU 只会执行一长串数字，而你写的是字。把字翻成数字、把散落的零件拼成一个
> 整体、再把它搬进内存跑起来——"编译一下"这四个字底下，真正发生的就是这些。**

### 你是从哪儿撞见它的

你按教程写完 `hello.c`，想让它在板子上跑，所以"得先编译一下"。
敲一条 `gcc hello.c -o hello`，出来一个文件，能跑，事情结束。

对绝大多数人来说，编译就是这么个东西：**一个动词、一条命令、一个黑盒。**
它之所以出现在你的世界里，只是因为"代码写完了"和"东西能跑了"之间还差一步。
报错了就把那行英文贴进搜索框，搜到的答案往往是"在后面加个 `-lm` 试试"，
加上确实好了，但你并不知道为什么好了。

机器那边根本没有"编译"这回事。它只有一串更小的动作，每个动作都有一条
非它不可的理由。这一篇干的事，就是把这个黑盒拆成四个能叫出名字的程序，
让你下次看到报错，能一眼知道是**第几步**在喊、该去改什么。

### 为什么是四个程序，不是一个

如果全世界只有你一个人写程序、而且只写一个文件，那一步确实就够了：
读进 `hello.c`，直接吐出能跑的东西。有两件事让这条近路走不通。

**一是你从没打算自己写全部代码。** 你的第一个程序就调了 `printf`，
那是别人几十年前写好的，早就翻译成机器码放在那儿了。你要的是**用**它，
不是把它重新翻译一遍。

**二是你自己的代码也不止一个文件。** 一个项目十几个 `.c`，
要是改一行就得把所有文件从头翻一遍，大项目一次要等几个小时。

所以这条路被切成了两段，而且是**不得不切**：

    第一段  一个 .c 单独翻译成一个 .o，互相不用管，改了哪个只重做哪个
    第二段  把所有 .o、连同别人写好的库，拼成一个完整的程序

切开是要付代价的，而这个代价正是本篇后面全部内容的来源：
**翻译 `main.c` 的时候，编译器不知道 `printf` 的代码在哪，
也不知道自己这段代码将来会被摆在内存的哪个地址。**
它只能先空着，并留下一张条子写着"这里等人来填"。

**填条子的那个人就是链接器。** 链接器不是技术上凭空冒出来的——
它是"分开编译"这个决定必然要还的账。全篇的名词都从这一句长出来：
得有个单位让它知道按什么拼（section），拼完地址全变了得挨个改回去（重定位），
条子上的名字谁也没提供就得报错（undefined reference）。

填完条子，你拿到一个躺在磁盘上的文件。**它还不是"正在运行的程序"。**
还得有人把它搬进内存、摆好位置、跳到第一条指令上去——那个人叫**加载器**，
在 Linux 上它是内核的一部分，在裸板上就是你自己写的那段启动代码。

### 这四个人具体在干什么

    程序        吃什么        吐什么       它的本质
    预处理器    .c            .i           文本替换。#include 就是把那个文件整个
                                           贴进来，#define 就是查找替换，没别的
    编译器      .i            .s           翻译官。把 C 翻成某一种 CPU 的汇编。
                                           "翻给哪种 CPU"就在这一步定死
    汇编器      .s            .o           誊写员。汇编和机器码几乎一一对应，
                                           它只是把助记符换成二进制
    链接器      一堆 .o + 库   可执行文件    装配工。把零件拼成整机，
                                           顺手把所有空条子逐个填上
    加载器      可执行文件     运行中的进程  搬运工。它不属于 gcc，
                                           是你敲下回车那一刻才登场的

`gcc` 自己一行代码都不翻译，**它是这条流水线上的工头**：按顺序把这几个程序叫来，
把上一个的输出交给下一个。`-E` `-S` `-c` 三个选项的作用就是让工头在第一、二、
三步之后停手，把中间产物留在原地给你看。第二节就动手把它们一个个抓出来。

## 结论先贴出来

下面每条都能直接背走，看不懂推导也不影响用。条数按本篇实际有几个独立结论来定，
不凑数：正文每一节至少对应下面一条，没对上就是漏了。

1. **符号就是留给链接器看的名字。** `nm` 里 `T` 是"我这儿有"，`U` 是"我用了但
   我没有"。**`U` 本身不是错**——链接全部结束后它还是 `U`，才叫 `undefined reference`。
2. **声明让编译器放行，定义让链接器放行。** 头文件里那行声明只是告诉编译器
   "这函数长这样，你照着生成调用指令"，它不提供任何实现。
   **这是"编译明明过了却链接失败"的唯一来源。**
3. **`.o` 里已经是机器码，但地址是假的、还欠着别人的东西，所以它不能单独运行。**
   反汇编里看到调用指令的目标是 `0`，那就是还没填的空条子。
4. **section 是链接器搬运的箱子。** `.text` 装代码、`.rodata` 装只读数据、
   `.data` 装有非零初值的全局/静态变量、`.bss` 装初值为零的那些。
   链接器拼东西的单位不是文件，是这些同名的箱子。
5. **拼完之后地址全变了，所以要照 `.o` 里留的条子把地址逐个改对，这叫重定位。**
6. **`.bss` 只记大小，不在文件里存那一堆零。** 所以一个大零数组能让程序吃掉很多
   内存，文件却几乎没变大。
7. **加载器不是"把文件读进内存"，是把文件映射进一个新进程的地址空间。**
   同一个程序每次跑起来地址都不一样，那是 ASLR（地址随机化），不是 bug。
8. **交叉编译就是让这四步全部对准另一种 CPU。** 编得出来和本机跑得了是两回事：
   在 x86 上执行 ARM 程序会报 `Exec format error`。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| `gcc -E` / `-S` / `-c` | 分别停在预处理文本、汇编文本、目标文件；大小写不能换 |
| `undefined reference to add` | 队伍走到第四步才没人提供 `add`；先查定义在不在、那个 `.o`/库有没有参与链接，再查顺序和名字 |
| `nm main.o` 里 `U add` | 正常，`main.c` 用了它但没定义它；这时候还没到该有的时候 |
| 改了 `add.c`，结果没变 | 只重编了 `.o` 没重新链接，或者跑的还是旧产物 |
| 反汇编里 `bl` 的目标地址是 0 或者指向自己 | 那是没填的占位；要看真地址得看链接后的产物 |

想补原理时：四个程序和中间产物看第二节，链接和重定位看第三节，
section 看第四节，加载和 ASLR 看第五节。

## 一、先看一个你以为你懂的事实

你敲过无数次：

    gcc hello.c -o hello

一条命令，一个输入，一个输出。看上去 gcc 就是"那个把 C 变成可执行文件的程序"。

**这是错的。gcc 自己一行代码都不翻译。** 它是个调度员，按顺序叫了四个程序干活。

先把这四个程序的名字摆出来，后面每一个都会亲手见到：

    你写的 hello.c
        |
        | 1. 预处理器  cpp        把 #include #define 展开成纯 C
        v
      纯 C 文本
        |
        | 2. 编译器    cc1        C -> 汇编语言（人能读的文本）
        v
      汇编文本 .s
        |
        | 3. 汇编器    as         汇编 -> 机器码（二进制，但还不能跑）
        v
      目标文件 .o
        |
        | 4. 链接器    ld         多个 .o 拼成一个能跑的文件
        v
      可执行文件 hello
        |
        | 5. 加载器（在内核里）    把文件搬进内存，让 CPU 开始执行
        v
      跑起来的进程

第 1 到 4 步发生在**你的开发机上，编译的时候**。
第 5 步发生在**目标机器上，运行的时候**。这条界线后面会反复用到。

> **为什么要分这么多步？** 一句话：为了让"改一个文件不用重编整个工程"。
> 如果 C 直接变成可执行文件，改一行就要把所有代码重新翻译一遍。
> 拆成 .o 之后，改哪个文件只重编哪个，最后拼一下就行。
> 这条也是 Makefile 存在的全部理由。

下面把这四个程序一个一个抓出来看。

## 二、实验 1：把四个程序抓个现行

### 2.1 先自己想

gcc 说它叫了别的程序，凭什么信？

线索：一个程序调用另一个程序，总得说出被调者的路径和参数。
gcc 有个选项能让它把这些"内部调用"全打印出来。

    提示：这个选项是 -v，v 是 verbose（啰嗦）。
          很多命令行工具都有它，作用一律是"把你平时看不到的过程打出来"。

### 2.2 动手

先建实验目录和两个源文件。这里故意分成两个文件，
原因到第三节就明白了（一个文件是看不出链接器在干什么的）。

    mkdir -p labs/00_basics/01_link_and_load
    cd labs/00_basics/01_link_and_load

`add.c`：

```c
int add(int a, int b)
{
	return a + b;
}
```

`main.c`：

```c
int add(int a, int b);      /* 只声明，不定义。函数体在 add.c 里 */

int g_init = 1;             /* 有初值的全局变量 */
int g_bss;                  /* 没初值的全局变量 */

int main(void)
{
	return add(g_init, 2) + g_bss;
}
```

现在让 gcc 交代它调了谁：

    arm-linux-gnueabihf-gcc -c main.c -o main.o -v

    参数逐个解释：
      -c          只做到"生成 .o"为止，不要链接。为什么加它？
                  因为我们现在只想看前三步，链接留到第三节
      -o main.o   输出文件名
      -v          打印内部调用

输出很长，只挑两行看（本机实测，路径已略去无关部分）：

    /usr/libexec/gcc-cross/arm-linux-gnueabihf/15/cc1 -quiet -v ... main.c
        -mfloat-abi=hard -mthumb -march=armv7-a+fp ... -o /tmp/ccOc0SoU.s

    /usr/lib/gcc-cross/.../arm-linux-gnueabihf/bin/as -v -march=armv7-a+fp
        -mfloat-abi=hard -meabi=5 -o main.o /tmp/ccOc0SoU.s

### 2.3 怎么读这两行

一行一行拆：

    cc1  ... main.c ... -o /tmp/ccOc0SoU.s
    ^^^                    ^^^^^^^^^^^^^^^
    真正的编译器            输出是个 .s 文件，扔在 /tmp 里

    as   ... /tmp/ccOc0SoU.s -o main.o
    ^^       ^^^^^^^^^^^^^^^    ^^^^^^
    汇编器    吃的正是上一行吐的  吐出 .o

**结论一：gcc 确实是调度员。** 你以为的"gcc 编译"，实际是 cc1 编译、as 汇编，
gcc 只负责把临时文件在两者之间传递。

**结论二：中间产物默认被扔在 /tmp 并删掉了**，所以你平时看不见。
`ccOc0SoU` 是随机名，你跑出来一定不一样，这不算不一致。

### 2.4 把中间产物留下来

既然中间有 .s，我们就要求 gcc 停在那一步：

    arm-linux-gnueabihf-gcc -E main.c -o main.i    # 停在预处理后
    arm-linux-gnueabihf-gcc -S main.c -o main.s    # 停在编译后（生成汇编）
    arm-linux-gnueabihf-gcc -c main.c -o main.o    # 停在汇编后（生成 .o）
    记法：E-S-c 三个开关是"越来越往后停"。
          -E = stop after prEprocessing
          -S = stop after compilation, output aSsembly
          -c = compile only, 不链接

看行数（本机实测）：

    $ wc -l main.c main.i main.s
       9 main.c
      15 main.i
      63 main.s

`main.i` 比 `main.c` 多 6 行，是因为预处理器插了行号标记（`# 1 "main.c"` 这类）。
你的 `main.c` 没有 `#include`，所以几乎没变。

**想看预处理真正的威力，在文件最前面加一行 `#include <stdio.h>` 再预处理一次：**

    $ printf '#include <stdio.h>\n' > t.c && cat main.c >> t.c
    $ arm-linux-gnueabihf-gcc -E t.c -o t.i && wc -l t.c t.i
      10 t.c
     842 t.i

10 行进去，842 行出来。多出来的 832 行全是 stdio.h 以及它自己 include 的
那一串头文件被摊平后的内容 —— 你一个字符都没写，但编译器要处理它们。
这就是"少 include 一点"能实打实缩短编译时间的原因。

### 2.5 读一眼汇编，确认"编译器输出的是文本"

    sed -n '/^main:/,/\.size\tmain/p' main.s

本机实测（略去几行注释）：

```
main:
	push	{r7, lr}
	add	r7, sp, #0
	ldr	r3, .L3
.LPIC0:
	add	r3, pc
	ldr	r3, [r3]
	movs	r1, #2
	mov	r0, r3
	bl	add(PLT)          <-- 注意这里：函数名还在，是个字符串
	mov	r2, r0
	...
	pop	{r7, pc}
.L3:
	.word	g_init-(.LPIC0+4)   <-- 变量名也还在
	.word	g_bss-(.LPIC1+4)
```

**这一步要抓住的唯一一件事：`bl add(PLT)` 里那个 `add` 还是名字。**
汇编是文本，文本里可以写名字。但 CPU 执行的机器码里没有名字这种东西，
`bl` 指令只能编码一个数字偏移。

于是问题来了：**`add` 这个名字，是在哪一步、被谁换成数字的？**
这就是下一节。

### 2.6 判据

    [ ] `gcc -v` 的输出里能找到 cc1 和 as 两个程序的完整路径
    [ ] -E / -S / -c 三个产物都生成了，且 wc -l 满足 main.c < main.i < main.s
    [ ] main.s 里能找到 `bl` 加函数名的那一行（名字仍是文本）

    注错见红：把 -S 换成 -s（小写）。小写 -s 是给链接器的 strip 选项，
    不是"停在汇编"，gcc 会一路做到链接。本机实测：

        $ arm-linux-gnueabihf-gcc -s main.c -o main.s
        ld.bfd: /tmp/ccgyyOtm.o: in function `main':
        main.c:(.text+0xe): undefined reference to `add'
        $ ls -l main.s
        ls: cannot access 'main.s': No such file or directory

    报的是链接错误，而且 main.s 根本没生成。
    如果你敲小写也顺利拿到了 main.s，说明你敲的不是这个命令。

## 三、实验 2：把链接器的活儿逼出来

上一节结束时留了个问题：名字什么时候变成数字。
现在正面回答它。

### 3.1 先自己想

`main.o` 已经是机器码了。那么 `main.o` 里调用 `add` 那条指令，
里面填的是什么？`add` 的代码在另一个文件 `add.c` 里，
编译 `main.c` 的时候 cc1 根本没看过 `add.c`，**它不可能知道 add 的地址**。

所以只有两种可能：要么填了个假的，要么留了个空。你猜是哪种？

怎么验证：**把 .o 反汇编，直接看那条指令。**

    提示：反汇编工具叫 objdump（object dump，把目标文件倒出来），
          反汇编的开关是 -d（disassemble）。

### 3.2 动手：先看名字，再看指令

第一步，看看 `main.o` 里都有哪些名字，以及每个名字是什么状态。
工具是 `nm`（name 的缩写，列出符号）：

    arm-linux-gnueabihf-nm main.o

本机实测：

    $ arm-linux-gnueabihf-nm main.o
             U add
    00000000 B g_bss
    00000000 D g_init
    00000000 T main

**逐列读**（nm 的输出是三列：地址、类型字母、名字）：

    第一列  地址。注意 main、g_init、g_bss 全是 00000000
    第二列  这个名字是什么货色：
              T  在本文件的代码里定义了（T = text，代码段）
              D  在本文件的数据里定义了，有初值（D = data）
              B  在本文件的数据里定义了，无初值（B = bss，下一篇讲）
              U  Undefined，本文件用到了它，但没有定义   <-- 关键
    第三列  名字本身

    小写字母（t/d/b）表示 static，只在本文件可见；大写表示全局可见。

**现象 1：`add` 是 U。** main.o 明确记着"我欠一个叫 add 的东西"。

**现象 2：main、g_init、g_bss 三个的地址全是 0。** 三个不同的东西不可能都在 0 号地址。
这说明 .o 里的地址不是真地址，只是"从本文件开头算起的偏移"。

再看 `add.o`：

    $ arm-linux-gnueabihf-nm add.o
    00000000 T add

`add` 在这里是 T（有定义），地址也是 0。
**两个文件里都有个东西住在"0 号地址"，它们显然不能同时成立。**
必须有人来重新安排门牌号 —— 这个人就是链接器。

### 3.3 动手：看那条调用指令里填了什么

    arm-linux-gnueabihf-objdump -d main.o

    -d = disassemble，只反汇编代码部分

本机实测（截取 main 那段）：

```
00000000 <main>:
   0:	b580      	push	{r7, lr}
   2:	af00      	add	r7, sp, #0
   4:	4b06      	ldr	r3, [pc, #24]
   6:	447b      	add	r3, pc
   8:	681b      	ldr	r3, [r3, #0]
   a:	2102      	movs	r1, #2
   c:	4618      	mov	r0, r3
   e:	f7ff fffe 	bl	0 <add>          <-- 就是它
  12:	4602      	mov	r2, r0
  ...
```

**怎么读这三列：**

    e:          这条指令在文件里的偏移（第 14 字节处）
    f7ff fffe   这条指令的机器码，4 个字节
    bl 0 <add>  objdump 反过来翻译给你看的助记符

**看机器码 `f7ff fffe`：全是 f。** 这是 GNU 汇编器留的占位模式，
意思是"偏移字段我没填，等人来填"。objdump 拿这个空偏移去算目标地址，
算出来是 0，所以显示 `bl 0`。

（不用去精确解码这 4 个字节的位域，那是 ARM 手册的事。
这里只需要认一个事实：**这条指令里的目标地址是空的。**）

### 3.4 动手：那"等人来填"这件事记在哪？

汇编器不能只留个空就走人，它得留张便条说明"第几个字节需要填、填谁的地址"。
这张便条叫**重定位记录**（relocation）。

    arm-linux-gnueabihf-readelf -r main.o

    readelf = 读 ELF 文件的工具（.o 也是 ELF，下一篇细讲）
    -r      = relocations，重定位记录

本机实测：

    Relocation section '.rel.text' at offset 0x1e0 contains 3 entries:
     Offset     Info    Type            Sym.Value  Sym. Name
    0000000e  00000f0a R_ARM_THM_CALL    00000000   add
    00000020  00000c03 R_ARM_REL32       00000000   g_init
    00000024  00000d03 R_ARM_REL32       00000000   g_bss

**逐列读，重点是第一列和最后一列：**

    Offset    要修补的位置，从本文件代码开头算起
    Type      按什么规则修补（THM_CALL = Thumb 的 bl 指令；REL32 = 32 位相对地址）
    Sym. Name 填谁的地址

**第一行的 Offset 是 `0000000e`。回到上一段的反汇编：`e:` 正是那条 `bl` 指令。**
一个字节不差地对上了。

到这里，链接器要干的活儿已经被完整定义出来了：

    1. 收集所有 .o，给每个名字分配真正的地址（解决 3.2 的"都住 0 号地址"）
    2. 按每张重定位便条，回去把那些空洞填上（解决 3.3 的 f7ff fffe）
    3. 如果某张便条上的名字谁都没定义 —— 报错

### 3.5 动手：故意让第 3 条发生

链接器平时闷声干活，唯一一次开口说话就是这个时候。你肯定见过这个报错，
但可能没意识到它是链接器发出来的：

    arm-linux-gnueabihf-gcc main.o -o app_bad
    # 故意不给 add.o

本机实测：

    /usr/bin/arm-linux-gnueabihf-ld.bfd: main.o: in function `main':
    main.c:(.text+0xe): undefined reference to `add'
    collect2: error: ld returned 1 exit status

**逐句读这个报错，它把前面所有内容都印证了一遍：**

    ld.bfd                 说话的是 ld，链接器。名字第一次直接出现
    main.o: in function    是 main.o 里出的事
    (.text+0xe)            偏移 0xe —— 和 3.4 那张便条的 Offset 一模一样
    undefined reference    "未定义的引用"，正是 nm 里那个 U

**这就是为什么 `undefined reference to xxx` 永远不是语法错误。**
代码语法完全正确，编译（cc1）早就过了；
是链接器拿着便条找不到人。所以这类错误的排查方向永远是
"少链了一个 .o / 少链了一个 -l 库"，不是"我代码写错了"。

### 3.6 动手：补上 add.o，看空洞被填上

    arm-linux-gnueabihf-gcc main.o add.o -o app

先看名字（本机实测）：

    $ arm-linux-gnueabihf-nm app | grep -E " (main|add|g_init|g_bss)$"
    00000500 T add
    00020010 B g_bss
    00020008 D g_init
    000004d8 T main

**和 3.2 对照着看：**

              .o 里         链接后
    main      00000000  ->  000004d8
    add       00000000  ->  00000500   （而且不再是 U，是 T）
    g_init    00000000  ->  00020008
    g_bss     00000000  ->  00020010

四个"都住 0 号地址"的东西，现在各有各的门牌。

再看那条指令：

    arm-linux-gnueabihf-objdump -d app | grep -A 20 '<main>:'

本机实测：

```
000004d8 <main>:
 4d8:	b580      	push	{r7, lr}
 ...
 4e6:	f000 f80b 	bl	500 <add>       <-- 机器码变了
 ...
00000500 <add>:
 500:	b480      	push	{r7}
```

    链接前   e:   f7ff fffe   bl 0 <add>
    链接后 4e6:   f000 f80b   bl 500 <add>
                  ^^^^^^^^^
                  机器码真的被改写了，不是显示上的差别

**顺手验算一次，确认 500 这个数不是巧合：**
ARM 的 `bl` 用的是相对偏移，基准是"当前指令地址 + 4"。

    当前指令地址 0x4e6，加 4  = 0x4ea
    机器码 f000 f80b 里的偏移 = 0x16（22 字节）
    0x4ea + 0x16 = 0x500  = add 的地址  ✓

对上了。**链接器就是把 0x16 这个数算出来、写进机器码的那个程序。**

### 3.7 判据

    [ ] nm main.o 里 add 是 U，main/g_init/g_bss 地址全是 0
    [ ] readelf -r main.o 第一条记录的 Offset，等于 objdump -d 里 bl 那条指令的偏移
    [ ] 只链 main.o 时报 undefined reference，且报错里的偏移与上一条一致
    [ ] 链接后 nm 里四个符号地址各不相同，且 bl 的机器码从 f7ff fffe 变成别的值
    [ ] 手算 (bl 指令地址 + 4 + 偏移) == add 的地址

    注错见红：把 add.c 里的函数名改成 add2，重新编 add.o 再链接。
    必须重新出现 undefined reference to `add'。
    如果没报错，说明你链接的是上一次编出来的旧 add.o —— 这本身就是
    "为什么需要 Makefile 管依赖"的现场教材。

## 四、section：链接器搬运的箱子

到这里，"链接器要给所有东西分配地址"已经是个既成事实。
现在问一个具体问题：**它是按什么单位分配的？**

一个一个函数分配吗？那太碎了。而且有个硬约束：

    代码      必须可执行、不可写（写了就是被攻击）
    只读数据  必须可读、不可写、不可执行
    可写数据  必须可读可写、不可执行

**权限相同的东西必须挨着放**，否则没法设权限（内存权限是按页设的，
一页 4KB，不可能一个函数一种权限）。

所以编译器在生成 .o 的时候，就已经按用途把内容分好类了。
**每一类叫一个 section（节）。**

> **section 的定义**：.o 和可执行文件内部的分块。每块有名字、大小、属性
> （可写吗？可执行吗？占不占文件空间？）。
> **它是链接器的操作单位** —— 链接器干活的方式就是"把所有输入文件里
> 同名的 section 首尾相接拼成一块，然后给这块分配地址"。

常见的几个名字，现在只需要认脸：

    .text      代码
    .data      有初值的全局/静态变量
    .bss       无初值的全局/静态变量（下一篇细讲为什么它特殊）
    .rodata    只读数据，比如字符串字面量 "hello"
    .symtab    符号表，就是 nm 读的那张表
    .rel.text  重定位便条，就是 readelf -r 读的那张表

### 4.1 动手：看 .o 里的 section 表

    arm-linux-gnueabihf-readelf -S main.o

    -S = Section headers（注意是大写 S；小写 -s 是看符号表，别弄混）

本机实测：

```
There are 11 section headers, starting at offset 0x254:

  [Nr] Name              Type            Addr     Off    Size   ES Flg Lk Inf Al
  [ 0]                   NULL            00000000 000000 000000 00      0   0  0
  [ 1] .text             PROGBITS        00000000 000034 000028 00  AX  0   0  4
  [ 2] .rel.text         REL             00000000 0001e0 000018 08   I  8   1  4
  [ 3] .data             PROGBITS        00000000 00005c 000004 00  WA  0   0  4
  [ 4] .bss              NOBITS          00000000 000060 000004 00  WA  0   0  4
  [ 5] .comment          PROGBITS        00000000 000060 000027 01  MS  0   0  1
  [ 6] .note.GNU-stack   PROGBITS        00000000 000087 000000 00      0   0  1
  [ 7] .ARM.attributes   ARM_ATTRIBUTES  00000000 000087 000033 00      0   0  1
  [ 8] .symtab           SYMTAB          00000000 0000bc 000100 10      9  12  4
  [ 9] .strtab           STRTAB          00000000 0001bc 000024 00      0   0  1
  [10] .shstrtab         STRTAB          00000000 0001f8 000059 00      0   0  1
```

**该看哪几列（其余先无视）：**

    Name   名字
    Type   PROGBITS = 文件里真的存着这些字节
           NOBITS   = 文件里不存，只记个大小        <-- .bss 是这个，下一篇讲
           SYMTAB / STRTAB / REL = 给工具用的元信息，不是你的程序内容
    Addr   全是 00000000 —— 又一次印证：.o 里没有真地址
    Size   大小，十六进制

**从这张表能直接读出三件事：**

1. `.text` 大小 `000028` = 40 字节。回头看 3.3 的反汇编，main 从偏移 0 到 0x1e，
   加上末尾两个 `.word` 常量（0x20、0x24 各 4 字节）正好到 0x28。对得上。
2. `.data` 4 字节 = `int g_init`，`.bss` 4 字节 = `int g_bss`。
   两个变量按"有没有初值"被分进了不同的箱子。
3. `.symtab`、`.strtab`、`.rel.text` 这些是**给工具看的**，不是程序的一部分。
   前面 nm 和 readelf -r 读的就是它们。

### 4.2 动手：亲眼看链接器合并 section

链接器有个选项，能把"我把谁放到了哪个地址"全部写成一份报告，叫 **map 文件**。
这是理解链接最直接的东西，但几乎没人用：

    arm-linux-gnueabihf-gcc main.o add.o -o app -Wl,-Map=app.map

    -Wl,xxx    把 xxx 这个选项转交给链接器 ld
               （gcc 自己不认识 -Map，必须借 -Wl, 转交。逗号后面不能有空格）
    -Map=app.map  让 ld 把布局报告写进 app.map

打开 `app.map`，找 `.text` 那一段：

    grep -n -A 12 '^\.text ' app.map

本机实测：

```
.text           0x000003dc      0x13e
 *(.text .stub .text.* .gnu.linkonce.t.*)
 .text          0x000003dc       0x34 .../Scrt1.o
                0x000003dc                _start
 .text          0x00000410       0x24 .../crti.o
 .text          0x00000434       0xa4 .../crtbeginS.o
 .text          0x000004d8       0x28 main.o
                0x000004d8                main
 .text          0x00000500       0x1a add.o
                0x00000500                add
 .text          0x0000051a        0x0 .../crtendS.o
 .text          0x0000051a        0x0 .../crtn.o
```

**这张表是本篇最值得盯住的东西。逐行读：**

    第一行  .text 0x3dc 0x13e
            合并后的 .text 整体：从地址 0x3dc 开始，总长 0x13e

    下面每一行 = 一个输入文件贡献的一块：
            起始地址   长度   来自哪个 .o
            0x3dc      0x34   Scrt1.o
            0x410      0x24   crti.o
            0x434      0xa4   crtbeginS.o
            0x4d8      0x28   main.o      <-- 你的代码
            0x500      0x1a   add.o       <-- 你的代码

**三个对账，全部自己动手核一遍：**

1. `main.o` 那块长度 `0x28`，和 4.1 里 `readelf -S main.o` 的 `.text` Size `000028`
   **完全相等**。链接器搬的就是那个箱子，一字节没变。
2. `0x4d8 + 0x28 = 0x500`，正好是 `add.o` 那块的起始地址。
   **首尾相接，中间没有缝。** 这就是"合并"的字面意思。
3. `0x4d8` 和 `0x500` 正是 3.6 里 nm 查到的 main 和 add 的地址。
   一条线从头对到尾。

**还有一个意外收获：Scrt1.o / crti.o / crtbeginS.o 是哪来的？**
你没写过它们，也没链接它们。是 gcc 偷偷加进去的 C 运行时启动代码，
`_start` 就在 Scrt1.o 里。

    程序的入口不是 main，是 _start。
    _start 负责准备好 argc/argv、初始化 libc，然后才调用你的 main。

这条留到 `01_ELF与程序加载.md` 第五节展开。这里只要记住：
**最终可执行文件里，你的代码只占很小一部分**（0x28 + 0x1a = 66 字节，
而合并后的 .text 有 0x13e = 318 字节）。

### 4.3 判据

    [ ] readelf -S main.o 里 .text 的 Size，等于 app.map 里 main.o 那一行的长度
    [ ] app.map 里 main.o 起始地址 + 长度 == add.o 的起始地址（首尾相接）
    [ ] 这两个地址与 nm app 查到的 main / add 地址完全一致
    [ ] app.map 的 .text 里能找到至少一个你没写过的 .o（Scrt1.o 之类）

    注错见红：在 add.c 里加一个函数（int sub(int a,int b){return a-b;}），
    重新编译链接，app.map 里 add.o 那块的长度必须变大。本机实测：

        原来        .text  0x00000500   0x1a  add.o
        加 sub 后   .text  0x00000500   0x34  add2.o

    长度 0x1a -> 0x34。注意 main.o 那行的地址 0x4d8 没变，因为它排在 add.o 前面；
    真正被推着走的是 add.o 之后的所有内容。
    如果长度没变，说明链接的还是上一次编出来的旧 .o。

## 五、加载器：文件怎么变成进程

前四节讲完了"编译时"。现在过那条界线，讲"运行时"。

### 5.1 先自己想

`app` 现在是一个文件，静静躺在磁盘上。你敲 `./app`，
它就开始执行了。中间发生了什么？

具体一点：4.2 里链接器把 main 安排在地址 `0x4d8`。
**谁负责保证程序跑起来的时候，main 的代码真的在内存 0x4d8 这个位置？**

答案是**加载器**。它不是一个独立程序，是内核的一部分：

> **加载器的定义**：内核里负责把可执行文件搬进内存、建立进程地址空间、
> 然后把 CPU 交给它的那段代码。你敲 `./app`，shell 调 `execve()` 系统调用，
> 内核里的 `load_elf_binary()` 就是这个加载器。

它干的事，正好和链接器对称：

    链接器  在文件里安排布局      "main 放 0x4d8"
    加载器  照这个布局摆进内存    "把文件的这一段映射到内存 0x4d8"

### 5.2 动手：让程序自己报告它被摆成什么样

Linux 把每个进程的内存布局放在 `/proc/<pid>/maps` 这个伪文件里。
进程读 `/proc/self/maps` 就是读自己的。

这里换成本机 x86 编译（`gcc` 而不是 `arm-linux-gnueabihf-gcc`），
因为**要真跑起来**，而 ARM 程序在 x86 上跑不了。
换工具链不影响结论，布局规则是一样的。

`maps.c`：

```c
#include <stdio.h>

int g_init = 1;
int g_bss;

int main(void)
{
	char line[256];
	FILE *f = fopen("/proc/self/maps", "r");

	while (fgets(line, sizeof line, f))
		fputs(line, stdout);
	fclose(f);

	printf("&main  =%p\n", (void *)main);
	printf("&g_init=%p\n", (void *)&g_init);
	printf("&g_bss =%p\n", (void *)&g_bss);
	printf("g_bss  =%d\n", g_bss);
	return 0;
}
```

    gcc maps.c -o maps
    ./maps

本机实测（只截和本程序有关的前 6 行）：

```
5ea4b54d9000-5ea4b54da000 r--p 00000000 .../maps
5ea4b54da000-5ea4b54db000 r-xp 00001000 .../maps
5ea4b54db000-5ea4b54dc000 r--p 00002000 .../maps
5ea4b54dc000-5ea4b54dd000 r--p 00002000 .../maps
5ea4b54dd000-5ea4b54de000 rw-p 00003000 .../maps
5ea4cb274000-5ea4cb295000 rw-p 00000000 [heap]

&main  =0x5ea4b54da1e9
&g_init=0x5ea4b54dd010
```

### 5.3 怎么读 maps

每行的格式：

    起始地址-结束地址  权限  文件内偏移  ...  这段内存对应哪个文件

    权限四个字符：r 读  w 写  x 执行  p 私有（改了不影响别人）

**逐行读这 5 行，把它和第四节的 section 对上：**

    5ea4b54d9000-...da000  r--p   只读不可执行     -> 只读数据
    5ea4b54da000-...db000  r-xp   可读可执行不可写 -> 代码（.text）
    5ea4b54db000-...dc000  r--p   只读
    5ea4b54dc000-...dd000  r--p   只读
    5ea4b54dd000-...de000  rw-p   可读可写不可执行 -> 数据（.data/.bss）

**验证一：`&main = 0x5ea4b54da1e9`，落在第 2 行 `[da000, db000)` 区间内。**
那一行的权限正是 `r-xp` —— 可执行。代码确实被放进了可执行的那块。

**验证二：`&g_init = 0x5ea4b54dd010`，落在第 5 行 `[dd000, de000)`。**
权限 `rw-p` —— 可写。全局变量确实在可写的那块。

**这就是第四节开头那句"权限相同的东西必须挨着放"的兑现现场。**
编译器分 section、链接器合并 section、加载器按权限成块映射，
三步是同一条链上的。

**验证三（意外但重要）：`g_bss = 0`，而你从没给它赋过值。**
谁清的零？是加载器。下一篇 `01_ELF与程序加载.md` 会讲它凭什么知道要清零、清多少。

### 5.4 一个附赠现象：再跑一次，地址全变了

    $ ./maps | tail -4
    &main  =0x64ea98fdd1e9      <-- 上一次是 0x5ea4b54da1e9
    &g_init=0x64ea98fe0010
    &g_bss =0x64ea98fe0024
    g_bss  =0

**两次运行，同一个文件，地址完全不同。** 这叫 ASLR（地址空间布局随机化），
内核故意每次换个地方装，让攻击者猜不到函数地址。

注意低 12 位没变：`...1e9` 两次都是 `1e9`。
因为随机的是"整块搬到哪"，块内部的相对位置是链接器定死的，不会动。

**这一条对嵌入式的意义**：裸机（ysyx 那种、以及你 SoC 上跑的 bin）
地址是写死的，加载 = 把整个文件塞进 0x80000000。
有了 MMU 和操作系统之后，程序看到的地址是虚拟地址，可以每次都不一样。
这是"为什么裸机能用 .bin，Linux 必须用 ELF"的根本原因之一。

### 5.5 判据

    [ ] maps 输出里能找到 5 行指向本程序文件的映射，其中恰好一行带 x 权限
    [ ] &main 落在带 x 的那一行的地址区间内
    [ ] &g_init 落在带 w 的那一行的区间内，且那一行不带 x
    [ ] 连跑两次，两次 &main 不同，但末三位十六进制数相同
    [ ] g_bss 打印出来是 0

    注错见红：把 main 的地址硬当成数据去写，在 return 0 前面加一行

        *(int *)main = 0;

    编译能过（只是个警告），本机实测运行结果：

        Segmentation fault
        退出码 139        （139 = 128 + 11，11 号信号就是 SIGSEGV）

    崩的原因不是"指针写错了"，而是 main 落在 r-xp 那块内存，没有 w 权限，
    CPU 的 MMU 直接拒绝。**这是本篇唯一一次让硬件替你判卷。**
    如果它没崩，说明内存权限没生效，那才是真出问题了。

## 六、整篇串起来

一条完整的因果链，每一环都有你亲手看过的证据：

    C 源码
      |  cc1 翻成汇编，函数名还是文本            main.s 里的 bl add(PLT)
      v
    汇编
      |  as 翻成机器码，名字变成占位 + 一张便条  f7ff fffe + readelf -r
      |  内容按用途分箱                          readelf -S 的 .text/.data/.bss
      v
    .o（还不能跑：地址全是 0，且欠着 add）        nm 里的 U 和一堆 00000000
      |  ld 合并同名箱子、分配地址、按便条填空洞  app.map + 机器码变成 f000 f80b
      v
