# 00 基础通用知识

## 这个文件夹解决什么问题

主线章节（01、02、03...）讲的是"这一章的事"，遇到通用名词只能一笔带过，
不然主线就断了。但一笔带过的结果是：你看到 `s0`、`sysroot`、`PLT` 这种词，
知道它在句子里的位置，却不知道它是什么。

所以约定：

    主线章节里出现一个名词，如果它
        不属于本章主线            例如 ARM 寄存器编号不属于"工具链"这一章
        且以后还会反复出现        例如 ELF、系统调用、动态库
    就在这里单开一篇，主线里只留一句话加一个跳转。

用到就加，不预先写全。没被任何一章引用过的篇章不要写。

## 每篇开头的那一块

每篇正文之前固定有两块：**“这一篇到底在讲什么”**和**“结论先贴出来”**。
它俩合起来干两件事——让你一进来就知道这东西的本质是什么，
以及即使后面全没看懂，也能把结论直接背走。

“这一篇到底在讲什么”按四步写，顺序不能换：

    1 一句话本质    用引用块摆在标题正下方。要能一句话说清这东西是什么，
                    像“掮客就是中介”那样。**不许从这一章的难点起笔**，
                    难点是给已经入门的人看的
    2 你是从哪儿撞见它的
                    读者不会像机器那样思考。他是写完代码要上板，
                    才第一次遇到“编译”这个词的。先把他真实的遭遇场景写出来
                    （那条报错、那个疑问），再往下讲
    3 它是被什么逼出来的
                    把本质放回它所在的位置：没有它会怎样、当初是什么问题
                    逼出了它。**这一步是全篇的承重墙**，后面所有名词
                    都应该是从这里推出来的，而不是并列罗列的知识点
    4 关键细节      它具体怎么工作。只讲支撑上面那条推理的部分

“结论先贴出来”：

    - 每条都是能直接背走的答案，结论句在前，适用条件放句尾
    - **条数按这一篇实际有几个独立结论来定，不许凑成固定条数**。
      检查办法写在块首：正文每一节至少对应一条，没对上就是漏了
    - 后面跟一张“看到什么，就先想到什么”，把报错和现象映射到第一反应
    - 块末指明想补原理该回哪一节

前置声明、实验目录、判据自查这些元信息**放在这两块之后**，
不要挡在读者和本质中间。

## 体例

被推翻，原因有三条，写在这里防止再犯：

    问题 1  术语凭空出现
            旧版 01 篇第一句就用 program header、e_entry、mmap、ASLR 讲"对照"，
            但这些词一个都没定义过。搭桥本身成了新门槛。

    问题 2  拿"你学过"当"你会了"
            有 ysyx 和龙芯 SoC 的底子，不等于每个概念都清楚。
            对照只能当辅助，**不能替代从零讲一遍**。

    问题 3  验证是玩具
            旧版给"先自己想"三个问题 + 几条命令 + 打勾框，
            没有输出长什么样、看哪一列、看到之后能推出什么。
            结果是做到一半就卡住（旧 01 篇四条判据实际只勾了两条）。

2026-09-12 又修订了一次开头那一块，原因是第四条，同样写在这里防止再犯：

    问题 4  开头块写成了机械模板
            旧版每篇都是"先带走这 5 条 + 3 组问答"，条数写死。
            先定框再往里塞，结果是塞不下的漏掉、塞不满的注水，
            条数一致恰恰说明没人检查过完整性。
            更要命的是那 5 条全是"注意事项"的语气（不一定、取决于、不能背成），
            读完不知道这一章到底是什么。
            **而且它从本章的难点起笔**——那是给已经入门的人看的。
            新版改成"本质 -> 遭遇场景 -> 被什么逼出来 -> 关键细节"，
            条数按内容定，判定办法见上一节。

新体例，每篇按这个结构写：

    1. 开头两块：“这一篇到底在讲什么”+“结论先贴出来”，写法见上一节。
       前置声明、实验目录、判据自查放在这两块之后
    2. 从上一篇留下的问题接上，让新概念是被"逼出来"的，不是空降的
    3. 主体由若干个实验组成，每个实验固定五步：

         先自己想   给目标和线索（工具叫什么、开关的首字母是什么意思），
                    不给现成命令
         动手       完整命令，**每个参数注明它在管什么**，
                    以及"为什么是这条命令"的推理过程
         贴输出     本机真跑的原始输出，不省略、不美化
         逐行读     指名道姓说看哪一列哪一行，那个数字是什么意思，
                    和前面哪个数字能对上账
         下结论     从现象推出一句话，并说明它在实际工程里意味着什么

    4. 判据：每个实验一组，可勾选。至少有一条是"两个数字必须相等"的对账型
    5. 注错见红：故意改坏，写明**实测的**失败现象。没红过的判据不算数
    6. 被谁用到

硬规矩：

    - 每篇必须有上述两块开头，不能用“读完你会知道什么”或待勾选判据代替。
      直接写出应该带走的答案，不折叠、不把“先自己想”作为查看答案的门槛。
      结论用短句，必要术语就地解释，适用条件紧跟结论；不能把本机某次耗时、
      地址、缺页次数背成通用规律。新增或修改正文结论时，同步更新开头块。
    - **一句话本质不许从本章的难点写起。** 难点默认读者已经入门，
      而开头块的读者是"只知道要做这一步，不知道为什么"的人。
      判定办法：把那句话念给没学过的人听，他能不能复述出这东西是干嘛的。
    - **结论条数不许写死。** 写完回头对着正文小节点一遍，
      每节至少有一条对应得上，没对上就是漏了；凑不满就说明分条分错了。
    - 每个术语第一次出现必须就地定义，用 > 引用块标出来。
      一篇里不许出现"后面会讲"的名词超过两个；兜底块用同行短释义，正文仍保留引用块定义
    - 所有输出、数字、报错都是本机实跑的，写明日期和工具链版本。
      写笔记的人要先自己完整跑一遍，再把过程写成手把手的步骤
    - 对照 ysyx / RISC-V / 龙芯 SoC 的内容一律放在**靠后**的"顺带一提"，
      并注明"没做过也不影响，跳过即可"。正文不许依赖它
    - 能画图就配 ASCII 图，尤其是"哪一步在内核里、哪一步在用户态"这种边界
