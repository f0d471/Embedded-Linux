## 没看懂也先记住

先能回答“实现现在在哪、什么时候找到它、改库后谁要重建”，就能处理很多实际问题。
PLT/GOT 的具体跳转过程可以以后再追。

### 先带走这 5 条

1. **符号就是工具用来识别函数、变量等对象的名字。** `nm` 里先认 `T` 代码定义、`D` 已初始化数据、`B` 零初始化数据、`U` 当前文件没有定义；常见的 `t/d/b` 表示对应的局部符号。
2. **静态库 `.a` 是一包 `.o`。** 普通链接时通常按需要抽取成员目标文件，合进最终产物；选择的基本单位是成员 `.o`，不能简单背成“精确只复制用到的函数”。
3. **动态库 `.so` 的实现通常留在独立库文件中，运行时再装入。** 所以可执行文件的动态符号表中仍有 `U` 可以是正常依赖，不等于链接失败。
4. **静态库改了，已有程序要重新链接才能用上新实现。** 动态库换成 ABI 兼容的新版本后，新启动的程序若确实加载了它，就可使用新实现；不要把它理解成已运行进程会自动热更新。
5. **PLT 是动态函数调用的中转入口，GOT 是存放地址等信息的表。** 先记“运行时还要把调用接到真正实现上”；是否延迟到第一次调用才处理，取决于具体链接和加载方式。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| 用了 `.a` 仍然 `undefined reference` | 查库是否包含定义、是否真的参与链接；GNU 链接器常见顺序是引用它的 `.o` 在前，提供实现的库在后 |
| `nm -D app` 里还有 `U` | 这是动态符号表，先查 `readelf -d app` 的 `NEEDED` 依赖和库提供的定义 |
| 启动时报 `cannot open shared object file` | 查目标机器有没有库、动态加载器能否从运行时搜索路径找到它 |
| 换了 `.a`，旧程序行为没变 | 正常，旧程序已经拿走一份实现，要重新链接 |

### 反复看这 3 组问答

- **问：静态和动态最先记哪个区别？答：静态通常在链接时合入实现，动态通常运行时装入独立的库。**
- **问：只要看到 `U` 就有错吗？答：不是，目标文件的外部引用和动态程序的库依赖都可能正常显示 `U`。**
- **问：改库后一定要重新编译所有 `.c` 吗？答：不一定；只改静态库实现且接口兼容时，已有 `.o` 可以重新链接，动态库则要确认兼容性和实际加载路径。**

想补原理时：符号看第二节，静态库看第三节，动态库及替换实验看第四、五节，PLT/GOT 看第六节。

## 一、从 00 篇的半个答案说起

00 篇 3.5 节做过一个实验：只链 `main.o`、不给 `add.o`，链接器报

    undefined reference to `add'

当时的结论是"少链了一个 .o"。但真实工程里，你依赖的不是一个 `.o`，
而是一整个库 —— libc、libfreetype、libpng……

**问题来了：一个库里有几千个函数，你只用其中三个。**

    全都塞进你的程序？        那每个程序都得背着整个 libc
    只塞用到的？              怎么知道哪些用到了
    干脆不塞，运行时再找？     那"找"这件事谁来干、什么时候干

这三种想法对应两种库和一整套机制，就是本篇的内容。

先把 00 篇的符号表补全 —— 后面全靠它读现象。

## 二、实验 1：nm 的符号类型一网打尽

### 2.1 先自己想

00 篇只用到了 `T`（本文件定义的函数）和 `U`（需要但没有）两种。
全局变量、`static` 变量、只读常量，在符号表里各是什么样？

**写一个文件把各种情况全占上，一次看全。**

### 2.2 动手

`sym.c`：

```c
#include <stdio.h>

int         g_init = 1;                  /* 有初值的全局 */
int         g_bss;                       /* 无初值的全局 */
const char *g_str = "abc";               /* 指针本身可写，指向的字符串只读 */
const int   g_ro = 42;                   /* 只读全局 */
static int  s_local = 7;                 /* static：只在本文件可见 */

int helper(int x) { return x + s_local; }
static int shelp(int x) { return x - 1; }

extern int nobody(void);                 /* 只声明，不实现 */

int main(void)
{
	printf("%d\n", helper(g_init) + shelp(g_ro) + nobody());
	return 0;
}
```

    gcc -c sym.c -o sym.o        # -c 只编译（00 篇 2.4）
    nm sym.o

### 2.3 本机实测

```
0000000000000000 B g_bss
0000000000000000 D g_init
0000000000000004 R g_ro
0000000000000000 D g_str
0000000000000000 T helper
000000000000002b T main
                 U nobody
                 U printf
0000000000000004 d s_local
0000000000000018 t shelp
```

### 2.4 逐行读

**先看类型字母那一列，对照源码一条条认：**

    T helper      源码里 int helper(...)          代码，全局可见
    t shelp       源码里 static int shelp(...)    代码，只在本文件可见
    D g_init      源码里 int g_init = 1;          有初值的数据
    d s_local     源码里 static int s_local = 7;  有初值的数据，本文件可见
    B g_bss       源码里 int g_bss;               无初值 —— 01 篇第四节的 .bss
    R g_ro        源码里 const int g_ro = 42;     只读数据（.rodata）
    U nobody      只声明没实现                    需要它，但没有
    U printf      来自 libc                       需要它，但没有

**规律一：大写 = 全局可见，小写 = 只在本文件可见。**

    int  helper(...)         ->  T helper    别的 .c 能调
    static int shelp(...)    ->  t shelp     别的 .c 看不见

`static` 这个关键字的全部作用，在符号表里就是"把大写变小写"。

**规律二：字母对应它落在哪个 section。**（section 见 00 篇第四节）

    T/t -> .text     D/d -> .data     B/b -> .bss     R/r -> .rodata

**规律三：`U` 那两行前面是空白，没有地址。** 因为压根还不知道地址。

**`printf` 和 `nobody` 在这一步没有任何区别** —— 都是 `U`。
编译器对"libc 里的函数"和"我瞎编的函数"一视同仁，
它只管记下"我需要这个名字"。区别要到链接时才出现：

```
$ gcc sym.c -o sym
ld.bfd: sym.c:(.text+0x56): undefined reference to `nobody'
```

`printf` 解决了（在 libc 里找到了），`nobody` 没有。

### 2.5 这张表的实际用法

以后遇到 `undefined reference to 'xxx'`，第一步永远是：

    nm 你的所有.o 和库 | grep xxx

看有没有人是 `T`（提供它）。全是 `U` 就说明库没链上或者链接顺序错了。

### 2.6 判据

    [ ] helper 是 T、shelp 是 t，差别只在源码里有没有 static
    [ ] g_init 是 D、g_bss 是 B、g_ro 是 R，能对应到三个不同的 section
    [ ] nobody 和 printf 都是 U，且都没有地址
    [ ] 完整链接时只报 nobody 未定义，不报 printf

    注错见红：把 static int s_local 的 static 去掉，重新编译。
    本机实测 nm 里那一行从小写 d 变成大写 D。
    一个关键字的全部作用就体现在这一个字母上。

## 三、实验 2：静态库 —— 打包和挑拣

### 3.1 先自己想

现在要把几个 `.o` 打包成一个库给别人用。**最朴素的做法是什么？**

就是**打个包**。把 `.o` 装进一个文件，用的时候拆开取。

    提示：干这件事的工具叫 ar（archiver，归档器），
          和 tar 是同一类东西。产物按惯例叫 lib<名字>.a

**但有个关键问题：链接的时候，是把整个包都塞进程序，还是只塞用到的？**
这个能测出来。

### 3.2 动手

准备一个有两个函数的库，其中一个故意不用：

`mathx.c`：

```c
#include "mathx.h"
int mx_add(int a, int b) { return a + b; }
```

`strx.c`：

```c
#include "mathx.h"
int mx_len(const char *s) { int n = 0; while (*s++) n++; return n; }
```

`app.c`：

```c
#include <stdio.h>
#include "mathx.h"

int main(void)
{
	printf("mx_add(3,4) = %d\n", mx_add(3, 4));
	return 0;                  /* 故意不调用 mx_len */
}
```

```bash
gcc -c mathx.c strx.c            # 编出 mathx.o strx.o
ar rcs libmathx.a mathx.o strx.o # 打包
ar t libmathx.a                  # t = list，列出包里有什么

gcc app.c -o app_static -L. -lmathx
```

    ar rcs   r = 插入/替换成员，c = 不存在就新建且别啰嗦，s = 建符号索引
    -L.      去当前目录找库（03 篇第七节）
    -lmathx  链接 libmathx.a 或 libmathx.so —— 名字中间那截才是 mathx

### 3.3 本机实测

```
$ ar t libmathx.a
mathx.o
strx.o

$ nm app_static | grep -c ' T mx_add'
1
$ nm app_static | grep -c ' T mx_len'
0

$ ./app_static
mx_add(3,4) = 7
```

### 3.4 逐条读

**`ar t` 证实了静态库的本质：它就是一个装 `.o` 的包**，
里面原封不动地放着 `mathx.o` 和 `strx.o`。

**关键结论在后面两个数字上：**

    mx_add 在 app_static 里是 T（有定义，被抄进来了）      -> 1
    mx_len 在 app_static 里根本不存在                      -> 0

**链接器只从包里挑出用得到的 `.o` 抄进你的程序，没用到的整个丢掉。**
挑拣的粒度是 `.o` 文件，不是函数 —— 所以库作者习惯把函数拆得很细，
一个函数一个文件，就是为了让使用者能挑得更干净。

**这也解释了 `-l` 为什么要放在源文件后面**（03 篇 7 节那个坑）：
链接器从左往右扫，扫到 `libmathx.a` 时才决定挑哪些 `.o`。
如果 `-lmathx` 放在 `app.c` 前面，扫到库的时候它还不知道谁需要 `mx_add`，
挑完（什么也没挑）就走了。

### 3.5 判据

    [ ] ar t 列出的就是你打包进去的那两个 .o
    [ ] app_static 里有 mx_add，没有 mx_len
    [ ] 程序能正常跑出 7

    注错见红：把 -lmathx 挪到 app.c 前面：

        gcc -L. -lmathx app.c -o app_bad

    本机实测报 undefined reference to `mx_add'。
    **文件顺序会改变链接结果** —— 这是 00 篇那个报错的另一种成因，
    比"忘了链库"更难查，因为库明明写了。

## 四、实验 3：动态库 —— 链接完了还是 U

### 4.1 先自己想

静态库有个明显的代价：**每个用它的程序都带一份副本。**
系统上一百个程序都用 libc，就有一百份 libc 的代码占着磁盘和内存。

**换个思路：链接时不抄代码，只记一句"我需要 libmathx"，
等运行的时候再去找。**

那么问题是：**如果链接时不抄代码，那个函数的地址怎么办？**
00 篇讲过，链接器的活就是"分配地址、填空洞"。地址都不知道，怎么填？

**先做出来看现象，再解释。**

### 4.2 动手

```bash
gcc -shared -fPIC -o libmathx.so mathx.c strx.c
gcc app.c -o app_dyn -L. -lmathx -Wl,-rpath,'$ORIGIN'

nm app_dyn | grep mx_add
readelf -d app_dyn | grep NEEDED
```

    -shared    生成共享库而不是可执行文件
    -fPIC      position independent code，见 4.5 节
    -Wl,-rpath,'$ORIGIN'
               把"到程序自己所在的目录去找库"这条路径记进可执行文件。
               不写的话运行时得靠 LD_LIBRARY_PATH=. 指路
    readelf -d 看 .dynamic 段（01 篇 3.2 节 segment 表里那个 DYNAMIC）

### 4.3 本机实测

```
$ nm app_dyn | grep mx_add
                 U mx_add            <-- 链接完了，它还是 U

$ readelf -d app_dyn | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [libmathx.so]
 0x0000000000000001 (NEEDED)  Shared library: [libc.so.6]

$ ./app_dyn
mx_add(3,4) = 7
```

### 4.4 逐条读

**最反直觉的一行：`mx_add` 在链接完的可执行文件里仍然是 `U`。**

对照静态版：

    app_static     T mx_add      代码被抄进来了，地址定死了
    app_dyn        U mx_add      仍然是"我需要它，但不知道在哪"

**链接器并没有解决这个符号，它只做了两件事：**

    1. 确认 libmathx.so 里确实有 mx_add 这个名字（不然现在就报错）
    2. 在 .dynamic 段里记一条 NEEDED: libmathx.so，把活推给运行期

**推给谁？** 01 篇 5.3 节的答案：`PT_INTERP` 指定的动态链接器 `ld.so`。
程序启动时内核先加载它，由它读 `NEEDED` 列表、把库映射进来、
把地址填好，再把控制权交给你的 `main`。

**所以 `undefined reference` 有两种截然不同的下场：**

    静态链接时找不到    -> 链接器当场报错，你根本编不出程序
    动态链接时找不到    -> 编译一切正常，运行时才崩：
                          error while loading shared libraries: libmathx.so:
                          cannot open shared object file

第二种是部署到板子上最常见的翻车方式：开发机上跑得好好的，
拷到板子上说找不到库。

### 4.5 -fPIC 是什么

动态库被加载到哪个地址，事先不知道（01 篇 5.4 节的 ASLR 也是这个原因）。
所以库里的代码**不能写死绝对地址**，必须全部用"相对于当前位置"的方式寻址。

> **PIC（position independent code，位置无关代码）**：
> 编译出的代码放在任何地址都能正确运行。代价是访问全局数据要多绕一层
> （通过下一节的 GOT 表），有一点性能损失。

00 篇 2.5 节看 `main.s` 时见过的这两行，就是 PIC 在起作用：

```
	ldr	r3, .L3
	add	r3, pc          <-- 加上 pc：算出"相对于当前位置"的地址
```

（PIE 是同一个思路用在可执行文件上，01 篇 2.4 节 `readelf -h` 里
`Type: DYN (Position-Independent Executable file)` 那行说的就是它。）

### 4.6 判据

    [ ] nm app_dyn 里 mx_add 仍然是 U
    [ ] readelf -d 里有 NEEDED: libmathx.so
    [ ] 程序能跑出 7
    [ ] 能说出"链接器为 mx_add 做了什么、没做什么"

    注错见红：把 libmathx.so 改名藏起来再跑：

        mv libmathx.so libmathx.so.bak && ./app_dyn

    本机实测报 error while loading shared libraries，退出码 127。
    **注意这个错误发生在 main 的第一行之前** —— 是 ld.so 报的，不是你的程序。
    做完记得改回来。

## 五、实验 4：改了库不重编程序（决定性实验）

### 5.1 先自己想

前两节的区别，能不能用一个实验一次说清？

**能。既然静态库是"编译期抄代码"、动态库是"运行期找代码"，
那么改了库之后不重编程序：**

    静态版    应该纹丝不动（代码早就抄进去了）
    动态版    应该跟着变（运行时才去找）

**这是两者区别的唯一硬证据，必须亲手做一次。**

### 5.2 动手

```bash
# 先记下两个程序的指纹
md5sum app_dyn app_static

# 把加法改成乘法，只重编库，不碰程序
sed -i 's|return a + b;|return a * b;|' mathx.c
gcc -shared -fPIC -o libmathx.so mathx.c strx.c
gcc -c mathx.c strx.c && ar rcs libmathx.a mathx.o strx.o

# 再看指纹，然后跑
md5sum app_dyn app_static
./app_dyn
./app_static
```

### 5.3 本机实测

```
改之前：
  动态版: mx_add(3,4) = 7
  静态版: mx_add(3,4) = 7

只重编了库，两个程序一个字节都没重编：
  app_dyn    md5 前 8 位: de85b007 -> de85b007
  app_static md5 前 8 位: 591733fd -> 591733fd

改之后：
  动态版: mx_add(3,4) = 12          <-- 3 * 4，跟着库变了
  静态版: mx_add(3,4) = 7           <-- 3 + 4，纹丝不动
```

### 5.4 逐条读

**两个可执行文件的 md5 完全没变**（前 8 位一致，说明文件一个字节没动），
**但一个的行为变了，一个没变。**

    动态版 7 -> 12    它每次运行都去 libmathx.so 里取代码，库变了它就变
    静态版 7 -> 7     mx_add 的机器码在链接时就抄进它自己肚子里了

**这一条实验把两种库的全部区别讲完了。** 它的现实后果：

    修一个 libc 的安全漏洞
      动态链接的程序：升级 libc.so.6，所有程序立刻都修好了
      静态链接的程序：每一个都得重新编译、重新分发

    磁盘和内存
      本机实测：app_dyn 15,984 字节，同样功能的全静态版 816,920 字节，51 倍
      而且系统上一百个动态链接的程序，内存里只有一份 libc 的代码页
      （靠 01 篇的 MAP_PRIVATE 共享，见 07 篇 6.4 节）

    部署
      动态：必须保证板子上有对应的 .so，版本还得对得上
      静态：拷过去就能跑

**嵌入式上怎么选**：根文件系统里程序多就用动态（省 flash），
单个独立工具、或者要塞进 initramfs 的救援程序就用静态（少依赖）。

### 5.5 判据

    [ ] 改库前后，两个可执行文件的 md5 完全相同
    [ ] 动态版的输出从 7 变成 12
    [ ] 静态版的输出仍然是 7
    [ ] 全静态版的体积比动态版大一个数量级以上

    注错见红：改完库之后，把动态版也重新链接一次（gcc app.c -o app_dyn ...）。
    这时两版都会变成 12，实验的对比就没了。
    **这个实验的关键恰恰是"不重编"** —— 一旦重编，你测的就不是
    静态动态的区别，而是"你有没有重编"。

## 六、实验 5：PLT 和 GOT —— 地址是怎么填进去的

### 6.1 先自己想

回到 4.1 节那个没回答的问题：**动态链接时，那条调用指令里填什么？**

00 篇 3.6 节看过，`bl` 指令里编码的是一个数字偏移。
可 `mx_add` 的地址运行时才知道。

**那能不能等运行时，让 ld.so 回来改写 `.text` 里那条 `bl` 指令？**

不行，两个理由：

    1. .text 是只读的（01 篇 3.2 节，LOAD #1 的权限是 R E）。
       改它得先加写权限，安全上不可接受
    2. .text 是多进程共享同一份物理内存的（07 篇 6.4 节）。
       一个进程改了，所有进程都被改

**解法：代码里的跳转目标写死不变，但让它跳到一个"跳板"；
跳板去查一张可写的表。** 表可以改，代码不用改。

    .text（只读，共享）      .plt（只读）           .got.plt（可写，每进程一份）
    -------------------      -------------------    --------------------------
    main:                    mx_add@plt:            [ mx_add 的真实地址 ]
      ...                      ldr pc, [ip, ...] -->  由 ld.so 运行时填进来
      blx mx_add@plt  ------>                              |
      ...                                                  v
                                                    libmathx.so 里的代码

> **PLT（Procedure Linkage Table）**：跳板表，在只读段里，每个外部函数一个条目。
> **GOT（Global Offset Table）**：地址表，在可写段里，存真实地址。
> 代码跳 PLT，PLT 查 GOT，GOT 由 ld.so 填。

**这是猜想，下面找证据。**

### 6.2 动手：证据一，main 调的是跳板

用 ARM 版看（指令短，好读）：

```bash
arm-linux-gnueabihf-gcc -O1 h.c mathx.c strx.c -o h_arm
arm-linux-gnueabihf-objdump -d h_arm | sed -n '/<main>:/,/^$/p'
```

本机实测：

```
00000510 <main>:
 510:	b508      	push	{r3, lr}
 512:	2104      	movs	r1, #4
 514:	2003      	movs	r0, #3
 516:	f000 f80b 	bl	530 <mx_add>              <-- 直接跳
 51a:	1c42      	adds	r2, r0, #1
 ...
 522:	f7ff ef6a 	blx	3f8 <__printf_chk@plt>    <-- 跳到跳板
 528:	bd08      	pop	{r3, pc}
```

**两条调用指令，两种目标：**

    bl  530 <mx_add>              mx_add 和 main 一起编进了这个文件，
                                  地址链接期就定死了，直接跳
    blx 3f8 <__printf_chk@plt>    printf 在 libc.so.6 里，
                                  只能跳到 @plt 这个跳板

（名字是 `__printf_chk` 而不是 `printf`，因为 Ubuntu 默认开了
`_FORTIFY_SOURCE`，把 `printf` 换成了带缓冲区检查的版本。不影响结论。）

### 6.3 动手：证据二，跳板里是什么

```bash
arm-linux-gnueabihf-objdump -d -j .plt h_arm | head -20
```

    -j .plt   只反汇编 .plt 这一个 section（section 见 00 篇第四节）

本机实测：

```
000003d4 <__libc_start_main@plt>:
 3d4:	e28fc600 	add	ip, pc, #0, 12      \
 3d8:	e28cca1f 	add	ip, ip, #126976      |  三条指令算出 GOT 表项的地址
 3dc:	e5bcfbfc 	ldr	pc, [ip, #3068]!    /   最后一条：把表项里的值装进 pc
```

**最后一条指令是全部秘密：**

    ldr pc, [ip, #3068]!
    ^^^^^^^ 把内存里的一个值装进 pc

02 篇 2.5 节讲过，**pc 是通用寄存器，写它就等于跳转**。
所以"跳到哪"完全取决于那个内存单元里存着什么 ——
**而那个内存单元（GOT 表项）在可写段里，ld.so 想填什么就填什么。**

### 6.4 动手：证据三，谁在等着被填

```bash
readelf -r app_dyn | grep -A 4 'rela.plt'
```

本机实测（x86 版，条目更清楚）：

```
Relocation section '.rela.plt' contains 2 entries:
  Offset          Type              Sym. Value    Sym. Name + Addend
000000003fc8  R_X86_64_JUMP_SLO    0000000000000000  printf@GLIBC_2.2.5 + 0
000000003fd0  R_X86_64_JUMP_SLO    0000000000000000  mx_add + 0
```

**这就是留给 ld.so 的待办清单**，形式和 00 篇 3.4 节那张"重定位便条"一模一样：

    Offset      要填的 GOT 表项在哪
    JUMP_SLO    JUMP_SLOT，"这是个函数地址槽"
    Sym. Value  全是 0 —— 还没填
    Sym. Name   填谁的地址

00 篇里那张便条是给**链接器**看的、编译期就用掉了；
这张是给**动态链接器**看的、运行期才用。**同一套机制，两个时间点。**

### 6.5 动手：证据四，看它当场填

`ld.so` 有个调试开关能把绑定过程打出来：

```bash
LD_LIBRARY_PATH=. LD_DEBUG=bindings ./app_dyn 2>&1 | grep mx_add
```

本机实测：

```
61511:	binding file ./app_dyn [0] to ./libmathx.so [0]: normal symbol `mx_add'
mx_add(3,4) = 7
```

**"binding file app_dyn to libmathx.so: symbol mx_add"** ——
这就是 4.4 节那个 `U` 被解决的瞬间，发生在程序运行的时候。

> **延迟绑定（lazy binding）**：ld.so 启动时并不填完所有 GOT 表项，
> 初始值指向一段解析器代码。**第一次**调用某个函数时才去查找并回填，
> 之后就直接跳过去。好处是启动快，用不到的函数永远不解析。
> 环境变量 `LD_BIND_NOW=1` 可以关掉它，改成启动时全部解析。

### 6.6 判据

    [ ] main 里调自己的函数是 bl <名字>，调库函数是 blx <名字@plt>
    [ ] objdump -d -j .plt 里，每个跳板的最后一条指令是 ldr pc, [...]
    [ ] readelf -r 的 .rela.plt 里，Sym. Value 全是 0
    [ ] LD_DEBUG=bindings 能看到 mx_add 被绑定到 libmathx.so
    [ ] 能说出为什么不能直接改写 .text 里的调用指令

    注错见红：把 h.c 里的 mx_add 调用去掉，只留 printf，重新编译。
    .rela.plt 的条目数会从 2 减到 1，且 mx_add 那条消失。
    **待办清单的长度，等于你用了几个外部函数。**

## 七、工具表

    工具         看什么                  常用法
    ----------   --------------------    ------------------------------
    nm           符号表                  nm a.o；nm -D a.so 看动态符号
    readelf -d   .dynamic 段             看 NEEDED / SONAME / RPATH
    readelf -r   重定位表                看哪些位置等着被填
    objdump -d   反汇编                  -j .plt 只看某个 section
    ldd          递归列出依赖的所有 .so   只能对本机架构的文件用
    ar t         静态库里有哪些 .o
    strings      文件里的可打印字符串     快速看有没有某个路径/版本号

**两个注意：**

1. 交叉编译的产物要用**带前缀**的版本：`arm-linux-gnueabihf-nm` 等。
   本机的 `nm` 有时也能读 ARM 文件，但遇到 ARM 特有的 section 会报错。

2. **`ldd` 不能用于 ARM 文件。** 它是靠真的跑一遍来列依赖的，
   ARM 程序在 x86 上跑不起来。看 ARM 程序的依赖用 `readelf -d`。

`nm` 和 `nm -D` 的区别值得单说：

```
$ nm -D libmathx.so | grep ' T '
0000000000001111 T mx_len
00000000000010f9 T mx_add
```

`-D` 看的是**动态符号表**（`.dynsym`），也就是"这个库对外导出了什么"。
不带 `-D` 看的是普通符号表（`.symtab`），01 篇 3.3 节实测过：
**`.symtab` 会被 `strip` 删掉，`.dynsym` 不会** ——
删了动态链接就没法工作了。

## 八、顺带一提：和 ysyx 的对照

**没做过 ysyx 也不影响，跳过即可。**

    ysyx / NPC                       Linux 应用
    ---------------------------      ------------------------------
    全静态链接，一个 .bin 跑天下      默认动态链接
    klib 就是几个 .o 打包成 .a       libc.so.6 独立存在，多个程序共用
    链接后地址全部定死                有一部分地址要等运行时才知道
    没有 PLT/GOT                     有，而且是理解动态库的关键
    ld 脚本你自己写过（linker.ld）    ld 用默认脚本，原理一样

你在 ysyx 见过的 `undefined reference to xxx`，和本篇 2.4 节是同一个东西。
区别只是那边永远停在"链接期报错"这一档，
而 Linux 下它还可能推迟到运行期才爆（4.4 节）。
