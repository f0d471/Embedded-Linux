# 12 第三方库的交叉构建与部署

## 这一篇到底在讲什么

> **交叉构建第三方库，就是在电脑上生产“板子能运行”的头文件和库，再把它们先装进一个隔离的假根目录。**
> 编译应用时去假根里找头文件和链接库；运行应用时，板子的加载器还要再找到目标库。
> 这是三个时刻、三套搜索路径，不能混成“缺啥就往工具链里拷啥”。

### 你是从哪儿撞见它的

第 04 章要调用 FreeType。源码里只写一行：

```c
#include <ft2build.h>
```

从这里开始会连续撞上三种完全不同的报错：

```text
fatal error: ft2build.h: No such file or directory       编译时没找到头文件
ld: cannot find -lfreetype                               链接时没找到开发库
error while loading shared libraries: libfreetype.so.6   板上运行时没找到目标库
```

视频 4_6-4 的解决办法是把新头文件、库直接复制进交叉工具链的系统目录。
这能让眼前的命令通过，但会把“哪次安装放进来的、给哪块板、依赖哪个版本”全部抹掉；
以后升级工具链、换板或清理依赖时，没有办法完整撤回。

### 它是被什么逼出来的

一个第三方库至少同时服务两个世界：

```text
构建世界                                  运行世界
电脑 x86-64                               开发板 ARM
configure / make 在这里执行                libfreetype.so 在这里被加载
需要能在电脑运行的构建工具                 需要 ARM 指令和板端 ABI
头文件只在编译时读取                       运行时不需要头文件
```

如果构建系统只看当前电脑，它会自然地调用 `gcc`，编出 x86-64 库；
如果安装命令直接写 `/usr`，它会自然地污染电脑或工具链的公共目录；
如果链接阶段只找到库就算结束，程序拷到板上后，动态加载器仍可能找不到同名 `.so`。

所以交叉构建系统必须额外回答三件事：

1. **构建动作在哪里执行，产物在哪里运行？** `--build` / `--host`。
2. **最终希望装到目标机哪个前缀，本次先暂存到电脑哪里？** `--prefix` / `DESTDIR`。
3. **应用的编译器、链接器和板端加载器分别去哪找？** `-I`、`-L/-l`、运行时库路径。

### 放在一条流程里

1. 在 x86-64 电脑上准备 FreeType 源码。
2. 执行 `./configure --build=x86_64... --host=arm-linux-gnueabihf --prefix=/usr`，再用 `CC=arm-linux-gnueabihf-gcc make`，生成 ARM 头文件和库。
3. 用 `make DESTDIR=$STAGE install` 安装进隔离的“板子根目录替身”。

   | staging 中的路径 | 在什么时候使用 |
   |---|---|
   | `$STAGE/usr/include/freetype2/` | 编译应用时由 `-I` 或 `pkg-config` 找到 |
   | `$STAGE/usr/lib/libfreetype.so` | 链接应用时由 `-L`、`-lfreetype` 找到 |

4. 选择部署动态库，或把 `.a` 静态链接进应用。
5. 采用动态部署时，开发板的运行时加载器还要在 `/usr/lib/libfreetype.so.6` 等路径再找一次。

## 结论先贴出来

1. **普通库的 `--host` 指产物运行的平台，不是眼前运行 configure 的电脑。**
   本机是 x86-64、产物给 ARM 板跑，所以 `--build=x86_64-pc-linux-gnu --host=arm-linux-gnueabihf`。
2. **`--target` 通常只在构建编译器、汇编器这类“还要生成另一平台代码”的工具时才有意义。**
   编 FreeType 这种普通库，不要为了凑齐三个参数乱填 `--target`。
3. **`--prefix=/usr` 是目标机最终路径，`DESTDIR=$STAGE` 是本次安装的临时假根。**
   两者合起来得到 `$STAGE/usr/include` 和 `$STAGE/usr/lib`，不会污染本机 `/usr`。
4. **头文件、链接库、运行库发生在三个时刻。** `-I` 只管编译，`-L/-l` 只管链接，
   `LD_LIBRARY_PATH` 只管运行；拿一个选项救另外一个阶段一定无效。
5. **链接器通常把库的 SONAME 写进可执行文件，不写构建机绝对路径。**
   本机从 `/tmp/.../libanswer.so` 链接，ELF 的 `NEEDED` 仍只有 `libanswer.so.1`。
6. **安装共享库要保留符号链接链。** 常见结构是
   `libfoo.so -> libfoo.so.1 -> libfoo.so.1.2.3`；复制时把链接解引用，会破坏开发名或浪费空间。
7. **不要把第三方库直接复制进交叉工具链目录。** 用独立 staging/sysroot 保存，
   编应用时显式给 `pkg-config` 或 `-I/-L` 指路，版本和清理边界才看得见。
8. **能否链接不代表能否在板上运行。** 还要核对 ELF `Machine`、动态加载器、glibc 版本、
   `NEEDED` 依赖和板端实际文件；静态链接只是把部署问题换成体积和许可证问题。
9. **旧第三方源码在新编译器下出现警告，不等于构建失败。** 本机 GCC 15 编 FreeType 2.10.2
   出现两条 `-Wdangling-pointer` 告警，但库成功生成；不要给未经维护的上游源码武断加全局 `-Werror`。

### 看到什么，就先想到什么

| 报错或现象 | 第一反应 |
|---|---|
| `xxx.h: No such file` | 编译阶段；查 `-I` 和目标头文件，不要先找 `.so` |
| `cannot find -lfoo` | 链接阶段；查 `-L` 下是否有 `libfoo.so` 或 `libfoo.a` |
| `undefined reference to foo` | 找到库名也可能顺序错、库里没有该符号，或少了传递依赖 |
| `Exec format error` | 产物架构错；先 `readelf -h` 看 Machine |
| `error while loading shared libraries` | 运行阶段；查板端库、SONAME、加载器搜索路径 |
| configure 说 `cross compiling... no` | `--host` 没生效，或交叉工具没有被选中 |
| 安装后工具链目录多了一堆说不清来源的文件 | 没有 staging，安装边界已经丢失 |

想补原理时：三个时刻看第二节，build/host/prefix 看第三节，真实 FreeType 构建看第五节。

## 一、先按时间排，不按文件类型排

一行 `gcc app.c -lfoo -o app` 看起来把所有事一次做完，实际上至少有三次查找：

```text
时刻 1  预处理/编译     #include <foo.h>       在哪里找声明？
时刻 2  链接            -lfoo                  在哪里找实现？
时刻 3  板上启动        ELF NEEDED libfoo.so.1  加载器在哪里找运行库？
```

> **头文件**：给编译器看的声明和类型布局，不进入板上运行流程。
>
> **链接库**：链接器用来解析符号的 `.a` 或 `.so`；必须是目标架构。
>
> **运行库**：动态程序启动时由目标机加载器映射的 `.so`；头文件此时完全没用。

选项也按时间一一对应：

```text
-I/path/include        只增加编译器头文件搜索目录
-L/path/lib            只增加链接器库目录
-lfoo                  请求 libfoo.so 或 libfoo.a
LD_LIBRARY_PATH=/path  只增加运行时动态加载器目录
```

这解释了一个常见误区：程序在电脑上已经成功链接，复制到板上仍报缺库，
并不矛盾。**链接器完成的是“把库名记进 ELF”，板端加载器才负责“按这个名字找到文件”。**

## 二、实验 1：把三个时刻的错误依次逼出来

### 2.1 先自己想

实验提供一个最小第三方库：

```text
upstream/answer.h       声明 answer_value()
upstream/answer.c       实现并返回 42
upstream/Makefile       生成 libanswer.so.1.0 和两级符号链接
app.c                   调用 answer_value()
```

库先安装到临时的 `$STAGE/usr`。现在分别去掉 `-I`、`-L`、`LD_LIBRARY_PATH`，
三个阶段应该按什么顺序失败？先写下答案，再跑脚本。

### 2.2 动手

```bash
cd /mnt/e/Workspace/embedded-linux/labs/00_basics/11_cross_library
bash check.sh
```

脚本把一切放在 `mktemp -d` 创建的临时目录，退出时自动删除，不写本机 `/usr`。

对应的三条命令骨架是：

```bash
gcc app.c                                      # 没 -I，先找不到 answer.h
gcc -I$STAGE/usr/include app.c -lanswer       # 找到头，没 -L，找不到库
gcc -I$STAGE/usr/include -L$STAGE/usr/lib \
    app.c -lanswer -o app                     # 链接成功
./app                                          # 板端类比：运行时仍找不到库
LD_LIBRARY_PATH=$STAGE/usr/lib ./app           # 三处都接通
```

### 2.3 本机实测

```text
=== 本机库：暂存安装，不污染 /usr ===
  PASS  头文件装进 stage/usr/include
  PASS  真实库文件装进 stage/usr/lib
  PASS  链接名 libanswer.so 仍是符号链接
  PASS  SONAME 链接 libanswer.so.1 仍是符号链接
=== 三次找东西发生在三个时刻 ===
  PASS  不加 -I，编译期先报 answer.h 找不到
  PASS  只有 -I 没有 -L，链接期报 -lanswer 找不到
  PASS  ELF 记录的是 SONAME，不是构建机绝对路径
  PASS  运行时没指路，加载器报 libanswer.so.1 找不到
  PASS  LD_LIBRARY_PATH 只解决运行时找库
=== ARM 库：产物架构跟 CC 走 ===
  PASS  ARM 共享库的 ELF Machine
  PASS  注错见红：x86 链接器拒绝 ARM 库（2 行架构不兼容证据）
  PASS  ARM 应用的 ELF Machine
  PASS  ARM 应用也只记 SONAME
======================================
  13 PASS / 0 FAIL / 0 SKIP
======================================
```

### 2.4 逐行读

前四条检查安装树，而不是检查“make 返回了 0”。一个可用共享库通常同时需要：

```text
libanswer.so       -> libanswer.so.1        开发链接名，-lanswer 找它
libanswer.so.1     -> libanswer.so.1.0      SONAME，运行时加载器找它
libanswer.so.1.0                              真正 ELF 文件
```

`cp -L` 会把链接全部解引用成三份真文件；只复制最后一个真文件又会让 `-lanswer`
和运行时 SONAME 都找不到。实验使用 `cp -a` 保留链接关系。

`readelf -d app` 的关键行：

```text
Shared library: [libanswer.so.1]
```

里面没有临时目录。这是为什么把应用复制到板上后，加载器会重新按板端路径查一次。

### 2.5 注错见红

脚本最后故意让本机 x86 链接器去吃 ARM 共享库，实测出现两行独立证据：

```text
skipping incompatible .../libanswer.so when searching for -lanswer
cannot find -lanswer
```

如果只检查“目录里有 `libanswer.so`”，这次会假绿；必须检查 ELF `Machine` 或真的链接一次。

### 2.6 判据

```text
[ ] staging 下头文件、真库、两级符号链接都存在
[ ] 去掉 -I，失败发生在编译阶段
[ ] 补 -I 但去掉 -L，失败发生在链接阶段
[ ] 链接成功后直接运行仍因运行库路径失败
[ ] 加 LD_LIBRARY_PATH 后输出 answer=42
[ ] ARM 库和 ARM 应用的 readelf Machine 都是 ARM
[ ] x86 链接器处理 ARM 库时判据变红
```

## 三、`build`、`host`、`target` 到底是谁

Autoconf 使用的名字有点反直觉：

> **build**：正在执行 configure 和编译命令的机器。
>
> **host**：这次产物将来运行的机器。
>
> **target**：产物将来还要为谁生成代码；普通应用和库通常没有这一层。

本仓的 FreeType 构建是：

```text
build   x86_64-pc-linux-gnu       WSL，configure/make 在这里跑
host    arm-linux-gnueabihf       libfreetype.so 在 i.MX6ULL 上跑
target  不填                       FreeType 不会再去生成另一种机器码
```

因此配置命令写成：

```bash
./configure \
  --build=x86_64-pc-linux-gnu \
  --host=arm-linux-gnueabihf \
  --prefix=/usr
```

三项各管什么：

- `--build`：让检测脚本明确知道当前执行环境。
- `--host`：触发交叉编译模式，并优先寻找 `arm-linux-gnueabihf-gcc` 等工具。
- `--prefix=/usr`：记录目标机最终逻辑位置；不是让当前命令直接写本机 `/usr`。

配置输出必须出现：

```text
checking build system type... x86_64-pc-linux-gnu
checking host system type... arm-unknown-linux-gnueabihf
checking whether we are cross compiling... yes
```

最后一行是判据。只看命令里写了 `--host` 不够，configure 可能没找到相应工具后退回本机编译器。

## 四、`prefix` 和 `DESTDIR`：最终路径与临时假根

这两个变量最容易被写成一个：

```text
--prefix=/usr          库到了板子上以后，逻辑上属于 /usr
DESTDIR=$STAGE         这一次先把整个目标根套在电脑上的 $STAGE 前面
```

所以：

```bash
make DESTDIR="$STAGE" install
```

实际写入：

```text
$STAGE/usr/include/freetype2/ft2build.h
$STAGE/usr/lib/libfreetype.so.6.17.2
$STAGE/usr/lib/pkgconfig/freetype2.pc
```

但 `.pc` 文件、SONAME 等仍把目标前缀理解成 `/usr`。部署时把 `$STAGE` 看成板子的 `/` 即可。

反过来，如果写 `--prefix=$STAGE/usr`，临时电脑路径可能被烙进 `.pc`、配置工具或文本文件；
换一台电脑，这个绝对路径就失效。**临时根用 DESTDIR，目标前缀用 prefix。**

## 五、实测交叉构建 FreeType 2.10.2

### 5.1 为什么本次先关闭可选依赖

资料包的依赖链是：

```text
FreeType -> libpng -> zlib
```

FreeType 还可能探测 bzip2、Brotli、HarfBuzz。为了先只验证“ARM FreeType 本体能否构建、
能否渲染 TrueType/TTC 轮廓”，本次控制变量关闭可选依赖：

```bash
--without-zlib --without-bzip2 --without-png --without-harfbuzz --without-brotli
```

这不是说这些库没用；它只是让第一次闭环只含一个变量。需要 PNG 字形、压缩字体或复杂塑形时，
再逐个把依赖以同样方式装进同一个 staging。

### 5.2 完整命令

```bash
Q=/mnt/e/Workspace/01_all_series_quickstart-master
WORK=/tmp/freetype-arm
STAGE=$WORK/stage

mkdir -p "$WORK/src" "$WORK/build" "$STAGE"
tar -xJf "$Q/04_嵌入式Linux应用开发基础知识/source/10_freetype/freetype-2.10.2.tar.xz" \
    -C "$WORK/src"
cd "$WORK/build"

../src/freetype-2.10.2/configure \
    --build=x86_64-pc-linux-gnu \
    --host=arm-linux-gnueabihf \
    --prefix=/usr \
    --without-zlib --without-bzip2 --without-png \
    --without-harfbuzz --without-brotli

make -j2
make DESTDIR="$STAGE" install
```

- `tar -xJf`：`x` 解包，`J` 表示 xz，`f` 后面跟文件。
- 单独 `build/`：out-of-tree 构建，生成物不混进上游源码。
- `-j2`：并行两个任务；不是正确性的必要条件。
- `DESTDIR`：只写临时 staging，不碰 `/usr` 和交叉工具链目录。

### 5.3 本机实测

GCC 15.2.0 编译旧版 FreeType 2.10.2 时出现两组 `-Wdangling-pointer` 告警，
分别来自 `ttgload.c` 和 `ftgrays.c`。它们没有被当成错误，构建和安装继续完成。

产物：

```text
libfreetype.so.6.17.2: ELF 32-bit LSB shared object, ARM, EABI5, dynamically linked
libfreetype.a:         current ar archive
Machine:               ARM
```

安装树里实测有 50 个头文件、5 个顶层库文件/链接。`pkg-config` 从 staging 给出的参数：

```bash
PKG_CONFIG_LIBDIR="$STAGE/usr/lib/pkgconfig" \
PKG_CONFIG_SYSROOT_DIR="$STAGE" \
pkg-config --cflags --libs --static freetype2
```

```text
-I.../stage/usr/include/freetype2 -L.../stage/usr/lib -lfreetype
```

`PKG_CONFIG_LIBDIR` 让它只看目标库的 `.pc`，防止误拿宿主机 x86-64 FreeType；
`PKG_CONFIG_SYSROOT_DIR` 给 `/usr/include`、`/usr/lib` 这类目标绝对路径套上 staging 假根。

### 5.4 和视频做法的差别

视频最后把头文件和库复制进工具链自带的 include/lib。这套命令在一次性教学环境里能跑，
本仓不照做，原因可验证：

```text
直接复制到工具链                 staging
来源边界       混在系统文件里      一个目录就是一套版本
删除           不知道该删哪些       整个目录可丢弃
多板并存       容易串 ABI           每块板各一棵
升级工具链     手工文件丢失         重新给新工具链指 staging
权限           可能需要 root        普通用户即可
```

“缺啥补啥”只适合作为定位思路，不应该等价于“往公共工具链目录复制啥”。

## 六、静态还是动态：两条可交付路线

### 路线 A：动态部署

动态部署时，应用 ELF 中的 `NEEDED libfreetype.so.6` 必须能在板子上解析为 `/usr/lib/libfreetype.so.6`，再由这个 SONAME 链接指向实际版本文件。

优点是多个程序共用一份库、应用更小；代价是必须把 FreeType 及其所有 `NEEDED`
依赖一起部署，并保证 ABI 兼容。检查：

```bash
arm-linux-gnueabihf-readelf -d app | grep NEEDED
```

临时测试可以用：

```bash
LD_LIBRARY_PATH=/tmp/ch04/lib ./app
```

量产系统应把路径纳入 rootfs/Buildroot 配方，而不是永久依赖临时环境变量。

### 路线 B：静态链接

```bash
arm-linux-gnueabihf-gcc -static ... "$STAGE/usr/lib/libfreetype.a" -lm
```

本仓板端 glibc 2.30，WSL 交叉工具链的动态 glibc 更高；前几章已经实测动态程序不兼容。
本章真机探针因此选择静态链接。判据：

```text
ELF 32-bit LSB executable, ARM, EABI5, statically linked
There is no dynamic section in this file.
```

静态不是“永远更好”：程序会变大，安全更新要重链所有程序，还要核对库许可证。
这里选择它，是因为真机实验只有一个程序，而且它切断了板端运行库版本这个变量。

## 七、顺带一提：和 ysyx 工具链对照

没做过也不影响，跳过即可。

你给 RISC-V 交叉编译 Newlib 或 NEMU 相关组件时，也在同时处理两种程序：

```text
构建辅助程序       在 x86-64 电脑上运行
目标库/目标程序    含 RISC-V 指令，将来在模拟器或板上运行
```

本章只是把目标架构换成 ARM，并把“临时安装树”明确成 staging。
判断产物归哪边，仍然不要看文件名，直接看 `readelf -h` 的 `Machine`。
