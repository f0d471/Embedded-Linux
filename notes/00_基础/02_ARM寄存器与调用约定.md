## 没看懂也先记住

先把寄存器当成 CPU 里几个有编号的小格子。读汇编时，先认出参数、返回值、
返回地址放在哪里，暂时不会逐条翻译也可以继续学。

### 先带走这 5 条

1. **本篇记的是 32 位 ARM 的函数交接规则，不能直接套到 64 位 ARM。** 调用约定就是双方约好参数放哪、结果放哪、谁保存现场。
2. **对本篇这种连续的 32 位整数参数，前四个依次放 `r0`～`r3`，剩下的放栈上。** `int` 返回值放 `r0`；本篇小端平台的 64 位整数返回值用 `r0`、`r1`，低半在 `r0`。遇到 64 位参数、结构体或浮点，不能只按“第几个参数”硬数。
3. **函数调用后，别指望 `r0`～`r3`、`r12` 还保留旧值。** 调用方需要旧值就先保存；被调函数若使用 `r4`～`r8`、`r10`、`r11`，必须恢复它们。`r9` 的用途和保存要求看平台约定。
4. **`sp` 是栈指针，`lr` 存返回地址，`pc` 是程序计数器。** `bl` 调用函数并写 `lr`，`bx lr` 是常见返回方式；函数还要调用别人时，要妥善保存自己的返回地址。
5. **浮点 ABI（机器码交接规则）要匹配。** `soft` 用软件计算、按基础规则传参；`softfp` 允许硬件浮点计算、仍按基础规则传参；`hard` 对适用的浮点参数使用浮点寄存器。不能把“用了浮点指令”直接等同于 `hard`，也不能任意混链 `hard` 与另外两种产物。

### 看到什么，就先想到什么

| 看到的东西 | 第一反应 |
|---|---|
| 调用前给 `r0`、`r1` 赋值，调用后读取 `r0` | 先按“传前两个整数参数、取整数返回值”理解 |
| `push` / `pop` | 往栈里保存值 / 从栈里恢复值；结合保存了哪些寄存器看用途 |
| `uses VFP register arguments` 一类链接错误 | 先查各个 `.o` 和库的浮点 ABI 是否一致；用 `readelf -A` 看 ARM 属性，结合编译参数判断 |
| Thumb-2 反汇编相邻地址有时差 2、有时差 4 | 指令可以是 16 位或 32 位，不能按“每条固定 4 字节”数 |

### 反复看这 3 组问答

- **问：普通 `int` 函数的返回值先看哪？答：`r0`。**
- **问：`softfp` 可以出现硬件浮点指令吗？答：可以，计算方式和传参方式是两件事。**
- **问：只要都是 ARM 文件就能混着链接吗？答：不能，指令集和 ABI 等条件也要兼容。**

想补原理时：参数和返回值看第二节，保存现场看第三、四节，浮点看第五、六节，Thumb-2 看第七节。
规则边界可核对 Arm 官方 [AAPCS32](https://github.com/ARM-software/abi-aa/blob/main/aapcs32/aapcs32.rst)。

## 一、一个必须有人回答的问题

```c
int add(int a, int b);       /* 在 add.c 里 */
...
add(g_init, 2);              /* 在 main.c 里调用 */
```

00 篇讲过：这两个文件是**分别编译**的。编译 `main.c` 时，编译器根本没看过
`add.c` 的函数体；编译 `add.c` 时，它也不知道谁会来调自己。

**那么 `a` 和 `b` 这两个值，是怎么从一个文件交到另一个文件手上的？**

必须有一份双方都遵守的约定，比如"第一个参数放 r0，第二个放 r1"。
这份约定不能靠猜，得写死。

> **调用约定（calling convention）**：关于"函数之间怎么交接"的一整套规定：
> 参数放哪、返回值从哪取、哪些寄存器可以随便改、栈怎么用。
> ARM 上这份文档叫 **AAPCS**。
>
> **寄存器**：CPU 内部的存储单元，比内存快得多，但数量极少。
> ARM 32 位有 16 个通用寄存器，叫 `r0` 到 `r15`。

**约定的内容不用背，用 `objdump` 直接看出来。** 这一篇就是这么读的。

## 二、实验 1：参数到底放在哪

### 2.1 先自己想

想知道参数放哪，最直接的办法：**写一个只做加法的函数，反汇编看它从哪儿取数。**

如果参数在 r0、r1，那函数体里应该出现 `add r0, r1` 之类的指令，
而且函数开头不会有任何"从内存里读参数"的动作。

**再多问一步：ARM 只有 16 个寄存器，参数超过一定数量怎么办？**
所以要写两个函数，一个 4 个参数、一个 6 个参数，对比着看。

### 2.2 动手

`args.c`：

```c
/* 只声明不定义：编译器无法内联，也无法把结果提前算出来 */
int ext6(int a, int b, int c, int d, int e, int f);

int use4(int a, int b, int c, int d)
{
	return a + b + c + d;
}

int use6(int a, int b, int c, int d, int e, int f)
{
	return a + b + c + d + e + f;
}

long long ret64(void)
{
	return 0x1122334455667788LL;
}

int caller(void)
{
	return ext6(1, 2, 3, 4, 5, 6);
}
```

    arm-linux-gnueabihf-gcc -O1 -c args.c -o args.o
    arm-linux-gnueabihf-objdump -d args.o

    -O1  开一点优化。不开的话满屏都是把参数存进栈再读回来的废动作，看不清重点
    -c   只编译不链接（00 篇 2.4）
    -d   反汇编

**关于 `ext6` 那句"只声明不定义"：** 第一次做这个实验时我没这么写，
直接 `use6(1,2,3,4,5,6)`，结果反汇编出来是

    caller:
        movs  r0, #21          <-- 1+2+3+4+5+6 编译器自己算完了
        bx    lr

**整个函数调用被优化没了。** 想观察传参过程，就必须让编译器无法预知结果 ——
调用一个它看不见函数体的外部函数就够了。

### 2.3 本机实测：4 个参数

```
00000000 <use4>:
   0:	4408      	add	r0, r1
   2:	4410      	add	r0, r2
   4:	4418      	add	r0, r3
   6:	4770      	bx	lr
```

**逐行读（三列的含义和 00 篇一样：偏移、机器码、助记符）：**

    add r0, r1      r0 = r0 + r1
    add r0, r2      r0 = r0 + r2
    add r0, r3      r0 = r0 + r3
    bx  lr          跳到 lr 寄存器存的地址去 —— 这就是"返回"

**四条指令，没有任何一条访问内存。** 结论直接摆在脸上：

    四个参数 a b c d  分别在  r0 r1 r2 r3
    返回值            留在    r0（最后一条 add 的结果就在 r0，没再搬动）
    返回地址          在      lr

`bx lr` 里的 `lr` 是 link register（链接寄存器），存着"我干完活该回到哪"。
00 篇里 `bl add` 那条指令，做的就是两件事：把下一条指令的地址存进 `lr`，然后跳。

### 2.4 本机实测：6 个参数

```
00000008 <use6>:
   8:	4408      	add	r0, r1
   a:	4410      	add	r0, r2
   c:	4418      	add	r0, r3
   e:	9b00      	ldr	r3, [sp, #0]        <-- 第 5 个参数
  10:	4418      	add	r0, r3
  12:	9b01      	ldr	r3, [sp, #4]        <-- 第 6 个参数
  14:	4418      	add	r0, r3
  16:	4770      	bx	lr
```

**前三条和 use4 一模一样。变化从第 4 条开始：**

    ldr r3, [sp, #0]     从"sp 指的地址 + 0"处读 4 字节到 r3
    ldr r3, [sp, #4]     从"sp 指的地址 + 4"处读 4 字节到 r3

    ldr = LoaD Register，从内存读到寄存器
    sp  = stack pointer，栈指针，指向当前栈顶

**第 5、6 个参数不在寄存器里，在栈上。** 结论：

    前 4 个参数走 r0-r3，第 5 个开始压栈。

为什么是 4 个？因为 ARM 一共才 16 个寄存器，还得留给别的用途。
（RISC-V 有 8 个参数寄存器，见第八节。）

### 2.5 本机实测：调用方怎么把参数交出去

看 `caller`，它是"交出去"的那一方：

```
00000028 <caller>:
  28:	b500      	push	{lr}            保存返回地址
  2a:	b083      	sub	sp, #12         在栈上挖 12 字节
  2c:	2306      	movs	r3, #6
  2e:	9301      	str	r3, [sp, #4]    第 6 个参数放 [sp+4]
  30:	2305      	movs	r3, #5
  32:	9300      	str	r3, [sp, #0]    第 5 个参数放 [sp+0]
  34:	2304      	movs	r3, #4          第 4 个参数
  36:	2203      	movs	r2, #3          第 3 个
  38:	2102      	movs	r1, #2          第 2 个
  3a:	2001      	movs	r0, #1          第 1 个
  3c:	f7ff fffe 	bl	0 <ext6>        调用（f7ff fffe 是占位，见 00 篇 3.3）
  40:	b003      	add	sp, #12         把挖的 12 字节还回去
  42:	bd00      	pop	{pc}            返回
```

    movs r0, #1      把立即数 1 放进 r0
    str  r3, [sp,#4] STore Register，把 r3 写进内存（ldr 的反向）
    push / pop       压栈 / 出栈

**和 use6 严丝合缝地对上了：**

    caller 写 [sp+0] = 5, [sp+4] = 6      use6 从 [sp+0] 和 [sp+4] 读
    caller 写 r0..r3 = 1,2,3,4            use6 从 r0..r3 读

**两个函数分别编译，谁也没看过谁，但它们对得一字不差。**
这就是第一节说的"必须有一份双方都遵守的约定" —— 你现在看到它生效了。

**两个细节值得留意：**

1. `sub sp, #12` 挖了 12 字节，但只用了 8 字节（两个参数）。
   多挖 4 字节是为了让 `sp` 保持 8 字节对齐 —— AAPCS 的硬性要求。

2. 最后一条是 `pop {pc}`，把栈上存的返回地址**直接弹进 pc**。
   pc 是程序计数器，写它就等于跳转。
   **这是 ARM 的特色：pc 是通用寄存器，可以当普通寄存器写。**
   （x86 和 RISC-V 都不允许这样。）

### 2.6 本机实测：64 位返回值放哪

r0 只有 32 位，那 `long long` 怎么返回？

```
00000018 <ret64>:
  18:	a101      	add	r1, pc, #4
  1a:	e9d1 0100 	ldrd	r0, r1, [r1]     一次读 8 字节到 r0 和 r1
  1e:	4770      	bx	lr
  20:	55667788 	.word	0x55667788       <-- 低 32 位
  24:	11223344 	.word	0x11223344       <-- 高 32 位
```

`ldrd` = LoaD Register Dual，一次读两个寄存器。

**常量 `0x1122334455667788` 被拆成两半存在代码后面**，低半段 `0x55667788`
先存（对应 r0），高半段 `0x11223344` 后存（对应 r1）。

    64 位返回值用 r0:r1，低 32 位在 r0，高 32 位在 r1。

（低位在前是小端序，和 01 篇 2.3 节看 `e_machine` 时是同一回事。）

### 2.7 判据

    [ ] use4 里出现且仅出现 r0、r1、r2、r3，没有任何内存访问
    [ ] use6 里第 5、6 个参数用 ldr 从 [sp,#0] 和 [sp,#4] 读
    [ ] caller 写进 [sp,#0] 的是 5、写进 [sp,#4] 的是 6，和 use6 读的位置对得上
    [ ] caller 用 movs 把 1/2/3/4 分别放进 r0/r1/r2/r3
    [ ] ret64 的低 32 位常量 0x55667788 对应 r0

    注错见红：把 caller 里的 ext6 换回 use6（编译器看得见函数体）。
    本机实测整个调用被优化成 movs r0, #21 —— 一条指令，
    传参过程完全消失。
    **优化会改变你看到的现象**，做这类实验时必须先确认编译器没把你要观察的
    东西优化掉。

## 三、实验 2：谁负责保存寄存器

### 3.1 先自己想

寄存器只有 16 个，大家共用。现在有个矛盾：

    我（caller）把一个重要的值放在 r1 里，然后调用你（callee）。
    你干活也要用寄存器，很可能也用 r1。
    等你返回，我的值就没了。

**两个解决方向，各有代价：**

    方向 A：调用方负责    我调你之前，先把我在乎的值存到栈上，回来再取
                          代价：即使你根本没用 r1，我也白存了一趟

    方向 B：被调方负责    你用哪个就先存哪个，用完恢复
                          代价：即使我根本不在乎 r1，你也白存了一趟

**AAPCS 的做法是两种都用，把寄存器分成两组。** 哪组是哪组？看反汇编。

**怎么设计这个实验？** 要让编译器不得不"跨越一次函数调用保住一个值"。
方法：连续调用四次外部函数，把每次的结果都留着，最后一起加起来。

### 3.2 动手

在 `args.c` 里加：

```c
int many(int a, int b, int c, int d)
{
	int v1 = ext6(a, 0, 0, 0, 0, 0);
	int v2 = ext6(b, 0, 0, 0, 0, 0);
	int v3 = ext6(c, 0, 0, 0, 0, 0);
	int v4 = ext6(d, 0, 0, 0, 0, 0);
	return v1 + v2 + v3 + v4;      /* 四个值必须同时活着 */
}
```

### 3.3 本机实测

```
00000044 <many>:
  44:	e92d 41f0 	stmdb	sp!, {r4, r5, r6, r7, r8, lr}    <-- 进门第一件事
  48:	b082      	sub	sp, #8
  4a:	460e      	mov	r6, r1        把参数 b 挪到 r6
  4c:	4615      	mov	r5, r2        把参数 c 挪到 r5
  4e:	4698      	mov	r8, r3        把参数 d 挪到 r8
  ...
  5c:	f7ff fffe 	bl	0 <ext6>
  60:	4607      	mov	r7, r0        第 1 次的结果存进 r7
  ...
  6e:	f7ff fffe 	bl	0 <ext6>
  72:	4606      	mov	r6, r0        第 2 次的结果存进 r6
  ...
  96:	463b      	mov	r3, r7        四个结果加起来
  98:	4433      	add	r3, r6
  9a:	442b      	add	r3, r5
  9c:	4418      	add	r0, r3
  9e:	b002      	add	sp, #8
  a0:	e8bd 81f0 	ldmia.w	sp!, {r4, r5, r6, r7, r8, pc}   <-- 出门最后一件事
```

### 3.4 逐条读

    stmdb sp!, {r4, r5, r6, r7, r8, lr}
    ^^^^^ STore Multiple, Decrement Before：一次把这些寄存器全压栈

    ldmia.w sp!, {r4, r5, r6, r7, r8, pc}
    ^^^^^ LoaD Multiple, Increment After：一次全弹回来

**第一条和最后一条构成一对。函数进门先存 r4-r8，出门再恢复。**

**为什么偏偏是 r4 到 r8？** 看中间的代码就明白了：

    参数 b、c、d 一进门就被挪到 r6、r5、r8
    每次调用的结果被存进 r7、r6、r5

**这些值都要跨越 `bl ext6` 活下来。** 编译器不敢把它们放在 r0-r3 ——
因为 `ext6` 有权随便用那几个。它只能放在"约定了必须保持原值"的那组里。

**而 `many` 自己要用 r4-r8，所以它有义务先存起来、走之前还回去。**
这样它的调用者也能放心。

> **callee-saved（被调方保存）**：r4-r11。谁要用谁先存、用完恢复。
> 调用者有权假定这些寄存器调用前后不变。
>
> **caller-saved（调用方保存）**：r0-r3、r12、lr。被调用的函数可以随便糟蹋。
> 调用者如果在乎，自己先存好。

**再看最后一条的一个巧妙之处：** 弹出时列表里是 `pc` 而不是 `lr` ——
压栈时存的是 `lr`（返回地址），弹出时直接弹进 `pc`。
**恢复寄存器和函数返回，被合并成了一条指令。**

### 3.5 判据

    [ ] many 的第一条指令是 stmdb，最后一条是 ldmia，两者的寄存器列表一致
        （除了压 lr、弹 pc 这个差别）
    [ ] 被保存的寄存器全部落在 r4-r11 范围内
    [ ] 跨越 bl 存活的那些值，都被放在被保存的那些寄存器里
    [ ] use4 里没有 stmdb/ldmia，能说出为什么（它不调别人，不需要保住任何东西）

    注错见红：把 many 改成只调一次 ext6 并直接返回结果。
    没有值需要跨越调用存活了，stmdb 的寄存器列表会大幅缩短甚至只剩 lr。
    **保存哪些寄存器不是固定的，是编译器按需决定的。**

## 四、寄存器全表

前两节把规则实测出来了。现在给全表，此时每一行你都能对上一个现象：

    寄存器   别名    角色                              谁负责保存
    ------   -----   ------------------------------    ----------------
    r0       a1      第 1 个参数 / 返回值              caller
    r1       a2      第 2 个参数 / 返回值高 32 位      caller
    r2       a3      第 3 个参数                       caller
    r3       a4      第 4 个参数                       caller
    r4-r8            局部变量                          callee   <- 第三节实测
    r9       sb      平台寄存器，各平台另有用途         看平台
    r10      sl      局部变量                          callee
    r11      fp      帧指针                            callee
    r12      ip      过程内 scratch，长跳转中转         caller
    r13      sp      栈指针                            callee   <- 2.5 的 sub/add sp
    r14      lr      返回地址                          caller   <- 2.3 的 bx lr
    r15      pc      程序计数器                        --       <- 2.5 的 pop {pc}

    参数超过 4 个：第 5 个开始压栈                            <- 2.4 实测
    64 位返回值：r0:r1，低位在 r0                             <- 2.6 实测

浮点寄存器另有一组，是第五节的主题：

    s0  - s31     32 个单精度（single）
    d0  - d15     双精度（double），与 s 重叠：d0 = s1:s0，d1 = s3:s2
    q0  - q15     NEON 的 128 位向量，q0 = d1:d0

**s / d / q 是同一片物理存储的三种视图**，往 s0 写一个 float，d0 的低 32 位就变了：

```
    q0  ├───────────────────────────────────────────────┤  128 位
        │                     q0                        │
        ├───────────────────────┬───────────────────────┤
        │          d1           │          d0           │   64 位
        ├───────────┬───────────┼───────────┬───────────┤
        │    s3     │    s2     │    s1     │    s0     │   32 位
        └───────────┴───────────┴───────────┴───────────┘
```

## 五、实验 3：浮点参数走哪 —— 三种 ABI

### 5.1 先自己想

整数参数走 r0-r3，这是定死的。**但浮点数呢？**

历史原因造成这里有三种做法（早期 ARM 芯片没有浮点单元）：

    没有 FPU 的芯片      浮点加法只能用软件模拟，参数只好走整数寄存器
    有 FPU 的芯片        参数直接走浮点寄存器 s0/s1，算完就走

`gcc` 用 `-mfloat-abi=` 选这个。**三种取值，同一个函数编三遍，一比就清楚。**

### 5.2 动手

`fadd.c`：

```c
float  fadd2(float a, float b)   { return a + b; }
double dadd2(double a, double b) { return a + b; }
int    iadd2(int a, int b)       { return a + b; }
```

```bash
for abi in hard softfp soft; do
    echo "===== $abi ====="
    arm-linux-gnueabihf-gcc -O1 -S -mfloat-abi=$abi -o - fadd.c \
        | sed -n '/^fadd2:/,/\.size/p' | grep -vE '@|\.'
done
```

    -S            停在汇编（00 篇 2.4），不生成 .o
    -o -          输出到屏幕，不落文件（Unix 里 - 表示标准输出）
    for abi in …  shell 循环，把三个字符串依次代入
    sed -n '/起/,/止/p'   只打印这两行之间的内容
    grep -vE '@|\.'       去掉注释（ARM 汇编用 @ 起注释）和汇编伪指令

### 5.3 本机实测

```
===== -mfloat-abi=hard =====        2 条指令
fadd2:
	vadd.f32	s0, s0, s1
	bx	lr

===== -mfloat-abi=softfp =====      5 条指令
fadd2:
	vmov	s14, r0
	vmov	s15, r1
	vadd.f32	s15, s14, s15
	vmov	r0, s15
	bx	lr

===== -mfloat-abi=soft =====        3 条指令，但其中一条是函数调用
fadd2:
	push	{r3, lr}
	bl	__aeabi_fadd(PLT)
	pop	{r3, pc}

===== 对照：整数加法（hard）=====
iadd2:
	add	r0, r0, r1
	bx	lr

===== double 版（hard）=====
dadd2:
	vadd.f64	d0, d0, d1
```

### 5.4 逐条读

**`hard`：参数本来就在 s0/s1，直接算，结果留在 s0。**

    vadd.f32 s0, s0, s1
    ^^^^     ^^^  V 开头的是 VFP（浮点单元）指令
             .f32 = 32 位浮点

和整数版 `add r0, r0, r1` 结构完全一样，只是换了一组寄存器。**这是该有的样子。**

**`softfp`：多出三条纯搬运指令。**

    vmov s14, r0     参数在 r0/r1（整数寄存器），先搬进浮点寄存器
    vmov s15, r1
    vadd.f32 ...     用 FPU 算
    vmov r0, s15     结果再搬回整数寄存器

**它用了 FPU，但接口按"没有 FPU"的规矩来。** 三条 `vmov` 是纯粹的浪费。
它存在的唯一意义：能和 soft 编的旧库链接。

**`soft`：连 FPU 都不用。**

    bl __aeabi_fadd(PLT)

一次浮点加法变成一次**函数调用**，跳进 libgcc 里一个软件模拟浮点加法的函数
（那里面是几十条整数指令）。**IMX6ULL 有 FPU，用 soft 就是白扔硬件。**

**double 版是 `vadd.f64 d0, d0, d1`** —— 用的是 d 寄存器。
对照第四节那张图：`d0` 就是 `s1:s0` 那 64 位。

### 5.5 判据

    [ ] hard 版是 2 条指令，出现 s0、s1
    [ ] softfp 版是 5 条，出现 r0、r1 和三条 vmov
    [ ] soft 版出现 bl __aeabi_fadd
    [ ] 整数版 iadd2 三种 ABI 下完全相同，能说出为什么
        （浮点 ABI 只管浮点参数，整数参数一直走 r0-r3）
    [ ] double 版用 vadd.f64 和 d0/d1

    注错见红：把 fadd2 的 float 全改成 double，再编 hard 版。
    本机实测指令从 vadd.f32 s0,s0,s1 变成 vadd.f64 d0,d0,d1。
    如果没变，说明你改的文件和编译的不是同一个。

## 六、实验 4：ABI 不一致会怎样

### 6.1 先自己想

上一节的三种 ABI，如果两个 `.o` 用了不同的那种，会发生什么？

    调用方是 hard 编的            被调方是 soft 编的
    把 a 放进 s0                  从 r0 取 a
    把 b 放进 s1                  从 r1 取 b
             |                             |
             +--- 两边说的不是一种语言 ----+
                  r0 里是别的东西，取出来是垃圾

**猜三种可能：**

    A. 链接器插一段转换代码            —— 但 00 篇讲过，链接器只会填地址
    B. 链接通过，运行时结果是垃圾       —— 最坏的情况
    C. 链接器直接拒绝                  —— 需要它能知道每个 .o 用的哪种 ABI

**如果是 C，那 ABI 信息必须记在 `.o` 文件里。记在哪？**
00 篇 4.1 节看 `readelf -S main.o` 时，有一个 section 当时没解释：

    [ 7] .ARM.attributes   ARM_ATTRIBUTES  ...

### 6.2 动手

```bash
cat > m.c <<'EOF'
#include <stdio.h>
float fadd2(float a, float b);
int main(void) { printf("%f\n", fadd2(1.5f, 2.5f)); return 0; }
EOF

arm-linux-gnueabihf-gcc -c m.c    -o m_hard.o    -mfloat-abi=hard
arm-linux-gnueabihf-gcc -c fadd.c -o fadd_soft.o -mfloat-abi=soft
arm-linux-gnueabihf-gcc m_hard.o fadd_soft.o -o bad        # 故意混着链

arm-linux-gnueabihf-readelf -A m_hard.o        # -A = ARM 架构相关信息
arm-linux-gnueabihf-readelf -A fadd_soft.o
```

### 6.3 本机实测

```
$ arm-linux-gnueabihf-gcc m_hard.o fadd_soft.o -o bad
ld.bfd: error: bad uses VFP register arguments, fadd_soft.o does not
ld.bfd: failed to merge target specific data of file fadd_soft.o
collect2: error: ld returned 1 exit status
退出码=1
```

```
--- m_hard.o ---
  Tag_FP_arch: VFPv3-D16            <-- 只有 hard 版有这一行
  Tag_ABI_FP_denormal: Needed
  Tag_ABI_FP_exceptions: Needed
  Tag_ABI_FP_number_model: IEEE 754

--- fadd_soft.o ---
  Tag_ABI_FP_denormal: Needed
  Tag_ABI_FP_exceptions: Needed
  Tag_ABI_FP_number_model: IEEE 754
```

### 6.4 逐条读

**答案是 C：链接器直接拒绝。** 而且报错话说得很清楚：

    bad uses VFP register arguments, fadd_soft.o does not
    ^^^                                          ^^^^^^^^
    要生成的可执行文件用浮点寄存器传参            但这个 .o 不是

**它凭什么知道？** `readelf -A` 给出了答案：`m_hard.o` 里有
`Tag_FP_arch: VFPv3-D16` 这条标记，`fadd_soft.o` 里没有。

**这些标记就存在 `.ARM.attributes` 那个 section 里** ——
00 篇 4.1 节那张表里，它排在第 7 行，当时跳过了。现在它有用了。

**为什么必须拒绝，不能凑合：**
00 篇 3.4 节讲过，链接器干的活是"分配地址 + 按重定位便条填空洞"。
**它不会、也不可能在两个函数中间插一段搬运参数的代码。**
所以两边对"参数放哪"的理解必须字面一致，差一点就是读到垃圾。

这就是 01 章那句"`hf` 是硬约束"的完整含义：
它不是性能选项，是**两个 `.o` 能不能放在一起**的资格问题。

### 6.5 判据

    [ ] 混链接时报 "uses VFP register arguments"，退出码非 0
    [ ] readelf -A 里，hard 版有 Tag_FP_arch，soft 版没有
    [ ] 两个都用 hard 编，链接成功
    [ ] 能指出这些 ABI 标记存在哪个 section 里

    注错见红：把 soft 那个改成 softfp 再链一次。
    softfp 和 soft 的传参方式相同（都走整数寄存器），
    所以它和 hard 一样链不上，报同样的错。
    **决定能不能链的是"参数走哪种寄存器"，不是"用不用 FPU"。**

## 七、Thumb-2：为什么指令有的 2 字节有的 4 字节

回头看 2.3 节的反汇编，机器码那一列长短不一：

```
   0:	4408      	add	r0, r1          2 字节
  1a:	e9d1 0100 	ldrd	r0, r1, [r1]    4 字节
```

**同一个 CPU，指令长度不一样。** 这是 Thumb-2。

    ARM 模式      所有指令固定 4 字节
    Thumb 模式    指令 2 字节为主，代码密度高，但功能受限
    Thumb-2       2 字节和 4 字节混合，功能基本追平 ARM 模式
                  常用指令用短的，复杂指令用长的。现在嵌入式默认就是它

确认当前是哪种模式：

    arm-linux-gnueabihf-gcc -O1 -S -o - fadd.c | grep -E '^\s*\.(thumb|arm)' | sort -u

本机实测：

```
	.thumb
	.thumb_func
```

**代码密度在嵌入式上是真金白银**：Flash 更小、每次取指能取到更多条指令、
指令缓存命中率更高。

一个副作用要知道：**Thumb 函数的地址最低位是 1。**
01 篇 5.1 节遇到过 —— `Entry point address: 0x3dd`，而 `_start` 在 `0x3dc`。
那个多出来的 1 不是地址差异，是"这是个 Thumb 函数"的标记位。
（地址本来就是偶数对齐的，最低位空着，正好拿来当标志。）

## 八、顺带一提：和 RISC-V 的对照

**没学过 RISC-V 也不影响，跳过即可，本篇不依赖这一节。**

如果你在 ysyx 见过 RISC-V 那套：

    概念              RISC-V                  ARM 32 位
    --------------    --------------------    ------------------------
    通用寄存器        32 个 x0-x31            16 个 r0-r15
    恒零寄存器        x0 / zero               没有
    返回地址          x1 / ra                 r14 / lr
    栈指针            x2 / sp                 r13 / sp
    参数寄存器        a0-a7，8 个             r0-r3，只有 4 个
    返回值            a0（64 位用 a0:a1）      r0（64 位用 r0:r1）
    被调方保存        s0-s11                  r4-r11
    程序计数器        pc，不是通用寄存器       r15 / pc，是通用寄存器
    函数返回          ret                     bx lr 或 pop {pc}
    压缩指令          C 扩展，可自由混排       Thumb-2，有模式概念

**两个最容易绊住人的差异：**

1. **ARM 的 `pc` 是通用寄存器。** `pop {pc}` 就是返回（2.5 节实测过）。
   RISC-V 刻意不让 pc 参与通用运算，因为那会让分支预测和乱序执行变复杂。
   ARM 后来也认了：AArch64（64 位）把 pc 从通用寄存器里拿掉了。

2. **浮点 ABI 的三种取值，RISC-V 只有两种对应：**

        ARM                     RISC-V           含义
        --------------------    -------------    ------------------------
        -mfloat-abi=soft        ilp32            软件模拟，参数走整数寄存器
        -mfloat-abi=softfp      （没有对应）      用 FPU 算，参数走整数寄存器
        -mfloat-abi=hard        ilp32f / ilp32d  参数直接走浮点寄存器

   RISC-V 没有 softfp 这个中间态。ARM 有它纯粹是历史包袱。

3. **ARM 的浮点寄存器 s/d/q 是同一片存储的三种视图**（第四节那张图），
   RISC-V 的 f0-f31 是 32 个独立寄存器，单精度存进去时高位做 NaN-boxing。
