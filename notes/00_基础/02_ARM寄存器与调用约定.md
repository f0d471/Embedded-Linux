# 02 ARM 寄存器与调用约定

被 01 章 2.1 节用到（讲 `hf` 为什么是硬约束）。

## 一句话

`r0`、`s0` 这些是 ARM 的寄存器名字，跟 RISC-V 的 `x10`/`a0`、`f0` 是同一类东西；
"调用约定"规定了函数的参数放进哪几个寄存器、返回值从哪个寄存器取。

## 一、先跟 RISC-V 对上

你在 ysyx 见过的那套，和 ARM 的对照关系：

    概念                RISC-V                    ARM (32 位, ARMv7-A)
    ----------------    ----------------------    --------------------------
    通用寄存器个数      32 个 x0-x31              16 个 r0-r15
                        (riscv32e 是 16 个)
    恒零寄存器          x0 / zero                 没有，ARM 没这东西
    返回地址            x1 / ra                   r14 / lr  (link register)
    栈指针              x2 / sp                   r13 / sp
    参数寄存器          a0-a7 (x10-x17), 8 个     r0-r3, 只有 4 个
    返回值              a0 (64 位用 a0:a1)        r0 (64 位用 r0:r1)
    被调用者保存        s0-s11                    r4-r11
    程序计数器          pc, 不是通用寄存器        r15 / pc, 是通用寄存器
                        不能直接当操作数用        可以直接写, 写它就等于跳转
    函数返回指令        ret  (= jalr x0, ra, 0)   bx lr
    浮点寄存器          f0-f31, 独立一组          s0-s31 / d0-d31 / q0-q15
                                                  同一片物理寄存器的三种视图

两个最容易绊住人的差异：

1. **ARM 的 `pc` 是通用寄存器**。`mov pc, lr` 就是返回，`add pc, pc, r0` 就是跳转表。
   RISC-V 刻意不让 pc 参与通用运算，因为那会让分支预测和乱序执行变复杂。
   ARM 后来也后悔了，AArch64（64 位）把 pc 拿掉了，跟 RISC-V 一样。

2. **ARM 的浮点寄存器是"同一片存储的不同视图"**，这个下面单独讲。

## 二、通用寄存器 r0-r15

    寄存器   别名    调用约定里的角色                     谁负责保存
    ------   -----   ---------------------------------    ------------------
    r0       a1      第 1 个参数 / 返回值                 caller (调用方)
    r1       a2      第 2 个参数 / 返回值高 32 位         caller
    r2       a3      第 3 个参数                          caller
    r3       a4      第 4 个参数                          caller
    r4-r8    v1-v5   局部变量                             callee (被调方)
    r9       sb/v6   平台寄存器, 有的 ABI 另有用途        看平台
    r10      sl/v7   局部变量                             callee
    r11      fp      帧指针 (frame pointer)               callee
    r12      ip      过程内 scratch, 长跳转的中转         caller
    r13      sp      栈指针                               callee
    r14      lr      返回地址                             caller
    r15      pc      程序计数器                           --

    参数超过 4 个怎么办？第 5 个开始压栈。
    RISC-V 有 8 个参数寄存器 (a0-a7)，所以压栈来得晚一些。

caller-saved / callee-saved 的意思跟 RISC-V 完全一样：

    caller-saved (r0-r3, r12, lr)
        我调用别人前，如果这些寄存器里有我还要用的值，我自己先存起来。
        因为被调用的函数可以随便糟蹋它们。

    callee-saved (r4-r11)
        我作为被调用的函数，如果要用这几个，必须先 push 保存，返回前 pop 恢复。
        调用我的人有权假定这些寄存器返回后原封不动。

## 三、浮点寄存器：s / d / q 是同一片存储的三种视图

这是 ARM 和 RISC-V 差别最大的地方。RISC-V 的 `f0-f31` 就是 32 个独立寄存器，
单精度存在里面时高位做 NaN-boxing。ARM 不是这样：

    物理存储（VFPv4 + NEON，Cortex-A7 就是这个配置）

    q0  ├───────────────────────────────────────────────┤  128 位
        │                     q0                        │
        ├───────────────────────┬───────────────────────┤
        │          d1           │          d0           │  64 位
        ├───────────┬───────────┼───────────┬───────────┤
        │    s3     │    s2     │    s1     │    s0     │  32 位
        └───────────┴───────────┴───────────┴───────────┘

    换算关系：
        d(n)  =  s(2n+1) : s(2n)         d0 就是 s1:s0，d1 就是 s3:s2
        q(n)  =  d(2n+1) : d(2n)         q0 就是 d1:d0

    范围：
        s0  - s31       32 个单精度
        d0  - d15       与 s0-s31 重叠
        d16 - d31       只有带 NEON/VFP-D32 时才有，不与任何 s 重叠
        q0  - q15       NEON 的 128 位向量寄存器

    直接后果：往 s0 里写一个 float，d0 的低 32 位就变了。写汇编时要当心，
    编译器会自动处理。

`s` 是 single，`d` 是 double，`q` 是 quad word。你在 01 章看到的
"浮点参数走 s0/s1"，说的就是这里的 s0、s1。

## 四、三种浮点 ABI，用汇编看它们的区别

这一节是 01 章 2.1 那张对照图的证据。三条命令，同一个函数，三种结果。

源码就一行：

    float fadd2(float a, float b) { return a + b; }

编译成汇编（不是目标文件），三种 ABI 各来一遍：

    arm-linux-gnueabihf-gcc -O1 -S -mfloat-abi=hard   -o - f.c
    #                       ^^  ^^ ^^^^^^^^^^^^^^^^^     ^^
    #                        |   |  |                     |
    #                        |   |  |                     -o - 输出到标准输出，
    #                        |   |  |                     不落文件，方便直接看
    #                        |   |  三种取值 hard / softfp / soft
    #                        |   -S 只编译到汇编就停，不汇编不链接
    #                       -O1 开一点优化，不然满屏都是栈操作，看不清重点

本机实测，把三份输出里 `fadd2:` 那一段挑出来：

    -mfloat-abi=hard                    2 条指令
    ------------------------------
    fadd2:
        vadd.f32   s0, s0, s1           参数本来就在 s0/s1，直接算，结果留在 s0
        bx         lr                   跳回 lr 指的地址，就是返回

    -mfloat-abi=softfp                  5 条指令
    ------------------------------
    fadd2:
        vmov       s14, r0              参数在 r0/r1（整数寄存器），先搬进 VFP
        vmov       s15, r1
        vadd.f32   s15, s14, s15        再用 FPU 算
        vmov       r0, s15              结果再搬回 r0
        bx         lr

    -mfloat-abi=soft                    调库函数，展开是几十条
    ------------------------------
    fadd2:
        push       {r3, lr}
        bl         __aeabi_fadd(PLT)    整个加法交给一个软件模拟函数
        pop        {r3, pc}

    对照组，整数加法（hf）：
    iadd2:
        add        r0, r0, r1
        bx         lr

读出三件事：

    1. hard 和整数加法一样干净，2 条指令。这是有 FPU 时该有的样子。
    2. softfp 用了 FPU 但接口按 soft 的来，所以多出 3 条纯搬运指令。
       它存在的意义只有一个：能和 soft 编的库链接。
    3. soft 连 FPU 都不用，一次加法变成一次函数调用。
       IMX6ULL 有 FPU，用 soft 就是白白扔掉硬件。

**跟 RISC-V 对照**（你在 ysyx 见过这套命名）：

    ARM                        RISC-V              含义
    -------------------        ---------------     ------------------------------
    -mfloat-abi=soft           ilp32               没 FPU，软件模拟，参数走整数寄存器
    -mfloat-abi=softfp         (没有对应)          用 FPU 算，但参数仍走整数寄存器
    -mfloat-abi=hard           ilp32f / ilp32d     参数直接走浮点寄存器

    RISC-V 没有 softfp 这个中间态。ARM 有，纯粹是历史包袱：
    早期 ARM 没 FPU，一大堆库是 soft 编的，softfp 是让新硬件兼容旧库的过渡方案。

回到 01 章那个问题——为什么 hf 和 soft 的 `.o` 链接不到一起：

    调用方是 hf 编的                   被调方是 soft 编的
    -----------------------            --------------------------
    把 a 放进 s0                       从 r0 取 a
    把 b 放进 s1                       从 r1 取 b
             |                                  |
             +--- 两边说的不是一种语言 ---------+
                  r0 里是别的东西，取出来是垃圾

    链接器不做任何转换（它只填地址），所以只能报错拒绝：
        uses VFP register arguments, xxx.o does not

## 五、Thumb-2：ARM 的"压缩指令"

01 章看到工具链配置里有 `--with-mode=thumb`，说的是这个。

    ARM 模式        所有指令固定 32 位
    Thumb 模式      指令 16 位为主，代码密度高，早期只有精简的一套
    Thumb-2         16 位和 32 位指令混合，功能基本追平 ARM 模式
                    现在嵌入式默认就用这个

    跟 RISC-V 对照：
        RISC-V 的 C 扩展（压缩指令）也是 16 位，也是为了代码密度。
        但 RISC-V 的 C 指令和普通 32 位指令可以自由混排，没有"模式"概念。
        ARM 是有模式的：CPSR 里有个 T 位，处理器整体处于 ARM 态或 Thumb 态，
        靠 bx 指令切换。函数指针最低位为 1 表示"这是个 Thumb 函数"。
        （地址本来就是偶数对齐的，最低位空着，正好拿来当标志位。）

代码密度在嵌入式上是真金白银：Flash 更小、icache 命中率更高。

## 六、亲手验证

别直接抄下面的命令。先自己想：

    问题 1  怎么让 gcc 只输出汇编不生成可执行文件？
            线索：gcc 的四个阶段是 -E（预处理）、-S、-c、不加（全走完）。
    问题 2  怎么让它输出到屏幕而不是文件？
            线索：很多 Unix 工具用 - 表示标准输入/输出。
    问题 3  怎么确认默认是 Thumb 模式？
            线索：汇编文件里会有伪指令声明当前模式，grep 一下。

想过之后再看答案：

    # 建个最小的测试文件
    printf 'float fadd2(float a, float b){return a+b;}\n' > f.c

    # 问题 1+2
    arm-linux-gnueabihf-gcc -O1 -S -o - f.c

    # 问题 3
    arm-linux-gnueabihf-gcc -O1 -S -o - f.c | grep -E '\.thumb|\.arm'
    # 本机输出 .thumb / .thumb_func，确认默认 Thumb-2

    # 三种 ABI 并排看
    for abi in hard softfp soft; do
        echo "===== $abi ====="
        arm-linux-gnueabihf-gcc -O1 -S -mfloat-abi=$abi -o - f.c \
            | sed -n '/^fadd2:/,/\.size/p' | grep -v '@'
    done
    #     ^^^^^^ shell 的 for 循环，把三个字符串依次赋给 abi
    #                sed -n '/起/,/止/p' 只打印这两个模式之间的行
    #                grep -v '@' 去掉 gcc 生成的注释行（ARM 汇编用 @ 起注释）

[判] 判据

    [ ] 三种 ABI 的 fadd2 指令条数依次是 2 / 5 / 3(其中一条是 bl 调库)
    [ ] hard 版里出现 s0、s1，softfp 版里出现 r0、r1 和 vmov，soft 版里出现 __aeabi_fadd
    [ ] 整数版 iadd2 是 add r0, r0, r1，说得出为什么整数不受浮点 ABI 影响
    [ ] 说得出 d0 和 s0、s1 的关系

    注错见红：把 f.c 里的 float 改成 double 再跑一遍 hard 版。
    指令应该从 vadd.f32 s0,s0,s1 变成 vadd.f64 d0,d0,d1。
    如果没变，说明你改的文件和编译的不是同一个。
